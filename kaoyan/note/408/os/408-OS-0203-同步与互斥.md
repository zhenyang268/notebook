# 408-OS-0203 同步与互斥

> 章：OS-02 进程与线程　｜　档位：掌握　｜　真题落点：7 题：2016 #27、#30、#32；2018 #25、#28、#32；2020 #32

**在考什么**：关键看能否按互斥或同步定初值，并用 P/V 先后正确卡住等待与唤醒，顺序写反即错。

## 考法 1：临界区四原则与软件/硬件实现方案的“满足哪几条”

**思路**：第一步把四原则按“入口—出口—等待方式”拆开记忆：空闲让进（没人就让我进）、忙则等待（有人就在外等）、有限等待（不能永久饿死）、让权等待（等不到就让出 CPU）。然后拿方案逐条对照：Peterson 与 TSL/交换指令都是用“忙等（自旋）”实现互斥，前三条能满足，**让权等待不满足**。

**坑**：把“有限等待”和“让权等待”混为一谈——忙等的方案是“有限等待成立、让权等待不成立”；以及看到 Peterson 的 `flag` 与 `turn` 两个变量，就以为它靠一个变量原子完成，实际上它需要“先写自己的 flag、再写 turn”的顺序，若两条语句之间被切换，需要靠 `turn` 兜底。

## 考法 2：用信号量 PV 描述互斥与同步，判断初值与顺序

**思路**：第一步分清“这个信号量是干什么用的”：**互斥**用的信号量初值为 1，P、V 紧贴临界区两端；**同步**（前趋关系）用的信号量初值为 0，在“前驱动作之后 V、后继动作之前 P”。检查时按两条规矩扫描：同一进程内不得先 P 同步信号量再 P 互斥信号量（否则持锁等待造成死锁），以及同步的 P 一定要出现在对应的 V 之前。

**坑**：生产者—消费者中把 `wait(mutex)` 写在 `wait(empty)` 之前——一旦缓冲区满，生产者拿着锁去睡，消费者永远进不来；以及把缓冲区容量 $n$ 的信号量初值写成 $n-1$ 或 1，导致“缓冲区未满/未空”的判断整体偏移一格。

## 考法 3：经典同步模型的“变形追问”

**思路**：第一步识别模型骨架再改动：生产者—消费者是“一空一满两个计数信号量 + 一把互斥锁”；读者—写者是“读者计数 + 一把锁 + 一个写者信号量”，并额外注意“第一个读者进来要拦写者、最后一个读者走要放写者”；哲学家进餐的关键是打破循环等待——要么一次性拿两只筷子（用互斥锁把取筷动作整体包住），要么规定奇偶号不同的取筷顺序。看到“最多允许 $k$ 个进程”“写者优先”这类附加条件，就在骨架上加一个计数信号量或再加一个排队信号量。

**坑**：读者—写者中把读者计数的加减放在互斥区之外，导致两个读者同时通过“第一个读者”的判断；哲学家问题里用“先拿左再拿右”并且声称已解决死锁——这只是把环路换了个位置，必须破坏“请求并保持”或“循环等待”中的一条。

## 考法 4：条件变量与管程，和信号量的区别

**思路**：第一步抓住两者的本质差异：**信号量有值、会记忆**，V 操作在没有等待者时把值加 1，之后来的 P 可以直接通过；**条件变量无值、不记忆**，signal 时若无人等待则什么也不发生，因此必须在 `while` 循环里检查条件、并且 `wait` 必须与互斥锁配对（它原子地“释放锁并睡眠、被唤醒后重新获得锁”）。管程把互斥内建在过程调用上，同一时刻只有一个进程在管程内活动。

**坑**：把条件变量的 `wait` 写成 `if` 判断——被唤醒后条件可能已被第三方改掉，必须重新判断；以及把条件变量当成计数器使用，写“signal 之后计数加一”这类不存在的语义。

### 2016 #27 TSL互斥机制
使用 TSL (Test and Set Lock) 指令实现进程互斥的伪代码如下所示。  
```
do {
  ...
  while ( TSL ( & lock ));
  critical section ;
  lock = FALSE ;
  ...
} while ( TRUE );
```
下列与该实现机制相关的叙述中，正确的是（ ）。

A. 退出临界区的进程负责唤醒阻塞态进程
B. 等待进入临界区的进程不会主动放弃 CPU
C. 上述伪代码满足“让权等待”的同步准则
D. while (TSL(&lock))  应在关中断状态下执行

**思路**：识别 TSL 是原子硬件指令，循环里反复测试即忙等；关键一步是看等待者是否主动让出 CPU，以及退出者是否直接唤醒阻塞进程。

**坑**：看到 lock 被置为 FALSE 就误以为退出者唤醒阻塞进程；或把能实现互斥误当成同时满足让权等待。

### 2016 #30 共享变量互斥判断
进程 P1 和 P2 均包含并发执行的线程，部分伪代码描述如下所示。 进程 P1 int x = 0 ; Thread1 () { int a ; a = 1 ; x += 1 ; } Thread2 () { int a ; a = 2 ; x += 2 ; } 进程 P2 int x = 0 ; Thread3 () { int a ; a = x ; x += 3 ; } Thread4 () { int b ; b = x ; x += 4 ; } 下列选项中，需要互斥执行的操作是（ ）。

A. a=1 与 a=2  
B. a=x 与 b=x  
C. x+=1 与 x+=2  
D. x+=1 与 x+=3  

**思路**：抓住“是否访问同一存储位置且并发执行结果依赖执行次序”这一关键，先区分线程私有局部变量、同一进程内共享的全局变量，以及不同进程各自独立的地址空间。  

**坑**：看到两个线程都出现同名局部变量就误判为共享冲突，看到两个进程都定义了同名的 `x` 就误判为同一变量；实际应看它们是否属于同一进程的共享数据。

### 2016 #32 管程特性
下列关于管程的叙述中，错误的是（ ）。

A. 管程只能用于实现进程的互斥
B. 管程是由编程语言支持的进程同步机制
C. 任何时候只能有一个进程在管程中执行
D. 管程中定义的变量只能被管程内的过程访问

**思路**：管程是语言级同步机制，既承担互斥也承担同步；同时看其封装性和任一时刻仅一个进程在管程内执行。

**坑**：看到“互斥”就以为管程只能做互斥，误把“只能用于实现进程的互斥”当成正确描述。

### 2018 #25 并发加1序列数
属于同一进程的两个线程 thread1 和 thread2 并发执行，共享初值为 0 的全局变量 x。thread1 和 thread2 实现对全局变量 x 加 1 的机器级代码描述如下： thread1 mov R1, x // (x) → R1 inc R1 // (R1) + 1 → R1 mov x, R1 // (R1) → x thread2 mov R2, x // (x) → R2 inc R2 // (R2) + 1 → R2 mov x, R2 // (R2) → x 在所有可能的指令执行序列中，使 x 的值为 2 的序列个数是（）。

A. 1
B. 2
C. 3
D. 4

**思路**：把每个线程的三条指令看成对共享变量的读改写临界区，关键看两个读改写能否交叉覆盖。

**坑**：误以为只要两个线程各执行一次加 1 就必得 2，忽略交叉执行时后写覆盖前写。

### 2018 #28 条件变量wait
若 x 是管程内的条件变量，则当进程执行 x.wait() 时所做的工作是（）。 管程

A. 实现对变量 x 的互斥访问
B. 唤醒一个在 x 上阻塞的进程
C. 根据 x 的值判断该进程是否进入阻塞态
D. 阻塞该进程，并将之插入 x 的阻塞队列中

**思路**：抓住管程内条件变量的 wait/signal 配对语义，wait 是主动睡眠并让出管程，signal 才是唤醒。

**坑**：容易把 wait 与 signal 混淆，误以为 wait 是唤醒阻塞进程，或误以为执行 wait 后仍占着管程。

### 2018 #32 让权等待同步机制
在下列同步机制中，可以实现让权等待的是（ ）。 硬件互斥指令

A. Peterson 方法
B. swap 指令
C. 信号量方法
D. TestAndSet 指令

**思路**：让权等待指进程无法进入临界区时主动放弃 CPU、进入阻塞态；应找带阻塞/唤醒机制的同步方式。关键一步是区分“忙等”和“阻塞等待”，而不是只看能否互斥或有限等待。

**坑**：把 Peterson 方法满足有限等待误当成让权等待；或看到硬件互斥指令就以为它会让出 CPU。

### 2020 #32 临界区互斥准则
下列准则中，实现临界区互斥机制必须遵循的是（ ）。 Ⅰ、两个进程不能同时进入临界区 Ⅱ、允许进程访问空闲的临界资源 Ⅲ、进程等待进入临界区的时间是有限的 Ⅳ、不能进入临界区的执行态进程立即放弃 CPU

A. 仅Ⅰ、Ⅳ
B. 仅Ⅱ、Ⅲ
C. 仅Ⅰ、Ⅱ、Ⅲ
D. 仅Ⅰ、Ⅲ、Ⅳ

**思路**：把四条分别归入“忙则等待、空闲让进、有限等待、让权等待”，前三条是互斥机制必须满足的，最后一条不是强制要求。

**坑**：看到“立即放弃 CPU”就误以为它和“有限等待”一样必须实现，把让权等待错当成互斥的必要准则。
