# 408-NET-0504 可靠传输与流量控制

> 章：NET-05 传输层　｜　档位：掌握　｜　真题落点：3 题：2019 #8、#38；2021 #40

## 考法 1：给一段收发过程，问下一段的序号或确认号落在哪个字节

**题（2021#40）**：题干给出甲在 t0 时刻发出 $seq=501$、携带 200B 数据的报文段，t1 时刻之后连接上继续有报文段往来，问某个报文段的序号或确认号应该是多少。

**思路**：第一步先把“序号空间”和“数据字节”分开列成一张记录表：一个报文段首字节序号为 $seq$、数据长度为 $L$，则该段覆盖 $[seq,\ seq+L-1]$；接收方回的确认号表示它期望收到的下一个字节，即 $seq+L$。t0 那一段的 200B 覆盖到哪个字节、下一个报文段的首字节该写多少，全都由这个式子决定。第二步再看这段过程里有没有插入 SYN 或 FIN——它们各占 1 个序号但不携带数据，出现一次，后面所有序号整体后移一位。

**坑**：看到“带 200B”就把序号加 200 当成末字节，于是把下一段的 seq 或对方的 ack 写成“起始序号+长度”这种边界值；正确的直觉是长度 $L$ 覆盖 $L$ 个字节、末字节是 $seq+L-1$，而确认号永远指向“还没收到的第一个字节”。另一处最容易犯的错：把 SYN/FIN 当成不占序号的普通控制位，FIN 之后算下一段序号时想不起来要跳一号。

**题（常见考法·自拟变形）**：发送方当前 $snd\_una$、$snd\_nxt$ 已知，此刻收到一个确认号为某值、通告 $rwnd$ 的确认段，问这一刻还能再发多少字节。

**思路**：第一步算在途未确认字节数 $snd\_nxt-snd\_una$；第二步算可用窗口 $\min(cwnd,rwnd)-$在途，这个差值才是此刻能塞进网络的新数据；同时这个确认号会把 $snd\_una$ 推进到该值，滑动窗口整体右移。

**坑**：看到通告了一个接收窗口就直接答“还能发这么多”，把已经在路上的字节忘干净；第二个误判是把确认号读成“这个字节已经收到了”，于是把下一个待发字节算成“确认号+1”，而实际上确认号本身就是“期望的下一个”。

## 考法 2：超时重传的计时与 RTT 估计（Karn）

**题（常见考法·自拟变形）**：给出若干个 RTT 采样值，或者给“某报文段被重传一次之后才收到确认”的情形，问 RTT 估计与 RTO 该怎么处理。

**思路**：第一步只回答一个问题——这次到达的确认对应的是“原报文段”还是“重传的那一份”？只要这一轮里发生过重传，就落在 Karn 的模糊区：这个样本作废、不更新 RTT 加权估计，RTO 按指数退避翻倍。只有收到对“从未重传过的新报文段”的确认，才恢复 $RTT\leftarrow(1-\alpha)RTT+\alpha\cdot 样本$。第二步核对计时器挂在谁身上：重传计时器只跟“最老的未确认报文段”走，收到推进 $snd\_una$ 的新确认就重启它。

**坑**：看到“收到确认”就条件反射代加权公式，把重传之后到达的确认也算成有效样本——Karn 恰恰要把它排除掉，否则 RTT 估计会被“迟到/二义”的样本污染。第二个坑是以为“每个报文段各有一个定时器”，于是把多个到期时间并列起来算，实际上实现上只有一个重传计时器在跑。

## 考法 3：快重传——数到第几个重复 ACK 才动手、动手重传哪一段

**题（常见考法·自拟变形）**：给出接收方连续回送的若干确认段，问发送方何时重传、重传的是哪一段数据。

**思路**：第一步把确认号排成一列，找出“同一个确认号反复出现”的那一串；重复 ACK 的确认号指向缺口处的第一个字节，所以发送方要重发的是“从该确认号开始的那一段”，并且不必等超时计时器到期，立刻重传。第二步确认触发条件已满足：必须是同一确认号的第 3 个重复 ACK 才动手。

**坑**：把收到的第一个“重复”也计入计数，收到两个就急着重传；还有一个常见误判是重传“最近刚发出去的那一段”或者干脆整窗重发，而缺口位置由重复 ACK 的确认号唯一确定。

## 考法 4：零窗口通告与持续计时器

**题（常见考法·自拟变形）**：接收方缓冲区满，回了窗口为 0 的确认；之后接收方应用读走数据，但发送方并不知情，问发送方的动作与定时器归属。

**思路**：第一步判断“窗口关闭之后发送方还能不能往这条连接上放字节”——新数据不能放，但必须启动持续计时器，到期发一个零窗口探测报文，逼对方回一个带当前窗口值的确认；收到非零窗口后停掉持续计时器，恢复按 $\min(cwnd,rwnd)$ 发送。

**坑**：看到窗口为 0 就认定“连接断了/只能干等超时重传”，把流量控制形成的死锁当成连接故障；第二个坑是把持续计时器和重传计时器当成同一个东西——前者专为“窗口为零时双方互相等待”而生、窗口一开就撤，后者跟着未确认数据走。还有一处易错：把零窗口探测当成“把上一段数据原样重发一遍”，于是在序号记录表里把同一批字节又记一次。

### 2019 #8 TCP快速重传时刻
某客户通过一个 TCP 连接向服务器发送数据的部分过程如题 38 图所示。客户在 t 0 时刻第一次收到确认序列号 ack_seq=100 的段，并发送序列号 seq=100 的段，但发生丢失。若 TCP 支持快速重传，则客户重新发送 seq=100 段的时刻是（ ）。〔原卷附图，纯文本从略〕

A. t 1
B. t 2
C. t 3
D. t 4

**思路**：盯住发送方收到的重复确认：对同一确认号累计到三个重复确认时，立即触发快速重传，而不是等超时。

**坑**：容易把第一次收到的确认也算作重复确认，从而提前一个时刻；或误把超时时刻当成重传触发点。

### 2019 #38 TCP快速重传时刻
某客户通过一个 TCP 连接向服务器发送数据的部分过程如题 38 图所示。客户在 t 0 时刻第一次收到确认序列号 ack_seq=100 的段，并发送序列号 seq=100 的段，但发生丢失。若 TCP 支持快速重传，则客户重新发送 seq=100 段的时刻是（ ）。〔原卷附图，纯文本从略〕

A. t 1
B. t 2
C. t 3
D. t 4

**思路**：快速重传看“对同一序号的重复确认”累计个数，图中客户发出后续段后服务器反复回同一个确认号，数到第三个重复确认的到达时刻就触发重传；不要等超时。

**坑**：看到图上标注“超时”就等到超时时刻，忽略快速重传；或把最早那个确认号也一并算作重复确认，导致重传时刻提前。
