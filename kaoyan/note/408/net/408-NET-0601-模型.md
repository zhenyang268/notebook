# 408-NET-0601 模型

> 章：NET-06 应用层　｜　档位：掌握　｜　真题落点：2 题：2022 #40；2024 #40

## 考法 1：给出一个应用场景或协议名，判断它属于 C/S、P2P 还是混合模型

**思路**：第一步不要看“有没有服务器”这个表面特征，先看通信前是否必须存在一个地址已知、长期在线、被动等待的服务方：有，就说明它具备 C/S 的骨架；第二步再看同一份资源是否天然存在多份对等副本、每个节点既下载又上传：有，就说明它带有 P2P 的特征。判到“又像又像”时按功能拆开：定位或索引走 C/S，内容批量传输走 P2P，这就是混合模型。

**坑**：看到“两个用户之间直接传文件”立刻判成纯 P2P，忽略了握手之前必须先到集中索引服务器查对方地址这一步，把混合模型误判成纯 P2P；反向也常错：看到“有个中心服务器”就判 C/S，没注意该服务器只发目录、一个字节的文件都不转发。

## 考法 2：应用层协议与其传输层承载的对应、报文边界由谁保证

**思路**：第一步把协议名与它的硬需求绑定：文件、邮件、网页要求一字不差，挂 TCP；查询—应答式的小报文或对时延比丢包敏感的流，挂 UDP。第二步追问“这条连接上，一次读到的字节流里怎么切出一个个报文”：若底下是 TCP 字节流，边界只能由应用层自己用长度字段、结束标记或自描述格式来划。

**坑**：把“DNS 主要用 UDP”推广成“DNS 永远不用 TCP”，遇到区传送或响应超长时判错；另一个高频错是看到 HTTP 首部里有 Content-Length，就以为 TCP 会替应用保留报文边界，进而误判“发一次对应收一次”。

## 考法 3：某个功能究竟该由哪一层实现

**思路**：第一步先问“传输层管不管这件事”——端到端可靠、复用分用、拥塞控制归传输层；而命名与资源定位、内容的编码与压缩、用户身份与状态、字符集与多语种，传输层一概不管，只能在应用层做。第二步据此判断题干要求补的模块应加在哪一侧。

**坑**：把“Cookie 维持用户状态”说成传输层连接状态（连接状态是 TCP 的，用户状态是 HTTP 靠 Cookie 模拟的）；把 MIME 的编码误认成传输层的分片重组；把“加密”一律归到传输层，忘了应用层也能自己加密。
