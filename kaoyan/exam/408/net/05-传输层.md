## 二、正文

### 5.1 服务与端口：复用、分用与 socket 四元组

网络层把分组送到**主机**，可主机上同时跑着浏览器、QQ、DNS 解析器。要把数据交到**进程**，必须再加一层标识——这就是端口存在的原因。端口是 16 位整数（0–65535），传输层用它做进程级寻址，因此传输层通信叫「端到端」而不是「主机到主机」。

**复用与分用**是一对动作：

- **复用（发送侧）**：多个应用进程把数据交给同一个传输层实体，传输层加上各自端口号后统一交给 IP。多个进程共用一条网络层通道。
- **分用（接收侧）**：传输层剥掉首部，按目的端口把数据交给对应进程。TCP 还要按四元组分用，UDP 按端口（加目的 IP）分用。

**socket 四元组**定义为

$$\text{socket} = (\text{源 IP},\ \text{源端口},\ \text{目的 IP},\ \text{目的端口})$$

一条 TCP 连接由四元组**唯一**确定，而不是由某个端口确定。

> **最小例**：服务器 `192.168.1.2:80` 同时被 A(`10.0.0.1:5000`) 和 B(`10.0.0.2:6000`) 访问。两条连接的四元组分别是 `(10.0.0.1,5000,192.168.1.2,80)` 与 `(10.0.0.2,6000,192.168.1.2,80)`，源侧不同，互不冲突——这就是 80 端口能同时服务上万客户的原因。反之，同一主机上两个进程想绑同一个 `(本地 IP, 本地端口)` 且都是 TCP，会失败。

面向连接与无连接的差别落在「有没有状态」上：TCP 在两端维护连接状态（序号、窗口、定时器），提供可靠、有序、字节流、全双工服务；UDP 不建连、不维护状态，提供尽力而为的报文服务。

### 5.2 UDP：八字段首部与伪首部校验

UDP 首部固定 8 字节，四个字段各 2 字节，共「八个字节」：

| 字段 | 长度 | 说明 |
|---|---|---|
| 源端口 | 2B | 不需要回信时可全 0 |
| 目的端口 | 2B | 分用依据 |
| 长度 | 2B | **首部 + 数据**的总长，最小 8，最大 65535 |
| 校验和 | 2B | 覆盖伪首部 + UDP 首部 + 数据 |

由此得 UDP 数据部分上限：$65535 - 8 - 20 = 65507$ 字节（减 20 是 IP 首部）。

**伪首部**共 12 字节：源 IP(4) + 目的 IP(4) + 全 0(1) + 协议号 17(1) + UDP 长度(2)。它**只在校验和计算时临时拼出来**，不随报文传输，也不上传给 IP。为什么需要它？因为 UDP 校验要额外验证「这份数据确实送到了正确主机的正确进程」——只校验端口不够，IP 地址必须一起进校验。

校验和算法三步：

1. 把伪首部 + UDP 首部 + 数据按 16 位分组，做**反码和**（16 位一组的二进制求和）；
2. 若和的高 16 位有进位，把进位**回卷**加到低 16 位（可多次）；
3. 对结果**按位取反**，填入校验和字段。接收方把包括校验和在内的全部内容再求一次反码和，结果应为 `0xFFFF`。

**例题（2024#39 型）**：源 IP `192.168.1.1`，目的 IP `192.168.1.2`，源端口 `0x1234`，目的端口 `0x5678`，12 字节应用数据为 6 个 16 位字 `0x0001,0x0002,…,0x0006`，求 UDP 校验和。

UDP 长度 $= 8 + 12 = 20 = \texttt{0x0014}$。逐项求和：

$$
\begin{aligned}
&\texttt{0xC0A8}+\texttt{0x0101}+\texttt{0xC0A8}+\texttt{0x0102} &&\text{(伪首部 IP)}\\
+\;&\texttt{0x0000}+\texttt{0x0011}+\texttt{0x0014} &&\text{(零/协议/长度)}\\
+\;&\texttt{0x1234}+\texttt{0x5678}+\texttt{0x0014}+\texttt{0x0000} &&\text{(UDP 首部)}\\
+\;&\texttt{0x0001}+\cdots+\texttt{0x0006} &&\text{(数据)}
\end{aligned}
$$

十进制累加：$49320+257+49320+258+0+17+20+4660+22136+20+0+1+2+3+4+5+6 = 126029$。

$126029 = \texttt{0x1EC4D}$，回卷：$\texttt{0xEC4D} + \texttt{0x0001} = \texttt{0xEC4E}$。取反：$\texttt{0xFFFF} - \texttt{0xEC4E} = \texttt{0x13B1}$。

校验和为 `0x13B1`。注意：若算出的校验和恰好是 `0x0000`，要写成 `0xFFFF`；若发送方根本不校验，填 `0x0000`（接收方见 0 就跳过校验）。所以「校验和字段为 0」在 UDP 里是特例，与 TCP 的 20 字节全 0 校验不同。

UDP 适用的场景由它的缺点反推：DNS、DHCP、RIP、SNMP、TFTP、实时音视频。理由是开销小（8B 首部）、无建连时延、无拥塞控制不因丢包而自我减速、支持广播/组播——代价是不保证可靠与有序，可靠性由应用层自己补。

### 5.3 TCP 连接管理：三次握手、四次挥手、11 状态

TCP 是面向连接的，连接建立要交换初始序号并同步双方能力。

**为什么必须三次？** 两次不够：若某个早已失效的 SYN 延迟到达服务器，服务器回 SYN+ACK 并直接认为连接建立，就会空等一个根本不存在的客户端，浪费资源。三次握手中，客户端第三个 ACK 让服务器确认「对方确实收到了我的 SYN 并且现在还想连」，同时双方各自完成「我能发、你能收」和「你能发、我能收」的双向确认。另外，三次正好完成双方 ISN（初始序号）的交换与确认。

**序号消耗规则**（每年都考）：SYN 占 1 个序号，FIN 占 1 个序号，纯 ACK 不占序号，数据每字节占 1 个序号。

> **最小例（2021#40 型）**：甲在 $t_0$ 发送 `seq=501` 携带 200B 数据。这段数据占用字节号 501–700，故 `snd_nxt = 701`、`snd_una = 501`。乙正确收到后回 `ACK=701`（累积确认：701 之前全部收到，期望下一个是 701）。若 $t_1$ 甲再发 100B，则 `seq=701`，占 701–800，`snd_nxt=801`。若这个 `ACK=701` 中途丢失，甲超时重传的仍是 `seq=501`、200B，`snd_nxt` 回退为 701。

**四次挥手**：FIN → ACK → FIN → ACK。为什么不是三次？因为 TCP 全双工，两个方向独立关闭。A 发 FIN 只表示「A 没数据要发了」，B 回 ACK 后进入 `CLOSE_WAIT`，此时 B 可能还有数据要发（半关闭状态），必须等 B 的数据发完再单独发 FIN。若 B 恰好也没数据，ACK 与 FIN 可合并，退化成三次。

**TIME_WAIT 与 2MSL**：主动关闭方发出最后一个 ACK 后进入 `TIME_WAIT`，等待 2MSL。两个理由：

1. 保证最后这个 ACK 能到达对方。若 ACK 丢失，对方会重传 FIN，处于 TIME_WAIT 的一方还能再回一次 ACK；若已 CLOSED，就会回 RST，对方异常终止。
2. 让本连接产生的旧报文段在网络中全部消亡（MSL 是报文最大生存时间），避免它们被后续同四元组的新连接误收。

> **最小例（2022#39 型）**：RTT = 50 ms，MSL = 800 ms，C 主动断开。则 TIME_WAIT 持续 $2 \times 800 = 1600$ ms，相当于 $1600/50 = 32$ 个 RTT。从 C 发出 FIN 到彻底 CLOSED 的总时长还要再加前面挥手的 2 个 RTT（100 ms），即 1700 ms。

**11 状态机**要能默画：CLOSED、LISTEN、SYN_SENT、SYN_RCVD、ESTABLISHED、FIN_WAIT_1、FIN_WAIT_2、CLOSE_WAIT、LAST_ACK、CLOSING、TIME_WAIT。其中 `CLOSING` 只在「自己发了 FIN 还没收到 ACK，就先收到对方的 FIN」时进入（同时关闭）；`LAST_ACK` 是被动关闭方发完 FIN 后的状态；`CLOSE_WAIT` 是被动关闭方收到 FIN 后、应用还没关闭时的状态，这个状态堆积就是服务器句柄泄漏。

### 5.4 可靠传输与流量控制：字节序号账本

TCP 把应用数据看成连续字节流，每个字节一个编号。维护三个指针对账：

- `snd_una`：最早发出但未确认的字节号（发送窗口左沿）；
- `snd_nxt`：下一个要发的字节号（窗口内已发/待发的分界）；
- `rcv_nxt`：期望收到的下一个字节号。

发送窗口大小

$$W = \texttt{snd\_nxt} - \texttt{snd\_una} \le \min(\texttt{cwnd},\ \texttt{rwnd})$$

`cwnd` 是拥塞窗口（发送方自己估的），`rwnd` 是接收窗口（接收方通告的）。取 min 是因为两个限制都要满足：网络受不了就少发，接收方缓冲区满了也少发。

**超时重传与 RTO**：RTO 略大于加权平均 RTT。Karn 算法规定：**重传过的报文段不能用它的 ACK 来更新 RTT 估计**——因为发送方无法判断这个 ACK 是对第一次发送的确认还是对重传的确认，采样会造成歧义。重传时 RTO 采用指数退避（翻倍）。

**快重传**：接收方收到失序段要立刻重复发上一个已确认的 ACK。发送方连续收到 **3 个重复 ACK**（即同一个 ACK 号共收到 4 次）就判定该段丢失，立即重传，不必等 RTO 到期。

**零窗口与持续计时器**：接收方缓冲区满时通告 `rwnd=0`，发送方停发并启动**持续计时器**。计时器到期就发一个零窗口探测报文（1 字节），对方回当前窗口值。若没有这个计时器，而那个「窗口更新」ACK 又丢了，双方会永久互等——死锁。

**糊涂窗口综合症**两条对策：接收方不要一有空间就通告小窗口

## 三、真题落点

- 2021 #38 选择题：TCP 连接释放。考的是「主动关闭方收到对方 FIN 之后」这一步：从 FIN_WAIT_2（或 LAST_ACK）迁移到 TIME_WAIT 并回 ACK 的状态判定，以及此时连接为什么还不能立刻删除。
- 2021 #39 选择题：12B 应用数据分别用 1 个 UDP……考的是封装这一步：8B UDP 首部加上 12B 数据得到 UDP 长度，再推算交给 IP 后的总长度，并比较首部开销占有效载荷的比例。
- 2021 #40 选择题：甲 t0 发 seq=501 携带 200 字节。考的是序号含义这一步：首字节编号 501、末字节编号 700，由此确定下一个报文的 seq 和对方应回的 ack。
- 2022 #38 选择题：MSS=1KB、拥塞窗口 16KB 时超时。考的是拥塞控制这一步：超时后 ssthresh 取当前 cwnd 的一半、cwnd 回到 1 MSS，走慢开始而不是快恢复。
- 2022 #39 选择题：RTT=50ms、MSL=800ms。考的是 TIME_WAIT 计时这一步：2MSL 与若干 RTT 的相加，以及只有主动关闭方需要等这 2MSL。
- 2024 #38 选择题：TCP 从建立连接到关闭的总时间。考的是时延累加这一步：建连 1 个 RTT、数据传送若干 RTT、四次挥手 2 个 RTT 的逐段折算。
- 2024 #39 选择题：UDP 校验和。考的是计算这一步：加伪首部、按 16 位反码求和、进位回卷后取反，以及校验和字段的填法。

## 四、易错清单

1. 把序号当成「第几个报文」→ 序号是字节编号：seq=x 携带 n 字节，则下一报文 seq=x+n，对方回的 ack=x+n。
2. 以为双方都要等 2MSL → 只有主动关闭方进入 TIME_WAIT 等 2MSL，且从最后一次发出 ACK 起算；被动关闭方收到 FIN 回 ACK 后即可到 CLOSED。
3. 超时后还套用快恢复的窗口值 → 超时一律 ssthresh=⌊cwnd/2⌋、cwnd=1 MSS 重新慢开始；快恢复只在收到 3 个重复 ACK 时使用。
4. 把「每收到一个 ACK 窗口加 1」当成「每轮加 1」→ 慢开始每经过 1 个 RTT 窗口翻倍；拥塞避免每 RTT 只加 1 MSS，即每 ACK 加 MSS/cwnd。
5. 算 UDP 校验和时漏掉伪首部 → 伪首部含源 IP、目的 IP、0、协议号 17、UDP 长度，只参与累加不随报文传输。
6. 校验和算出 0 就填 0x0000 → 全 0 表示「未使用校验和」，反码求和取反后为 0 时必须写成全 1（0xFFFF）。
7. 把 UDP 首部中的长度字段当成数据长度 → 该字段 = 8 + 数据长度，最小值为 8；同时 16 位累加产生进位时要回卷加到最低位，最后再取反。
