## 1. 先搞清：这三个结构解决的是同一个问题

### 1.1 一棵普通二叉排序树有什么毛病

插入 `1 2 3 4 5 6 7`（有序序列），BST 会退化成一条链：

```
1
 \
  2
   \
    3
     \
      ...
```

查找 7 要比较 7 次。**n 个结点最坏 n 次比较**，等于顺序查找，白建了树。

于是第一个念头：**别让它长歪**。这就是 AVL 树 —— 左右子树高度差不超过 1。
但 AVL 太严：插入/删除一次可能连转好几层，旋转开销大。

第二个念头：**放松一点，用颜色记账**。这就是红黑树 —— 不要求每层高度差 ≤ 1，
只要求「最长的路径不超过最短的 2 倍」。旋转次数大幅下降，代价是查找路径略长一点。

**这两者都还在「二叉树」框架内：一个结点只存 1 个关键字，最多 2 个孩子。**

### 1.2 换个思路：为什么一个结点只能存 1 个关键字？

如果内存里，这没问题。**但磁盘不行。**

磁盘读数据的单位是「块」（block/page），一次常是 4KB 或 16KB。
你要读 1 个字节，也得把整个块搬进内存。所以：

```
二叉树查 100 万个关键字  ≈ 树高 20 层  = 20 次磁盘 I/O
```

每次 I/O 大概 10ms（机械硬盘）。20 次 = **200ms**，只查一个 key。

**关键洞察**：既然一次 I/O 反正要搬一整块，**为什么不把一整块都塞满关键字？**

一块 4KB 能装几百个关键字。于是每个结点变成「一个装着几百个关键字的大盒子」，
一次 I/O 就能比较几百个 key。树高立刻从 20 层掉到 2~3 层。

**这就是 B 树。** 它不是为了「好看」，是为了**把树高（= I/O 次数）压到极小**。

### 1.3 三个结构的定位

| 结构 | 每结点关键字 | 靠什么控制高度 | 主战场 |
|---|---|---|---|
| AVL / **红黑树** | **1 个** | 旋转（红黑树靠染色放宽） | **内存**（`std::map`、`std::set`） |
| **B 树** | **m−1 个**（m 阶） | 一个结点装很多 | **磁盘**（早期数据库索引） |
| **B+ 树** | 内部 m−1 个，数据**只在叶子** | 同上，且内部更瘦 | **磁盘**（MySQL InnoDB、文件系统） |

**B+ 树比 B 树更好在哪**（这是必考对比，先记住结论，§4 有详细）：
1. 内部结点**不存数据、只存索引**，所以同样一块能装更多关键字 → 树更矮 → I/O 更少
2. 叶子串成**链表** → 范围查询（`WHERE id BETWEEN 10 AND 20`）只需顺着链表扫，不用回树里跳
3. 每次查找**必然走到叶子** → 查找长度稳定，容易预估性能

**核心一句话：不考写代码，只考手算和判断。**

| 结构 | 408 采分点 | 不考 |

## 2. B 树：一个结点装很多关键字

### 2.1 定义（m 阶 B 树）

**术语警告**：「阶」的定义国内教材有分歧。408 统考口径是 **m 阶 = 最多 m 棵子树**。
（有的书说「m 阶 = 最多 m 个关键字」，那是另一套约定，考场上按题目给的定义走。）

按 408 口径（m 阶 = 最多 m 棵子树）：

| 项 | 上限 | 下限（非根） |
|---|---|---|
| 子树数（孩子数） | **m** | **⌈m/2⌉** |
| 关键字数 | **m−1** | **⌈m/2⌉ − 1** |

根结点特殊：可以只有 2 个孩子（1 个关键字）。

**为什么关键字数 = 子树数 − 1**：这是 B 树的骨架结构 ——
关键字把区间切成段，每段对应一棵子树。

```
        [ 10 | 20 | 30 ]        ← 3 个关键字
       /     |     |     \
    <10   10~20  20~30   >30    ← 4 棵子树
```

**这个 `子树数 = 关键字数 + 1` 是 B 树一切题的根基**，也是我修你 B+ 树时那个 bug 的核心（合并时只删了 key 没删 child）。

**实算一遍上下界**（这几个数要能在考场上秒答）：

| m | 关键字上限 m−1 | 关键字下限 ⌈m/2⌉−1 | 子树上限 m | 子树下限 ⌈m/2⌉ |
|---|---|---|---|---|
| 3 | 2 | 1 | 3 | 2 |
| 4 | 3 | **1** | 4 | 2 |
| 5 | 4 | 2 | 5 | 3 |
| 6 | 5 | 2 | 6 | 3 |
| 100 | 99 | 49 | 100 | 50 |

> ⚠️ **m=4 最容易算错**：⌈4/2⌉−1 = 2−1 = **1**，不是 2。很多人写成 m/2=2。
> 这个坑我在写 B+ 树校验器时也踩过（第一次用 `M/2` 当内部结点下界，导致 M=4 全部误报）。

### 2.2 插入：分裂（408 的核心手算）

**规则只有一条**：**插到叶子结点里；如果关键字数超过 m−1，就分裂，把中间的关键字上移给父结点。**

具体做法（假设溢出后结点有 m 个关键字，编号 k₁..k_m）：

1. 取中间那个 **k_⌈m/2⌉**（m 为奇数时取正中间；m 为偶数时取偏右那个）**上移**到父结点
2. 左边 ⌈m/2⌉−1 个留在原结点
3. 右边留下的一批放进新结点
4. **如果父结点也溢出了，继续往上分裂**
5. **如果根结点溢出，分裂出新根 —— 这是 B 树唯一长高的方式**

**唯一长高结构，一定要记住**：B 树只从根往上长。叶子永远在同一层。

#### 手算实例：3 阶 B 树依次插入 1..8

3 阶 → 关键字上限 **2**，下限 **1**。下面每一步都经过独立模拟器验证（中序为 1..8，每步 `子树数 = 关键字数+1`）。

```
插 1,2:        [1,2]              ← 满了但没溢出

插 3:          [1,2,3] 溢出 → 分裂
               取中间（正中间是第 2 个）= 2 上移，1 和 3 各成一边
               →    [2]
                  /    \
                [1]    [3]

插 4:             [2]
                 /    \
               [1]   [3,4]

插 5:          [3,4,5] 溢出 → 中间（第2个）= 4 上移给根
               →   [2,4]
                  /  |  \
                [1] [3] [5]

插 6:             [2,4]
                 /  |  \
               [1] [3] [5,6]        ← 还能装，不分裂

插 7:          [5,6,7] 溢出 → 中间 = 6 上移给根
               根 [2,4,6] 也溢出了（3 个 > 上限 2）→ 继续分裂
               取根中间 = 4 上移成【新根】← 树长高的唯一方式
               →        [4]
                      /     \
                   [2]       [6]
                  /   \     /   \
                [1]  [3]  [5]  [7]

插 8:             [4]
                 /     \
              [2]       [6]
             /   \     /   \
           [1]  [3]  [5]  [7,8]
```

**三个必须记住的点**：

1. **只有根分裂会让树长高**（插 7 那一步）。叶子永远都在同一层。
2. **中间关键字是「上移」，不是「复制」** —— 分裂后 4 只在根里出现，不在叶子里。
   （对比：B+ 树叶子分裂时是**复制**，原结点保留）
3. **分裂会连锁**：插 7 时叶子先分裂，根跟着溢出，又分裂一次。手算时必须**一步步重画**。

> **我第一版讲义这里手推错了**（把插 6 的结果写成了 `[2,4,6]`），是跑模拟器才发现的。
> 这正是 §2.2 强调的：**不要脑内推，每步画出来**。

### 2.3 删除：借（borrow）或并（merge）

删除比插入难，因为要处理**下溢**（关键字数 < ⌈m/2⌉−1）。

**分两步**：

**第一步：先定位要删的关键字在哪儿**
- 如果在**叶子**：直接删
- 如果在**内部结点**：用它的**中序前驱或后继**（简单说：左子树最大 / 右子树最小）顶替，
  然后**转去删那个前驱/后继**（它一定在叶子里）

**第二步：检查下溢，修**

假设结点 X 删完不够了（下溢），看它的兄弟：

| 情况 | 操作 | 记法 |
|---|---|---|
| 某兄弟关键字数 > 下限（**够借**） | 从兄弟「借」一个过来 | 经过**父结点中转** |
| 两个兄弟都刚好在下限（**不够借**） | 和兄弟**合并**，父结点下移一个关键字 | 父结点可能因此下溢 → **继续往上** |

**「借」的关键细节（最易错）**：不是直接把兄弟的关键字搬过来。
必须**经过父结点**：兄弟的边界关键字上移到父结点，父结点对应的关键字下移到 X。
（因为父结点的关键字就是两个子树的分隔值。）

**「并」的关键细节**：合并时，父结点那个分隔关键字要**一起拉下来**放进合并后的结点。
因为合并后两棵子树变一棵，不需要分隔值了，但它是个数据不能丢。

#### 一个完整例子（3 阶，每步都用模拟器验证过）

初始状态：插入 `2 3 5 7 8` 得到

```
        [3,7]
       /  |  \
     [2] [5] [8]
```

**第 1 步：删 2**

左叶子 `[2]` → `[]`，0 个 < 下限 1 → **下溢**。
兄弟 `[5]`：1 个关键字 = 下限，**不够借** → **合并**：
- 父结点的分隔键 3 **拉下来**
- 和左右两边合起来 → `[3,5]`
- 父结点少一个键（剩 `[7]`），仍合法（下限 1）

```
        [7]
       /   \
    [3,5]  [8]
```

> **注意「借」和「并」的判别条件**：兄弟的关键字数 **> 下限**才能借。
> 兄弟刚好等于下限时**必须合并** —— 因为借走一个它就下溢了。

**第 2 步：再删 3**

左叶子 `[3,5]` → `[5]`，1 个 = 下限，**刚好合法，什么都不用做**。

```
        [7]
       /   \
     [5]   [8]
```

> 这一步很多人以为要调整。**下限是「允许的最少」，等于下限就合法**，不用修。

**第 3 步：再删 5**

左叶子 `[5]` → `[]`，下溢。兄弟 `[8]` 只有 1 个 = 下限，**不够借** → 合并：
- 父结点 7 拉下来，和空 + `[8]` 合成 `[7,8]`
- 父结点键数变 0 → **根降级**

```
      [7,8]
```

> 这就是「删到根被降级」，和插入时「根分裂长高」正好对称。
> **B 树只有这两个地方会改变树高。**

#### 如果是「够借」的情况

上面三步都没遇上借。看一个借的例子：3 阶树

```
        [5]
       /   \
    [2,3]  [7,8]
```

删 2：左叶子 `[2,3]` → `[3]`，1 个 = 下限，**合法不用管**。

删 3：左叶子 `[3]` → `[]`，下溢。右兄弟 `[7,8]` 有 2 个 > 下限 1，**够借**：
- 父结点 5 **下移**到左叶子 → `[5]`
- 右兄弟最小的 7 **上移**替父结点 → 父变 `[7]`
- 右兄弟变 `[8]`

```
        [7]
       /   \
     [5]   [8]
```

> **「借」必须经父结点中转**，不能直接把兄弟的关键字搬过来。
> 因为父结点的关键字正是两个子树的分隔值 —— 借走兄弟的最小值，分隔值也得跟着变。
> 这是 408 最爱设的陷阱：`[2,3]` 和 `[5]` 直接搬，答案会错。

### 2.4 树高与 I/O 次数（计算题）

**高度上界公式**（n 个关键字的 m 阶 B 树）：

$$h \le \log_{\lceil m/2 \rceil}\left(\frac{n+1}{2}\right) + 1$$

U: h <= log_ceil(m/2) ( (n+1)/2 ) + 1

**推导思路**（理解比记公式重要）：
- 第 1 层至少 1 个结点
- 第 2 层至少 2 个结点
- 第 3 层至少 2·⌈m/2⌉ 个结点
- 第 h 层至少 2·⌈m/2⌉^(h−2) 个结点
- 每个结点至少 ⌈m/2⌉−1 个关键字

把这些加起来 ≥ n，解出 h。

**经典题**：m=100，3 层 B 树最多存多少关键字？

- 第 1 层：1 个结点 × 99 = 99
- 第 2 层：最多 100 个结点 × 99 = 9900
- 第 3 层：最多 100² = 10000 个结点 × 99 = 990000
- 合计 **99 × (1 + 100 + 10000) = 999999**

**约 100 万**。这就是 B 树存在的意义 —— 3 次 I/O 定位百万数据。

### 2.5 自测

1. m=5 的 B 树，非根结点最少几个关键字？最少几棵子树？
   → **2 个关键字、3 棵子树**（⌈5/2⌉−1=2，⌈5/2⌉=3）

2. m=4 的 B 树，一个非根结点可能有 2 个关键字吗？
   → **可以**。下限是 ⌈4/2⌉−1 = **1**，不是 2。m=4 是最容易算错的。

3. 3 阶 B 树依次插 `10 20 30 40 50`，画出最终形状。
   → 与 §2.2 的 1..8 同构（都是 3 阶顺序插入 5 个）：
   ```
        [20,40]
       /   |   \
    [10] [30] [50]
   ```
   验算：根 2 个关键字（≤2 ✓），每个叶子 1 个（≥1 ✓）。

4. m=100 的 3 层 B 树最多存多少关键字？
   → **999999**（99 × (1+100+10000)）

5. 为什么 B 树的「借」必须经过父结点？
   → 父结点的关键字是两棵子树的**分隔值**。借走兄弟的最小值后，
      分隔值必须同步变成那个值，否则左子树会出现 ≥ 分隔值的 key，BST 性质破坏。

## 3. B+ 树：把数据全赶到叶子去

### 3.1 B 树的问题在哪

B 树每个结点都存数据。这带来两个麻烦：

**麻烦一：空间浪费 → 树更高**
一个 4KB 的块，如果存「关键字 + 数据（比如一整行记录）」，可能只放得下十几个。
若只存「关键字 + 子结点指针」，能放几百个。**同样一块，装得越多，树越矮，I/O 越少。**

**麻烦二：范围查询难受**
B 树里查 `10 ≤ id ≤ 20`，得在树里反复上下跳：找到 10 → 中序后继 → 再找 → 可能跨层。
每次跳都可能是一次 I/O。

### 3.2 B+ 树的三个改法

```
B 树：                          B+ 树：
                                
   [10|20]  ← 也存数据             [10|20]  ← 只存索引，不存数据
   /  |  \                        /   |   \
 [5] [15] [25]                 [5,8] [10,15] [20,25]  ← 数据全在这
    ↑                              |_____|_____|
  数据分散在各层                    叶子串成链表 →
```

| 改法 | 效果 |
|---|---|
| ① 内部结点**只存索引**，不存数据 | 同样一块装更多关键字 → 树更矮 → I/O 更少 |
| ② 数据**全部**在叶子层 | 查找路径长度稳定（必到叶子），性能可预测 |
| ③ 叶子用**指针串成链表** | 范围查询 / 全表扫描顺着链表走，不用回树 |

**代价**：即使查的是内部结点里出现过的 key（比如 10），**也必须走到叶子**才能拿到数据。
所以 B+ 树的查找「永远不会提前结束」。

### 3.3 与 B 树的区别（必考，背这 5 条）

| # | B 树 | B+ 树 |
|---|---|---|
| 1 | 每个结点都存数据 | **只有叶子存数据**，内部只存索引 |
| 2 | 一个 key 只出现一次 | **key 可能在内部和叶子重复出现**（内部的是"索引副本"） |
| 3 | 叶子之间无连接 | **叶子串成有序链表** |
| 4 | 查找可能在中途命中返回 | **必须走到叶子** |
| 5 | 范围查询要中序遍历树 | **顺着叶子链表扫** |

**为什么 B+ 更适合磁盘索引**（要能说 3 点）：
1. 内部更瘦 → 每块装更多 → 树更矮 → I/O 更少
2. 叶子链表 → 范围查询和全表扫描是顺序 I/O，不是随机 I/O
3. 查找路径长度固定 → 性能可预测（数据库最看重这个）

> **记忆锚**：MySQL InnoDB 的索引就是 B+ 树。你可以想「为什么 MySQL 不用 B 树」来反推这三点。

### 3.4 手算注意力点（和你代码里的坑对应）

B+ 树的**阶数约定**和 B 树一致，但**分裂时的中间关键字处理不同**：

| | 分裂时中间关键字 |
|---|---|
| B 树 | **上移**到父结点，原结点不再保留 |
| **B+ 树（叶子）** | **复制**一份上移，原结点**保留**（因为数据必须留在叶子） |
| **B+ 树（内部）** | **上移**（和 B 树一样，内部只是索引） |

**这就是 B+ 树叶子分裂时「key 会重复出现」的原因。**

我修你代码时那个 bug 就在这里：内部结点合并时，
`keys[i]` 必须等于 `children[i+1]` 子树的最小关键字。合并两个结点后，
**中间那个分隔键没法靠「拼接两边 keys」得到** —— 必须重新算。

最小例（M=3，插 1..8 删 1）：

```
child = keys={}   children=[叶子{2,3,4}]
right = keys={7}  children=[叶子{5,6}, 叶子{7,8}]
拼接 → keys={7} children=3   ← 错！
应为 → keys={5,7} children=3
```

那个 `5` 就是「夹在中间、拼接不出来」的分隔键。

## 4. 红黑树：用颜色记账的平衡树

### 4.1 它到底是"什么"的折中

回到 §1.1：BST 会退化，AVL 修得太狠。

**红黑树的取舍**：放弃「高度差 ≤ 1」这个严格要求，改成
「**最长路径 ≤ 2 × 最短路径**」。

这个放松换来什么？**插入/删除时旋转次数大幅减少**（AVL 可能要转到根，红黑树最多 2~3 次）。
代价是树可能高一点，查找慢一点。

**结论**：读多写少 → AVL；**读写都多 → 红黑树**。
这就是为什么 `std::map` / `std::set` / Java `TreeMap` 都用红黑树。

### 4.2 五条性质（背这五条，考试就考这个）

1. **每个结点是红的或黑的**
2. **根结点是黑的**
3. **每个叶子结点（NIL 空结点）是黑的**
4. **红结点的两个孩子必须是黑的**（即不存在连续两个红结点）
5. **从任一结点到其所有后代叶子的路径上，黑结点数目相同**

**第 3 条容易被忽略**：这里的「叶子」指的是**外部的 NIL 空结点**，不是你平时说的「没有孩子的结点」。
408 考题里如果画了 NIL，必须把它当黑色算进去。

**第 5 条是"黑高"的来源**：从这个结点出发，每条路径的黑结点数（不含自己/含自己看约定）相同。
这个数叫**黑高（black height）**。

**由 2/4/5 推出关键结论**：最长路径 ≤ 2 × 最短路径。
- 最短路径：全是黑结点
- 最长路径：红黑交替（因为不能连续红），所以红结点数 ≤ 黑结点数
- 最长 ≤ 2 × 最短

**所以树高 h ≤ 2·log₂(n+1)**，查找 O(log n)。

### 4.3 一个真实例子（你仓里代码跑出来的）

插入 `10 20 30 15 25 5 1` 后：

```
        20(B)
       /      \
   10(R)      30(B)
   /    \        \
5(B)   15(B)    25(R)
  |
1(R)
```

**逐条验证五条性质**：

| 性质 | 检查 | 结果 |
|---|---|---|
| ① 红或黑 | 每个结点都有颜色 | ✓ |
| ② 根黑 | 20 是 B | ✓ |
| ③ NIL 黑 | 所有空孩子视为黑 | ✓ |
| ④ 红孩子必黑 | 10(R) → 5(B)、15(B) ✓；25(R) 无孩子 ✓；1(R) 无孩子 ✓ | ✓ |
| ⑤ 黑高相等 | 见下表 | ✓ |

**黑高验算**（这是最常考的「判断是不是红黑树」）：

```
路径            颜色序列       黑结点数
20-10-5-1      B,R,B,R        2
20-10-5-NIL    B,R,B,NIL      2
20-10-15-NIL   B,R,B,NIL      2
20-30-25-NIL   B,B,R,NIL      2
20-30-NIL      B,B,NIL        2
```

**全部 = 2，黑高相等 ✓**（我实际用脚本算过，见上面的验证输出）

顺便验证「最长 ≤ 2×最短」：最短路径长度 2（`20-30-NIL`），最长 4（`20-10-5-1`），4 = 2×2 ✓

### 4.4 插入调整：只有两种情况

**新插入的结点一律染红**（染黑会破坏黑高，染红只可能破坏「红孩子必黑」）。
然后只有两种修复：

**情况 A：叔叔是红的 → 只变色，不旋转**
```
父红、叔红 → 父变黑、叔变黑、祖父变红，然后【把祖父当新插入结点，继续往上查】
```

**情况 B：叔叔是黑的（或 NIL）→ 旋转 + 变色**

先看「插入结点 相对 父」和「父 相对 祖父」的方向：

| 方向 | 判断 | 操作 |
|---|---|---|
| **LL**（左左） | 插在父的左边，父在祖父的左边 | 父变黑、祖父变红、**祖父右旋** |
| **RR**（右右） | 插在父的右边，父在祖父的右边 | 父变黑、祖父变红、**祖父左旋** |
| **LR**（左右） | 插在父的右边，父在祖父的左边 | 先**左旋父**（转成 LL）→ 再按 LL 做 |
| **RL**（右左） | 插在父的左边，父在祖父的右边 | 先**右旋父**（转成 RR）→ 再按 RR 做 |

**记忆法**：看「插入结点到祖父」这条路径的最下两步。
- LL / RR 是"直的" → 一次旋转（转祖父）
- LR / RL 是"折的" → 两次旋转（先转父，再转祖父）

> **和 AVL 的区别**：AVL 是「失衡结点在新结点哪一侧，就往反方向转」。
> 红黑树只看**叔叔的颜色**决定走哪条路 —— 这是两者最大的不同。
> 做题时先看叔叔，再看方向。

**最后一步（最常漏）**：`while` 循环结束时，**把根染黑**。
因为情况 A 可能一路往上把根染红了。

### 4.5 红黑树在 408 里到底怎么考

**明确一点：408 不考红黑树的插入/删除代码。** 考的是：

| 题型 | 怎么答 |
|---|---|
| 给一棵树，判断是不是红黑树 | 逐条查五条性质，重点查 ⑤ 黑高（最容易挂） |
| 给插入序列，问插入后形态 | 只考**变色方向**和**旋转方向**，通常只插 3~5 个结点 |
| 红黑树 vs AVL | 红黑树平衡更松（≤2×）、旋转更少、适合读写混合 |
| 红黑树 vs B 树 | 红黑树是「2-3-4 树」的二叉表示（这个联系 408 不考，但理解了不亏） |

**答题模板（判断题）**：
1. 根是不是黑的？
2. 有没有连续两个红结点？
3. **从根到每个 NIL，数黑结点个数，必须全部相等**
4. 顺便确认中序有序（BST 性质）

> 第 3 条必须动手数，不能"看着差不多"。你原代码里 `blackHeight` 累加了却从不比较，
> 就是这个思路的缺失 —— 打印出来看着对，其实没验。

## 5. 三者的关系：一条主线串起来

### 5.1 统一视角

```
BST（会退化）
  ↓ 要求高度平衡
AVL（严格：|高度差| ≤ 1，转得凶）
  ↓ 放松平衡要求
红黑树（宽松：最长 ≤ 2×最短，转得少）
  
BST（内存，1 结点 1 key）
  ↓ 换到磁盘：一次 I/O 搬一整块，别浪费
B 树（1 结点 m-1 key）
  ↓ 内部只留索引、数据全下叶子、叶子成链表
B+ 树（数据库索引的选择）
```

**两条线是平行的**：左边「怎么在内存里平衡」，右边「怎么在磁盘上减少 I/O」。
408 把它们放在一起考，你答题时要分清**题目问的是哪条线**。

### 5.2 复杂度对比（背这张表）

| | 查找 | 插入 | 删除 | 树高 | 适用 |
|---|---|---|---|---|---|
| BST（平均） | O(log n) | O(log n) | O(log n) | O(log n) | 简单场景 |
| BST（最坏） | **O(n)** | **O(n)** | **O(n)** | **O(n)** | 退化成链 |
| AVL | O(log n) | O(log n) | O(log n) | ≤ 1.44 log n | 读多写少 |
| 红黑树 | O(log n) | O(log n) | O(log n) | **≤ 2 log n** | 内存通用 |
| B 树 | O(log_m n) | O(log_m n) | O(log_m n) | log_⌈m/2⌉ | 磁盘 |
| B+ 树 | O(log_m n) | O(log_m n) | O(log_m n) | 同上（但更矮） | 数据库索引 |

**注意 B/B+ 树的高度底数是 `⌈m/2⌉` 不是 m**（因为最坏情况下每个结点只有下限那么多）。

### 5.3 记忆锚（帮你考场秒答）

- **B 树的分裂方向 = 往上**（中间关键字上移）；**合并方向 = 往下**（父关键字下移）
- **B+ 树叶子分裂时 key 要复制**（数据留在叶子），内部结点分裂时 key 上移
- **红黑树先看叔叔颜色**（红→变色、黑→旋转），不是先看方向
- **红黑树的"叶子"是 NIL**，不是没孩子的结点
- **m=4 的下限是 1 不是 2**（⌈4/2⌉−1 = 1）
