## 二、正文

### 1. 应用层要解决什么：从 socket 往上还剩哪些事

传输层把数据从一台主机的一个进程送到另一台主机的另一个进程（TCP 靠四元组，UDP 靠端口），到此交差。剩下的四件事传输层一概不管：**谁先说话、报文长什么样、每个字段什么含义、什么时候该重发或复用**。这四件事——报文类型、语法、语义、时序——就是应用协议的定义域。

所以"应用层"包含两个东西：**分布式进程**（两个不同主机上的进程互相通信）+ **应用协议**（它们说话的规矩）。注意应用协议不规定程序内部怎么写，只规定"线上字节怎么排"，因此同一个协议可以有无数的实现。

**C/S 与 P2P 的分野**在于"谁在等、谁在找"：

- C/S：服务器 7×24 被动监听一个**已知端口**（HTTP 80、SMTP 25），客户用临时端口主动发起，客户之间不直接通信。优点是集中管理、易计费、易做安全策略；缺点是服务器是瓶颈和单点故障，扩展只能靠加机器。
- P2P：每个对等方既请求又提供，没有永远在线的服务器（或只有一个做索引的追踪服务器）。可扩展性好——用户越多，供给方越多；代价是节点进出的动态性（churn）强、管理难、安全与版权问题突出。

最小例子：浏览器访问 Web 服务器是纯 C/S；BitTorrent 里 .torrent 文件充当索引，真正的数据块在对等方之间直接传，是 P2P。

### 2. DNS：层次命名 + 分布式解析

**为什么需要**：IP 地址是给路由器看的数字，人不该记；而且服务器换 IP 时，所有用户不该跟着改。DNS 就是那张"域名 → IP"的**分布式数据库**，顺带提供主机别名（CNAME）、邮件路由（MX）等信息。

**层次域名空间**：域名从右往左读，越右越靠近根。`www.cs.example.com.` 的末尾那个点就是根（通常省略），`com` 是顶级域，`example` 是二级域，`cs` 是子域，`www` 是主机名。每一级对应一个**区（zone）**，由一台权威域名服务器管。空间是树，所以解析只能自顶向下逐级逼近——这就是为什么必须有"根"和"顶级域"这两级服务器。

域名服务器分四类：根（知道所有顶级域服务器的 IP）、顶级域（知道其下每个域的权威服务器）、权威（真正存本区主机记录）、**本地域名服务器**（不属于这棵层次树，是主机配置里的第一站，通常由 ISP 或校园网提供）。

**递归查询 vs 迭代查询**——这一对最容易背反：

- 递归：被问者替你跑完全程，只回最终答案。主机 → 本地 DNS 通常用递归。
- 迭代：被问者只回"下一步去问谁"，剩下的路你自己走。本地 DNS → 根 / 顶级域 / 权威通常用迭代。

设主机到本地 DNS 往返 $RTT_0$，本地到根、本地到顶级域、本地到权威依次 $RTT_1,RTT_2,RTT_3$，忽略服务器处理时延，串行执行时两种方式的总时延都是

$$T = RTT_0 + RTT_1 + RTT_2 + RTT_3$$

**时延相同，区别在谁承担负担**：递归把整条链的查询压力压给上级服务器，如果根和顶级域都做递归，早被压垮；所以真实 DNS 里根与顶级域只做迭代，把"继续问"这件事退回给本地 DNS。另外报文数不同：迭代时本地 DNS 要发 3 次询问、收 3 次响应（另加主机那一次），共 8 个报文。

**缓存**：每条记录带 TTL。本地 DNS 缓存后，同域名的第二次查询（哪怕换了主机）只需 $RTT_0$。浏览器和操作系统也各有缓存（hosts 文件、浏览器 DNS 缓存）。

**记录类型**：A（域名→IPv4）、AAAA（→IPv6）、CNAME（别名→规范名）、MX（邮件服务器，带优先级）、NS（本区权威服务器）、PTR（反向解析）。

最小例子：主机查 `www.example.com`，本地 DNS 无缓存，迭代全过程——

1. 主机 → 本地 DNS（递归），1 次询问；
2. 本地 → 根，根返回 `com` 顶级域服务器的名字与 IP（A 记录，即"胶水记录"）；
3. 本地 → `com` 顶级域，返回 `example.com` 的权威服务器；
4. 本地 → 权威服务器，拿到 `www` 的 A 记录；
5. 本地 DNS 把结果回给主机，并按 TTL 缓存。

**DNS 默认走 UDP/53**：一问问一答、报文短，省掉 TCP 的三次握手（否则每次查询凭空多一个 RTT）。但**区域传送**数据量大、要求可靠，改用 TCP/53。

### 3. FTP 的双连接与电子邮件的三件套

**FTP 为什么用两条 TCP 连接**：它把控制和数据分到两条连接上，叫"带外控制（out-of-band）"。

- **控制连接**：客户端随机端口 → 服务器 **21**，整个会话期间一直保持，传的全是 ASCII 命令行（`USER`/`PASS`/`RETR`/`STOR`/`LIST`）。
- **数据连接**：每传一个文件**新建一条，传完就关**。主动模式下服务器用 **20** 端口发起。

两种模式的区别在"谁先动手"：

- 主动模式（PORT）：客户端告诉服务器"我在 x 端口等"，**服务器从 20 端口主动连**客户端。
- 被动模式（PASV）：服务器告诉客户端"我在 y 端口等"，**客户端主动连**服务器。客户端在 NAT 后面时只能用它。

为什么要双连接：控制连接必须随时可用。用户在传大文件时按 Ctrl+C，客户端要能立刻在同一条控制连接上发 `ABOR`；如果命令和数据挤一条连接，命令就排在几百兆字节后面了。代价是服务器要为**每条控制连接**保存状态（登录用户、当前目录、传输类型），所以 **FTP 是有状态协议**，这让它难以做大规模负载均衡。

最小例子：`PORT 192,168,1,5,20,10` 里的六个数字是 h1.h2.h3.h4.p1.p2，数据端口 = $p_1\times 256 + p_2 = 20\times256+10 = 5130$，即客户端在 192.168.1.5:5130 等服务器来连。

**电子邮件**由三件套组成：用户代理 UA、邮件服务器、协议。链条上只有两种动作——**推**和**拉**：

| 环节 | 协议 | 端口 | 方向 |
| --- | --- | --- | --- |
| 发送方 UA → 发送方邮件服务器 | SMTP | TCP 25 | 推 |
| 发送方服务器 → 接收方服务器 | SMTP | TCP 25 | 推 |
| 接收方服务器 → 接收方 UA | POP3 / IMAP | TCP 110 / 143 | 拉 |

POP3：把报文下载到本地，可选"下载后删除"或"保留"；默认不在服务器上维护文件夹结构，多设备不同步。IMAP：报文留在服务器，UA 直接在服务器上操作文件夹，多设备状态一致，还支持只取首部以省流量。

**MIME 的定位**：SMTP 最初只能传 7 位 ASCII。MIME **不是替换 SMTP**，而是在报文首部追加 `Content-Type: image/jpeg; name="a.jpg"` 和 `Content-Transfer-Encoding: base64`，把任意二进制编码成 ASCII 字符流交给 SMTP 运，收方按同样的首部解码。所以准确说法是"MIME 是对 SMTP 的补充"。

最小例子：一封带图的邮件线上长这样——SMTP 信封（`MAIL FROM` / `RCPT TO` / `DATA`）+ RFC 822 首部（From/To/Subject）+ MIME 首部 + base64 正文。四层叠在一起，缺一层就传不了图。

### 4. WWW 与 HTTP：连接模式与 RTT 账

**URL**：`协议://主机:端口/路径?查询#片段`，HTTP 默认 80，HTTPS 默认 443。URL 负责"定位"，URN 负责"命名"，二者合称 URI。

**HTTP 报文**：请求 = 请求行（`GET /index.html HTTP/1.1`）+ 首部 + 空行 + 实体；响应 = 状态行（`HTTP/1.1 200 OK`）+ 首部 + 空行 + 实体。方法 GET/POST/HEAD/PUT/DELETE；状态码记住 200、301、304、400、404、500 各自的语义。

**三种连接模式的 RTT 账**——本章唯一必须动手算的地方。原则只有一句：**每个对象都要问"它需不需要重新握手"**。

设页面共 $N$ 个对象（1 个 HTML 主页 + $N-1$ 个引用对象），忽略传输时延与处理时延：

- **非持续连接**：每个对象单独建 TCP、传完就关。每个对象 = 1 RTT 建连 + 1 RTT 请求/响应，故

$$T_{\text{非持续}} = 2N\cdot RTT$$

- **持续连接、非流水线**：只建一次连接，之后每个对象 1 RTT，故

$$T_{\text{持续}} = (N+1)\cdot RTT$$

这里的 $N+1$ 就是"1 次建连 + $N$ 次请求响应"，不要漏掉那个 1。

- **持续连接、流水线**：建连 1 RTT，取主页 1 RTT，解析出引用对象后**并行**发出请求，再 1 RTT 收齐，故理想情况

$$T_{\text{流水线}} = 3\,RTT$$

一般写作 $2RTT + \sum \frac{L}{R}$，前提是引用对象能并行请求。

**例**：主页 + 3 张图，$RTT=100\text{ ms}$，忽略传输时延。

- 非持续：$4\times 2\times 100 = 800$ ms；
- 持续非流水线：$(4+1)\times100 = 500$ ms；
- 持续流水线：$3\times100 = 300$ ms。

若传输时延不可忽略，每一项后面再补真实的 $\frac{L}{R}$（按对象逐个累加，非持续模式下每个对象还要单独算一次）。

**Cookie**：HTTP 是**无状态**的，服务器不记得两次请求来自同一人。好处是服务器设计简单（不必保存会话），坏处是做不了登录态和购物车。Cookie 有四个部件：① 响应首部的 `Set-Cookie:`；② 请求首部的 `Cookie:`；③ 浏览器本地的 cookie 文件；④ 服务器后端的数据库。要点是：Cookie 不是"服务器端的会话表"，而是**客户端替服务器保存并自动回送的键值对**，真正的状态还在服务器数据库里。

最小例子：登录成功后服务器回 `Set-Cookie: sid=1234`，浏览器此后每次请求都自动带 `Cookie: sid=1234`，服务器拿 sid 去查库，才"认出"你。

**代理服务器与缓存**：代理对客户端是服务器、对源服务器是客户。作用有三：就近命中缩短响应时间、压掉出口带宽、做访问控制。一致性靠**条件 GET**：代理手上有副本时发 `If-Modified-Since: <时间>`，源服务器若未变，回 `304 Not Modified`（只有首部、无实体），代理把本地副本直接发给客户。

最小例子：客户端到代理 $RTT=10$ ms，客户端到源服务器 $RTT=500$ ms，命中一次就差 50

## 三、真题落点

**2022 #40 选择题**：考的是 HTTP/1.1 持久连接下“取主页（1 MSS）”的往返次数拆解。解题步骤是：先判断题目给定的版本号能否满足持久连接的条件，即 HTTP/1.1 默认支持持久连接；然后算出 TCP 三次握手占 1 个 RTT；再算出请求-响应占 1 个 RTT；最后单独判断 1 MSS 报文的发送时延是否需要额外叠加。关键是判断同一条连接能否被后续请求复用，因为持久化正是为了省去重复握手。

**2024 #40 选择题**：考的是非持久 HTTP 的 RTT 计数。解题步骤是：先确定每个对象都要独立建连，也就是每个对象共需 2RTT，即 1 次握手加上 1 次请求/响应；再按对象个数串行累加，得到 $2N$ RTT；最后在首次访问域名时补上 DNS 解析产生的 RTT。这一步最容易出错的地方，是把一次请求与一次响应拆成两个往返，或者误以为可以复用连接。

## 四、易错清单

1. **错在把请求和响应各算一个 RTT** → RTT 是往返时延，一次“发请求—收响应”在忽略发送时延时就只占 1 个 RTT。做题时画时间轴：$t=0$ 发送请求，$t=\mathrm{RTT}$ 收到响应。
2. **错在非持久 HTTP 只算请求-响应不算重新握手** → 每个对象都要新建 TCP 连接，故单个对象 2RTT；$N$ 个对象串行共 $2N$ RTT，若有 $k$ 条并行连接则按 $\lceil N/k\rceil$ 轮累加。
3. **错在漏掉 DNS 查询** → 首次访问域名先加一次 DNS 解析 RTT（本地无缓存时）；只有题目明确说“已知服务器 IP”或“已缓存”，才可省去。
4. **错在把 1 MSS 的发送时延当 0** → 发送时延 $=L/R$，与传播时延、RTT 分开相加；题目给了链路带宽和 MSS 就必须代入算，不能默认忽略。
5. **错在把持久连接的默认值记反** → HTTP/1.1 默认持久连接（可流水线），HTTP/1.0 默认非持久（要显式 `Connection: keep-alive`）。看版本号先定默认，再决定是否复用连接。
6. **错在流水线与持久非流水线混用** → 持久非流水线：每个对象仍需 1 个 RTT（串行）；持久流水线：所有对象可在 1 个 RTT 内连续发出，合计约 1RTT 加总发送时延。动笔前先把依据写出来。
7. **错在报文格式步把首部行写进请求行** → 请求行格式为 `方法 SP URL SP 版本 CRLF`，每行首部以 CRLF 结束，首部与实体之间必须有一个空行（单独一个 CRLF）。
8. **错在 URL 省略部分补全错误** → http 默认端口 80，URL 中路径省略时应补 `/` 而不是留空，否则算错请求行对象。
