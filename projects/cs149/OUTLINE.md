## 一、它在做什么

把“并行能加速”这句话拆成一串可复现的数字，并说清每个数字的来源。

输入是一组固定 workload（向量加、点积、归约、矩阵乘、stencil）加一份配置：规模 N、后端（标量、SIMD、多线程、GPU）、线程数、重复次数、是否绑核。输出是三样东西：一份带抖动区间的加速比表；一张加速比随 N 变化的曲线（不是单点）；以及每个加速比的归因说明——这个 6× 里多少来自向量宽度，多少来自核数，多少被内存带宽或拷贝开销吃掉。

验收长这样：换一台同架构机器，别人拿同样配置能跑出落在你误差棒内的数字；任取表里一个加速比，你能指着代码和硬件计数器说清它是怎么来的；把 N 故意调小到全塞进 L1，曲线形状必须按预期变化。三条里缺一条，数字就只是数字。

**入口（本文的读法）**：在固定 workload 与可复现配置（N、后端、线程数、绑核）下，把每个加速比拆成可计数事件：串行基线的 `clock_gettime`、roofline 的 FLOP/byte、`vmovups`/`vfmadd` 指令、伪共享的 cache line、强/弱扩展斜率、`perf_event_open` 的归因。换的是配置项与实现路径，不换的是「加速比必须能被事件计数器解释」这条要求。

**不换的是什么**：全程不变的是同一组 workload 的元素类型 float/int、访问步长与边界条件、随机种子与 fill 函数，同一 clock_gettime/CLOCK_MONOTONIC 计时器，同一 perf_event_open 事件集（cycles、instructions、cache-references、cache-misses、L1-dcache-load-misses、dTLB-load-misses），同一 64-byte cache line 对齐与 padding 布局，同一 warmup 次数与 median/IQR 统计口径；看到差异先问是否换了 N、后端、线程数、重复次数、sched_setaffinity 绑核、malloc/posix_memalign 分配器、编译器 -O/-march/-ffast-math 标志、GPU cudaMemcpy/kernel launch/stream 顺序、cpufreq governor。

## 二、为什么这样做（功能设计）

这一节写的是几个关键取舍：把哪些现成组件替换掉、替换在哪一层替换、以及为什么值得付这个代价。

**（1）用手写 SIMD 替换编译器自动向量化。** 替换的层次是 workload 的后端实现，不是编译选项层。`-O3 -march=native` 到底有没有向量化、向量化了哪个循环，取决于编译器版本、循环形态和别名分析，你无法在报告里指着某一行说“这 8 个 float 是一条指令吃掉的”。手写 intrinsics 之后，有三件原本由编译器代劳的事必须自己实现：64 字节对齐的分配与尾部处理（N 很少是向量宽度的整数倍）、分支的向量化改写（`if` 会让 lane 分叉，要么改成 select/blend，要么先分区再算）、以及归约顺序（浮点加法不满足结合律，改变求和顺序会改结果，所以校验和必须带容差而不是判等）。代价很直接：代码量是标量的三到五倍，换个指令集要重写一遍，所以只挑两个 workload 做，不是全部。

**（2）把计时和调度从操作系统手里拿回来。** 这一层是 harness。绑核不是优化手段而是测量前提——线程在核间迁移会带走 cache，抖动可以到 30%。warmup 若干次后丢弃、重复 R 次取中位数和四分位距，而不是取均值或最小值。不可靠性有明确的几个来源：频率与 turbo、线程迁移、NUMA 远端访存、后台负载、冷热缓存。压制的办法不是“多跑几次”，而是把每个来源单独关掉或固定住。为什么不用 Google Benchmark 这类现成框架：它不给你绑核，不给你统一的 CSV 字段，也不给你和 Amdahl 拟合对齐的统计口径。代价是 harness 自己有 bug 会污染全部数据，所以先要拿一个纯串行函数反复测，确认 harness 自身的抖动在 2% 以内，再去测并行。

**（3）把测试从“一个点”改成“一条曲线”。** 输入数组统一 64 字节对齐，N 从塞得进 L1 一直扫到远超 LLC。孤立的一个 6× 没有信息量——它可能来自核数，也可能只是因为数据本来就全在缓存里。只有看到 N 跨过 L1/L2/LLC 边界时加速比掉下来，才能把“多核并行”和“内存带宽”这两个原因分开。代价是测试矩阵膨胀成后端 × N × 线程数 × 重复次数，必须先把单轮时间压到秒级，否则一轮扫不完。

**（4）伪共享实验必须用裸线程，不能用 OpenMP。** OpenMP 的 `reduction` 和调度策略把数据布局藏起来了，而伪共享实验的全部要求就是你能精确控制“两个线程写的两个变量是否落在同一条 64 字节 cache line 上”。做法是对照组和修复组只差一个 `alignas(64)` 或 padding，其余完全相同。这里有个真实的坑：编译器可能把循环里的累加变量提到寄存器，于是根本没有发生内存写，实验“测不出伪共享”。要么加 `volatile`，要么每轮强制写回，并在报告里承认这个现象是被构造出来的、构造的条件是什么。

**（5）GPU 只做端到端核算，不做极致调优。** GPU 后端与 CPU 后端同构，都实现同一个 `run(config)` 接口，但计时被切成四段：分配、H2D 拷贝、kernel、D2H 回传。理由是：这里要证明的是“那个 10× 里有多少被拷贝和启动开销吃掉”，而不是去刷一个更高的 10×。选 CUDA 不选 OpenCL 纯粹是环境成熟度问题。代价是需要一块 GPU；拿不到就退化成“读 kernel 代码 + 用 CPU 侧数据算账”，验收降级但不断裂。

**（6）为什么不用更省事的做法。** 最省事的是跑几个现成 benchmark 抄结论。代价是：你回答不了“这个 6× 从哪来”，换台机器也复现不了。本项目的全部产出是归因能力，所以计时、正确性校验、配置记录这三件事必须握在自己手里，不能外包。

## 三、章节大纲

1. **计时基座与串行基线**——workload 接口、64B 对齐分配、校验和、warmup 与重复、绑核。知识点：计时误差、抖动来源、中位数与均值之别。做完能验证：harness 自身抖动 < 2%，串行基线可复现。
2. **算术强度与 roofline 定位**——把每个 workload 标在 roofline 图上，判断它是算力受限还是带宽受限。知识点：算术强度、峰值算力、带宽、平均访存时间。做完能验证：你能事先预测哪个 workload 的加速比上限低，且预测被实测打中。
3. **SIMD 向量化**——标量到 AVX2/NEON，向量宽度、对齐、尾部、掩码、分支改写、归约顺序。知识点：SIMD 执行模型、lane 分叉、浮点非结合性。做完能验证：相对标量 ≥ 2.5×，且掉速点能用尾部或对齐解释。
4. **多核并行的两种写法**——OpenMP 的 `parallel for`/`reduction` 与 `std::thread` 手工划分、静态与动态调度、归约树。知识点：数据划分、负载不均、调度开销。做完能验证：8 核上测出实际加速比，并用 Amdahl 反推串行比例。
5. **缓存一致性与伪共享**——MESI 直觉、cache line、padding、复现与修复对照。知识点：一致性流量、写失效、对齐。做完能验证：修复后相对未修复 ≥ 2×，且差异只在 padding 一处。
6. **强扩展与弱扩展**——固定问题规模加核数，对比固定每核负载加核数，Amdahl 与 Gustafson 两条曲线。知识点：可扩展性定义、串行部分、规模效应。做完能验证：同一份数据能同时拟合出两条曲线并解释差异。
7. **GPU 编程模型与端到端开销**——kernel 写法、grid/block、内存层次、四段计时、occupancy 的基本观察。知识点：SIMT、host-device 带宽、启动开销。做完能验证：端到端加速比与纯 kernel 加速比的差额能被拷贝量解释。
8. **归因报告**——CSV 字段设计、误差棒、加速比表、每个数字的因果链。知识点：性能报告规范、可复现性。做完能验证：别人按你的配置能跑出落在误差棒内的数字。

## 四、不做什么 · 必要性 · 失效点

### 必要性：删掉会怎样

| 机制 | 删掉会怎样 | 判定 |
|---|---|---|
| 手写 SIMD intrinsics | 无法把 `_mm256_add_ps` 的 8 float/指令计入向量宽度来源；自动向量化缺失时 6× 被误归因到核数，验收“指着代码和硬件计数器说清来源”破 | 选择 |
| 64 字节对齐的分配与尾部处理 | `_mm256_load_ps` 触发未对齐访存或 fallback `_mm256_loadu_ps`，N 非整数倍时尾部 select/blend 错误，校验和超容差 | 必需 |
| 绑核 | `sched_setaffinity`/`taskset` 缺失后线程迁移带走 L1/L2，中位数与 IQR 误差棒覆盖不了 30% 噪声，验收“同架构机器落在误差棒内”破 | 必需 |
| 中位数和四分位距 | 取均值或最小值会把 turbo 尖峰/后台负载当稳定值，加速比表失去 IQR 误差棒，Amdahl 拟合口径断裂 | 必需 |
| `alignas(64)` 或 padding | 对照组与修复组不再只差 padding，无法用 64B cache line 争用解释裸线程时间差；OpenMP `reduction` 隐藏布局时伪共享实验不可证伪 | 必需 |
| GPU 计时被切成四段：分配、H2D 拷贝、kernel、D2H 回传 | `cudaMalloc`/`cudaMemcpy`/kernel launch 混成一个 `run(config)` 总时间，无法拆出 10× 被 H2D/D2H 吃掉多少，验收“每个加速比归因说明”破 | 选择 |

### 失效点：哪条前提一破，结论就变

- 物理核数/SMT 拓扑不同（`lscpu` 的 core/socket/thread、`OMP_NUM_THREADS`） → 多线程加速比随线程数的拐点位移，Amdahl 拟合的串行分数改变。
- `sched_setaffinity`/cpuset 权限位不可用 → 线程迁移使中位数/IQR 误差棒外，加速比归因混入 L1/L2 冷热。
- cpufreq governor 非 `performance` 且 turbo 未关 → `clock_gettime(CLOCK_MONOTONIC)` 下同 workload 周期数变，6× 可能来自 boost 而非核数。
- 内存介质/NUMA 拓扑不同（DDR 通道、LLC 容量、远端节点） → N 扫描曲线 L1/L2/LLC 拐点位移，多核并行收益被带宽限制改变。
- OpenMP runtime 版本或 `reduction`/schedule 策略改变、编译器把累加变量提升到寄存器 → 伪共享对照/修复组不再只差 `alignas(64)`，64B line 争用测不出。

### 不做什么（范围）

**课程不要求、明确不碰**：不写 LLVM/GCC 的向量化 pass，不实现自动向量化；不写 cache 模拟器或 CPU 微体系结构模拟器——一致性只做到“能测出流量差异”这一层，MESI 状态机本身归体系结构那边；不碰 MPI、多机、分布式一致性；GPU 不展开 PTX/SASS 级调优，不做 tiling 与 occupancy 的极限搜索，那是 GPU 深入项目的事。

**属于实现自由度、可以自己定**：语言选 C++17 是为了 intrinsics、线程、CUDA 在同一语言里，换成 C 或 Rust 也行，但要保证计时边界不被运行时干扰；workload 挑哪几个自定，但必须覆盖一个算力受限和一个带宽受限；SIMD 指令集按机器走，x86 用 AVX2、Apple Silicon 用 NEON，报告里写清楚；GPU 章节整体可选，没有硬件就降级为算账练习。

**常见跑偏，见到就停**：

- 只报加速比不报基线——没有“相对什么、什么机器、什么规模”的加速比是废数字。
- 单次计时就下结论，或者取最小值当成绩。
- 多线程不绑核，数据在核间跳。
- 把 N 调到全塞进 L1，测出漂亮加速比，然后宣称“多核很好”。
- 开了 `-O3 -march=native` 就把功劳记在“我做了 SIMD”头上，其实一行 intrinsics 都没写——要么关掉自动向量化做对照，要么明确标注这是编译器做的。
- 伪共享实验里累加变量被优化进寄存器，测了个寂寞，还以为复现失败。
- GPU 只测 kernel 时间不算拷贝，得出一个没人能复现的 100×。

## 五、面试怎么讲

### 30 秒版本

> 这个项目把“并行能加速”拆成一串可复现的数字：输入是几个固定 workload 加一份配置，输出是带误差棒的加速比表、一条随 N 变化的曲线，以及每个数字的归因——多少来自向量宽度、多少来自核数、多少被带宽或拷贝吃掉。卡点有两个：一是计时本身不可信，线程迁移、turbo、冷热缓存能让抖动到 30%，所以绑核、warmup、取中位数和 IQR 是测量前提而不是优化；二是浮点归约不满足结合律，换求和顺序结果就变，校验和必须带容差。验证口径是：换一台同架构机器，别人拿同样配置能跑出落在误差棒里的数。

### 可能被追问的 8 个点

**1. “你这个 6× 是怎么来的？”**
→ 考点：能不能把加速比拆开，还是只会报总数。
→ 怎么答：先定基线——同一份代码、同一台机器、同一个 N，标量串行版的时间才是分母。然后拆：先用 roofline 判断这个 workload 是算力受限还是带宽受限；算力受限的上界由向量宽度乘核数给出，实测低于上界的差额，去查是尾部没处理、跨了 LLC、还是被拷贝开销吃掉。再往上用 Amdahl 反推串行比例，看还剩多少空间。说完这一项你应该能讲清“基线、上界、差额”三件事怎么对上，而不是只记住一个倍数。

**2. “为什么不直接 `-O3 -march=native` 让编译器向量化？”**
→ 考点：知不知道自动向量化的前提，以及“可归因”的价值。
→ 怎么答：`-fopt-info-vec-optimized` / `-fopt-info-vec-missed` 能告诉你哪个循环向量化了，但决定因素包括编译器版本、循环形态、别名分析——指针可能别名时它会插运行时检查甚至直接放弃，所以要 `restrict` 或 `__builtin_assume_aligned`。手写不是为了更快，是为了报告里能指着一行说这 8 个 float 是一条 `vaddps` 吃掉的。做对照要加 `-fno-tree-vectorize` 关掉自动向量化再比，否则分不清功劳归谁。

**3. “你怎么知道计时是可信的？”**
→ 考点：抖动来源是否清楚，统计口径是不是拍脑袋。
→ 怎么答：先列来源：turbo 与频率、线程在核间迁移带走 cache、NUMA 远端访存、后台负载、冷热缓存。逐个固定：`pthread_setaffinity_np` 绑核，warmup 若干轮丢弃，用 `clock_gettime(CLOCK_MONOTONIC)` 而不是 `gettimeofday`，重复 R 次取中位数和四分位距——最小值是“最好情况”，不是“典型情况”。上并行之前先拿一个纯串行函数测 harness 自身抖动，压到 2% 以内再往下测。

**4. “SIMD 的尾部和对齐怎么处理？”**
→ 考点：边界条件有没有真的想过。
→ 怎么答：分配用 `aligned_alloc` / `posix_memalign` 按 64 字节对齐——不是 32，是为了不跨 cache line 产生 split load，也覆盖更宽的指令。主循环走 `N / 8 * 8`，剩下 `N % 8` 用标量补齐，或者 `maskload` / `maskstore` 配 `_mm256_setr_epi32` 生成的掩码；`loadu` 能用，但不对齐时会有跨行代价。如果 N 是 8 的倍数反而变慢，要去查对齐是不是没落实——这个掉速点解释不了，就说明还没测明白。

**5. “向量化之后结果和标量版对不上，是不是写错了？”**
→ 考点：知不知道浮点加法不满足结合律。
→ 怎么答：改变求和顺序就会改结果，这不是 bug。校验和用相对误差容差，不判等。另外 `_mm256_hadd_ps` 的语义要清楚：它在 128 位 lane 内做横向相加，两个 lane 之间不会自动合并，最后还得手动把高低 128 位加起来。归约树的形状要写进报告，不然别人复现不出同一个数。

**6. “伪共享那个实验，怎么保证测到的真是伪共享？”**
→ 考点：MESI、cache line，以及会不会被编译器骗。
→ 怎么答：对照组和修复组只差一处——`alignas(64)` 或 padding，其余代码完全相同；两个线程各写各的变量，但两个变量落在同一条 64 字节 line 上，写就让对方的副本失效，产生一致性流量。最大的坑是累加变量被编译器提到寄存器，循环里根本没发生内存写，看起来像“复现失败”——要么加 `volatile`，要么每轮强制写回，并且在报告里承认这个现象是被构造出来的、构造条件是什么。

**7. “强扩展和弱扩展为什么是两条曲线？”**
→ 考点：Amdahl 和 Gustafson 是不是真分得清。
→ 怎么答：强扩展是固定 N 加核数，串行部分占比不变，加速比被 Amdahl 卡住上限；弱扩展是固定每核负载加核数，问题规模跟着长，串行占比被摊薄，对应 Gustafson。同一份数据要能同时拟合两条并解释差异：强扩展那条的饱和点对应串行比例，弱扩展那条的斜率对应并行效率。补一句边界：把 N 故意调到全塞进 L1，曲线形状必须按预期变，这是验证你理解缓存层次而不是碰巧测出好数字。

**8. “GPU 那个加速比里，拷贝占多少？”**
→ 考点：会不会拿纯 kernel 时间吹数。
→ 怎么答：计时切四段——分配、H2D、kernel、D2H，用 `cudaEventRecord` 卡在每段边界。端到端加速比和纯 kernel 加速比的差额，要能用拷贝量除以 PCIe 有效带宽算出来对上；N 小的时候 launch 开销可能比 kernel 本身还大。没有 GPU 就降级成读 kernel 代码加用 CPU 侧数据算这笔账，验收降级但不断裂。

### 别说什么

- **别把工具当原理讲。**“我用了 OpenMP 所以并行”“开了 `-O3 -march=native` 所以做了向量化”——这两句必然被追问“那运行时/编译器具体做了什么”，答不上来就露怯。
- **别报没测过的数字。**“大概 10×”“应该有 8 倍”比不说更糟。每个数字都要能立刻补上机器、规模、基线、误差棒四件事。
- **别把跑通当实现对了。** 校验和过了不代表归约顺序对、不代表尾部处理对；掉速点解释不了，就说明只是碰巧跑出了结果。
- **别把功劳混在一起。** SIMD、多核、缓存三个因素同时开然后报一个总数——这恰好是这个项目要避免的事。
