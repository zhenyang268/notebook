## 一、它在做什么

这个项目要写一个共识内核：让一组（通常 3 或 5 台）机器对「接下来执行哪条命令」达成完全一致的意见——即使其中少数机器宕机、重启，或者网络时断时续。

接口很窄。上层服务调用 `Start(cmd)` 提交一条命令：如果当前节点是 leader，拿到这条命令将来在日志里的位置 `(index, term)`；如果不是，拿到 `isLeader=false`，由上层去别处重试。所有节点上有一个 `applyCh` 通道，Raft 把「已被多数派确认、不会再被推翻」的命令，按完全相同的顺序一条条投进去。上层拿到后自己执行（比如写 KV），不需要知道日志、任期、投票这些内部结构。

验收看四个场景：杀掉 leader，一秒内集群自己选出新的；一百个客户端并发写，停下来之后每个节点上的日志前缀完全相同；把少数派网线拔掉再插回来，被隔离期间没提交的日志要被覆盖掉，已提交的一条都不能丢；整组机器同时断电重启，任期不回退、同一任期不投两次票；一个日志被快照压缩过的节点，能把严重落后的新节点追上。

## 二、为什么这样做（功能设计）

**替换掉的是什么。** 现实里没人手写共识——用 etcd/raft 或 hashicorp/raft 的库，几行代码就能起一个复制组。这个项目把那层库整个抽掉自己写，只保留两样给定的东西：一个可注入丢包、延迟、乱序、重复、断网的 RPC 框架，和一个只能整块读写字节的假磁盘。也就是说，「不可靠」的两个来源是给定的，不替换；被换掉的是中间那层「把不可靠通信变成可靠全序」的逻辑。

接口切在状态机边界上，必须守住：上层只能把命令扔进去、从通道里取出已提交的命令，不允许反过来读 Raft 内部的日志做「快速读」——那等于跳过了「多数派确认」这一步，读到的东西随时可能被覆盖。

**它是同进程的库，不是独立服务。** 这个选择决定了后面所有并发写法。因为 Raft 和上层在同一地址空间里、共享一个结构体，所以用互斥锁保护状态、把临界区压短，比「把每个事件变成消息投进一个循环」更省事也更好审计。代价是锁顺序要自己维护：一旦在持锁状态下发 RPC，就会拖住整个节点甚至死锁，而在分布式测试里这表现为随机超时，极难定位。所以「发 RPC 前必须放锁」要在写第一行复制逻辑之前就当成硬规矩。

**不可靠性从哪来、怎么压住。** 四个来源对四个机制：

- RPC 会丢、会重复。→ 每个 handler 写成幂等的：收到 AppendEntries 先比任期，再比 `prevLogIndex/prevLogTerm`，对不上就拒绝让 leader 回退；同一请求收到两次，结果一样。发送端不问「成没成」，只循环重试到成功或发现自己不再是 leader。at-least-once 投递 + 幂等处理，等价于恰好一次。
- 消息会乱序、会迟到。→ 每条 AppendEntries 携带 `(prevLogIndex, prevLogTerm)`，接收方检查自己那个位置是不是真这条日志，不是就拒绝。这一条检查就是「日志匹配性质」的全部实现：它把乱序变成「暂时不接受」，而不是「接受错的」。
- 会网络分区。→ 用任期号当逻辑时钟、用多数派当准入条件。少数派那侧既凑不够票选不出 leader，也凑不够 `matchIndex` 推进不了 `commitIndex`；分区恢复后它带着更高任期回来，旧 leader 被迫退位。
- 会断电重启。→ `currentTerm`、`votedFor`、日志和快照必须在**回复之前**落盘。顺序反过来也能跑通大部分场景，但会在断电点暴露双投票。

**为什么不用更简单的做法。** 单机不复制，那就不需要这个项目。「主同步写全部副本」：一台慢机器卡死整个集群，而且分不清「慢」和「死」，只能靠超时；一引入超时就有脑裂，就必须有任期和多数派，绕一圈还是回到这里。固定超时：同时参选的节点一直撞车，选票分散，可能长期选不出 leader；随机区间 `[T, 2T]` 是把撞车概率压到可接受的最低成本手段。把 `commitIndex` 直接取多数派 `matchIndex` 而不检查任期：更简单，但会允许 leader 提交一条「本任期之前、其实没被多数派确认」的日志，随后它被覆盖，已经返回给客户端的命令就丢了——「只有当前任期的条目能靠多数派直接提交」这条限制就是用来堵这个洞的。

**数据形态。** 日志是追加写数组，每条带 `(term, command)`，下标隐式；快照是对前缀的压缩，压缩后日志不再从 0 开始，所有下标运算都要加偏移。这个偏移是后半程最大的错误来源——凡是出现 index 的地方都要问一句「这是逻辑下标还是物理下标」。

## 三、章节大纲

1. **共识与复制状态机**——为什么单机不够；线性一致性到底在说什么（「看起来像一台机器」）；共识层 / 状态机层 / 分片层三层分解；Raft 承诺的不变量清单。做完能说清「已提交」的确切含义，并能指出一个看似正确的实现违背了哪条不变量。
2. **RPC 与并发骨架**——RPC 会丢会重会乱序的语义；每个 RPC 一个 goroutine；临界区怎么划；定时器与 `select`；持锁发 RPC 的危害。做完能用两节点互相 ping、在注入丢包和延迟下仍收敛，并在竞态检测器下不报警。
3. **Leader 选举**——任期单调递增、一个任期一票、RequestVote 参数、「候选人日志不够新就不投」这条限制、随机化选举超时、心跳。做完能验证：杀 leader 后一秒内选出新的；重复多轮不出现偶发选不出；分区期间两侧不可能在同一任期同时获胜。
4. **日志复制**——AppendEntries 完整参数、`prevLogIndex/prevLogTerm` 检查、`nextIndex` 回退（逐个退还是带任期跳跃）、用 `matchIndex` 中位数推进 `commitIndex`、当前任期限制、`applyCh` 有序投递。做完能验证：并发写收敛到同一份日志；旧 leader 隔离期间攒下的未提交条目被覆盖。
5. **持久化与崩溃恢复**——三个必须落盘的状态、落盘与回复的先后、重启后的重放、快照也要一起持久化。做完能验证：断电重启后任期不回退、不重复投票、已提交命令还在。
6. **快照与日志压缩**——快照里存什么、`lastIncludedIndex/Term` 的语义、下标偏移、InstallSnapshot 的触发条件、装完快照后 `nextIndex` 怎么对齐。做完能验证：日志被压缩后，全新节点仍能从 leader 追上并继续正常复制。
7. **正确性论证与测试方法**——五条安全性质逐条对照实现；故障注入（丢包率、延迟、分区、重启）；为什么分布式测试必须重复跑、一次通过不算通过；竞态检测器与随机种子；线性一致性检查的思路（把历史记录拿出来看能不能排成一个合法全序）。做完能对一个 bug 假设设计出必然暴露它的场景，而不是靠加长超时碰运气。
8. **向上接一层：KV 与分界**——`Start` + `applyCh` 的实际用法；客户端请求号去重表实现「恰好一次」；为什么线性一致读比线性一致写更难（ReadIndex / lease 两条思路）；为什么上层不能反读日志。做完能验证：一个最小 KV 在分区与重启下 get/put 行为符合预期，且上层没有引用 Raft 内部结构。

## 四、不做什么

**课程不要求的**：成员变更（joint consensus，增删节点）、跨分片与分片迁移、多组分片管理、生产级 TLS/鉴权/监控。这些是真实系统必需、但和「理解多数派」无关的部分。

**明确留给上层的**：状态机的业务语义、客户端会话与去重表的具体实现、读请求优化路径、批处理与流水线。Raft 只保证「同样的命令以同样的顺序到达每个 `applyCh`」，别的都不管。

**实现自由度（怎么做都行，只要不变量成立）**：日志序列化格式（gob 还是自己拼二进制）；快照触发策略（按条数、按字节、还是上层说了算）；`nextIndex` 是逐个退还是快速回退；一把大锁还是分段锁；`applyCh` 由独立协程投递还是提交路径直接投。取舍只看一条：能不能让 bug 更容易被发现。

**常见跑偏**：

- 为了「跑通」而调大超时、加 `sleep`。这是把不确定性藏起来，换个种子或多跑几轮就原形毕露。
- 把一次通过当做完。分布式测试的默认状态就是不稳，必须重复跑、开竞态检测。
- 持锁发 RPC。轻则整体卡顿，重则死锁，且表现为随机超时，最难排查。
- 先回复再落盘。多数场景能过，专测断电的那一类会在最难受的地方挂掉。
- `commitIndex` 直接取多数派 `matchIndex` 而不检查任期，导致已提交条目被覆盖。
- 上层图省事直接读日志拿结果，读到未提交数据，整个分层就白设计了。
- 只做完选举就以为懂了，跳过持久化和快照——那只是「能选主」，不是「能存数据」。

## 五、面试怎么讲

### 30 秒版本

> 「这个项目是手写一个 Raft 共识内核，对外只提供两个接口：`Start(cmd)` 提交命令并拿到 `(index, term)`，`applyCh` 按完全相同的顺序吐出已提交的命令。难点不在投票，在不可靠——RPC 会丢、会重、会乱序，机器还会断电。所以每个 handler 必须幂等，AppendEntries 靠 `prevLogIndex/prevLogTerm` 做匹配检查，`currentTerm`、`votedFor` 和日志必须在回复之前落盘。验证靠故障注入而不是等：杀 leader 看能否重选，分区恢复看未提交日志是否被覆盖，断电重启看任期是否回退，再开竞态检测重复跑。」

说完这一段，你应该能自然地接住下一句追问「那你说说为什么」，而不是只能重复结论。

### 可能被追问的 8 个点

**1. 「`commitIndex` 为什么不能直接取多数派的 `matchIndex`？」**
→ 考点：Figure 8 那个场景，以及「当前任期限制」到底在防什么。
→ 答法：新 leader 上任时，多数派上的 `matchIndex` 里可能包含**上一任期**遗留、其实并没被多数派确认的条目。直接按中位数提交，就可能在它随后被真正 leader 覆盖之后，已经返回给客户端的命令凭空消失。规则是：只有 `log[i].term == currentTerm` 的条目才能靠多数派计数直接提交；之前任期的条目只能通过「本任期的某条日志被提交」被间接带过去——实践中新 leader 上任先提交一条空操作（no-op），就是这个用途。

**2. 「`prevLogIndex/prevLogTerm` 这个检查到底解决了什么？」**
→ 考点：Log Matching Property，以及它怎样把乱序和回退变成安全行为。
→ 答法：接收方检查 `prevLogIndex` 位置上那条日志的 term 是否等于 `prevLogTerm`；不等就拒绝。这不是「防重复」，是防**接错位置**——乱序或延迟到达的 AppendEntries 会携带过期的前缀信息，检查不过就丢弃，而不是把日志截断到错误位置。三个边界必须说清：`prevLogIndex < snapshotLastIncludedIndex` 时不能直接判失败（那段已被压缩，应视为匹配或触发 InstallSnapshot）；`prevLogIndex > len(log)` 要拒绝；拒绝时返回 `(ConflictTerm, FirstIndexOfConflictTerm)` 而不是裸 false，leader 才能做跳跃回退而不是一条条退。

**3. 「`nextIndex` 回退为什么可以一次跳一个任期？」**
→ 考点：这个优化依赖哪条不变式，什么时候不成立。
→ 答法：依赖「同一 term 内、同一 index 上的日志条目一定相同」——这条由选举限制（候选人日志必须不落后于投票者）保证。所以 leader 收到 `ConflictTerm` 后：若自己有这个 term 的日志，就跳到该 term 最后一条之后；若没有，直接跳到 `FirstIndexOfConflictTerm`。如果实现里允许同 term 同 index 出现不同条目，这个跳跃就是错的——所以它不是纯优化，是拿安全性质换的。

**4. 「持久化要存什么、什么时候存？」**
→ 考点：崩溃点的顺序，不是「存了就行」。
→ 答法：三个字段——`currentTerm`、`votedFor`、日志（含快照的 `lastIncludedIndex/lastIncludedTerm` 和快照数据）。关键在**回复之前**落盘：RequestVote 的回复、AppendEntries 的回复，都得先 `Save` 再返回。反过来能跑通绝大多数测试，但会在「投完票、还没落盘就断电」这个点上暴露同一任期投两票，可能选出两个 leader。实现上通常把三者在同一个临界区里编码成一整块字节交给 `Save`，注意日志和快照的写必须原子，不能出现「快照更新了、日志还按老偏移算」的中间态。

**5. 「持锁发 RPC 会怎么样？」**
→ 考点：分布式测试里最难定位的那类 bug。
→ 答法：RPC 超时是几百毫秒级的，持锁期间这个节点收不了心跳、也回不了投票，别人在选主，你还卡在锁里；更糟的是 handler 里再取同一把锁，直接成环死锁。规矩固定成三步：持锁复制出参数 → 放锁发 RPC → 重新取锁。回来之后**必须重新校验** `state == Leader && term == currentTerm`，否则这份回复属于一个已经过期的自己，拿去更新 `matchIndex` 就是错的。这个「回来后重查身份」是最容易漏的一步。

**6. 「`applyCh` 怎么保证有序、不重、不阻塞 Raft？」**
→ 考点：提交路径与投递路径的耦合。
→ 答法：`lastApplied` 单调递增，只投 `lastApplied+1`，投完才加一——这样天然去重、天然有序（重投同一 index 会被跳过）。不能持锁往 `applyCh` 发：上层可能在 apply 的 handler 里回调 Raft，一持锁就死锁；常见做法是单独一个 goroutine 配合条件变量等 `lastApplied < commitIndex`。还有一个交互点：装完快照后 `lastApplied` 要直接跳到 `lastIncludedIndex`，否则会把已经被压缩掉的条目再投一遍。

**7. 「快照之后下标怎么算？」**
→ 考点：逻辑下标 vs 物理下标，后半程最大的错误来源。
→ 答法：压缩后日志不再从 0 开始，数组下标 `i` 对应的逻辑 index 是 `i + lastIncludedIndex`（或 +1，取决于数组第 0 位是不是哨兵）。凡是出现 index 的地方都要问一句「这是逻辑的还是数组的」，尤其是 `commitIndex`、`matchIndex`、`nextIndex`、`prevLogIndex` 四者混算的地方，以及 InstallSnapshot 的 RPC 分块偏移——分块偏移是**快照字节流的偏移**，跟日志 index 完全无关，混淆了就会在大快照上挂。

**8. 「你怎么知道它是对的？」**
→ 考点：测试方法论，也是最容易露怯的一题。
→ 答法：先说「一次通过不算通过」。做法是：给定故障注入（丢包率、延迟分布、分区、随机重启）跑随机化场景，重复很多轮且带 `-race`，种子固定可复现，挂了能回去重放。判据不是「没报错」，而是几条可检查的不变量：所有节点 apply 出的命令序列互为前缀；已提交的条目在任何节点任何时刻都不消失；任期单调不回退；同一任期不出现两个 leader。更进一步是把历史记录拿出来看能不能排成一个合法全序——即线性一致性检查的思路。如果做到这一步，可以这样答：「我没法说它一定对，我能说的是这几个不变量在 N 轮随机故障下没被打破，而且每个曾经挂掉的种子都留着。」

### 别说什么

- **别说「我全部实现了、测试全绿」。** 一句「最难的那个 bug 你是怎么定位的」就能验证真假；答不出具体现场（哪个种子、哪个不变量先破、日志长什么样），前面全白说。
- **别把库当原理讲。** 「用了 etcd/raft 所以……」在这里是反向信号——这个项目考的正是那层库被抽掉之后你还剩什么，讲 `prevLogTerm` 检查、讲落盘顺序，比讲 API 有用。
- **别报没测过的数字。** 「一秒内一定选出 leader」「性能提升 3 倍」都是坑。要谈效果就谈口径：「选举超时设在 150–300ms、心跳远小于它，在这个前提下杀 leader 后重选应该在选举超时量级内完成」——说条件，不说结论。
- **别说「加个 sleep / 调大超时就好了」。** 这句话等于承认把不确定性藏起来了；同理，「跑了一遍没报错」不是正确性证据，是正确的缺席。
