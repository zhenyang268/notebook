## 一、这个目录是什么

| 子项目 | 回答什么 | 判据 |
|---|---|---|
| `rasterizer/` | 一个像素的颜色从哪来：变换、光栅化、着色、纹理、阴影，整条流水线自己写一遍 | 渲染正确性——单个三角形能正确落屏，带纹理与阴影的场景能出图，中间结果与手推一致 |
| `raytrace/` | 同一场景的第二条路径：用求交与射线回答“这个点可不可见” | 交叉验证——两条路径在共同能力（硬阴影、反射）上互相印证，且能说清各自代价 |
| `geometry-anim/` | 连续的量怎么变成离散的帧：曲线、细分、插值、蒙皮、粒子 | 可手算——低阶曲线代一组控制点能在纸上算出坐标，插值端点与切线可验 |
| `engine/` | 渲染器之外那一层工程：主循环、场景图（scene graph）、提交（submission）、资源、世界查询、脚本 | 帧预算（frame budget）——一帧的时间花在哪能报出账，子系统边界不被上层穿透 |
| `game/` | 拿流星蝴蝶剑当案例：关卡、手感、战斗判定、摄像机，一路做到联网与上线检查 | 手感与联网——输入到表现的延迟可感可控，同步选型有立场也有代价 |

一句话走向：从“一个像素怎么被算出来”，到“两个人怎么在同一帧里对上”，中间靠**同一份场景数据换不同路径反复验**来衔接——光栅化与光追互证，几何与动画供顶点，引擎把顶点按预算组织成帧，游戏把这帧交给真人的按键。

**入口（本文的读法）**：在固定 `Scene`、`Camera`、`FrameId`、输入事件时间戳与一帧预算的约束下，解决同一场景从顶点到像素、从射线到可见性、从控制点到蒙皮顶点、从命令提交到网络状态包的一致性问题。换的是从 `rasterizer/` 的顶点属性寄存器、深度缓冲、纹理采样指令，到 `raytrace/` 的 `BVH` 节点、`Ray` 结构、射线-三角形求交函数，到 `geometry-anim/` 的样条控制点、四元数插值、蒙皮权重，到 `engine/` 的场景图节点、命令缓冲、`clock_gettime` 帧预算，到 `game/` 的输入采样、`epoll_wait`、`sendto`、`Packet` 序号与状态字段的实现路径。

**不换的是什么**：全程不变的是同一份 `Scene` 的 `Mesh` 顶点/索引缓冲、`Material` 纹理句柄、`Transform`/`Camera` 矩阵、`FrameId` 与输入事件时间戳，以及作为判据的 `Framebuffer` 像素、`DepthBuffer` 值、`CommandBuffer` 提交记录和 `Packet` 序号/状态字段；所以看到差异该先问是哪一数据结构、哪条指令或系统调用、哪一协议字段被改。

## 二、为什么这样分组（功能设计）

**渲染正确性与交叉验证先分开，再汇合。** `rasterizer/` 与 `raytrace/` 各自独立成篇，是因为验收方式不同：光栅化（rasterization）的判据是“逐像素能不能复现手推的变换与插值”，错了可以二分定位到某一段；光线追踪（ray tracing）的判据更像对照实验——“同一个场景，两条路径给出同一结论”。并成一个大文件，“我到底是在验管线还是在验求交”就说不清了。这两项也不并进 `cpu/`：那边关心指令、缓存、并发这类与画面无关的量，这里只关心结果对不对。

**几何与动画单独一层，因为它的尺子是“可手算”。** 贝塞尔（Bézier）与 B 样条（B-spline）、曲面细分（tessellation）、关键帧插值（keyframe interpolation）、骨骼蒙皮（skeletal skinning）、粒子积分，共同点是低维、连续、能在纸上验算。这跟“出图对比”“帧预算”都不是一回事，所以不塞进 `engine/` 当一章；但它是引擎的输入——顶点从哪来，正是这一层回答的。

**引擎单列，因为它把尺子从“对不对”换成“花多少”。** 主循环、场景图、提交、资源、世界查询、脚本，验收方式是帧预算——剔除、提交、更新各占多少能说清，换一个场景不必改引擎代码。它与 `eng/` 的分工是：那边是通用工程素养（构建、测试、抽象成本、分层），这里是把这些素养压到一个每帧必须出结果的约束上；通用部分讲一次就够，不在这里重讲。

**游戏放最后且不并进引擎，因为它的判据是主观且对抗的。** 手感（game feel）、战斗判定、摄像机、联网，验收靠“按键到画面变化这段延迟能不能感觉出来”和“两个人同时按，结果一致不一致”，这跟帧预算不是同一把尺子。整条链拆成五份而不是一份，根本原因就是**判据不同**：渲染正确性、交叉验证、可手算、帧预算、手感与联网——五把尺子量五个东西，混在一起就没法回答“这一段到底过了没有”。

## 三、推荐顺序与判据

| 阶段 | 内容 | 判据 | 成本 |
|---|---|---|---|
| P1 出图 | `rasterizer/` 主线：变换→光栅化→着色→纹理→阴影 | 单个三角形正确落屏；一个带纹理与阴影的场景能出图，关键中间量与手推一致 | 中，主要花在调试与定位 |
| P2 交叉验证 | `raytrace/` 求交、阴影射线、递归、包围盒层次结构（BVH）、选型判据 | 同一场景两条路径在共同能力上结论一致；能说清“什么时候才该考虑路径追踪” | 中高，BVH 是主要成本 |
| P3 连续量 | `geometry-anim/` 曲线、细分、插值、蒙皮、粒子积分 | 低阶曲线可纸算出点；插值端点与切线可验；积分步长变化时行为可解释 | 低到中，以数学为主 |
| P4 成帧 | `engine/` 主循环、场景图、提交、资源、世界查询、动画、脚本 | 一帧的时间分布能报账；加一个场景或换一份资源不动引擎核心 | 高 |
| P5 上手与联机 | `game/` 关卡、手感、判定、摄像机、同步、上线检查 | 输入到表现的延迟可感可控；同步选型给得出立场与代价；断线重连有路径 | 最高 |

**硬判据**：随便挑一个现象，能做到“指到链上某一层说这是谁的责任”，这一段就算过关——画面错了能定位到变换、光栅化、着色、纹理中的一段；卡了能定位到剔除、提交还是更新；对局不同步能定位到确定性（determinism）还是网络。做不到这一点，就说明还停在“能跑”，不叫走通。

## 四、不做什么 · 必要性 · 失效点

### 必要性：删掉会怎样

| 机制 | 删掉会怎样 | 判定 |
|---|---|---|
| `变换` | 删掉 MVP 矩阵与视口映射后，顶点停在世界坐标，裁剪空间到屏幕坐标的链路断裂；`rasterizer/` 的“单个三角形能正确落屏”承诺破，手推 `x/y/w` 无法对齐 | 必需 |
| `光栅化` | 删掉三角形边函数、重心插值和深度测试后，像素没有颜色来源；`纹理` UV 采样与阴影 `z-buffer` 比较没有输入，渲染正确性无法复现 | 必需 |
| `求交` | 删掉射线-三角形求交与命中 `t` 值选择后，`raytrace/` 不能回答“这个点可不可见”；硬阴影、反射没有第二路径，交叉验证不成立 | 必需 |
| `关键帧插值` | 删掉时间轴采样与切线求值后，骨骼蒙皮没有每帧姿态矩阵，粒子积分没有初位置/初速度；`geometry-anim/` 的“插值端点与切线可验”承诺破 | 必需 |
| `场景图` | 删掉父子变换矩阵与资源引用后，`提交` 阶段不能把模型、纹理、灯光按层级组织；`engine/` 帧预算无法拆分剔除、提交、更新各段计时 | 必需 |
| `脚本` | 删掉脚本回调与关卡状态机后，战斗判定参数、摄像机目标、联网事件只能编译进二进制；但 `rasterizer/`、`raytrace/`、`engine/` 仍可出图与记账 | 选择 |

### 失效点：哪条前提一破，结论就变

- CPU 核数 = 1 且 `raytrace/` 求交线程池关闭 → 射线求交占满 `主循环`，帧预算账本中剔除、提交、更新不可分，实时交叉验证退化为离线比对。
- 纹理介质为远程 HTTP 1.1 且无 `mmap`/本地缓存 → `资源` 加载进入 `提交` 阶段，`纹理` 采样首帧缺图，渲染正确性只能验缺省色，不能验手推 UV。
- 网络协议版本为 UDP 且无序列号/重传字段 → `同步选型` 无法保证两客户端对同一 `战斗判定` 输入序列得到一致结果，`输入到表现延迟` 变成丢包依赖。
- 时钟源从 `CLOCK_MONOTONIC`/垂直同步切到墙钟 → `关键帧插值` 的 `dt` 可跳变或倒退，骨骼蒙皮姿态不连续，`主循环` 帧预算归因失效。
- 权限位禁止 `mmap` 资源文件（`mmap` 返回 `EACCES`） → `资源` 只能用 `read()` 拷贝进堆，`提交` 阶段出现每帧/首帧分配与 `memcpy` 计时，`engine/` 帧预算账本无法把资源加载归入可关闭的预加载步骤。

### 不做什么（范围）

- **不复述子项目正文。** 这里只回答“为什么放在一起”“按什么顺序走”，具体章节、公式、代码在各子项目的 `OUTLINE.md` 里，本文件不搬运、不摘抄。
- **不越界进别组地盘。** 不在这里讲编译器、内存模型、语言特性、构建与测试基建——那是 `cpu/`、`langs/`、`eng/` 的事，需要时只写一句“此处依赖某能力”。
- **不追平台与工具细节。** 不展开图形 API 的厂商差异，不写“某个商业引擎怎么调参”，目标是把每一段在做什么弄清楚，而不是会用某个软件。
- **不追画质前沿。** 不追实时全局光照、不追影视级离线渲染；够用来做判据就停。
- **不做完成度声明。** 五个子项目是五条待走的路径，不是五份成果清单，任何时候都可以从任意一段重新进入。

## 五、面试怎么讲

> 我从“一个像素怎么来的”开始：先手写一个 CPU 离线光栅化渲染器，把变换、光栅化、着色、纹理、阴影走通；再用光线追踪做第二条路径，同一个场景用求交和阴影射线验一遍，目的是知道两条路各自的代价。然后往两头长：往下是几何与动画——曲线、细分、插值、蒙皮、粒子，这部分我能手算；往上是引擎——主循环、场景图、提交、资源，学会按帧预算算账。最后拿流星蝴蝶剑做案例，一路做到手感和联网同步。到这里，一条链就从像素走到了两个人对打。

1. **“渲染器都写了，为什么还要再写一个光追？”** 考点是代价模型，不是炫技。答法：说分工——光栅化是为三角形定制的流水线，胜在吞吐；光追胜在任意射线的表达力，阴影与反射不必绕路。主动给边界：能说出“什么时候不该上路径追踪”，比说“它更真实”值钱。
2. **“曲线和蒙皮跟渲染器有什么关系？”** 考点是能不能把离散与连续接上。答法：渲染器吃顶点，顶点从哪来是几何与动画的事；蒙皮本质是每帧对顶点做一次加权变换，代价直接记在帧预算上。
3. **“你的引擎和渲染器怎么分层？”** 考点是边界意识。答法：渲染器只回答“给我一批提交，我还你一张图”；引擎回答“这一帧该提交什么、资源什么时候进什么时候出”。讲一条边界被穿透的反例，比讲分层图可信。
4. **“手感和帧率是什么关系？”** 考点是能不能把主观体验拆成可测的量。答法：拆成输入采样、逻辑更新、动画混合、提交、显示几段延迟，说清哪几段是自己能控的。
5. **“联网为什么选帧同步（lockstep）或者状态同步（state synchronization）？”** 考点是选型有没有立场。答法：给四维权衡——带宽、成本、外挂、手感，落到一个具体场景的取舍上；再补确定性（determinism）的雷在哪、客户端预测（client-side prediction）与回滚（rollback）各解决什么问题。不要背对比表。

**别说什么**

- 别说“五个都做完了”。这条链的价值在路径和判据，不在完成度；被追问细节时答不上来，比直接说没做完更伤。
- 别说“光追更真实所以更好”。没有代价模型的比较，在图形岗是减分项。
- 别说“帧同步就是发指令”。省掉确定性与预测回滚，等于承认只看了科普。
