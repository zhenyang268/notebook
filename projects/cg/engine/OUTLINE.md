## 一、它在做什么

输入是三样：一份数据驱动的场景描述（实体、组件、变换层级、资产清单），一段带时间戳的可回放输入事件序列，一个可注入的时间源（真实时钟，或提前录制的帧间隔序列）。输出也是三样：每帧的渲染提交列表（render submission list，含批次键、排序后的绘制项、状态切换点），世界查询（world query）的结果（附近实体、射线命中、重叠对），以及逐帧状态日志（逻辑帧号、各子系统计时区间、状态哈希）。

验收不看什么、只看什么：

- 不看画面像不像游戏，只看确定性（determinism）：同一份场景、同一段输入、同一个时间源回放三次，导出的状态哈希序列逐帧相同。
- 不看帧率高低，只看归因是否闭合：日志里各子系统计时区间之和与帧总时长之差落在采样精度内，且每个子系统都有独立区间。
- 不看绘制调用（draw call）数量，只看提交列表与可见集（visible set）的差集为空：多一项少一项都能定位到具体实体。
- 不看加载快慢，只看生命周期是否闭合：引用计数归零的资产在下一个帧边界后从内存统计里消失，旧句柄（handle）被判为失效。
- 不看动画顺不顺，只看解耦：人为改动渲染帧率，逻辑帧序列与动画采样时间序列保持不变。

每条都能被别人用同一份数据重跑复现。

**入口（本文的读法）**：本文把 engine 读成一份 scene descriptor（entity/component/transform hierarchy/asset manifest）、一段 timestamped event log、一个 injectable clock source（real clock 或 recorded frame interval sequence）到 render submission list（batch key、sorted draw items、state change point）、world query result（nearby entities、ray hits、overlap pairs）、frame state log（logical frame id、subsystem timing intervals、state hash）的确定性回放状态机；任何章节都按“输入字段—logical frame boundary—输出集合/计数器/哈希”归位。换的只是执行载体：Vulkan command buffer、Metal render encoder、D3D12 root signature、thread pool、mmap/IO asset loader、GPU timestamp query、epoll_wait/IOCP 调度，只要 scene descriptor、event log、clock source、logical frame boundary、state hash 不变。

**不换的是什么**：全程不换的是 scene descriptor 的 entity/component/transform hierarchy/asset manifest、event log 的 timestamp→logical frame 映射、clock source 的 frame interval sequence、state hash 的逐帧序列、handle/reference count 的帧边界失效规则、render submission list 与 visible set 的差集、subsystem timing intervals 对 frame duration 的闭合误差；看到差异先问这些字段、计数器、集合、区间哪一项先分叉。

## 二、为什么这样做（功能设计）

**把可变步长逻辑换成「固定步长逻辑 + 可变步长渲染 + 追帧上限」，是这一节最核心的替换。** 现成教程把时间语义替你隐式处理掉了：你在一个 update 函数里写代码，从不追问 $\Delta t$ 从哪来、抖动多少、逻辑帧率是否恒定。换掉后必须自己定：逻辑步长 $\Delta t_{\text{fixed}}$、累加器 $a \leftarrow a+\Delta t_{\text{real}}$ 与取帧数 $n=\lfloor a/\Delta t_{\text{fixed}}\rfloor$、单帧最多追 $n_{\max}$ 帧、追不上时丢弃还是拉长、渲染侧要不要插值。代价是多一帧延迟和多一套插值代码；可接受，因为确定性与可回放是后面所有验收的前提，而单机场景里一帧延迟难以感知。

**把「渲染器直接遍历场景对象」换成「场景导出提交列表、渲染器只消费」，是第二个替换。** 现成做法把「谁决定可见性」隐式绑死在渲染器内部，剔除、排序、材质切换三件事搅在一起，没有 GPU 就没法测。换掉后要自己定：提交项的排序键与批次键、不透明与透明的两段排序方向、材质与网格句柄的生命周期、空批次是否保留。代价是多一次数据搬运。可接受，因为排序与批次变成纯数据运算，可以离线比对，换渲染后端时场景侧不动。

**把「裸指针持有资产」换成「世代句柄（generation handle）+ 引用计数（reference counting）+ 帧边界延迟卸载」，是第三个替换。** 现成容器替你把「对象还在不在」隐式处理成一次解引用，野指针只在崩溃时才暴露。换掉后要自己定：句柄里世代号的位宽与回绕策略、卸载只发生在帧边界、热重载（hot reload）是「换句柄」而非「原地改内容」。代价是一层间接寻址和一张句柄表。可接受，因为悬垂引用从「偶发崩溃」变成「一次可断言的失效判定」。

**把「动画时钟跟渲染帧走」换成「动画消费独立时钟并单独提取根运动（root motion）」，是第四个替换。** 现成示例把动画更新塞在绘制之前，于是动画速度随帧率漂移、根位移与碰撞位置打架。换掉后要自己定：动画采样时间由谁推进、混合权重如何归一化、根位移提取出来后由逻辑侧还是表现侧应用。代价是多一条数据流。可接受，因为它是「动画与逻辑解耦」这条验收的唯一实现路径。

**把「世界查询返回实体指针集合」换成「返回句柄 + 显式时间语义」，是第五个替换。** 现成接口把「结果是快照还是实时视图」「边界含不含接触」隐式留给你猜。换掉后要自己定：宽相（broad phase）与窄相（narrow phase）的分界、包围盒的更新时机、结果是否稳定排序。代价是查询多一层封装。可接受，因为语义定死之后，实现可以从暴力遍历换成空间划分（spatial partitioning）而不改调用方。

**为什么不用更简单的做法。** 「每帧两两判交」小规模看不出问题，但查询接口一旦被上层依赖，换空间划分要改所有调用点；「一个巨型 update 函数串起所有子系统」写起来最快，代价是帧慢了你只能猜，而验收要求每个子系统有独立计时区间；「全局单例拿资源」省掉传参，代价是生命周期不可观测，卸载与热重载无法验证；「用浮点累积时间当逻辑时钟」省掉整套固定步长机制，代价是同一段输入在不同帧率下结果不同，确定性与回放直接失效；「先把渲染做漂亮再说」不是简化，是把引擎做回渲染器。

## 三、章节大纲

**第 1 章 主循环与时间。** 把主循环写成可注入时间源的结构：逻辑累加器、固定步长、渲染插值、追帧上限、卡顿归因。关键知识点：固定与可变步长的分工、累加器余数、死亡螺旋的成因与上限。验证：喂一段含一次长卡顿的帧间隔序列，日志显示逻辑帧数按固定步长推进，追帧次数触顶后记为丢弃而非继续补偿。

**第 2 章 场景图与变换层级。** 父子变换、局部与世界矩阵、脏标记（dirty flag）传播与更新顺序。关键：世界矩阵必须按拓扑序先父后子单次遍历，脏标记只在局部变换变化时置位。验证：改一个中间节点的局部变换，只有它的子树世界矩阵哈希变化，其余节点不变。

**第 3 章 渲染提交。** 从场景导出可见项，生成批次键，不透明前到后、透明后到前，统计状态切换成本。关键：提交列表是数据结构而非调用序列、排序的稳定性、状态切换次数作为可观测量。验证：同一场景换两种排序策略，批次序列与状态切换计数可对比，且提交项集合与可见集差集为空。

**第 4 章 资源与资产管线。** 资产格式、异步加载、引用计数、世代句柄、热重载。关键：加载与上传分离、卸载只在帧边界、热重载替换句柄而非内容。验证：加载、释放、再取同一句柄返回失效；热重载后旧句柄失效、新句柄可用、内存统计里旧条目消失。

**第 5 章 输入与相机。** 输入采样成意图，死区（dead zone）与归一化，相机跟随的阻尼与延迟。关键：输入分「采样」与「映射」两层、相机更新归属哪个时钟。验证：同一段轴值序列在两种渲染帧率下产生相同的意图序列；相机跟随对阶跃输入的响应曲线可重跑复现。

**第 6 章 世界查询与碰撞。** 空间划分结构、宽相与窄相、查询接口的时间语义。关键：宽相只做包围盒、窄相才做精确相交、边界开闭与结果排序要写进接口说明。验证：随机撒点查询与暴力遍历结果集合一致（顺序可不同，排序后相同）。

**第 7 章 动画子系统。** 动画与逻辑解耦、独立时钟、混合、根运动提取。关键：采样消费游戏时钟、根位移交给逻辑侧应用、混合权重归一化。验证：改动渲染帧率时动画采样时间序列不变；带根运动的位移增量与提取出的根位移一致（口径：两者差值）。

**第 8 章 脚本与音频层。** 脚本边界（能碰什么、不能碰什么）、事件总线（event bus）、音频延迟与混音。关键：脚本经句柄与命令缓冲访问引擎、总线区分同帧投递与下一帧投递、触发到发声的延迟单独计时。验证：脚本在逻辑帧内多次修改同一属性，帧末统一应用一次，日志里命令数与实际应用数可对账。

**第 9 章 引擎设计理念五条。** 数据与逻辑分离、可观察性、确定性、可扩展、可测试，每条配一个「违反了会怎样」的具体症状。验证：五条各对应一条可执行检查，例如确定性对应状态哈希重放一致，可观察性对应每个子系统都有独立计时区间。

**第 10 章 性能预算与剖析。** CPU 帧预算拆分、GPU 提交侧、火焰图（flame graph）与指标口径（用什么测、量级大概多少、误差从哪来）。关键：预算是分给子系统的而非一个总数、计时区间要能嵌套、火焰图看宽度分布而不看峰值。验证：单帧导出的时间线里子系统区间之和与帧总时长在采样精度内闭合，每个区间能追到一条代码路径。

## 四、不做什么 · 必要性 · 失效点

### 必要性：删掉会怎样

| 机制 | 删掉会怎样 | 判定 |
|---|---|---|
| 固定步长逻辑 | 删掉后 `Δt_real` 直接驱动 `update`，逻辑帧号与输入时间戳不再一一对应，同一场景、同一段输入、同一时间源回放三次时状态哈希序列分叉；必需 | 必需 |
| 累加器 `a` 与追帧上限 `n_max` | 删掉后无法把可变步长输入切成固定步长逻辑帧，`n = floor(a / Δt_fixed)` 无界时单帧事件处理顺序与状态哈希写入顺序不稳定；必需 | 必需 |
| 提交列表（render submission list）与批次键 / 排序键 | 删掉后渲染器直接遍历场景对象，可见集（visible set）与提交项差集无法离线比对，状态切换点和绘制项顺序不能定位到具体实体；必需 | 必需 |
| 世代句柄（generation handle）与帧边界延迟卸载 | 删掉后裸指针持有资产，引用计数归零的资产可被旧句柄（handle）继续访问，生命周期验收从“可断言失效”变成 use-after-free；必需 | 必需 |
| 动画独立时钟与根运动（root motion）提取 | 删掉后动画采样时间跟渲染帧走，人为改动渲染帧率时动画采样时间序列变化，逻辑帧序列与动画解耦验收失败；必需 | 必需 |
| 插值代码 | 删掉后渲染帧率变化时实体 transform 只取最近逻辑帧，画面位置跳变，但逻辑帧序列、动画采样时间序列与状态哈希仍不变；选择 | 选择 |

### 失效点：哪条前提一破，结论就变

- 时间源只提供真实系统时钟、不提供提前录制的帧间隔序列 → 累加器 `a` 的 `Δt_real` 抖动，`n = floor(a / Δt_fixed)` 在三次回放中产生不同逻辑帧号，状态哈希序列不再逐帧相同。
- 帧边界延迟卸载被改成引用计数归零即时卸载 → 提交列表里的旧句柄（handle）指向已释放网格 / 材质，生命周期验收从“可断言失效”变成 use-after-free。
- 动画采样时间由渲染帧号推进 → 人为改动渲染帧率时动画采样时间序列变化，逻辑帧序列与动画解耦验收失败。
- 世界查询返回实体指针集合而非句柄 + 显式时间语义 → 宽相（broad phase）/ 窄相（narrow phase）从暴力遍历换成空间划分（spatial partitioning）时，调用方依赖指针稳定性，重叠对顺序不稳定，可见集差集不能定位到具体实体。
- 提交列表不导出批次键与排序键 → 渲染器直接遍历场景对象，状态切换点、绘制项顺序与可见集（visible set）差集无法离线比对，换渲染后端时场景侧必须改动。

### 不做什么（范围）

边界：不做网络同步（固定步长只留出接口，不做回滚与预测）；不做完整刚体求解器（只做查询与简单响应，约束求解是另一条线）；不做编辑器与工具 UI；不重写图形 API 封装与着色器编译（沿用已有渲染器）；不做音频 DSP 与混音器实现，只定触发与延迟口径；不做资产导出器，只定资产格式。理由一致：这些要么依赖另一条线的深度，要么会把面试叙事从「结构怎么组织」拉成「某个子系统的实现细节」。

常见跑偏清单：

- 把「引擎」做成渲染器改个名，其他子系统只有空壳。
- 主循环还没定稿就上实体组件系统（ECS, Entity-Component-System）全家桶，先设计原型表再回头补时间语义。
- 用渲染帧间隔直接缩放所有逻辑，掉帧时角色穿墙，再回头加固定步长。
- 追帧不设上限，卡一次之后连续追几十帧，越追越卡。
- 热重载时原地替换资产内容，正在被引用的对象变成半新半旧。
- 把相机与动画更新塞进渲染函数，理由是「它们看起来是画面的事」。
- 用「我觉得手感对了」验收相机跟随，无法被别人复现。

## 五、面试怎么讲

**30 秒版本（开场照着说）**

> 这条线是从渲染器往上长一个引擎：主循环怎么把时间切成固定逻辑帧和可变渲染帧，场景图怎么管变换层级和脏标记，可见项怎么变成一份可排序、可离线验证的提交列表，资源怎么用世代句柄和引用计数管生命周期，再往上叠世界查询、动画、脚本和音频。我的重点是每个决策都能被复现地验收——状态哈希重放一致、提交列表与可见集差集为空、子系统耗时能闭合到帧总时长。

**可能被追问的 6–8 个点**

1. 问法：「为什么逻辑一定要固定步长？」真实考点：确定性与可回放，不是性能。怎么答：固定步长让相同输入序列产生相同状态序列，物理、动画、脚本才有可复现的基准；变步长下同一段输入在不同帧率下结果不同，回归比对就失效。渲染侧用插值补平滑。
2. 问法：「固定步长会不会让手感变钝？」真实考点：延迟预算的量化。怎么答：延迟来自累加器余数、追帧上限、是否插值三者的组合，说清口径和量级，不用「感觉」。
3. 问法：「提交列表和直接发绘制调用差在哪？」真实考点：解耦与可测性。怎么答：提交列表是纯数据，没有 GPU 也能测排序与批次；渲染器只消费，换后端时场景侧不动。
4. 问法：「脏标记会不会漏更新？」真实考点：更新顺序。怎么答：按拓扑序先父后子单次遍历，置位沿子树传播；验证方式是改中间节点后比对全量世界矩阵哈希。
5. 问法：「引用计数遇到循环引用怎么办？」真实考点：所有权图是否清晰。怎么答：句柄带世代号防悬垂，循环引用靠所有权约定（父子不强互持）而不是靠计数器兜底。
6. 问法：「世界查询到底返回什么？」真实考点：语义而非实现。怎么答：返回句柄，明确是快照还是实时视图、边界开闭、结果是否稳定排序；语义定死之后实现可以换。
7. 问法：「动画为什么要单独时钟？」真实考点：解耦与根运动归属。怎么答：动画采样频率与渲染帧率、逻辑帧率都不同；根位移必须提取出来交给逻辑，否则碰撞用表现位置会抖。
8. 问法：「你怎么证明这套东西是对的？」真实考点：可观察性设计。怎么答：状态哈希重放、提交列表与可见集差集、子系统耗时闭合，三条都能被别人用同一份数据重跑。

**别说什么**

- 「就是照着某个商业引擎的架构抄的」——暴露没有自己的取舍。
- 「我这边帧率很稳」——没有实测就给结论，一追问测量口径就露怯，改说「用什么测、量级大概多少」。
- 「用了 ECS 所以性能好」——ECS 是组织方式，不是性能证据。
- 「这个很简单，就是把几个 update 串起来」——一句话否掉了前面所有设计取舍。
