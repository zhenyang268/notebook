# security · 分章详细

> 十章，每章四段：**要解决的问题 / 机制 / 最小例子 / 面试高频问法**。
> **内容边界**：只讲机制、原语与判据；不给 shellcode、不给具体偏移与 payload、不针对任何商业游戏或反作弊产品给绕过步骤。实验限定在自己写的示例程序或公开 CTF 环境。

## 第 1 章 攻击面地图与权限边界

**要解决的问题**：安全讨论最容易变成名词堆。先把"边界"画出来，才知道一个具体问题到底跨了哪一条线，以及靠的是硬件还是软件。

**机制**：三层边界，强制手段不同。

| 边界 | 靠什么强制 | 典型越界方式 | 一旦越过的后果 |
|---|---|---|---|
| 进程 ↔ 进程 | 页表（硬件） | 内核里少做一次地址校验；共享内存权限错 | 读/写别的进程内存 |
| 用户态 ↔ 内核态 | 特权级（硬件）+ 入口处的软件检查 | 系统调用参数未校验、内核 UAF | ring3 拿到 ring0 能力 |
| 内核 ↔ 硬件 | IOMMU（若存在）/ 设备寄存器访问 | 设备 DMA 未被隔离 | 设备可读写任意物理内存 |

**关键区分**：**硬件强制**的边界（页表、特权级）写错一次就是"能被绕过"；**软件检查**的边界（`access_ok`、`copy_from_user`、长度校验）写错一次就是漏洞。前者是设计问题，后者是实现问题——绝大多数 CVE 属于后者。

**最小例子**：一个 `ioctl` 处理函数直接 `memcpy(kbuf, (void __user *)arg, len)`，没有 `access_ok` 也没有 `copy_from_user`。用户传一个内核地址进去，内核就替它读了内核内存——**这不是"溢出"，是"少了一次检查"**。判据：能指出这行代码缺的是哪一类检查。

**面试高频问法**：

1. **「用户态指针为什么不能直接解引用？」** → 考点：边界与并发。答法：可能非法、可能跨页、可能指向内核；而且用户在检查之后还能改页表。所以要走 `copy_from_user`（内部 `access_ok` + 异常表恢复），缺页时返回未拷贝字节数而不是崩内核。
2. **「SMAP 存在为什么还要 `copy_from_user`？」** → 考点：两者管的事不同。答法：SMAP 阻止内核**意外**访问用户页，但合法访问仍需要走允许的路径（`stac/clac` 之间）；`copy_from_user` 负责合法性检查与失败恢复，二者互补。
3. **「DMA 为什么是安全边界问题？」** → 考点：绕过 MMU。答法：设备用物理地址直接读写内存，若不配 IOMMU，一个被攻陷的设备（或恶意的假设备）可以读写任意物理页——CPU 侧的页表保护对它无效。

## 第 2 章 内存破坏的四种形态

**要解决的问题**：所有内存破坏最终都要回答两个问题——**破坏了谁的元数据**、**拿到了什么原语**。按形态分只是入口不同。

**机制**：

| 形态 | 破坏什么 | 成立条件 | 现代缓解 |
|---|---|---|---|
| 栈溢出 | 保存的 `rbp`、返回地址、相邻局部变量 | 长度可控 + 无 canary 或 canary 被绕过 | canary、`-fstack-protector`、CET 影子栈 |
| 堆溢出 | 相邻块的头部（大小/标志）、用户数据 | 分配器元数据可写 + 布局可预测 | 块头校验、safe-linking、隔离区（tcache/`mmap` 阈值） |
| UAF（释放后使用） | 已释放对象的内容与其中的指针 | 有悬垂指针 + 能重新占位（同尺寸分配） | 延迟释放、引用计数审计、类型隔离 |
| 整数溢出/截断 | 长度或索引的计算结果 | `size * count` 回绕、有符号/无符号混用 | 编译期检查、`__builtin_mul_overflow`、边界断言 |

**共同点**：四种形态都只是"入口"。真正决定危害的是**溢出之后能改到什么**——改到返回地址是控制流，改到相邻对象里的函数指针是控制流，改到长度字段是越界读写。**所以我按原语（读/写/调用/跳转）归类，而不是按形态归类。**

**最小例子**：`malloc(n * sizeof(T))` 里 `n * sizeof(T)` 回绕成小值，然后 `memcpy` 按原始 `n` 拷贝——分配 32 字节、写 4 KB。判据：能指出"分配用的大小"和"拷贝用的大小"在哪一行分叉。

**面试高频问法**：

1. **「UAF 为什么比溢出更难防？」** → 考点：生命周期。答法：溢出是"越界"，一次边界检查可能挡住；UAF 是"合法指针指向已释放内存"，检查点分散在释放与再次使用之间，且常与引用计数、并发释放耦合。
2. **「堆溢出为什么需要先了解分配器？」** → 考点：元数据位置。答法：能不能利用取决于相邻块是什么、元数据在校验前还是校验后、有没有隔离；不理解分配器就只能"崩了"而不知道崩在哪一步。
3. **「整数溢出算不算内存漏洞？」** → 考点：因果。答法：算入口——它本身只是计算错误，但会让后续的长度检查失效或绕过，最终落到越界读写。**汇报时要写清"回绕发生在哪个乘法、被哪次拷贝放大"。**

## 第 3 章 控制流劫持的三个台阶

**要解决的问题**：同样是"改一个指针"，改返回地址、改函数指针、改虚表指针，难度和所需原语完全不同。这一章把台阶排出来。

**机制**：

1. **返回地址**：最直接。需要一个写原语 + 知道目标地址（可能被 ASLR 挡住）+ 不被 canary 发现。
2. **函数指针**：对象或结构体里的回调（`struct ops { void (*cb)(void); }`）。好处是**不触发 canary**（不改栈上的返回地址）；代价是要能写到那个结构体、且知道它何时被调用。
3. **虚表指针（vtable）**：C++ 多态对象头部存 vptr，改 vptr 就能让虚调用落到别处。难点在于**必须先有类型混淆或越界写**才能改到 vptr，而且调用索引与签名要对得上。

**台阶的规律**：越往下越依赖"程序自身的结构"，越不依赖"栈布局"。所以 CFI（控制流完整性）主要覆盖 2、3 两类，CET 影子栈专治第 1 类。

**最小例子**：一个驱动结构体 `struct file_operations` 被越界写覆盖，其中 `unlocked_ioctl` 指针被改成别的内核函数的地址——**这是"函数指针劫持"在内核里的形态**，比改返回地址更隐蔽，因为不经过 canary。

**面试高频问法**：

1. **「canary 能防住函数指针劫持吗？」** → 考点：保护范围。答法：不能。canary 只检查函数返回前栈上的值，覆盖对象里的函数指针不经过栈帧，canary 看不到。
2. **「CFI 的粒度是什么？」** → 考点：间接跳转白名单。答法：按类型签名（或按 vtable/函数指针类型）限制"这个间接调用能落到哪些函数"；粒度粗了误伤合法调用，细了开销大，所以实现上要折中。
3. **「为什么虚表劫持常和类型混淆一起出现？」** → 考点：原语来源。答法：类型混淆让程序把一个对象当另一个类型用，于是"读到的 vptr"其实是攻击者控制的数据；这是不依赖内存越界的第三条路。

## 第 4 章 ROP：用已有代码拼出一次调用

**要解决的问题**：NX 让"注入代码再跳过去"失效后，攻击者只剩"已有代码"。ROP 回答的是：**只用已有代码，能不能完成一次任意函数调用？** 答案是能，因为调用约定把参数放在寄存器，而寄存器可以用 `pop` 从栈上装填。

**机制**：

- **gadget**：以 `ret` 结尾的短指令序列，例如 `pop rdi; ret`、`pop rsi; pop r15; ret`、`mov [rdi], rax; ret`。
- **栈布局**：ROP 的"程序"就是一串地址，`ret` 不断把栈顶弹进 `rip`。

```text
[ 高地址 ]
   ...                      ← 溢出前的内容
   目标函数地址（如某库函数）
   返回后的下一跳（可再串一段）
   参数值（被 pop rdi 取走）
   pop rdi; ret 的地址
   ...（原返回地址的位置被覆盖）
[ 低地址 ]
```

- **家族差异**：
  - `ret2libc`：跳到 libc 里现成的函数，靠 gadget 装参数。
  - `ret2plt`：跳到 PLT 条目，借程序的动态链接设施调用外部函数。
  - `ret2syscall`：直接拼 `rax`（系统调用号）+ `rdi/rsi/rdx` + `syscall` gadget，绕过 libc。
- **栈迁移**：`leave; ret`（`mov rsp, rbp; pop rbp; ret`）把栈整体搬到攻击者可控的缓冲区，解决"可写空间太小"。
- **`ret2csu`**：程序里 `__libc_csu_init` 有一段通用的 `pop rbx/rbp/r12-r15; ...; call [r12+rbx*8]`，可在缺 `pop rdi` 时凑参数。
- **SROP**：利用 `sigreturn` 会从栈上恢复**全部寄存器**的特性，一次设置所有寄存器（含 `rax` 系统调用号），省掉逐个 gadget。
- **对齐**：x86-64 的 `movaps` 要求 16 字节对齐，栈错位会让某些 libc 函数直接崩——这是 ROP 链"逻辑对但跑不通"的头号原因。

**为什么 ROP 能成立**：**调用约定把"控制流"变成了"数据"**——参数在寄存器里，而寄存器能从栈上装填，栈又在攻击者手里。所以"不可执行数据"并不等于"数据无害"。

**最小例子**：一条"设第一参数 → 调用"的两段式链：`pop rdi; ret` ← 参数值 ← 目标函数地址。判据：能解释为什么中间那个参数值不是"跳到它"，而是"被上一条 `pop` 吃掉"。

**面试高频问法**：

1. **「ROP 怎么防？」** → 考点：不只看 NX。答法：三层——随机化（ASLR 让 gadget 地址不可知）、CFI/CET（限制间接跳转、影子栈保护返回地址）、减少 gadget（编译选项与库裁剪只能缓解）。**没有单一开关能"防住 ROP"。**
2. **「为什么需要信息泄露？」** → 考点：地址可知性。答法：ROP 链里每个地址都必须写对；ASLR/PIE 生效时，没有泄露就只能爆破或只改低字节（部分覆盖），可靠性大幅下降。
3. **「`ret2syscall` 比 `ret2libc` 强在哪？」** → 考点：依赖面。答法：不依赖 libc 是否存在、也不受 libc 版本影响，只要能找到 `syscall; ret` 和装 `rax` 的 gadget；代价是需要更多 gadget、通常要能控制多个寄存器。
4. **「SROP 为什么一次就能设全部寄存器？」** → 考点：`sigreturn` 语义。答法：信号返回时内核从用户栈上的 `sigframe` 恢复寄存器上下文，于是"把 frame 摆好"等价于"把寄存器全设好"，省掉了逐寄存器装填。

## 第 5 章 缓解机制与它们各自的假设

**要解决的问题**：把"缓解"讲成"防住了漏洞"是错的。每个机制都只是让某类原语变贵。这一章用统一格式罗列：**它假设什么 → 假设被违反会怎样**。

**机制**：

| 机制 | 假设 | 被违反时 | 提高了什么成本 |
|---|---|---|---|
| NX / DEP | 数据页不需要执行 | 用已有代码（ROP）代替注入 | 注入代码 |
| ASLR | 地址不可预测 | 信息泄露、部分覆盖、爆破 | 目标地址可知性 |
| PIE | 可执行文件基址随机 | 同上（相对偏移仍固定） | 同上 |
| stack canary | 返回前栈上标记不变 | 泄露 canary、改不在栈上的指针 | 改返回地址 |
| RELRO / `-z now` | GOT 只读 | 早期绑定前的时间窗、其他可写函数指针表 | 改 GOT |
| FORTIFY | 编译期已知长度 | 长度在运行期决定的分支 | 简单溢出 |
| CFI | 间接跳转目标在合法集合内 | 集合过粗、类型混淆构造合法目标 | 函数指针/虚表劫持 |
| CET（IBT + 影子栈） | 间接跳转落在 `endbr64`；返回地址与影子栈一致 | 数据面攻击（不劫持控制流） | 返回地址劫持 |
| 堆加固（safe-linking 等） | 堆指针需正确编码/校验 | 泄露堆地址后重算编码 | 堆元数据破坏 |
| SMEP / SMAP | 内核不执行/不随意访问用户页 | 先改页表项（需任意写 + 目标 PT 页） | ret2usr 与用户内存跳板 |
| KASLR | 内核基址随机 | 内核信息泄露 | 内核 gadget 地址 |
| KPTI | 用户页表不含内核映射 | 侧信道（Meltdown 类） | 直接读内核内存 |

**读法**：这张表不是"清单"，而是**一组假设**。攻击者永远在做的事是：**找出哪个假设在目标环境里不成立**（旧内核没开 KPTI、32 位熵不足、编译没加 FORTIFY、CFI 集合过粗）。

**最小例子**：同一个溢出，在四种构建下后果不同——无 canary 无 PIE（直接跳）、有 canary（需泄露）、有 PIE（需泄露 + 算偏移）、有 CET（返回地址不可改，转数据面）。判据：能说出每种构建下"下一步该找什么原语"。

**面试高频问法**：

1. **「为什么说 ASLR 只是提高成本？」** → 考点：熵与泄露。答法：随机化把"写死地址"变成"先泄露再算"；熵不足（fork 共享布局、32 位）时可爆破，有读原语时可泄露。**它不是不可绕过，是让利用从一步变成两步。**
2. **「CET 之后 ROP 就死了吗？」** → 考点：边界。答法：影子栈保护返回地址，IBT 限制间接跳转落点，ROP/JOP 都变难；但**数据面攻击**（改配置、改权限标志、类型混淆造成的逻辑越权）不受影响，所以攻击重心会迁移。
3. **「为什么内核需要 SMEP 和 SMAP 两个？」** → 考点：执行 vs 数据。答法：SMEP 管"能不能执行用户页"，SMAP 管"能不能读写用户页"，方向不同；只开一个，另一个方向仍可当跳板。

## 第 6 章 从用户态到内核

**要解决的问题**：本地提权的本质是"从 ring3 拿到 ring0 能力"。要看清入口在哪、链条怎么走、加固怎么打断。

**机制**：

- **常见入口**：`ioctl` 参数校验缺失、文件系统镜像解析（挂载恶意镜像）、网络栈协议解析、驱动里的竞态与 UAF。
- **经典骨架**：内核 UAF → 用同尺寸对象占位 → 得到一个内核地址上的读/写原语 → 改当前进程的凭据结构（把 uid 等字段改成 0）。**目标不是"执行任意代码"，而是"改一个结构体字段"**——这一点常被误解。
- **三道加固如何打断链条**：
  - **SMEP**：挡住"返回地址指向用户态代码"（ret2usr）。
  - **SMAP**：挡住"把用户内存当跳板/当参数区"。
  - **KPTI**：用户态页表不含内核映射，缓解 Meltdown 类侧信道，同时让"用户态直接读内核地址"失效。
  - 另有 **KASLR**（地址不可知，需泄露）与 **CFI**（限制间接调用）。

**最小例子**：一个 `ioctl` 把用户给的长度直接用于内核缓冲区写，且不做上限检查——先是越界写，再借"同尺寸对象占位"拿到凭据结构的地址，最后改字段。判据：能指出这条链上**每一步**被哪个机制拦住（没有 SMAP 时"用用户内存当参数区"这一步会成立）。

**面试高频问法**：

1. **「为什么很多提权链最后都是改凭据，而不是执行 shellcode？」** → 考点：目标最小化。答法：执行任意代码需要可执行内存（NX 挡）、需要绕过 CFI；改一个字段只需要一次写原语，且立即生效、不留新代码。
2. **「KPTI 是为了防什么？」** → 考点：侧信道而非漏洞。答法：Meltdown 类攻击利用乱序执行读内核映射；KPTI 让用户态页表里根本没有内核映射，从根上消除"可读的目标"。代价是每次进出内核要换页表（PCID 缓解开销）。
3. **「内核 UAF 为什么难修？」** → 考点：并发与生命周期。答法：释放点与使用点可能在不同 CPU、不同上下文；修复往往要引入引用计数或 RCU 延迟释放，而这些本身又可能引入新问题。

## 第 7 章 侧信道与硬件层面的攻击

**要解决的问题**：有些攻击不需要软件漏洞——硬件的实现细节（推测执行、缓存、DRAM 电气特性）就是攻击面。这一章只讲机制与后果。

**机制**：

- **推测执行 + 缓存痕迹**：CPU 会提前执行分支预测路径上的指令；即使这些指令的结果被丢弃，**它们对缓存的副作用留下了**。攻击者再用计时（`Flush+Reload` 一类）把"哪块数据被加载过"读出来。
- **Spectre 家族**：诱导受害者在自己的地址空间里越界读（利用边界检查被推测执行穿透），把秘密编码进缓存状态。
- **Meltdown**：利用乱序执行读内核映射（在 KPTI 之前），把内核内存内容通过缓存侧信道带出。
- **Rowhammer**：反复访问同一 DRAM 行，导致相邻行位翻转；在现代内存上需要特定访问模式与足够时间。
- **共同点**：都**不修改目标内存、不劫持控制流**，所以 CFI/canary 完全无关；缓解只能从硬件/内核布局层做（KPTI、retpoline/IBRS、ECC、刷新策略）。

**最小例子**：一个"数组越界读"在语言层被边界检查挡住，但推测执行可能让越界的那次加载**先发生**，把目标字节的缓存行拉进 cache；随后计时区分两种状态。判据：能说清"为什么结果被丢弃了，信息还是泄漏了"。

**面试高频问法**：

1. **「为什么这类攻击防不住在软件层？」** → 考点：抽象泄漏。答法：泄漏发生在硬件实现层，软件只能减少可利用的模式（消除数据依赖的分支、加屏障、隔离页表），不能保证消除；最终要靠硬件修订与新指令（如 `lfence` 语义强化、IBRS）。
2. **「KPTI 的代价是什么？」** → 考点：工程取舍。答法：每次用户态↔内核态切换都要换页表，TLB 受影响；用 PCID 与"保留少量必要映射"缓解，但仍有可测开销。
3. **「Rowhammer 和缓冲区溢出有什么本质不同？」** → 考点：故障模型。答法：溢出是软件的地址计算错误；Rowhammer 是硬件可靠性故障被利用——**没有 bug 的代码也会被影响**，所以只能靠 ECC/刷新/隔离来降低概率。

## 第 8 章 外挂的技术谱系

**要解决的问题**：外挂不是一种技术，是四层能力的组合。讲清谱系，才能把它和漏洞利用放在同一张图上，也才能说清反作弊为什么要进内核。

**机制**：四层能力，各自解决一个问题，各自留下痕迹。

| 层 | 能力 | 典型实现思路 | 留下的可检测面 |
|---|---|---|---|
| 读 | 看到目标进程的内存/状态 | 跨进程读（系统调用或驱动）、值扫描后追指针链、按特征码定位结构 | 打开目标进程的句柄、异常的高频读取、调试寄存器/`ptrace` 状态 |
| 写 | 改数值或结构 | 跨进程写、改对象字段、改配置表 | 内存页异常写、CRC/代码段校验、行为异常 |
| 调 | 调目标进程内的函数 | 注入后调用、Hook 拦截（inline/IAT/vtable）、远程线程 | 模块列表、`/proc/pid/maps` 异常映射、签名校验 |
| 藏 | 不被发现 | 反调试、隐藏模块/句柄、驱动级绕过、完整性校验对抗 | 时间差、驱动签名、内核回调、硬件虚拟化痕迹 |

**三条判断**（不写具体手法，只给判据）：

1. **能读就已经很强**：读原语是"信息泄露"的等价物——它让地址、状态、随机数都不再神秘。所以反作弊对"读"的检测优先级高于"写"。
2. **注入是为了"调"**：只有需要复用目标进程的既有逻辑（渲染、物理、AI）时才注入；纯改数值不需要注入，检测面也小得多。
3. **进内核是为了"藏"和"跨"**：用户态的跨进程能力受系统调用限制（权限、`ptrace_scope`、句柄保护），进内核才能绕过并提供隐藏能力。**这也是反作弊必须进内核的原因——对抗发生在同一层。**

**最小例子**（只到能力层）：目标是"让角色血量不掉"。路线一：找到血量字段并持续写回（写原语，检测面是页写与行为异常）；路线二：Hook 扣血函数让它直接返回（调原语，检测面是代码段完整性与模块列表）。判据：能说出两条路线各自的检测面，而不是"哪个更厉害"。

**面试高频问法**：

1. **「为什么外挂和反作弊都往内核跑？」** → 考点：权限对称性。答法：用户态的跨进程读写、隐藏、Hook 都受系统约束；一旦一方进内核，另一方在用户态就无法可靠观测它（对方可以过滤），于是被迫跟进。**这是能力对抗，不是技术偏好。**
2. **「怎么检测注入？」** → 考点：可观测面。答法：模块/映射列表与预期不符、代码段哈希变化、线程起始地址不在任何已加载模块内、句柄表里有不该有的权限。
3. **「驱动级外挂最大的代价是什么？」** → 考点：门槛与风险。答法：驱动要签名、要过 Secure Boot 与内存完整性检查、崩溃就是蓝屏级事故、被识别后是整机级封禁；**技术上"能做"和工程上"能活"是两件事**。

## 第 9 章 反作弊与防御工程

**要解决的问题**：防御不是"加一个检测"，而是**让攻击者的每一步都要付出可观测的成本**。这一章按层给防御手段与代价。

**机制**：

| 层 | 手段 | 拦住什么 | 代价 |
|---|---|---|---|
| 进程内 | 代码段/数据完整性校验、反调试检测 | 代码改写、调试器附着 | 性能开销、误报 |
| 系统调用层 | 句柄/权限过滤、访问审计 | 跨进程读写 | 兼容性、性能 |
| 内核 | 驱动（回调、对象回调、内核完整性）、驱动签名 + Secure Boot + HVCI | 内核级作弊、未签名驱动 | 稳定性风险、隐私争议、法律与合规 |
| 行为层 | 统计异常（命中率、反应时间、输入分布）、遥测 | 不改内存的"软"作弊 | 误判、隐私 |
| 平台层 | 服务器权威（状态不交给客户端）、加密与校验、随机化 | 客户端改本地状态无效 | 服务端成本、延迟 |

**Linux 侧的对应物**（不涉及反作弊，但机制同源）：`seccomp-bpf` 限制可用系统调用、LSM/eBPF 做访问控制、只读挂载与 `nosuid`、namespace 隔离、`ptrace_scope` 限制调试附着、`Yama` 的 ptrace 策略。**这些都是"把能力收窄"，与反作弊的"把能力观测"是同一类思路的两面。**

**最大的结构性结论**：**只要状态在客户端，就有被改的可能；能彻底解决的只有"服务器权威"。** 所以现代架构把"检测"当补充，把"不信任客户端"当地基。

**最小例子**：把一个数值从"客户端算、客户端存"改成"服务端算、客户端只显示"——攻击者仍能改显示，但改不了结果。判据：能说清"改了也没用"和"改了会被发现"是两种不同强度的防御。

**面试高频问法**：

1. **「反作弊为什么要进内核，用户态不行吗？」** → 考点：观测能力。答法：用户态观测会被同层的对手过滤或伪造（对手可以 Hook 你的检测函数）；进内核才有更底层的视野（对象回调、句柄过滤、页表级检查）。代价是稳定性、兼容性、隐私与法律风险。
2. **「为什么服务器权威是最强的防御？」** → 考点：信任边界。答法：把可信计算移到攻击者无法控制的一侧；客户端的一切都可被改，只有"结果不由客户端决定"才是结构性防御。
3. **「检测会不会误伤正常玩家？」** → 考点：工程现实。答法：会。所以工业实践是"多层信号 + 人工复核 + 申诉通道"，单条信号只做标记不做封禁；**误封的成本通常高于漏检**。

## 第 10 章 判据、实验方法与边界

**要解决的问题**：这一块最容易停留在"听过"。要有一组能在**自己写的程序**上跑通的判据，把"缓解生效/失效"变成可观测事实。

**机制**：

```bash
# 1) 看一个二进制开了哪些缓解
checksec --file=./demo            # 或 pwn checksec ./demo
readelf -lW ./demo | grep -E 'GNU_STACK|GNU_RELRO'
readelf -d ./demo | grep -E 'BIND_NOW|FLAGS'

# 2) 看运行期布局（ASLR 是否生效、栈/堆/库基址）
cat /proc/self/maps | head
setarch -R ./demo                 # 关掉 ASLR 做对照实验

# 3) 找 bug 而不是造利用（防御视角）
clang -g -fsanitize=address,undefined demo.c -o demo && ./demo
```

**判据表**：

| 观察 | 说明 |
|---|---|
| `GNU_STACK` 是 `RW` 而不是 `RWE` | NX 生效；若为 `RWE` 说明栈可执行（危险） |
| `GNU_RELRO` + `BIND_NOW` | GOT 尽早只读，改 GOT 的窗口关闭 |
| 两次运行 `/proc/pid/maps` 基址不同 | ASLR 生效；相同则需查 `randomize_va_space` |
| 溢出后进程报 `stack smashing detected` | canary 生效 |
| 溢出后只 `SIGSEGV` 而不报 canary | 可能覆盖的是函数指针或数据，而不是返回地址 |

**实验边界（务必遵守）**：只用自己写的示例程序或公开 CTF 题目；在隔离环境（容器/虚拟机、无外网）里做；不针对任何真实商业软件、游戏或反作弊产品做绕过实验；不产出可分发的利用或作弊工具。**这条边界不是形式要求——它决定这套知识是"能力"还是"风险"。**

**面试高频问法**：

1. **「你怎么验证一个缓解真的生效了？」** → 考点：可观测。答法：从二进制看（`checksec`/`readelf` 的段属性）、从运行期看（`/proc/pid/maps` 的基址随机性）、从行为看（构造受控溢出，观察是 canary 报错还是直接崩）。
2. **「为什么用 fuzz 而不是手写用例？」** → 考点：覆盖面。答法：fuzz 用覆盖率引导探索输入空间，能到人手想不到的路径；配合 sanitizer 把"静默越界"变成"立刻报错"。它是找 bug 的工具，不是造利用的工具。
3. **「讲这块的边界在哪？」** → 考点：判断力。答法：讲机制、原语、检测面；不给可用利用、不针对具体产品。**能讲清"为什么这样防"比"能打通某个靶机"更能证明理解。**

## 附：一张原语→能力的对照

| 拿到的原语 | 立刻能做 | 下一步通常是 |
|---|---|---|
| 读（任意地址） | 泄露地址、读状态 | 破 ASLR → 转成写/跳 |
| 写（任意地址） | 改标志/凭据/函数指针 | 转成调用或提权 |
| 调用（任意函数 + 可控参数） | 执行既有逻辑 | 组合成一次完整动作 |
| 跳转（可控 `rip`） | 进 ROP/栈迁移 | 拼出"调用" |
| 无原语，仅崩溃 | 拒绝服务 | 需重新找入口 |

**一句话**：安全分析的核心问题是"**给了你哪几个原语**"，不是"这是哪一类漏洞"。
