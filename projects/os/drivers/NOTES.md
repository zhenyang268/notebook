## 第 1 章 设备的四种"说话方式"

**要解决的问题**：同一个"读写设备"，机制组合不同，驱动形状就完全不同。先把这个坐标系建起来，后面两块设备才知道自己站在哪儿。

**机制**：

| 方式 | 做什么 | 代价 | 典型 |
|---|---|---|---|
| 端口 I/O（PIO） | `in/out` 指令读写设备寄存器与数据口 | 占 CPU，一次搬几个字节 | 老 IDE、串口 |
| 内存映射 I/O（MMIO） | 设备寄存器映射进地址空间，普通 load/store 访问 | 需要建立映射、需要内存屏障 | PCIe 设备、e1000 |
| 中断 | 设备主动通知 CPU | 需要 IDT/向量表、需要处理并发 | 几乎所有现代设备 |
| DMA | 设备直接读写内存 | 需要物理地址、需要缓存一致性维护 | 网卡、NVMe、显卡 |

**组合决定形状**：

- **PIO + 轮询**：最简。没有中断服务程序、没有并发，代价是 CPU 空转。JOS 的磁盘就是这样。
- **MMIO + DMA + 中断**：现代形态。寄存器用 MMIO 配，数据用 DMA 搬，完成用中断通知。JOS 的 e1000 就是这三件套齐活。
- **中间形态**：MMIO + 轮询（简单网卡的收包路径）、PIO + 中断（老串口）。

**最小例子**：同一个"读 512 字节"，PIO 是 `insl(0x1F0, buf, 128)`；DMA 是"把 `buf` 的物理地址写进描述符，然后写 `TDT` 敲门铃，等 `DD`"。**前者 CPU 一条条搬，后者 CPU 只说话不搬货。**

**面试高频问法**：

1. **「MMIO 和 PIO 有什么区别，为什么现代设备都用 MMIO？」** → 考点：寻址方式与指令集。答法：PIO 走独立的 I/O 地址空间，必须用专门的 `in/out` 指令；MMIO 把寄存器映射进内存地址空间，普通 load/store 就能访问，编译器与 CPU 的优化手段都能用上，也便于用统一的屏障语义。
2. **「DMA 为什么要物理地址？」** → 考点：设备不认虚拟地址。答法：设备只看到总线地址，所以驱动要把虚拟地址翻译成总线/物理地址（`dma_map_single`），并在需要时维护缓存一致性。
3. **「轮询和中断怎么选？」** → 考点：延迟与开销的权衡。答法：高频小包用轮询（或混合的 NAPI），避免中断风暴；低频事件用中断，避免 CPU 空转。

## 第 2 章 JOS 磁盘（一）：ATA PIO 读扇区

**要解决的问题**：让内核能按扇区读写一块真实磁盘，并且**错误可返回**——不能因为设备没响应就死在循环里。

**机制**：

端口表（主通道）：

| 端口 | 用途 |
|---|---|
| `0x1F0` | 数据（16 位，一次一个字） |
| `0x1F1` | 错误 / 特性 |
| `0x1F2` | 扇区计数 |
| `0x1F3`–`0x1F5` | LBA 低 / 中 / 高 |
| `0x1F6` | 驱动器/磁头 + LBA 高 4 位（`0xE0 \| 高4位`） |
| `0x1F7` | 状态（读）/ 命令（写） |

状态位：`ERR 0x01`、`DRQ 0x08`、`DF 0x20`、`DRDY 0x40`、`BSY 0x80`。

读写顺序固定：**写参数 → 发命令 → 等 `BSY` 落且 `DRDY` 起 → 等 `DRQ` 起 → 搬数据**。发完命令后设备需要时间响应，老 ATA 没有就绪中断，惯用做法是**连读四次备用状态寄存器**（`0x3F6`）凑出约 400ns。

```c
#define SECTSIZE 512
#define ATA_BSY 0x80
#define ATA_DRDY 0x40
#define ATA_DRQ 0x08

static int ide_wait_ready(void) {
    // 最多等一小会儿；教学实现常写成死等，但真实驱动必须有超时
    for (int i = 0; i < 1000000; ++i) {
        uint8_t st = inb(0x1F7);
        if ((st & ATA_BSY) == 0 && (st & ATA_DRDY)) return 0;
        if (st & 0x01) return -1;           // ERR
    }
    return -1;                              // 超时
}

int ide_read(uint32_t secno, void *dst, size_t nsecs) {
    outb(0x1F2, (uint8_t)nsecs);
    outb(0x1F3, secno & 0xFF);
    outb(0x1F4, (secno >> 8) & 0xFF);
    outb(0x1F5, (secno >> 16) & 0xFF);
    outb(0x1F6, 0xE0 | ((secno >> 24) & 0x0F));
    outb(0x1F7, 0x20);                      // READ SECTORS
    for (; nsecs > 0; --nsecs, dst = (char *)dst + SECTSIZE) {
        if (ide_wait_ready() < 0) return -1;
        while ((inb(0x1F7) & ATA_DRQ) == 0) ;   // 等数据就绪
        insl(0x1F0, dst, SECTSIZE / 4);         // 128 个 32 位字
    }
    return 0;
}
```

**最小例子**：读 0 号扇区（通常是引导区的尾部签名）。

```c
uint8_t sec[512];
if (ide_read(0, sec, 1) < 0) panic("disk error");
if (sec[510] != 0x55 || sec[511] != 0xAA) cprintf("no boot signature\n");
```

**面试高频问法**：

1. **「为什么必须先等 BSY 落？」** → 考点：设备状态机。答法：`BSY` 表示设备正在执行上一条命令，此时写寄存器会被忽略或写坏；必须等它落下、再看 `DRDY`（就绪）才安全。
2. **「`DRQ` 是什么意思？」** → 考点：数据阶段。答法：`DRQ` 表示设备已经把数据放到数据端口（读）或准备好接收（写），一次 `DRQ` 通常对应一个扇区的搬运窗口。
3. **「为什么真实驱动必须有超时？」** → 考点：错误路径。答法：设备可能掉线、线缆故障、控制器挂死；死等会变成不可恢复的挂起。教学实现可以死等，生产实现必须超时并上报。

## 第 3 章 JOS 磁盘（二）：块缓存与磁盘布局

**要解决的问题**：文件系统不能每次读写都直接打磁盘——太慢，而且无法表达"这块数据正在被改"。需要一个**带引用计数的块缓存**，以及一个能被解释的磁盘布局。

**机制**：

**两个粒度**：设备按**扇区**（512 B）读写，文件系统按**块**（4 KB = 8 扇区）管理。两者不要混。

**块缓存**（`bcache`）三个结构：哈希表（按 `dev, blockno` 定位）、双向 LRU 链（淘汰顺序）、每块的引用计数（有人用就不能淘汰）。

```c
struct buf {
    int flags;            // B_VALID / B_DIRTY
    uint32_t dev, blockno;
    uint32_t refcnt;
    struct buf *prev, *next;
    uint8_t data[BLKSIZE]; // 4096
};
```

三个操作的语义：

- `bget(dev, blkno)`：哈希查；命中则 `refcnt++` 并挪到 LRU 头；未命中则从尾部摘一个 `refcnt==0` 的（脏块要写回），重新初始化后挪到头部。
- `bread(dev, blkno)`：`bget` + 若 `!B_VALID` 则 `ide_read` 一整块并置 `B_VALID`。
- `brelse(b)`：`refcnt--`，挪到 LRU 头。**只要有人引用，这块就不会被换出。**

**磁盘布局**（JOS 教学口径，块号从 0 起）：

```text
块 0        引导块
块 1        superblock：magic / 总块数 / 数据块数 / inode 数
块 2        位图：每个 bit 对应一个块是否已分配
块 3 ...    inode（struct File 数组，每块若干个）
...         数据块
```

`struct File` 用 **10 个直接块指针 + 1 个单级间接块**（间接块里放 1024 个 4 字节块号），所以单文件上限约 $(10+1024)\times4\text{KB}\approx4\text{MB}$。**用单级间接把多级寻址的代码省掉，这是教学取舍的直接体现。**

**最小例子**：一次 `read` 的完整路径

```text
用户 read → FS 进程查 inode → 得到块号列表 → bread(块号)（可能命中缓存）→ 拷到共享页 → 回 IPC
```

判据：能说出每一步"谁持有引用、什么时候释放"。**漏掉 `brelse` 的后果不是崩溃，而是缓存逐渐被钉死、最终所有块都不可淘汰。**

**面试高频问法**：

1. **「块缓存和 CPU 的 cache 有什么像、有什么不像？」** → 考点：两类缓存的差异。答法：都吃局部性、都有替换策略；但块缓存是**软件显式管理**的（谁引用谁负责），CPU cache 是硬件透明管理的（一致性由硬件保证）。
2. **「为什么要引用计数，只用 LRU 不行吗？」** → 考点：淘汰的安全性。答法：LRU 只决定"淘汰顺序"，不知道"能不能淘汰"；正在被读写的块一旦被换出，数据就丢了。引用计数是"借用凭证"。
3. **「脏块什么时候写回？」** → 考点：写回策略。答法：JOS 在淘汰脏块时写回；也可以选周期回写（Linux 的 writeback）或提交时写回（日志文件系统）。

## 第 4 章 JOS 文件服务与 `spawn`

**要解决的问题**：把文件系统放在用户态，就必须解决"别的进程怎么访问它"和"程序怎么被加载"。

**机制**：

**请求集**（`FSREQ_*`）：`OPEN / MAP / SET_SIZE / CLOSE / STAT / UNLINK / FLUSH / READ / WRITE`。每个请求是一个结构体，客户端用 `ipc_send` 发给 FS 进程，FS 处理完用 `ipc_recv` 回值。

**页映射是关键**：`FSREQ_MAP` 让 FS 进程把"文件的第 n 页"映射进客户端的地址空间（`sys_page_map`），之后客户端直接读那块内存，**不需要拷贝**。这也是为什么 JOS 的 `file_read` 实现得很轻：它只是触发映射，然后 `memmove`。

**`spawn` 的步骤**（读 ELF 并起一个新进程）：

```text
1. open(path) → 读 Elf32_Ehdr，校验 magic
2. 遍历 phdr：对每个 PT_LOAD 段
     - 计算需要的页数，sys_page_alloc 分配子进程页
     - fsipc_map 把文件对应页映射到临时地址，memcpy 到子进程页（不完整页要清零）
3. 分配并映射用户栈，把 argv 字符串拷进去，构造 argc/argv
4. sys_env_set_status(child, ENV_RUNNABLE)
```

**最小例子**：`file_read` 与内核内 `read` 的成本对比——JOS 是"两次调度 + 一次 IPC + 一次页操作"；xv6 是"一次系统调用 + 一次块缓存拷贝"。**同样 4 KB，路径长度差 3 倍以上，但 JOS 的文件系统崩了不影响内核。**

**面试高频问法**：

1. **「为什么用页映射而不是把数据拷进 IPC 消息？」** → 考点：零拷贝与页粒度。答法：IPC 消息只有一个 `uint32_t` 的载荷；大块数据必须靠页共享。映射一次 4 KB 比逐字节拷贝便宜得多，而且天然按页对齐。
2. **「`spawn` 为什么需要自己清零 `.bss`？」** → 考点：ELF 语义。答法：`p_memsz > p_filesz` 的那部分是 `.bss`，文件里不存在；加载器必须显式清零，否则子进程会看到上一个进程的残留数据（信息泄露）。
3. **「用户态文件服务在生产里怎么活下来？」** → 考点：FUSE。答法：Linux 的 FUSE 就是同一形态：内核转发请求，用户态守护进程处理。代价是每次操作多次上下文切换，收益是崩溃隔离与开发便利。

## 第 5 章 JOS e1000（一）：MMIO 与描述符环

**要解决的问题**：网卡不是"读一个寄存器拿一个字节"的设备，它按**描述符环**批量收发。驱动要正确地和硬件共享这块环——谁写、谁读、什么时候归还。

**机制**：

**寄存器**通过 MMIO 访问（把 BAR 指向的物理区映射进内核虚拟地址，JOS 用 `mmio_map_region`）。常用的几组：

| 组 | 寄存器 | 作用 |
|---|---|---|
| 控制 | `CTRL` | 复位、链路 |
| 中断 | `IMS` / `IMC` / `ICR` | 掩码设置 / 清除 / 读状态并清 |
| 发送 | `TDBAL/TDBAH`（环基址）、`TDLEN`（字节长）、`TDH`（头）、`TDT`（尾）、`TCTL`（使能） | 配置与推动发送环 |
| 接收 | `RDBAL/RDBAH`、`RDLEN`、`RDH`、`RDT`、`RCTL` | 同上，方向相反 |

**描述符**（16 字节，必须按 16 字节对齐）：

```c
struct tx_desc {
    uint64_t addr;      // 数据缓冲的物理地址
    uint16_t length;
    uint8_t  cso, cmd;
    uint8_t  status;    // bit0 = DD（descriptor done）
    uint8_t  css;
    uint16_t special;
} __attribute__((packed));

struct rx_desc {
    uint64_t addr;
    uint16_t length;
    uint16_t csum;
    uint8_t  status;    // bit0 = DD
    uint8_t  errors;
    uint16_t special;
} __attribute__((packed));
```

**所有权规则**（这是本章唯一真正的难点）：

- 发送环：**驱动写描述符 → 写 `TDT`（门铃）→ 设备取走 → 置 `DD` 并前移 `TDH`**。驱动只能在 `TDH` 追上来之后回收那块缓冲。
- 接收环：**驱动预先填好缓冲地址 → 写 `RDT` 交给设备 → 设备填数据并置 `DD` → 驱动处理 → 归还并前移 `RDT`**。

**最小例子**：初始化到能发第一个包的最短序列

```c
regs[TCTL] = 0;                                  // 先关
regs[TDBAL] = (uint32_t)tx_ring_phys;
regs[TDBAH] = 0;
regs[TDLEN] = NTXDESC * 16;
regs[TDH] = regs[TDT] = 0;
regs[TCTL] = TCTL_EN | TCTL_PSP | TCTL_CT | TCTL_COLD;
regs[RCTL] = RCTL_EN | RCTL_BAM | RCTL_SECRC;
regs[IMS]  = ...;                                // 打开需要的中断
```

**面试高频问法**：

1. **「为什么描述符里放的是物理地址？」** → 考点：设备视角。答法：设备通过总线访问内存，只认物理/总线地址；虚拟地址对它没有意义。
2. **「`TDH` 和 `TDT` 分别由谁移动？」** → 考点：所有权。答法：`TDT` 由驱动写（告诉设备"到这里都可以发"），`TDH` 由设备写（告诉驱动"发到这里了"）。**谁移动，谁就拥有那一格。**
3. **「环大小怎么选？」** → 考点：延迟与内存的权衡。答法：太小容易满环丢包/降吞吐，太大增加延迟与缓冲内存；教学实现通常几十项，真实网卡上千项并配合多队列。

## 第 6 章 JOS e1000（二）：中断与收包

**要解决的问题**：包到了怎么知道？中断里能做什么、不能做什么？缓冲什么时候能还给设备？

**机制**：

- **中断注册**：把 e1000 的 IRQ 挂到 IDT，开 `IMS` 里需要的位（收包、发送完成、链路变化等）。
- **中断服务程序**：读 `ICR`（读即清），判断是哪类事件；**只做最少的事**——JOS 直接调 `e1000_recv()` 把包搬走，教学上可以接受，生产上必须推到下半部。
- **收包路径**：

```text
idx = (RDT + 1) % NRXDESC
while (rx_ring[idx].status & DD) {
    拷贝数据到上层（不能等，因为设备随时可能复用这块缓冲）
    重新分配一个缓冲，填回描述符 addr
    rx_ring[idx].status = 0
    RDT = idx                 // 归还给设备
    idx = (idx + 1) % NRXDESC
    net_rx(pkt)               // 交给协议栈（ARP/IP/UDP）
}
```

**三条硬约束**：

1. **必须先拷走再归还**：一旦 `RDT` 前移，设备就可能立刻往这块缓冲写新包。
2. **`RDT` 指向"最后一个已处理"而不是"下一个空位"**：所以取包从 `RDT+1` 开始。
3. **环满只能丢**：接收侧没有背压，丢包必须计数（否则你永远不知道丢了多少）。

**最小例子**：环满的表现——`RDT` 追不上设备，新包被设备丢弃，`RDH` 停住。判据是"应用收不到包，但链路是 up 的，且没有中断风暴"。

**面试高频问法**：

1. **「为什么中断里不能直接处理完整协议栈？」** → 考点：原子上下文。答法：硬中断里通常关本地中断、不能睡眠、长时间占用会丢中断；协议栈可能加锁、分配内存、甚至阻塞，必须放到下半部（`softirq`/`workqueue`/NAPI poll）。
2. **「接收环为什么比发送环更容易丢包？」** → 考点：背压缺失。答法：发送侧可以返回"忙"让上层重试；接收侧包已经到了，缓冲不够只能丢。
3. **「`RDT` 为什么要等处理完才前移？」** → 考点：所有权。答法：前移即表示"这块缓冲还给你了"，设备会立刻覆盖它；没拷走就前移等于把数据交给别人改写。

## 第 7 章 Linux 侧的配套：同一件事的五层加成

**要解决的问题**：JOS 的驱动是"能工作"的最小形态。生产内核要在同一件事上再叠五层，每层都为了解决一个 JOS 不需要面对的问题。

**机制**：

| 层 | JOS 的做法 | Linux 的做法 | 解决什么 |
|---|---|---|---|
| 设备发现 | 硬编码端口/IRQ | 总线模型：`bus_type` + `device` + `device_driver`，匹配后调 `probe()` | 热插拔、多设备、驱动与板级解耦 |
| 资源管理 | 手动 `mmio_map_region` / 注册 IRQ | `devres`（`devm_*`）托管，失败自动回收 | 错误路径不泄漏 |
| DMA | 直接写物理地址 | DMA API：`dma_map_single` / `dma_map_sg` / `dma_alloc_coherent` + IOMMU | 缓存一致性与地址翻译 |
| 中断 | 全部在 handler 里做 | 上半部（确认 + 唤醒下半部）/ 下半部（`softirq`、`workqueue`、线程化中断） | 缩短关中断时间 |
| 块 I/O | 直接 `ide_read` + 自建 bcache | 块层：`bio` → 请求队列（`blk-mq` 多队列）→ 驱动；页缓存 + 回写线程 | 并发、合并、调度、缓存 |
| 网络 | 自己写 `e1000_recv` 调 `net_rx` | `net_device` + `ndo_start_xmit` + NAPI + `sk_buff` | 批处理、零拷贝、流控 |

**两条最值得记住的对照**：

- **bcache → 页缓存 + 块层**：JOS 的块缓存是"文件系统的缓存"；Linux 把缓存上移到**页缓存**（按文件页缓存），块层只管"把 I/O 送到设备"，于是多种文件系统共用一套缓存与回写机制。
- **`e1000_recv` → NAPI**：JOS 每个包一次中断；NAPI 在中断里关中断并调度 poll，poll 里批量取包，取完再开中断——**用批处理换掉中断风暴**。

**最小例子**：同一个"发送一个包"。
JOS：填 `tx_desc` → `TDT++`。
Linux：上层组 `sk_buff` → `dev_queue_xmit` → qdisc → `ndo_start_xmit` → 驱动填描述符 → 门铃；完成由中断/NAPI 回收。**多出来的 qdisc 是为了流控与优先级，不是为了功能。**

**面试高频问法**：

1. **「`devm_` 系列解决了什么？」** → 考点：错误路径。答法：把资源绑定到设备生命周期，`probe` 失败或设备移除时自动释放，避免"申请了三个、第四个失败、前三个泄漏"这类经典 bug。
2. **「为什么需要 DMA API 而不是直接用 `virt_to_phys`？」** → 考点：抽象与一致性。答法：设备看到的地址不一定是物理地址（IOMMU 会重映射）；而且 DMA 与 CPU 缓存需要显式的方向性同步，`dma_map_single` 把这两件事一起处理。
3. **「NAPI 的 poll 和中断是什么关系？」** → 考点：混合模式。答法：第一个包用中断触发，随后关中断进入 poll 批量收；收到没包或预算用完再开中断。**高频时省中断，低频时省轮询。**

## 第 8 章 判据与调试：怎么证明驱动是对的

**要解决的问题**：驱动"能跑"和"正确"之间隔着错误路径与并发。这一章给出可执行的判据。

**机制**：

| 判据 | 做法 | 观察什么 |
|---|---|---|
| 通路 | 环回：自发自收（同一台机器 ping 自己/两块网卡对接） | 收发包计数、校验和 |
| 内容 | 抓包（`tcpdump`）对比设备侧与应用侧 | 顺序、长度、校验和 |
| 完成通知 | `/proc/interrupts` 看该 IRQ 计数增长 | 中断是否按预期发生、有没有风暴 |
| 错误路径 | 注入：磁盘读坏块 / 网卡拔线 / 环满 | 返回值、丢弃计数、是否死等 |
| 一致性 | 写后读回比对（块级）；`fsck` 等价检查（结构级） | 数据是否被覆盖、分配位图是否自洽 |
| 性能口径 | `iostat`（块）、`ethtool -S`（网卡） | 队列深度、丢弃、重传 |

**最小例子**：三条最有效的注入测试

```text
1. 磁盘：让 ide_wait_ready 的超时极小 → 应返回错误而不是 panic
2. 网卡：只初始化 RX 不初始化 TX → 发送应明确失败，而不是静默丢包
3. 环：把 NRXDESC 改成 2 → 立刻暴露"归还时机"与"环满丢包"两个 bug
```

**面试高频问法**：

1. **「怎么确认丢包是驱动的问题而不是网络的问题？」** → 考点：分层定位。答法：看三处计数——设备侧（`ethtool -S` 的 rx_dropped）、协议栈侧（`netstat -s` 的重传/错误）、应用侧（读到的字节数）。**驱动丢了，设备侧计数会涨；网络丢了，协议栈侧才会涨。**
2. **「为什么要把环调小做测试？」** → 考点：边界放大。答法：小环让"满"这个状态高频出现，把并发 bug 从偶发变成必现；这是驱动调试最有效的手段之一。
3. **「驱动正确性最容易被忽略的一环是什么？」** → 考点：错误路径。答法：初始化中途失败的回滚（第 3 个资源申请失败时前两个要释放）与"设备消失"后的处理；happy path 谁都能跑通。

## 附：两块设备的对照

| 维度 | IDE 磁盘（PIO） | e1000 网卡 |
|---|---|---|
| 寄存器访问 | 端口 I/O | MMIO |
| 数据搬运 | CPU `insl` | DMA |
| 完成通知 | 轮询状态位 | 中断 |
| 并发 | 单请求、可加锁 | 环形队列、收发并行 |
| 错误模型 | `ERR` 位 + 超时 | 描述符 `errors` + 丢包计数 |
| 上层 | 块缓存 → inode → 用户态 FS 进程 | ARP/IP/UDP → socket |
| 最易错的点 | 状态位顺序、超时 | 所有权转移、归还时机 |
