# kernel-compare · JOS / xv6 / Linux 的设计出发点与 API 对比

> 同一个问题（让用户程序跑起来），三个系统给出三种答案。本文只做**因果对比**：CPU 架构给了什么材料，内核因此长成什么样，API 又因此是什么形状。
> 设备层细节在 `../drivers/`，用户态 API 用法在 `../linux-api/`，JOS 逐 lab 实现见 `../jos/`。

## 一、它在做什么

把三个内核放在一起，回答一个问题：**为什么它们看起来完全不同**。

| | JOS | xv6 | Linux |
|---|---|---|---|
| 出身 | MIT 6.828 教学内核 | MIT 6.S081 教学内核（Unix V6 重写） | 生产内核 |
| 目标架构 | x86 32 位 | x86 与 RISC-V（S-mode） | 几十种架构 |
| 代码量级 | 万行以内 | 万行以内 | 千万行级 |
| 出发点 | 让每条机制都能在一学期内被看见、被验证 | 用最小代码复现 Unix 的核心抽象 | 兼容、可移植、可扩展、能跑真实硬件与生态 |

**它交付三样东西**：

1. **一张因果表**：出发点 → 架构选择 → 机制选择 → API 形状。例如"教学要可验证" → 不做 SMP → 一把大内核锁 → 系统调用可以是同步 rendezvous（JOS 的 IPC）；"生产要扩展" → 多核 → per-CPU + RCU → API 必须能表达无锁读。
2. **一张 API 对照表**：同一个意图（创建进程、等待、映射内存、传数据、读文件）在三个系统里叫什么、返回什么、错误怎么报、用户指针怎么校验。
3. **一组"为什么不能反过来"的论证**：为什么 Linux 不能做得像 xv6 一样简单，为什么 xv6 的简化在真实硬件上会崩，为什么 JOS 的用户态文件服务在生产里要靠 FUSE/io_uring 之类的形态复活。

**入口（本文的读法）**：同一件事（让用户程序跑起来），在三种**约束**下长出三种形状。所以本文换的是**约束**，不换的是**问题**与**硬件那三样材料**（特权级、地址映射、异步通知）——三家都用这三样，差别只在用法与代价。

**不换的是什么**：目标不变，硬件的机制类别也不变（没有哪家发明出第四种保护手段）。**所以看到任何差异，先问"这是哪条约束挤出来的"，而不是"哪家设计得更好"。**

## 二、为什么这样做（功能设计）

**取舍一：为什么必须从 CPU 架构讲起。** 内核代码的形状由硬件契约决定，而不是由"设计品味"决定。x86 32 位有分段、有四层环、有 TSS 提供内核栈，所以 JOS 的陷入路径里必然出现 `TSS.esp0`；RISC-V 没有分段、只有 U/S/M 三态，所以 xv6 的陷入路径里必然出现 `sscratch` 与 `stvec`；x86-64 用 `syscall/sysret` 与 `swapgs`，所以 Linux 的快速路径和中断路径是两套代码。**不先讲这一层，后面的 API 差异就变成"风格问题"。**

**取舍二：为什么按维度横切，不按系统纵切。** 按系统讲会写成三份导读，读者记不住任何一条；按维度横切（进程抽象、地址空间、陷入、调度、文件、设备）才能看出"同一格里的三个答案"。每一章固定四问：**这格要解决什么 → 硬件给了什么材料 → 三者各怎么解 → 换约束会怎样**。

**取舍三：为什么选这三个而不是别的一对。** 它们在同一谱系上但规模跨三个数量级：xv6 是 Unix V6 的直系后代（抽象最纯），JOS 在 xv6 的问题上多走一步（用户态文件服务、IPC rendezvous、COW），Linux 把同一批抽象推到工业强度。选它们能形成"最小 → 加一层 → 加满"的坡道；选两个教学内核看不出规模效应，选两个生产内核看不出教学取舍。

**取舍四：不做什么。** 不做 Linux 源码导读（不逐函数讲 `do_fork`）；不做发行版与配置；不做性能调优；不复述 `../jos/` 与 `../linux-api/` 已有的内容，只给"为什么不一样"。

## 三、章节大纲

**第 1 章 三种出发点。** 教学目标（机制可见、可验证、一学期做完）/ 教学复现（Unix 抽象最小闭环）/ 生产（兼容、可移植、可扩展）。把"代码量级差三个数量级"翻译成具体的取舍：要不要 SMP、要不要 ABI 稳定、要不要支持热插拔。

**第 2 章 CPU 起点：分段、分页与地址翻译。** x86 32 位的段 + 两级页表；RISC-V 的 Sv39 三级页表与 `satp`；x86-64 长模式（分段基本废除）与四级/五级页表。**关键点：地址翻译的级数与寄存器（CR3 / satp）决定了内核怎么切换地址空间，也决定了 TLB 冲刷的成本模型。**

**第 3 章 特权级与陷入路径。** JOS：`int 0x30` → IDT → `T_SYSCALL` → `Trapframe`，内核栈来自 TSS 的 `esp0`。xv6：U→S 的 `ecall` → `stvec` → `sscratch` 换栈 → `usertrap`。Linux：`syscall` 指令 → `MSR_LSTAR` 指定的入口 → `swapgs` 换 per-CPU 基址，与中断路径（IDT）**分成两套**。三者都回答了同一件事：进入内核的第一条指令之前，硬件替你做了什么、没做什么。

**第 4 章 进程抽象：字段即世界观。** `struct Env` / `struct proc` / `struct task_struct` 的字段对比：谁存 `Trapframe`、谁有独立内核栈、谁有 `mm`、谁有 `cred`、谁有调度类。**一个内核认为"什么该跟着进程走"，看它的结构体最清楚。**

**第 5 章 地址空间管理。** JOS 的 `UPAGES/UVPT/UTOP` 技巧（内核数据映射进每个用户页表，用户态可读页表）；xv6 的 `trampoline`（因为切 `satp` 时指令必须在新旧页表都映射的地址上）；Linux 的 `mm_struct` + VMA 红黑树 + 缺页驱动（先建描述、后按需分配）。三种"谁负责建立映射"的答案：显式系统调用 / 内核统一建 / 缺页时按描述建。

**第 6 章 调度与同步的复杂度阶梯。** JOS：大内核锁 + 关中断，够验证；xv6：`spinlock` + `sleeplock` 两层 + `sleep/wakeup`；Linux：CFS/EEVDF + per-CPU + RCU + 抢占内核。**同步机制的复杂度几乎完全由"有没有 SMP"和"能不能在原子上下文睡眠"这两条决定。**

**第 7 章 系统调用 API 的形状。** 三张表：调用序号与入口、错误约定（负数 `-E*` / `-1` + `errno`）、用户指针校验（`user_mem_assert` / `copyin,copyout` / `copy_from_user`）。再讲为什么 JOS 敢用同步 rendezvous 做 IPC、而 Linux 必须提供 pipe/socket/shm 多套。

**第 8 章 文件系统与设备的组织。** JOS：用户态 FS 进程 + IPC（故障域小、路径长）；xv6：内核内 inode + 块缓存 + 日志（最小崩溃一致闭环）；Linux：VFS + 页缓存 + 具体文件系统 + 设备模型。设备层细节指向 `../drivers/`。

**第 9 章 为什么 Linux 必须长成这样。** 四条硬约束：ABI 稳定（不能重命名系统调用、不能改结构体布局）、可移植（`arch/` 抽象 + 条件编译）、驱动生态（外部代码依赖内部 API，但不能随意变）、SMP 与规模（RCU、per-CPU、无锁读）。以及"教学最小性在生产中不可行"的具体反例。

**第 10 章 反向借鉴：把东西搬回用户态。** FUSE（文件系统在用户态）、io_uring（把系统调用批量化）、DPDK/SPDK（驱动在用户态轮询）、microVM——JOS 的"用户态服务 + 共享内存页"思路在生产里以另一种形态复活。这一章回答"什么时候该回到最小设计"。

## 四、不做什么 · 必要性 · 失效点

### 4.1 必要性：对比的三列，删掉哪一列会怎样

- 删掉「CPU 架构」这一层 → `TSS.esp0`、`sscratch`、`swapgs` 为什么必须出现就说不出来，API 差异退化成"风格问题"。
- 删掉「出发点」这一列 → 只剩机制清单，回答不了"为什么不能反过来"。
- 删掉「不能反过来」的论证 → 对比滑成"谁更好"的范畴错误。
- 三者是递推关系：**架构给材料 → 出发点给选择规则 → 反证给边界**，缺任一层后面都接不上。

### 4.2 失效点：这套对比在哪里不成立

- **量级不可比**：万行对千万行，任何"谁更快 / 谁更简单"的结论都无效（本文因此不做性能对比）。
- **版本漂移**：Linux 的具体实现随版本变，稳定的只有结构与约束；引到具体函数时必须标版本。
- **架构混用**：xv6 有 x86 与 RISC-V 两版，用 RISC-V 版解释 x86 现象会错（`sscratch` 对应不上 `TSS.esp0`）。
- **教学简化 ≠ 生产不可行**：JOS 的用户态文件服务在生产以 FUSE / io_uring 复活，"教学里这样做"不能直接推"生产不该那样做"。

### 4.3 不做什么（范围）

**不做 Linux 源码导读。** 不逐函数讲 `do_fork`、`copy_process`、`do_mmap`；只讲结构与约束。

**不做发行版与配置。** 不涉及 systemd、包管理、内核参数调优；`../linux-api/` 已覆盖可观测与调参。

**不做性能调优。** 不比较三者的吞吐与延迟（量级不可比，口径无法统一）。

**不重复已有内容。** JOS 逐 lab 实现在 `../jos/`；用户态 API 用法与症状在 `../linux-api/`；设备驱动机制在 `../drivers/`。本文只保留"为什么不同"。

**不写哪个更好。** 三个系统解决的是不同问题；说"xv6 比 Linux 简单所以更好"是范畴错误。

## 五、面试怎么讲

**30 秒版本**（开场直接说，140–180 字）

> 我把 JOS、xv6、Linux 当成同一问题的三个答案来准备：出发点不同，所以硬件契约用到的部分不同，机制形状也就不同。JOS 为教学可验证，用一把大内核锁、用户态文件服务、同步 IPC；xv6 为复现 Unix 抽象，内核内 inode 加日志；Linux 为兼容与扩展，必须 ABI 稳定、支持多架构与 SMP，于是有 per-CPU、RCU、VFS 与设备模型。我能对着同一格（比如"陷入"或"进程结构体"）把三个答案和背后的约束讲清楚，也能说明为什么不能把其中一条直接搬到另一条上。

**可能被追问的 8 个点**

1. **「JOS 为什么用 `int $0x30` 而不是 `syscall` 指令？」** → 考点：硬件能力与教学取舍。
   → 答法：JOS 跑在 32 位 x86 上，`syscall` 是 64 位长模式的指令（32 位下是 `sysenter`，语义与兼容性都更绕）；软中断一条路径就能覆盖系统调用、异常与设备中断，教学上省掉两套入口。代价是慢（要走 IDT、要做权限检查），生产内核因此把系统调用单独做成快速路径。

2. **「xv6 的 `trampoline` 是干什么的？为什么必须有？」** → 考点：切页表时的地址连续性。
   → 答法：陷入内核要先切到内核页表（改 `satp`），**切完的下一条指令必须在新旧页表里映射到同一物理地址**，否则立刻缺页。`trampoline` 就是这样一个"两边都映射"的页，里面放切页表与 `sret` 的代码。这正是"地址翻译机制决定内核代码形状"的最直接例子。

3. **「Linux 为什么把系统调用和中断做成两套入口？」** → 考点：成本与状态切换。
   → 答法：`syscall` 指令直接跳到 `MSR_LSTAR` 指定的地址，省掉 IDT 查表；但它只保存最少的寄存器状态，需要 `swapgs` 换 per-CPU 基址，且不像中断那样有完整的硬件栈帧。所以系统调用走快速路径，中断/异常走 IDT 完整路径；两条路径的保存/恢复代码不同，这也是"信号与系统调用交互"复杂度的来源之一。

4. **「为什么 JOS 的文件系统在用户态，而 xv6 在内核里？」** → 考点：故障域与路径长度的取舍。
   → 答法：JOS 把 FS 做成用户态进程，客户端通过 IPC 请求、通过页映射共享数据——文件系统崩溃不会拖垮内核，但每次操作要两次上下文切换。xv6 追求最小闭环，直接在内核里做 inode/块缓存/日志，路径短但故障域等于整个内核。Linux 选内核内 VFS + 页缓存，因为性能与一致性要求压倒隔离收益；想做隔离就用 FUSE，代价是延迟。

5. **「JOS 的 IPC 和 Linux 的 pipe 有什么本质区别？」** → 考点：消息语义 vs 流语义。
   → 答法：JOS 是**同步 rendezvous**：发送方必须等到接收方登记、可附带一页映射，天然有消息边界，也天然会阻塞。pipe 是**有界字节流**：有缓冲区、有 fd 生命周期、有阻塞与非阻塞两种语义，但没有消息边界（要靠上层协议划分）。pipe 可以建在 IPC 上，反过来不行。

6. **「xv6 的 `sleep/wakeup` 和 Linux 的等待队列差在哪？」** → 考点：丢失唤醒与扩展性。
   → 答法：xv6 用"持锁检查条件 → 睡眠"的顺序避免丢失唤醒，唤醒方遍历 `proc` 表找匹配的 `chan`，复杂度与进程数成正比。Linux 把等待项挂到队列上，唤醒方摘链，支持多等待者、优先级与超时，也能配合 `wake_up_process` 做选择性唤醒。**同一个正确性要求，规模不同解法就不同。**

7. **「为什么 Linux 不能像 xv6 那样"简单"？」** → 考点：约束意识。
   → 答法：四条硬约束——ABI 稳定（系统调用号与结构体布局不能变）、可移植（同一份代码适配几十种架构）、驱动生态（外部模块依赖内部 API）、SMP 规模（要 RCU、per-CPU、无锁读）。任意一条都会把"最简实现"推翻；把它们同时满足，复杂度就是必要成本而不是设计失误。

8. **「你更愿意在哪种内核上做开发？」** → 考点：判断力而不是站队。
   → 答法：**看要验证什么**。要验证机制本身（页表、陷入、COW、调度），xv6/JOS 的反馈循环短得多，一个 `make qemu` 就能看到全部代码；要交付可用系统，Linux 的驱动、文件系统、可观测性无可替代。把教学内核当"玩具"或把 Linux 当"唯一正确"都是误判。

**别说什么**

- **「Linux 就是复杂版的 xv6。」** 这会把约束差异抹平；被追问"那 `task_struct` 里为什么有 200 多个字段"就答不上。
- **「JOS 的 IPC 比 pipe 高级。」** 语义不同不是高下之分；同步会合在需要消息边界时更好，在需要吞吐时更差。
- **「xv6 的代码写得比 Linux 干净。」** 规模差三个数量级，可维护性的约束完全不同；这句话会暴露没读过大项目。
- **报三个系统的性能对比。** 硬件、负载、配置都不同，任何数字都不可比；要比就比机制成本（几次上下文切换、几次拷贝）。
