# os/ · 操作系统与系统 API

> 分组目录：把「自己造内核」「用真实内核」「看三者为什么不同」「设备层怎么接」「边界怎么被跨过」放在一起。五个子项目各自两件套，本文只做路由，不复制正文。

## 一、这个目录是什么

同一台机器的五层视角：

| 子项目 | 站在哪一层 | 回答什么 |
|---|---|---|
| `os/linux-api/` | **用户态** | 用真实内核提供的 API，并把症状对回内核机制：进程/线程、内存（VSS/RSS/PSS、缺页与 OOM）、CPU 使用率、I/O 与 epoll、网络（`ss -i`、TIME_WAIT）、信号与定时器；附录 A 给 macOS/Windows 的四条关键差异 |
| `os/jos/` | **内核态（自己写）** | 一个能跑用户进程的内核：引导、页表与地址转换、用户环境与陷入、COW fork、抢占调度、IPC、fork/exec、用户态文件系统 |
| `os/kernel-compare/` | **横向对比** | JOS / xv6 / Linux 为什么长得完全不同：CPU 架构给了什么材料 → 内核形状 → API 形状；含系统调用 API 对照表与"为什么不能反过来"的论证 |
| `os/drivers/` | **设备层** | 驱动到底在做什么：用 JOS 的 IDE 盘（PIO + 轮询）与 e1000 网卡（MMIO + DMA + 中断）把"找设备 / 配置 / 搬数据 / 处理完成"四步走完，再对照 Linux 的五层配套 |
| `os/security/` | **边界与对抗** | 权限边界怎么被跨过：内存破坏 → 原语（读/写/调用/跳转）→ 控制流劫持 → ROP → 内核提权 → 侧信道；以及外挂/反作弊这条"同一组原语、不同获取方式"的对抗线 |

一句话定位：**`linux-api` 是你天天用的那一侧，`jos` 是你自己造的那一侧，`kernel-compare` 解释两者为什么不同，`drivers` 解释硬件怎么被接进来，`security` 解释这些边界里的哪一条会被跨过、靠什么跨、被什么挡住。** 面试里最值钱的不是任一层知识点，而是层与层对不上的地方——`top` 显示 380% 到底在说几个核、epoll 边缘触发为什么会丢事件、描述符环的 `tail` 归谁、为什么 `copy_from_user` 不能省、为什么 NX 迫使攻击者去拼 ROP。

**入口（本文的读法）**：在 CPU 特权级、页表、内核对象与设备队列这四类约束下，把任意症状定位到「哪层实现、哪层绕过」。换的是 API 名、结构名、驱动路径与攻击原语，不换的是同一条从用户调用到寄存器 / 页表 / 队列的落点链。

**不换的是什么**：全程不变的是陷入入口（`CS/SS` selector、`RIP/RSP`、`TSS RSP0`、`syscall/sysret` 或 `int/iret`）、地址转换（`CR3` + 页表项 `U/R/W/NX/P`）、系统调用分发（syscall number → dispatch table → `task_struct`/`Env`/fd table）、队列所有权（descriptor ring 的 head/tail 由软件或硬件哪端推进）、完成通知（IRQ/EOI 或轮询状态位）和对象生命周期（引用计数、fd 表、inode/socket 状态机）；因此看到差异先问：它是否改变了“谁推进 head/tail、谁设置页表权限位、陷入时 RIP/RSP 来自哪里、syscall number 落到哪个分发表、数据经过哪个 buffer/descriptor”。

**积木**：①`syscall`/`sysret` 与 `MSR_LSTAR`/`MSR_STAR`/`MSR_FMASK` 保存 `RIP/RSP/RFLAGS/CS/SS`；它能独立验证用户态陷入内核时 `RIP` 是否从 `MSR_LSTAR` 进入、返回时 `RFLAGS` 是否被 `MSR_FMASK` 清零。②`CR3` + `PTE.P/U/R/W/NX` + `CR2` + `PFEC`；它能独立验证 CPU 是否按页表权限位拒绝访问并把故障地址写入 `CR2`。③PCI BAR + MMIO 寄存器偏移 + 描述符环 `head/tail` + `DD` 完成位；它能独立验证 e1000 收包时 CPU 与 DMA 对描述符的写所有权是否由 `tail` 与 `DD` 标记。

**最小情形**：单核单线程执行一次 `read(fd, buf, 1)`：`syscall` 把用户 `RIP/RSP` 切换到 `TSS.rsp0`/`RSP0` 指向的内核栈，内核用 `task_struct`/`Env` 查 `fd table`，`copy_to_user` 写 `buf`，`sysret` 返回；此情形下 `smp_call_function`、`TLB shootdown IPI`、`spinlock_irqsave`、`per-CPU runqueue`、`RCU`、`epoll 边缘触发`、`e1000 RSS 多队列` 均不触发。

**生成**：累加 单线程一次 `read` 到多线程 `fork/exec/exit` 与多核 `schedule`，新增 `task_struct->rcu`、`mm->mmap_sem`、`rq->lock`、`TLB flush`、`COW 引用计数`；覆盖 `syscall number`、`dispatch table`、`Env/task_struct`、`CR3/PTE`、`descriptor ring head/tail`、`IRQ/EOI` 的落点；最坏情形 `copy_from_user` 遇到用户指针跨页缺页、NX 页执行、e1000 DMA 与 CPU 同时写描述符、ROP 覆盖返回地址，触发 `CR2`、`PFERR`、`DD`、`RIP/RSP` 改变。

**两边**：用户态现场 / 内核栈上的 trapframe：用户态持有 `RIP/RSP/RAX` 与 `CS/SS` selector；内核持有 `pt_regs`/`Env->env_tf` 与 `TSS.rsp0`。

## 二、为什么这样分组（功能设计）

**取舍一：分成两份而不是合成一份。** 两者的判据根本不同。`jos` 的判据是**你写的代码能不能通过 lab 的检验**（页表映射对不对、陷入现场是否精确、COW 引用计数是否平衡），错一次程序就崩；`linux-api` 的判据是**你能不能用一个命令或一个系统调用解释真实症状**（380% 是哪几个字段、`ss -i` 里哪个计数在涨）。合成一份文档会让"实现正确"与"解释正确"互相稀释。

**取舍二：为什么 `jos` 不放进 `cpu/`。** `cpu/` 管的是硬件怎么执行指令（流水线、乱序、cache、时序），`os/` 管的是软件怎么使用硬件提供的机制（页表、特权级、陷入、调度）。两者的交集只有一处——MMU 与 TLB——而那一处在两边都只讲到自己需要为止：`cpu/riscv-core/` 明确不做 MMU，`os/jos/` 把页表当既定设施来用。

**取舍三：为什么不把 `csapp/` 也拉进来。** CSAPP 是"从位到并发"的整机视角，是另外几条线的**公共语言**；放进 `os/` 会把它降级成 OS 的下游，反而削弱它作为入口的价值。它留在顶层单列。

**取舍四：为什么加 `kernel-compare`，而不把对比塞进 `jos` 第 10 章。** `jos` 里已经有一章对照，但那是"站在 JOS 里往外看"；真正的差异要在**CPU 架构**这一层就拉开——x86-32 有分段、四环与 TSS，RISC-V 只有 U/S/M 三态与 `sscratch`，x86-64 用 `syscall` + `swapgs`。不把这一层单独讲，后面的 API 差异会被误读成"风格"。**对比需要自己的篇幅，因为它有三个主角。**

**取舍五：为什么驱动单独成项目，而不是并进 `jos` 的文件系统章。** 文件系统是"块之上的逻辑"，驱动是"块是怎么从硬件来的"；混在一起会变成"两步都讲一半"。而且驱动必须讲 Linux 的配套（设备模型、DMA API、中断上下半部、NAPI），这些不属于 JOS 的任何一章。

**取舍六：为什么安全单独成篇，而不是散在 `jos` 的驱动章或 `linux-api` 的权限章。** 安全的核心不是"某个系统调用的注意事项"，而是**跨边界的因果链**：一个内存错误 → 一类原语 → 一次权限跨越。这条链横跨进程内、内核、设备三层，任何单个子项目都装不下。而且这一块知识双用途，**必须集中把边界写清**（只在自己拥有或授权的环境实验、不给可用利用与绕过步骤），散着写最容易变成教程。

**分组只做路由**：五个子项目仍各自五段、各自判据；本文只负责顺序、口径与跨项目追问。

## 三、推荐顺序与判据

**先用户态 → 内核态 → 横向对比 → 设备层 → 安全。** 理由不是难度，而是**面试权重与反馈速度**：`linux-api` 的每一条都能在十分钟内用一个命令验证，且是线上问题的第一现场；`jos` 的每个 lab 都要真调通才有价值；`kernel-compare` 建立在两边都有画面之后（没写过内核就对不出差异）；`drivers` 是设备层的延伸；`security` 排最后，因为它要求你已经知道"边界在哪"——不知道页表、特权级与 `copy_from_user` 在做什么，就讲不清一次越界到底跨了什么。

> 若目标是**内核/驱动岗**，把 `drivers` 提前到 `jos` 之后立刻读——设备层的问题是这类岗位的主战场。

| 阶段 | 内容 | 判据 |
|---|---|---|
| 1（必做） | `linux-api/` 的 CPU、内存、I/O 三块：`top`/`ps` 字段口径、VSS/RSS/PSS、缺页与 OOM killer、`ss -i` 与 TIME_WAIT | 给一个真实症状，能在十分钟内定位到具体机制与具体字段 |
| 2（必做） | `linux-api/` 的进程与信号、epoll（水平/边缘触发差异与丢事件原因） | 能说清"边缘触发必须配非阻塞 + 读到 EAGAIN"的因果，而不是背结论 |
| 3（建议） | `jos/` 的页表 + 陷入 + COW 三块 | 能画出一次缺页的完整路径：硬件 → 陷入 → 内核 → 页表项 → 返回；能解释 COW fork 后父子进程的 PTE 状态 |
| 4（加分） | `jos/` 的调度与 IPC、fork/exec、文件系统 | 能说清进程创建/销毁的资源账本，以及一次 `exec` 前后地址空间发生了什么 |
| 5（建议） | `kernel-compare/` 的陷入路径、进程结构体、地址空间、API 对照四格 | 对着同一格（如"陷入"）能说出三家的硬件契约与代码形状，并解释为什么不能互换 |
| 6（看岗位） | `drivers/` 的 IDE PIO → 块缓存 → 文件布局，e1000 描述符环 → 收包路径 | 能画出一次块读与一次收包的所有权时间线；能指出 JOS 的某段代码在 Linux 里被拆成哪几层 |
| 7（建议） | `security/` 的原语框架、ROP 的三段式栈布局、缓解机制的"假设—违反"表、内核链条的三道加固 | 任给一个漏洞描述，能说出跨哪条边界、需要几个原语、被哪个机制挡住；能解释外挂与 ROP 在"能力 vs 权限"上的区别 |

**一条硬判据**：任何结论都要能落到「一个命令 + 一段输出」「一次 lab 通过」或「一条所有权时间线」。落不上去的，是背来的。

## 四、不做什么 · 必要性 · 失效点

### 必要性：删掉会怎样

| 机制 | 删掉会怎样 | 判定 |
|---|---|---|
| 页表与地址转换 | JOS 的用户环境无法把虚拟地址翻译成物理页，缺页处理找不到 PTE，lab 的页表映射检查破 | 必需 |
| 用户环境与陷入 | 系统调用没有跨特权级的现场保存/恢复，返回时 EIP/EFLAGS 或寄存器被破坏，用户环境崩溃 | 必需 |
| COW fork | 父子进程写同一页不触发缺页复制，COW 引用计数不平衡，fork 共享页的 lab 检查失败 | 必需 |
| copy_from_user | 内核直接解引用用户指针，缺页与权限边界丢失，系统调用会把用户态地址当内核地址访问并崩 | 必需 |
| 描述符环的 `tail` | e1000 网卡的收包路径无法判定 CPU 与 DMA 的写所有权，描述符会被重复写或跳过，`处理完成` 这一步不成立 | 必需 |
| TIME_WAIT | 网络章节无法解释主动关闭后的端口复用与 `ss -i` 计数，Linux API 症状归因少一条；JOS 不依赖 TCP 状态机，可后补 | 选择 |

### 失效点：哪条前提一破，结论就变

- 核数：单核 JOS 变为多核 Linux → `top` 的 380% 必须拆成 per-CPU 字段，JOS 的抢占调度与 Linux 的 `epoll` 唤醒需要按 CPU 运行队列和 TLB 一致性重新检查。
- 介质：IDE 盘 PIO + 轮询变为 e1000 网卡 MMIO + DMA + 中断 → 驱动四步中的“搬数据”从 CPU 读寄存器变成 DMA 写描述符环，`tail` 所有权与中断处理完成成为判据。
- 协议版本：TCP 正常关闭保留 TIME_WAIT 变为 `SO_LINGER` 跳过 TIME_WAIT → `ss -i` 的 TIME_WAIT 计数不再解释端口复用，网络章节的主动关闭等待结论失效。
- 权限位：页表 U/S 位与 `copy_from_user` 边界存在变为缺失 → 用户环境与陷入不再能挡住内核访问用户指针，内存破坏可直接跨过系统调用边界。
- 时钟源：TSC 变为 HPET/ACPI timer → 信号与定时器超时精度、CPU 使用率采样间隔和缺页/OOM 事件时间线需要重新校准。

### 不做什么（范围）

**不写完整操作系统。** 不做完整文件系统（日志、崩溃一致性）、不做网络协议栈——`jos` 只到能把用户进程跑起来；协议栈那条线（原 CS144）已下线，不重建。块设备与网卡的**设备层**细节归 `drivers/`，这里不重复。

**不做内核模块开发主线。** 写一个字符设备驱动能讲清 `file_operations`，但那属于驱动工程，不是操作系统原理；`drivers/` 只讲机制与判据，不写可加载模块。

**不做容器与虚拟化的实现。** namespace 与 cgroup 的原理可以讲（它们本质是内核对象的视图与配额），但不做 runc/CRIU 级别的实现。

**不移植 Linux。** 那是另一条线（且与 `cpu/riscv-core/` 明确分工：那边不做 MMU）。跑 Linux 需要的特权级、中断、原子指令是"换项目"级别的投入。

**不做发行版运维。** 包管理、systemd、发行版差异一律不涉及。

**安全只讲机制，不给可用利用与外挂实现。** `security/` 不写 shellcode、不给具体偏移与 payload、不针对任何商业游戏或反作弊产品提供绕过步骤；也不做纯 Web/业务安全（SQL 注入、XSS 那类属于应用层）。实验限定在自己写的程序或公开 CTF 环境。

## 五、面试怎么讲

**30 秒版本**（开场直接说，120–170 字）

> 操作系统这块我按四层准备：用户态这侧我能把一个线上症状（CPU 380%、OOM、连接建立慢）在十分钟内定位到具体机制和具体字段；内核态这侧我自己写过页表、陷入和 COW fork；横向能把 JOS、xv6、Linux 的同一格放在一起讲，并说清差异来自 CPU 架构给的什么材料；设备层能画出块读与收包的所有权时间线，也说得清 Linux 把它拆成了哪几层。四层连起来的价值是：看到指标能想到内核里哪段代码在动，看到内核结构也知道它在用户态长什么样。

**可能被追问的 7 个点**

1. **「`top` 里一个进程 380% 是什么意思？」** → 考点：CPU 使用率的分母与按核累加。
   → 答法：`%CPU` 是**单核为 100%** 的口径，多线程进程可超过 100%，380% 约等于占满 3.8 个核；判据是与 `nproc` 比、与 `ps -L` 的单线程分布比。边界：容器里读到的可能是宿主机的核数，要先确认 cgroup 配额（`cpu.max`）。

2. **「RSS 和 PSS 差在哪，为什么容器内存统计要用后者？」** → 考点：共享页的归属。
   → 答法：RSS 把共享库与共享内存按**整份**计入每个进程，PSS 按**共享者数量均摊**，所以多进程共享大量只读页时 RSS 之和会远大于物理占用。判据：`/proc/<pid>/smaps_rollup` 里的 `Pss`。边界：页被换出后 RSS 会降，但虚拟大小不变。

3. **「minor 与 major 缺页的区别，为什么前者便宜？」** → 考点：缺页的两条来源。
   → 答法：minor 缺页**内存里已有页**（页缓存、COW、已映射但未建 PTE），只需补页表项；major 缺页要**读磁盘/设备**。判据：`/proc/vmstat` 的 `pgfault`/`pgmajfault`，或用 `perf stat` 的 page-faults 事件。边界：COW 触发的是 minor，但写时复制本身有拷贝成本。

4. **「epoll 边缘触发为什么必须配非阻塞？」** → 考点：事件语义与"读干净"的要求。
   → 答法：边缘触发只在**状态变化**时通知一次，如果你没把数据读干净，内核不会再通知，事件就"丢"了；因此必须循环读到 `EAGAIN`，而读到 `EAGAIN` 的前提是 fd 非阻塞。水平触发则是"只要还可读就一直通知"。判据：`strace` 看 `epoll_wait` 与 `read` 的返回；边界：边缘触发 + 非阻塞 + 读到 EAGAIN 三者缺一就会出现"连接卡住但 CPU 空闲"。

5. **「TIME_WAIT 多了会怎样，怎么处理？」** → 考点：主动关闭方的状态机与端口耗尽。
   → 答法：TIME_WAIT 出现在**主动关闭方**，持续 2MSL，作用是保证最后一个 ACK 可重传、并让旧连接的残余报文在网络中死亡。大量短连接会让本地端口耗尽（`EADDRINUSE`）。判据：`ss -tan state time-wait | wc -l`、`net.ipv4.ip_local_port_range`。边界：`tcp_tw_reuse` 只在特定条件下安全，`tcp_tw_recycle` 在现代内核已移除——不要说"打开 recycle 就行"。

6. **「写时复制 fork 的页表项在 fork 那一刻是什么状态？」** → 考点：COW 的实现细节。
   → 答法：父子共享同一物理页，**双方的 PTE 都被改成只读**并标记 COW，引用计数加一；任何一方写触发保护缺页，内核复制一页、改回可写、减计数。判据：`jos` 的 lab 通过；用户态可用 `/proc/<pid>/smaps` 观察 `Shared_Clean` 与 `Private_Dirty` 的变化。边界：`vfork`/`posix_spawn` 走的是不复制路径，别混。

7. **「缺页处理时为什么不能睡眠，或者什么时候可以？」** → 考点：陷入上下文的约束。
   → 答法：缺页处理本身**需要睡眠**（要读磁盘、要等 I/O），所以它必须在一个可以睡眠的上下文中执行；这也是为什么缺页不能发生在中断上下文、以及在持有自旋锁时访问用户地址是 bug（`copy_from_user` 在原子上下文会告警）。判据：内核日志里的 `BUG: sleeping function called from invalid context`。边界：`jos` 的教学内核里没有这些严格区分，讲的时候要说明是简化模型。

**别说什么**

- **「我写过操作系统。」** 追问"你的调度器怎么处理优先级反转""页表几级、每级多少项"就崩。要说清做到哪一层：页表 + 陷入 + COW，还是连调度与 IPC 都做了。
- **「RSS 就是进程占的内存。」** 一句话暴露出没看过 `smaps`；共享页的归属必须说清。
- **「epoll 比 select 快。」** 没有事件复杂度与就绪队列的解释，这只是口号；且在小 fd 数下差异可以忽略。
- **报没测过的数字。** "优化后 QPS 提升 X 倍"必须带口径（并发数、请求分布、机器规格），否则不如说"我能给出复现路径"。
