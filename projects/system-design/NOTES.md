# system-design · 分章详细

## 第 1 章 从需求到约束：QPS、存储、延迟的量级估算

**要解决的问题**：把「日活一千万、要做个短链」这类模糊需求，换算成可比较的数字——峰值 QPS、存储总量、延迟预算，从而决定要不要缓存、要不要分片、要不要削峰。不做这一步，后面的选型全靠偏好，面试官一句「为什么这里必须上 Redis」就答不上来。

**机制**：核心是三条换算链，全部用心算量级而非精确值。

一是流量。日请求量除以一天的秒数得到均值 QPS，再乘峰值系数得到峰值 QPS。工程上常用的近似是「80% 的流量集中在 20% 的时间」，即峰值约为均值的 4 倍；实际业务曲线在 2~5 倍之间，按场景取。

二是容量。存储 = 行数 × 单行字节 × 副本数 × (1 + 索引膨胀)，再乘保留期。索引膨胀按实现而定，B+ 树二级索引通常让总占用涨一截，估算时留系数即可。

三是并发与延迟。用 Little's Law：在途并发 ≈ 到达率 × 平均停留时间，也就是 `并发 = QPS × 延迟`。这个数决定线程池、连接池、限流阈值的量级。延迟预算则是把一次请求的总预算按跳切分，每跳单独核算。

```text
daily_req   = DAU * req_per_user
avg_qps     = daily_req / 86400
peak_qps    = avg_qps * peak_factor          # 2~5，二八原则取 4
concurrency = peak_qps * p99_latency_s       # Little's Law
storage     = rows * row_bytes * replicas * (1 + index_overhead)
bandwidth   = peak_qps * resp_bytes

if peak_qps > single_node_capacity: 加缓存 / 分片 / 削峰
if storage  > single_instance_disk: 分库 / 冷热分离 / 归档
```

关键是最后两行：估算不是为了报数字，是为了得出「约束」。约束一旦成立，后面的方案就是被推出来的，而不是选出来的。

**最小例子**：一个短链系统，日新增 1000 万条，读写比 100:1，单条记录约 500 B（长链 + 短码 + 元数据），保留 5 年，三副本。

- 写：`1e7 / 86400 ≈ 116` QPS 均值，峰值 ×4 ≈ **460 QPS**，单库可承受。
- 读：`460 × 100 ≈ 46000 QPS` 峰值。单机 MySQL 点查通常在万级以下（按硬件与命中率而定），这里明显超了，结论是**读路径必须加缓存**。缓存命中率 95% 时回源约 2300 QPS，回到单库可承受区间。
- 存储：`1e7 × 500B = 5 GB/天`，5 年约 `5 × 365 × 5 ≈ 9.1 TB`，三副本约 **27 TB**，单实例放不下，结论是**必须分片或按时间冷热分离**。
- 带宽：`46000 × 500B ≈ 23 MB/s`，网卡不是瓶颈，可以排除。

一次估算直接产出两个决策：加缓存、做分片，而且每个都有数字支撑。

**面试高频问法**：

1. 「日活 1000 万的系统，QPS 大概多少？」→ 考点是换算链条是否完整，能否区分均值与峰值。→ 答法：「按人均 20 次请求算，日请求 2 亿，除以 86400 得均值约 2300 QPS，峰值按 4 倍算接近 1 万；再乘读放大和缓存回源比例，才得到真正压到 DB 上的量。」
2. 「为什么用 86400 和 4 倍？」→ 考点是这些常数从哪来。→ 答法：「86400 是一天的秒数，用来把日量摊成均值；4 倍来自二八原则，80% 流量在 20% 时间，等价于均值的 4 倍，实际业务按曲线在 2 到 5 倍之间取。」
3. 「并发数怎么估？」→ 考点是 Little's Law。→ 答法：「并发约等于 QPS 乘平均延迟，1 万 QPS 乘 50 毫秒就是 500 个在途请求，线程池和连接池按这个量级配，再留余量。」
4. 「什么时候才该分库分表？」→ 考点是能否先排除更便宜的方案。→ 答法：「先看单表行数和日增量，只有存储或写入真的顶到单实例上限才分；能靠加缓存、归档、冷热分离解决的先不做分片，因为分片会带来跨片查询和分布式事务的长期成本。」
5. 「延迟预算怎么分？」→ 考点是有没有把预算当约束用。→ 答法：「先定端到端预算比如 200 毫秒，按跳切给网关、服务逻辑、缓存、DB 各一段，留一半余量；哪一跳持续超预算就单独优化那一跳，而不是整体加机器。」

## 第 2 章 缓存：旁路、击穿、雪崩与一致性

**要解决的问题**：把热点读从数据库挪到内存，同时处理三个副作用——缓存与 DB 谁先写、单个热点 key 失效瞬间的回源风暴、大量 key 同时失效或缓存层整体不可用。不解决，DB 会被打挂，或者读到长期脏数据。

**机制**：默认模式是旁路缓存（Cache-Aside），读写路径不对称。

读：先查缓存，未命中再查 DB 并回填，回填时 TTL 加随机抖动。
写：**先写 DB，再删缓存**，而不是更新缓存。删而不更新的原因是并发下两次更新到达缓存的顺序不保证，可能用旧值覆盖新值；删除是幂等的，代价只是一次后续 miss。先写库再删缓存的原因是：若先删缓存再写库，删与写之间的读请求会把旧值回填，脏数据会一直留到过期；反过来最坏只是短窗口脏读，且能用延迟双删和 TTL 兜底。

三类异常各有对应手段：

- **击穿**：单个热点 key 过期，海量请求同时回源。用单飞（同一 key 只允许一个请求重建，其余等待或短暂重试）或逻辑过期（value 内自带过期时间，读到过期先返回旧值，后台异步刷新）。
- **雪崩**：大量 key 同时过期或缓存集群不可用。过期时间加随机抖动、多级缓存（本地 + 分布式）、限流降级、集群高可用与预热。
- **穿透**：查根本不存在的数据，缓存永不命中。缓存空值（短 TTL）或前置布隆过滤器。

```python
def get(key):
    v = cache.get(key)
    if v is not None:
        return v
    if not lock.try_lock(key + ":rebuild"):     # 单飞：只放一个请求回源
        sleep(small_ms); return get(key)
    try:
        v = cache.get(key)                       # 双检，防止锁等待期间已被回填
        if v is None:
            v = db.query(key)
            cache.set(key, v, ttl=BASE_TTL + rand(0, JITTER))
        return v
    finally:
        lock.unlock(key + ":rebuild")

def set(key, v):
    db.update(key, v)
    cache.delete(key)          # 先库后删；失败进重试队列，必要时延迟再删一次
```

**最小例子**：商品详情 key `item:1001`，商品改价时走「更新 DB → 删缓存」。设该 key 承载峰值 5 万 QPS，TTL 30 分钟并叠加 0~300 秒抖动。

不加保护时，TTL 到期的瞬间 5 万个请求同时未命中，全部打到 DB；若 DB 连接池只有 200，请求会排队直至超时，表现为「缓存一过期整站抖一下」。加上单飞后，同一时刻只有 1 个请求回源查 DB，其余要么短暂 sleep 后重试读缓存，要么返回逻辑过期里的旧值，DB 侧压力从 5 万降到个位数。抖动则保证不会有一批 key 在同一秒集体到期——这就是击穿和雪崩在同一个 key 上的分界：前者靠单飞解决「同一个 key」，后者靠抖动和降级解决「一批 key」。

写路径上，若删缓存失败，脏数据的最长存活时间等于 TTL 上限；业务要求更短的不一致窗口，就把 TTL 压到分钟级，并用 binlog 订阅异步补删。

**面试高频问法**：

1. 「为什么删缓存而不是更新缓存？」→ 考点是并发写乱序与收益。→ 答法：「更新缓存要保证两个并发写到达缓存的顺序和到达 DB 的顺序一致，否则旧值会覆盖新值；删除是幂等的，下一次读自然回填最新值，代价只是一次 miss。」
2. 「先删缓存还是先写库？」→ 考点是不一致窗口的大小。→ 答法：「先写库再删缓存。反过来，删和写之间若有读请求会把旧值回填，脏数据要留到过期；先写库最坏只脏很短一个窗口，还能用延迟双删和 TTL 兜底。」
3. 「缓存击穿怎么办？」→ 考点是回源是否被收敛。→ 答法：「对热点 key 做单飞或互斥重建，保证同一时刻只有一个请求查 DB，其余等待；或者用逻辑过期，先返回旧值、后台异步刷新，避免请求堆积。」
4. 「击穿和雪崩有什么区别？」→ 考点是失效范围。→ 答法：「击穿是单个热点 key 失效引发的回源风暴，靠单飞和逻辑过期；雪崩是一批 key 同时失效或缓存层整体不可用，靠过期时间加随机抖动、多级缓存、限流降级和集群高可用。」
5. 「缓存和 DB 的一致性怎么保证？」→ 考点是能否说清一致性级别。→ 答法：「一般不追求强一致，而是有界延迟的最终一致：写库后删缓存、TTL 兜底、binlog 异步补偿删除；要更强就让读也走同一把 key 锁，代价是吞吐下降。」

## 第 3 章 限流与降级：令牌桶、漏桶、滑动窗口

**要解决的问题**：当下游容量是固定的（DB 连接数、线程池、第三方配额），必须把进入系统的请求速率压到可承受范围；如果过载时不主动丢弃非核心流量，队列会堆积、RT 会上涨、线程会被占满，最终整条链路一起不可用。

**机制**：

限流器只做一件事——对每个请求判定“放行 / 拒绝”，有三种经典形状：

- **令牌桶**：桶容量 $b$，补充速率 $r$（token/s）。请求到来时先按经过的时间补令牌 $tokens = \min(b,\ tokens + r\Delta t)$，够 1 个就扣掉放行，不够就拒绝。它允许**不超过 $b$ 的突发**，长期均值被压到 $r$。工程上不用定时器，用「懒补充」：只在请求到达时按时间戳算一次增量，避免空转。
- **漏桶**：请求先入固定容量队列，出口以恒定速率 $r$ 流出，队列满则丢弃。它**不允许突发**，把流量整形为均匀输出；代价是引入排队延迟。
- **滑动窗口**：固定窗口（如每秒 100 次）在窗口边界会双倍放行。滑动窗口日志记录每条请求的时间戳，统计 $(now-W,\ now]$ 内的条数，超限即拒；内存是 $O(请求数)$，实际多用**滑动窗口计数**：把窗口切成 $N$ 个桶存环形数组，估算值 = 当前桶已计数 + 前 $N-1$ 个桶的全量，误差上界约 $1/N$。

分布式场景一般是**两层**：单机令牌桶做本地预限流（粗粒度、无网络开销），Redis/Lua 做全局配额；本地桶按「全局配额 / 实例数」分配，最坏误差上界约等于「实例数 × 本地桶容量」。

降级是限流之后的第二道措施策略：按等级分——读降级（返回缓存/默认值/空列表）、写降级（转异步、只落日志）、功能降级（关闭推荐、评论等非核心）、超时降级（快速返回兜底）。触发依据是错误率、RT 分位、线程池饱和度；开关由配置中心推送，自动触发要有半开探测恢复，避免一直停在降级分支里。

```lua
-- 令牌桶的懒补充（Redis 侧，rate 单位 token/s，now 单位 ms）
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or tonumber(ARGV[2])      -- capacity
local ts     = tonumber(b[2]) or tonumber(ARGV[3])
local delta  = math.max(0, tonumber(ARGV[3]) - ts)
tokens = math.min(tonumber(ARGV[2]), tokens + delta * tonumber(ARGV[1]) / 1000)
if tokens >= tonumber(ARGV[4]) then
  redis.call('HMSET', KEYS[1], 'tokens', tokens - tonumber(ARGV[4]), 'ts', ARGV[3])
  return 1
end
redis.call('HMSET', KEYS[1], 'tokens', tokens, 'ts', ARGV[3])
return 0
```

**最小例子**：

1）令牌桶 $r=100/s$、$b=200$，空闲 2s 后桶被补满 200 个。此刻 500 个请求同时到达：前 200 个立即通过，剩余 300 个在同一毫秒内被拒（令牌已耗尽）；再过 1s 左右才重新积累约 100 个令牌。换成漏桶 $r=100/s$、队列 200：200 个入队、300 个丢弃，出口严格 100/s，队尾大约 2s 后才被处理。

2）固定窗口 $W=1\text{s}$、上限 100：$t=0.99$s 放行 100 个，$t=1.01$s 又放行 100 个，跨边界 0.02s 内实际放行 200 个，是限额的 2 倍。换成滑动窗口日志，在 $t=1.01$s 统计 $(0.01,\ 1.01]$ 内已有 100 条，第 101 个请求直接被拒。

**面试高频问法**：

1. **令牌桶和漏桶到底差在哪？** → 考点在“是否允许突发”与“是否引入排队延迟”。→ 令牌桶按速率攒令牌、允许最多一桶的突发、只约束长期均值；漏桶以恒定速率流出、把突发整形成均匀流量，超过队列容量直接丢弃。
2. **固定窗口的临界问题怎么解？** → 考点是边界双倍放行。→ 用滑动窗口日志精确统计窗口内请求数，或用分桶的滑动计数以精度换内存，$N$ 越大误差越小。
3. **分布式限流为什么不干脆每个请求都走 Redis？** → 考点是热点 key 与 RT 成本。→ 每请求一次 Redis 会把限流器变成新的瓶颈，常用本地令牌桶预限流 + 全局配额兜底，并明确误差上界（实例数 × 本地桶容量）。
4. **限流、熔断、降级三者的边界？** → 考点是各自保护谁。→ 限流控入口速率、保护自己不被压垮；熔断看下游错误率、保护调用方不被拖死；降级是被限/被熔之后返回什么，是结果侧的兜底策略。
5. **被限流的请求怎么处理？** → 考点是有没有考虑排队反噬。→ 快速失败并给出明确语义（429 + Retry-After 或自定义错误码），绝不能默默排队等到超时；核心链路可转异步排队，非核心直接降级返回兜底值。

## 第 4 章 消息队列：至少一次、幂等与顺序

**要解决的问题**：用异步解耦生产者与消费者，但生产、broker、消费三段都可能失败、重试、重平衡，必须明确“消息会不会丢、会不会重复生效、会不会乱序”这三件事的语义与代价；不解决就会出现丢单、重复扣款、状态回退。

**机制**：

投递语义只有三种，且**投递语义和消费语义是两件事**：

- **at-most-once**：先 ack 再处理，或发后不管。快，但故障即丢。
- **at-least-once**：处理成功后才 ack/提交位点，失败或超时则重投。**代价必然是重复**。
- **exactly-once**：端到端恰好一次需要生产、存储、消费三方原子协同；工程上普遍的做法是 **at-least-once + 幂等消费**。MQ 自称的 EOS 通常限定在它自己的流处理链路内（消费位点、业务状态、下游生产在同一事务里提交），跨系统仍然做不到。

**不丢要三段都堵**：生产端等 broker 确认并重试（配合本地消息表或事务消息，避免“业务提交了但消息没发出去”）；broker 持久化 + 多副本（如 Kafka 的 `acks=all` 与 `min.insync.replicas`，具体默认值按实现与版本而定）；消费端**处理完再提交位点**，不能先提交后处理。

**重复的来源**：生产端超时重试（其实第一次已成功）、消费端处理完未 ack 就崩、rebalance 后位点回退重放。所以幂等不是可选项，是 at-least-once 的必备配套。三种常见做法：

1. **去重表**：`msg_id` 建唯一索引，插入冲突即视为已处理；去重记录与业务变更放在**同一个本地事务**里，保证“业务生效”和“记下已处理”同生共死。
2. **状态机 / 条件更新**：`UPDATE orders SET status='PAID' WHERE id=? AND status='CREATED'`，影响 0 行就说明重复或状态不允许，直接当成功处理。
3. **天然幂等写**：覆盖写、set 语义。Redis `SETNX` 只能当前置拦截，键过期或实例故障就会漏，最终仍要靠库上的唯一约束兜底。

**顺序**：全局有序等价于单分区单消费者，吞吐被锁死，绝大多数业务要的是**分区内有序**——按业务主键（如 orderId）哈希到同一分区，单分区串行消费。两个容易被忽略的破坏点：消费端用线程池并发处理会打破顺序，必须按同一 key 路由到固定 worker；失败重试若跳到别的分区或进重试队列后并行重投，也会乱序，所以通常原地重试若干次后进死信队列，宁可阻塞该分区也不乱序。

```text
consume(msg):
  begin tx
    insert into consumed(msg_id)        -- 唯一索引；冲突 → 回滚并 ACK，视为重复
    applyBusiness(msg)                  -- 条件更新 / 状态机校验，影响 0 行即幂等跳过
  commit
  ack(msg)                              -- 位点提交必须在事务提交之后
```

**最小例子**：

支付回调消息 `msg_id=pay_8891, order_id=O1001`，消费逻辑是“扣库存 + 订单置为已支付”。第一次消费成功，但 ack 前进程被杀；broker 重投。第二次消费时 `insert into consumed('pay_8891')` 命中唯一索引冲突 → 回滚事务并直接 ack，库存只扣一次。若换成条件更新方案：`UPDATE orders SET status='PAID' WHERE id='O1001' AND status='CREATED'` 第二次影响 0 行，同样不重复扣减。

顺序例：分区数 16，`hash('O1001) % 16 = 3`，该订单的「创建 / 支付 / 发货」三条消息都进 3 号分区串行消费，状态依次前进；若消费端把三条丢进线程池并发执行，“发货”可能先于“支付”被处理，订单状态回退——所以必须按 orderId 路由到固定线程。

**面试高频问法**：

1. **怎么保证消息不丢？** → 考点是有没有分环节回答。→ 三段堵：生产端等确认加重试（配本地消息表防“业务成功、消息丢失”），broker 持久化加多副本，消费端处理完再提交位点；代价就是会重复，所以必须配幂等。
2. **exactly-once 到底能不能做到？** → 考点是知不知道跨系统事务无法原子提交。→ 端到端做不到，工程解是 at-least-once 加幂等消费；MQ 宣称的 EOS 一般只覆盖它内部“消费—处理—再生产—位点”在同一事务域内的链路。
3. **幂等怎么做，放 Redis 够不够？** → 考点是可靠性边界。→ 落库的唯一索引或条件更新，与业务变更同事务；Redis SETNX 只能挡掉绝大多数重复，键过期或宕机就漏，不能作为唯一防线。
4. **怎么保证顺序？** → 考点是知道顺序的代价。→ 按业务主键哈希到同一分区、单消费者串行，消费端也按 key 串行；代价是热点分区、吞吐下降，重试要原地阻塞或进死信，不能换队列重投。
5. **消息积压了怎么办？** → 考点是定位顺序。→ 先判断是消费太慢还是毒消息反复重投：扩分区加消费者（注意这会改变顺序语义），临时降级非核心消费，毒消息进死信队列，而不是无限重试堵住整个分区。

## 第 5 章 分库分表与路由

**要解决的问题**：单库单表在数据量和写入吞吐上达到上限时，把数据水平拆到多个库表，并让业务代码不必关心数据落在哪一片。不解决，拆完之后每条 SQL 都要手写分片逻辑，跨片查询直接不可用。

**机制**：拆分两个维度。垂直拆按业务或按列拆（订单库、用户库），水平拆按行拆（同一张表按分片键散到 N 库 M 表）。真正难的是水平拆。

分片键是第一决策，标准三条：基数足够高、分布均匀、绝大多数查询都带它。订单表选 `user_id` 而不是 `order_id`，因为「我的订单列表」是主查询；选 `order_id` 会让按用户查退化成广播所有分片。

路由算法四种取舍：

- 范围分片：按时间或 ID 区间。范围查询、归档友好，代价是写入热点集中在最新区间。
- 取模分片：$shard = hash(key) \bmod N$。分布均匀，但 N 一变几乎全量迁移。
- 成倍扩容：库数按 2 的幂增长，从 N 扩到 2N 时旧库 i 的数据只可能落到新库 i 或 i+N，迁移量约一半。
- 预分片：一次建 1024 个逻辑分片，映射到少量物理库，扩容只搬逻辑分片、改映射表，路由算法不动。

路由执行位置三种：客户端 SDK 在进程内算分片、拼 SQL（少一跳网络，多语言支持差）；代理层解析 SQL 转发（对应用透明，多一跳）；数据库原生分区（受单机边界限制）。按团队与实现而定。

拆完必须面对四件事。全局唯一 ID：号段模式（DB 一次发一批缓存在内存）或雪花式（时间+机器号+序列，要处理时钟回拨）。跨分片 join：改冗余字段，或两次查询在应用层拼。深分页：各分片返回前 `offset+limit` 条在内存归并，再深就改游标分页。分布式事务：优先把关联表用同一分片键落库，让事务落在单库；必须跨片的走最终一致 + 对账补偿。

```python
def route(key, n_shards):            # 唯一路由入口，模数从配置读
    return hash64(key) % n_shards

def migrate(old_n):
    new_n = old_n * 2
    for i in range(old_n):
        for row in scan(f"db{i}"):
            t = route(row.key, new_n)
            if t != i:               # 只有一半数据要搬
                write(f"db{t}", row)
    # 迁移期间双写：写操作同时写 route(key, old_n) 与 route(key, new_n)
    # 之后按灰度比例切读、比对结果，全量切读后再停双写
```

**最小例子**：`order` 表 1 亿行，按 `user_id` 水平拆成 16 库 × 每库 4 表 = 64 个分片。取 `user_id = 123456789`：

- 分片号 $= 123456789 \bmod 64 = 21$
- 库 $= 21 \bmod 16 = 5$，库内表号 $= 21 \div 16 = 1$（第 2 张表）

`select * from t_order where user_id = 123456789` 命中 `db5` 的 `t_order_1`，单分片单表。而 `select * from t_order where order_id = 987` 没有 `user_id`，只能广播 64 个分片——这就是分片键选错的代价。

**面试高频问法**：

1. 「分片键怎么选？」→ 考点在数据倾斜与查询路由，而不是算法本身 → 答：分片键要高基数、分布均匀，且大多数在线查询必须带它；如果主要查询路径带不上，说明该换拆分维度，而不是加中间件。
2. 「取模分片怎么扩容？」→ 考点是迁移量而不是能不能迁 → 答：走成倍扩容，旧库 i 的数据只会分裂到新库 i 和 i+N，迁移量约 50%，配合双写、校验、灰度切读、停双写四步完成。
3. 「跨分片分页和排序怎么办？」→ 考点是分片各返回一页拼接的错法 → 答：必须让各分片返回前 `offset+limit` 条在内存归并；深翻页改用游标，带上上一页最后一条的排序键，避免越翻越慢。
4. 「分库分表后 ID 怎么生成？」→ 考点在生成器的可用性与单调性 → 答：号段模式批量取号，DB 压力小且趋势递增；雪花式性能好但要处理时钟回拨，两者都别依赖单点。
5. 「要不要上分布式事务？」→ 考点是能否把跨片写变成同片写 → 答：先把关联表按同一分片键落库，让事务回到单库；剩下真正必须原子的少数链路才考虑 2PC，其余走最终一致加对账。

## 第 6 章 短链系统的完整设计

**要解决的问题**：把任意长 URL 压成几字符的短码，写一次读千万次，在短码唯一、不可枚举、跳转延迟极低的前提下完成跳转。不解决，长链接不可分发，渠道点击统计也无从做起。

**机制**：数据模型就两条 KV：`s:<code> -> long_url` 是读路径，`u:<hash(long_url|channel)> -> code` 是写路径的去重索引。选 KV 而非关系库，因为访问模式就是按单键取整值，且天然按 code 哈希分片。

短码生成三条路：

- 发号器 + Base62：自增 ID 转 62 进制，无冲突、长度随存量可控（$62^k$ 决定容量上界），缺点是顺序可枚举，需要加盐混淆或打乱字母表。
- 随机码 + 唯一索引：随机取 k 位，写入用 SETNX 兜底，冲突重试，实现最简单、不可预测。
- hash 截断：必然冲突，要么重试要么加长，一般只在长 URL 天然去重的场景用。

读路径是设计重心：短码 → 本地缓存 → Redis → 回源 KV → 回填并设 TTL；不存在的短码用布隆过滤器或空值短 TTL 缓存挡住，防止被遍历打穿；超热短码用本地缓存 + Redis 两级。301 与 302 是业务决策：301 让浏览器永久缓存，省回源但丢统计、改链失效；302 每次回源，可统计、可改链、可插风控确认页，默认选 302。写路径要处理长 URL 校验与黑名单（防钓鱼、防内网地址造成 SSRF），以及同 URL 是否复用短码——复用省存储，但按渠道各生成一个才能分开统计。

```python
def shorten(long_url, channel):
    fp = "u:" + sha256(long_url + "|" + channel)
    if (code := kv.get(fp)) is not None:
        return code
    for _ in range(3):                     # 冲突重试上限
        code = b62(next_id())              # 或 secrets 随机 k 位
        if kv.set_nx("s:" + code, long_url):
            kv.set(fp, code)
            return code
    raise Conflict

def resolve(code):
    if not bloom.might_contain(code):
        return 404
    url = local_cache.get(code) or redis.get(code)
    if url is None:
        url = kv.get("s:" + code)
        redis.set(code, url or "", ttl=...)   # 空值也缓存，挡穿透
    return redirect(url, status=302)
```

**最小例子**：本地起服务，两次请求。

```bash
$ curl -i -X POST localhost:8080/api/links -H 'Content-Type: application/json' \
    -d '{"url":"https://example.com/docs/2024/q3/report?src=newsletter","channel":"newsletter"}'
HTTP/1.1 201 Created
{"code":"1Zk9fQ","short":"http://sho.rt/1Zk9fQ"}

$ curl -i http://sho.rt/1Zk9fQ
HTTP/1.1 302 Found
Location: https://example.com/docs/2024/q3/report?src=newsletter
```

同 URL 同 channel 再提交一次，命中 `u:` 索引返回同一个 `1Zk9fQ`；换成 `channel=weibo` 则生成新短码，两条短码各自统计点击。

**面试高频问法**：

1. 「短码怎么生成，为什么不用 hash？」→ 考点在冲突成本 → 答：hash 截断必然冲突，得靠重试或加长兜底；发号器 + Base62 无冲突、长度可控，随机码不可枚举但需要唯一索引兜底。
2. 「301 还是 302？」→ 考点是缓存语义与业务可控性 → 答：默认 302，因为要统计点击、要能改链和下线；只有确定永久不变且放弃统计才用 301。
3. 「读写比悬殊怎么扛？」→ 考点是缓存层级与存储选型 → 答：短码到长 URL 是纯 KV 读，用本地缓存加 Redis 挡掉绝大部分流量，存储按短码哈希分片水平扩，写路径由发号器或唯一索引保证唯一。
4. 「怎么防遍历爬取？」→ 考点是短码熵而不是加防火墙 → 答：短码用随机段或加盐混淆保证不可预测，同时对来源 IP 和短码前缀限流，并监控异常 404 比例。
5. 「缓存穿透和热点怎么处理？」→ 考点是两类问题要分开答 → 答：不存在的短码靠布隆过滤器或空值短 TTL 缓存挡回源；热点短码靠本地缓存 + Redis 多级，配合热点探测预热。

## 第 7 章 秒杀：超卖、库存扣减与削峰

**要解决的问题**：把「瞬时几十万次点击、只有几百件库存」的流量收敛成有限次、可串行化的扣减——不超卖（卖出量多过库存）、不少卖（有库存却卖不掉），同时不让数据库被瞬时流量压垮。不解决，要么库存被扣成负数，要么数据库被打挂，两种结果都是资损或事故。

**机制**

一句话：入口过滤掉无效流量，Redis 原子预扣发出「资格」，MQ 削峰后由 DB 做最终条件扣减，补偿与对账处理大量失败请求。

超卖有三个独立来源，要分开解决：
1. **缓存扣减非原子**：`GET` 后判空再 `DECR`，两步之间能插进任意多个请求。用 Lua 把「读—判断—扣」合成一次原子执行（Redis 执行 Lua 期间不插入其他命令）。
2. **缓存与 DB 不一致**：只允许一条写入路径（预扣只写 Redis，落库只写 DB），不双写。
3. **DB 层非原子更新**：`SELECT` 再 `UPDATE`（check-then-act）在并发下必然超卖；InnoDB RR 下普通 `SELECT` 还是快照读，读到的可能是旧值。必须用条件更新并判断影响行数。

```lua
-- KEYS[1]=stock:sku:1001  ARGV[1]=购买数量
local left = tonumber(redis.call('GET', KEYS[1]))
if left == nil then return -2 end              -- 未预热，直接拒绝
if left < tonumber(ARGV[1]) then return -1 end -- 售罄
return redis.call('DECRBY', KEYS[1], ARGV[1])  -- 返回剩余，>=0 即抢到资格
```

```sql
-- 落库兜底：看影响行数，不看先前查到的值
UPDATE stock SET available = available - 1, version = version + 1
 WHERE sku_id = 1001 AND available >= 1;
-- 影响 0 行 → 已被抢完，回补 Redis 并对外置为售罄
```

削峰：抢到资格的请求只写 MQ 就算成功（同步链路只回答「抢到/没抢到」，结果页轮询），消费者按数据库能承受的速率匀速落库。队列积压是设计内的，队列丢了才是事故，所以扣减与发消息要么用本地消息表，要么用事务消息保证一致。

回补与对账：预扣成功但落库失败（风控拒绝、消费者异常、超时）必须把库存 `INCRBY` 回去，并且回补要幂等——用「预扣记录」的状态机 `pending → consumed / released`，只有 `pending` 能转 `released`，重复投递不会二次回补。定时对账三方：Redis 已扣量、DB 实扣量、订单量。

热点：单 key 会打满一个分片。把库存拆成 N 个桶（`stock:sku:1001:{0..N-1}`），按 `userId % N` 选桶，桶空则尝试其他桶。代价是可能出现「总量有货但这次没抢到」，秒杀场景可接受。

**最小例子**

sku=1001，库存 100，预热为 `stock:sku:1001 = 100`。假设 1000 个请求在同一秒到达：Lua 返回 `>=0` 的恰好 100 次（依次返回 99…0），其余 900 次拿到 `-1` 直接返回「已售罄」，这 900 次一次都没碰数据库。这 100 个中假设 3 个被风控拒绝，补偿任务对 3 个 orderId 各执行一次回补：`INCRBY stock:sku:1001 1` 并把预扣记录从 `pending` 改为 `released`，库存回到 3。最终 DB `available` 卖出 97、订单表 97 行、Redis 剩余 3，三者自洽。补偿消息重复投递两次时，第二次因状态已是 `released` 被丢弃，不会回补成 4。

**面试高频问法**

1. **怎么防超卖？** → 考点：原子性落在哪一层。→ 答法：三层，Redis 用 Lua 把「读库存 + 判断 + 扣减」做成单线程原子操作挡住绝大部分流量，DB 用 `available = available - 1 WHERE available >= 1` 的条件更新做最终兜底，并且判断的是影响行数而不是先查后改。
2. **Redis 扣了但下单失败怎么办？** → 考点：一致性补偿与幂等。→ 答法：预扣时写一条带状态机的预扣记录，落库成功置 `consumed`，失败或超时由补偿任务把库存 `INCRBY` 回去并置 `released`，只有 `pending` 能转移所以重复补偿无害，再加定时三方对账兜底。
3. **为什么要 MQ，MQ 挂了怎么办？** → 考点：削峰的本质是「把并发变成排队」。→ 答法：MQ 把「抢资格」和「落库」解耦，消费者按数据库能承受的速率消费，队列积压是预期内的；MQ 不可用时降级成同步小批量写或直接返回「排队中」让前端轮询，绝不把原始流量直接放给 DB，同时用本地消息表保证扣减和发消息不丢。
4. **单个库存 key 打爆一个分片怎么办？** → 考点：热点 key 拆分。→ 答法：库存分桶，拆成 N 份放不同分片，按用户哈希选桶，桶空则顺延尝试其他桶；代价是概率性的「有货没抢到」，用一次重试或后台汇总补偿来处理，比单点打爆划算。
5. **怎么保证不少卖？** → 考点：失败路径的闭环。→ 答法：所有「预扣成功但未成交」的路径（风控拒绝、落库失败、消费者超时）都必须有回补，回补靠状态机幂等，再靠 Redis 已扣量 / DB 实扣量 / 订单量三方对账发现漏补和错补。

## 第 8 章 高可用：超时、重试、熔断与隔离舱

**要解决的问题**：当某个下游变慢而不是直接挂掉时，调用方的线程、连接、队列会被慢慢占满，故障顺着依赖链向上传染成全站雪崩。这一章解决的是「单点变慢不升级为全局故障」。

**机制**

四个手段分别对应四句话：超时是「别等」，重试是「再试一次」，熔断是「别再试了」，隔离舱是「别连累别人」。

**超时**：每个远程调用都必须设超时，并且整条链路要有超时预算。父调用的超时应该大于其内部子调用超时之和再加上排队与序列化开销，否则父调用先放弃、子调用还在跑，计算和连接白占。超时值按下游延迟分位数定，不是凭感觉定。

**重试**：三个前提缺一不可——被调操作幂等、错误类型可重试、次数有上限。只重试连接失败、连接重置、明确的 5xx；不重试参数错误、鉴权失败、非幂等写。必须指数退避加随机抖动，否则一批请求会在同一时刻集体重试，形成第二波尖峰。更关键的是**只在链路最外层重试**：L 层每层重试 r 次，故障时下游要承受 $r^L$ 倍流量，三層各重试 3 次就是 27 倍。有条件时再加一个重试预算，限制重试请求占总请求的比例。

**熔断**：三态状态机 `closed → open → half-open`。用滑动窗口统计失败率和慢调用比例，样本量足够且超过阈值才打开；open 期间直接走 fallback（快速失败，不再占用调用资源）；冷却后 half-open 放少量试探请求，成功则关闭，失败则重新 open。失败率和慢调用比例要分开统计——下游变慢通常早于开始报错。

**隔离舱**：按依赖划分独立资源池，一个慢依赖只耗尽自己的池子，不抢占其他依赖的线程和连接。线程池隔离的调用方线程不被阻塞、能异步超时，代价是上下文切换和线程数要规划；信号量隔离只做计数、更轻量，但调用方线程仍阻塞在 IO 上，适合低延迟且可信的内部调用。更大粒度是机房、单元、租户级隔离。

**降级**：熔断打开后必须有 fallback，否则「快速失败」等于「快速报错」。fallback 取缓存旧值、默认值、空列表或只读模式。

```python
def call(dep, req):                       # 外层：重试
    for attempt in range(3):
        if breaker[dep].is_open():        # 熔断：快速失败
            return fallback(dep, req)
        try:
            with bulkhead[dep].acquire(50):        # 隔离舱：只占自己的池
                r = http_call(dep, req, timeout_ms=200)   # 单次调用内建超时
            breaker[dep].record_success(); return r
        except (Timeout, ConnReset) as e:
            breaker[dep].record_failure()
            if attempt == 2: return fallback(dep, req)
            sleep(backoff(attempt) + jitter())        # 退避 + 抖动
```

**最小例子**

调用推荐服务：单次超时 200ms，最多重试 2 次，退避 100ms 加 0–50ms 抖动；熔断滑动窗口 10s、最少 20 个样本、失败率阈值 50%、open 持续 30s、half-open 放 3 个试探；假设给它一个 20 线程的独立小池。

某时刻推荐服务变慢，10s 内 20 个请求里 12 个超时，失败率 60% 超过阈值且样本量达标，熔断打开。接下来 30s 内所有推荐请求直接返回缓存的旧推荐列表，一次都不占用调用线程；30s 后放 3 个试探，其中 2 个成功，状态回到 closed 恢复正常调用。整个过程商品详情主流程不受影响——慢的是推荐，被限制在推荐自己的 20 个线程里，主流程线程池没有被拖住。

**面试高频问法**

1. **超时怎么设？** → 考点：超时预算而非单个数字。→ 答法：按下游延迟的高分位（比如 P99）的 1.5 到 2 倍来设，同时保证父调用超时大于内部子调用超时之和加上排队开销，否则父调用已经放弃、子调用还在执行，等于白占资源。
2. **重试怎么不放大故障？** → 考点：重试风暴与幂等。→ 答法：只在最外层重试一到两次，只重试幂等且可重试的错误，指数退避加随机抖动，再用重试预算限制重试请求占比；中间层一律不重试，因为每层重试 r 次在故障时就是 $r^L$ 倍放大。
3. **熔断和限流有什么区别？** → 考点：一个治入口，一个治出口。→ 答法：限流控制的是自己入口的请求速率，是预防；熔断是根据下游健康度自动切断调用、保护自己和下游，是止损。限流管「进来的太多」，熔断管「出去的回不来」。
4. **线程池隔离和信号量隔离怎么选？** → 考点：隔离的代价。→ 答法：线程池隔离能让调用方线程不被阻塞、支持异步超时，适合慢依赖，代价是线程切换和线程数要算准；信号量隔离只计数、开销小，但调用方线程仍阻塞在 IO 上，适合低延迟的内部调用，同步调用做不到线程池隔离除非先异步化。
5. **调用超时了，到底成功没有？** → 考点：分布式不确定性。→ 答法：不知道，超时是「结果未知」不是「失败」，所以非幂等写不能盲目重试，只能靠业务幂等键加查询确认或对账来收敛，写接口必须带客户端生成的唯一请求号做去重。

**面试高频问法**

1. **怎么防超卖？** → 考点：原子性落在哪一层。→ 答法：三层，Redis 用 Lua 把「读库存 + 判断 + 扣减」做成单线程原子操作挡住绝大部分流量，DB 用 `available = available - 1 WHERE available >= 1` 的条件更新做最终兜底，并且判断的是影响行数而不是先查后改。
2. **Redis 扣了但下单失败怎么办？** → 考点：一致性补偿与幂等。→ 答法：预扣时写一条带状态机的预扣记录，落库成功置 `consumed`，失败或超时由补偿任务把库存 `INCRBY` 回去并置 `released`，只有 `pending` 能转移所以重复补偿无害，再加定时三方对账兜底。
3. **为什么要 MQ，MQ 挂了怎么办？** → 考点：削峰的本质是「把并发变成排队」。→ 答法：MQ 把「抢资格」和「落库」解耦，消费者按数据库能承受的速率消费，队列积压是预期内的；MQ 不可用时降级成同步小批量写或直接返回「排队中」让前端轮询，绝不把原始流量直接放给 DB，同时用本地消息表保证扣减和发消息不丢。
4. **单个库存 key 打爆一个分片怎么办？** → 考点：热点 key 拆分。→ 答法：库存分桶，拆成 N 份放不同分片，按用户哈希选桶，桶空则顺延尝试其他桶；代价是概率性的「有货没抢到」，用一次重试或后台汇总补偿来处理，比单点打爆划算。
5. **怎么保证不少卖？** → 考点：失败路径的闭环。→ 答法：所有「预扣成功但未成交」的路径（风控拒绝、落库失败、消费者超时）都必须有回补，回补靠状态机幂等，再靠 Redis 已扣量 / DB 实扣量 / 订单量三方对账发现漏补和错补。
