# cpp-basics · 分章详细

## 第 1 章 类型系统、值与引用

**要解决的问题**：区分「这行代码在内存里到底动了什么」，是后面生命周期、拷贝、移动、并发全部讨论的前提条件。如果不理清值、引用、指针和对象的关系，就会出现「函数传参到底拷没拷」「`auto&` 和 `auto` 差在哪」这类只能靠背答案而不理解的问题。

**机制**：

C++ 的类型系统按两个维度给每个表达式打标签：**类型**（决定能对它做什么操作）和**值类别**（决定它能被怎么用、绑定到谁）。值类别只有三类基础形态：

- lvalue（左值）：有名字、有确定地址、可取址。变量、`*p`、返回左值引用的函数调用。
- prvalue（纯右值）：临时量、字面量、返回值的函数调用，没有可取的地址。
- xvalue（将亡值）：`std::move(x)` 的结果，有地址但被标记为「可以被掏空」。

lvalue 和 xvalue 合称 glvalue，prvalue 和 xvalue 合称 rvalue。

引用是对一个已存在对象的别名，本身不占独立存储：

- `T&` 只能绑定 lvalue；`const T&` 能绑定两者，绑定 prvalue 时**延长临时量寿命**到该引用的作用域结束。
- `T&&` 只能绑定 rvalue，是移动语义的入口（第 4 章展开）。

关键约束：引用必须初始化、不可重新绑定、没有空引用（但可以通过解引用空指针制造出引用的未定义行为）。指针是独立对象，可以为空、可以改指向、可以算术。

```cpp
int  a = 1;
int& r = a;              // ok：lvalue 绑定 lvalue
// int& r2 = 2;          // 错：非常量引用不能绑 prvalue
const int& cr = 2;       // ok：临时量寿命延长到 cr 作用域结束，但注意——绑定到函数返回值不延长！
int&& rv = 2;            // ok：右值引用，同样延长
auto  x = r;             // x 是 int，拷贝；auto 丢弃引用与顶层 const
auto& y = r;             // y 是 int&
decltype(r) z = a;       // z 是 int&，decltype 保留引用
```

`auto` 按值推导（丢弃引用、顶层 const/volatile），`decltype` 保留完整类型，`decltype(auto)` 按初始化表达式的值类别推导——这是面试常考的三角关系。

数组与函数在参数传递时会**退化**为指针，`sizeof` 在函数内因此不可靠；模板参数推导时对引用形参则有引用折叠规则（`&& + & = &`），这是完美转发的基础，属于第 6 章的延伸。

**最小例子**：

```cpp
#include <cstdio>
struct Big { int buf[64]; };

void byValue(Big b)  { b.buf[0] = 99; }   // 拷贝 256 字节
void byRef(Big& b)   { b.buf[0] = 99; }   // 不拷贝，改原对象

int main() {
    Big g{};
    byValue(g);                  // g.buf[0] 仍是 0
    byRef(g);                    // g.buf[0] 变成 99
    auto  c = g;                 // 拷贝，size = sizeof(Big) = 256
    auto& d = g;                 // 别名，sizeof(d) 也是 256，但 &d == &g
    printf("%zu %d\n", sizeof(c), d.buf[0]);   // 256 99
}
```

`sizeof(c)` 与 `sizeof(d)` 相同——引用不额外占存储，`sizeof` 报的是被引用类型的大小。但 `&d == &g` 为真而 `&c != &g` 为假，这才是「拷没拷」的判据。

**面试高频问法**：

1. **「引用和指针有什么区别？」→ 考点是语义而非语法 → 答法**：引用是别名、必须初始化、不可重绑、无空值，编译器可当它是语法糖不做额外存储；指针是独立对象，可为空、可改向、可算术、可有多级。实现上引用常被编译成指针，但那只是实现细节，语言层面不能对引用取地址（取到的是被引用对象的地址）。

2. **「`const T&` 和 `T&&` 都能绑定临时量，区别是什么？」→ 考点是寿命延长与重载决议先行 → 答法**：两者都延长临时量寿命到引用作用域结束，但 `const T&` 会参与普通拷贝重载，`T&&` 告诉编译器「这个对象可被掏空」，从而优先匹配移动构造/移动赋值。引用绑定本身构造不出移动，移动语义靠的是 `T&&` 进入重载决议后的选择。

3. **「传参用值、引用还是 const 引用？」→ 考点是对拷贝成本与所有权的判断 → 答法**：内置类型和小对象按值；大对象只读用 `const&`；需要修改实参用 `T&`；需要接管所有权才按值或 `T&&`。注意按值传参 + `std::move` 进成员是「拷贝并移动」惯用法，成本取决于调用方是否能给右值。

4. **「`auto` 和 `decltype` 推导出的类型可能不同，举个例子。」→ 考点是值类别与引用保留 → 答法**：`int a; int& r = a;` 下 `auto x = r` 得 `int`（丢弃引用），`decltype(r)` 得 `int&`。另外 `decltype((a))` 带括号得到 `int&` 而 `decltype(a)` 得到 `int`，因为带括号的表达式是 lvalue 而变量名是「名字表达式」特例。

5. **「函数返回局部变量的引用为什么错？」→ 考点是生命周期与悬垂 → 答法**：局部对象在函数返回时销毁，引用指向已失效的对象，是未定义行为；`const&` 绑定返回值时也不延长——寿命延长规则只对绑定到临时量的**直接用引用初始化**成立，绑定到函数返回值是另一个临时量，函数一返回就销毁。

## 第 2 章 构造、析构与对象生命周期

**要解决的问题**：对象从「内存分配」到「构造完成」到「析构」是一条有明确状态的流水线，中间任何一步失败都必须有确定行为（尤其异常时的回滚）。不理解这条流水线，就无法解释「为什么不推荐在构造函数里调用虚函数」「为什么析构函数需要是虚的」。

**机制**：

对象的生命周期分四段：

1. **存储期开始**：分配内存（栈上随作用域，堆上经 `operator new`）。
2. **构造**：先按声明顺序构造成员（按**声明顺序**，不是初始化列表书写顺序），再执行构造函数体；基类先于成员。
3. **使用期**。
4. **析构**：析构函数体执行完，成员按**逆声明顺序**析构，然后基类析构；最后存储回收。

关键规则：

- **成员初始化顺序 = 声明顺序**。初始化列表里写反顺序是典型的「看起来没毛病」bug，编译器通常只给 warn。
- **构造期间 `this` 的虚表状态是当前正在构造的类**。在基类构造函数里调用虚函数，调不到派生类override 版本——派生类部分还没构造，出错是好事，但也常导致设计错误。析构同理反过来。
- **析构函数为虚，是删除多态对象的必要条件**：`delete base_ptr` 且 `~Base()` 非虚，是未定义行为，通常只调 `~Base`，派生部分泄漏。
- **异常与构造**：构造函数体抛异常，已经构造完的成员和基类会按逆序析构（**栈展开**），但对象自身析构函数不会执行。因此「构造中申请的资源」要靠 RAII 成员管理，不能靠构造函数里的手动 `new` + 构造函数末尾释放。
- **聚合初始化**：C++11 起 `T x{a, b}` 对聚合体（无用户提供构造函数、无私有成员等）按声明顺序初始化；C++17 起有保证的复制消除使 `T x = T{...}` 不再多一次构造。
- **`new` / `delete` 成对**：`operator new` 分配原始内存、构造函数在其上执行；`delete` 先调析构、再 `operator delete` 释放内存。`new[]` 与 `delete[]` 混用是未定义行为。

```cpp
struct Member { Member(int) { /* ... */ } };

struct Base {
    Base() { /* 此时 vptr 指向 Base 的 vtable */ }
    virtual ~Base() = default;     // 多态删除必须
    virtual void f() {}
};

struct Derived : Base {
    Member m;                      // 声明顺序：m 在 b 之前？
    int    b;
    Derived() : b(1), m(2) { }     // 实际先构造 m，再构造 b（按声明），列表顺序无效
    void f() override { }
};

// delete 一个指向 Derived 的 Base*，~Base 为虚 → 正确调 ~Derived
```

**最小例子**：

```cpp
#include <cstdio>
struct A { A() { puts("A()"); } ~A() { puts("~A()"); } };
struct B { B() { puts("B()"); } ~B() { puts("~B()"); } };
struct C : A { B b; C() { puts("C()"); } ~C() { puts("~C()"); } };

int main() {
    { C c; }
    // 输出顺序：A() B() C() ~C() ~B() ~A()
}
```

构造从上到下（基类 → 成员 → 自身），析构严格逆序。若把 `B b;` 写在 `A` 继承之后仍不变——基类永远最前。

异常版：`C` 的构造函数若在 `b` 已构造后抛出，`~C` 不执行、`~B` 执行、`~A` 执行。这道痕迹就是「构造函数中泄漏资源」的根因。

**面试高频问法**：

1. **「为什么析构函数常写成 virtual？」→ 考点是多态删除的未定义行为 → 答法**：通过基类指针 `delete` 派生对象时，若基类析构非虚，标准称未定义行为，通常只调基类析构，派生成员泄漏。只要类打算被多态使用，析构就应 virtual；不打算被继承的类可以用 `final` 加非虚析构，或 `protected` 非虚析构限制删除方式。

2. **「构造函数能不能是虚函数？」→ 考点是构造与虚表的时序 → 答法**：不能。虚函数要求对象已有 vptr，而 vptr 正是构造函数的工作之一，构造开始时对象还没有完整类型，无法按动态类型分派。需要「按类型创建」时用工厂函数或虚 clone。

3. **「构造/析构函数里调用虚函数会发生什么？」→ 考点是 vptr 在构造阶段的状态 → 答法**：构造函数里调到的是**当前正在构造的类**的版本，不是最终派生类；析构同理反向。派生类部分尚未构造或已销毁，调到它是错的——通常说的「调不到派生覆盖版」就是这个现象。

4. **「成员初始化列表的顺序重要吗？」→ 考点是初始化顺序由声明决定 → 答法**：初始化顺序永远按成员声明顺序，与初始化列表书写顺序无关。列表顺序写反会在编译器警告之外酿成真实 bug：用后声明的成员初始化先声明的成员时，后者还没构造。

5. **「构造函数抛异常，已经申请的资源谁来释放？」→ 考点是栈展开范围 → 答法**：已完整构造的成员和基类会逆序析构，对象自身析构不执行。所以资源要放在 RAII 成员里，构造中途失败时成员析构自动兜底；裸 `new` 写在构造函数体里，构造后段抛异常就泄漏。

## 第 3 章 RAII 与资源管理

**要解决的问题**：C++ 没有 GC，资源（堆内存、文件、锁、socket）必须由某种确定性机制在离开作用域时释放。RAII 就是这套机制：把资源生命周期绑到对象生命周期上，是所有「异常安全」和「不写 delete」的前提。

**机制**：

RAII = Resource Acquisition Is Initialization。核心是一个类，构造时获取资源并持有，析构时释放资源。因为 C++ 保证**栈上对象在离开作用域时必然析构**（正常返回、`break`、`goto` 出作用域、异常栈展开都成立），资源释放就有确定时机。

一个合格的 RAII 句柄需要：

- 构造即持有，失败就抛异常（不产生半成品）。
- **禁止拷贝**（否则两次析构同一资源）或实现**移动**（把所有权转走，源对象置空）。
- 析构函数**不抛异常**。析构中抛异常若此时已在栈展开，会触发 `std::terminate`。
- 提供 `get()` / `release()` / `reset()` 一类接口但谨慎暴露裸句柄。

标准库把 RAII 铺满：`std::unique_ptr`（独占堆内存）、`std::shared_ptr`（引用计数）、`std::lock_guard` / `std::unique_lock`（锁）、`std::fstream`（文件）、`std::vector`（动态数组、容器内元素也是 RAII）。这些在第 5 章展开，本章只关注模式本身。

```cpp
class File {
public:
    explicit File(const char* path) : fp_(std::fopen(path, "r")) {
        if (!fp_) throw std::runtime_error("open failed");
    }
    ~File() { if (fp_) std::fclose(fp_); }

    File(const File&)            = delete;             // 禁止拷贝
    File& operator=(const File&) = delete;
    File(File&& o) noexcept : fp_(o.fp_) { o.fp_ = nullptr; }  // 移动：转所有权
    File& operator=(File&& o) noexcept {
        if (this != &o) { if (fp_) std::fclose(fp_); fp_ = o.fp_; o.fp_ = nullptr; }
        return *this;
    }
    std::FILE* get() const noexcept { return fp_; }
private:
    std::FILE* fp_;
};
```

`noexcept` 在移动构造上不是装饰：容器扩容时若移动构造可能抛异常，`vector` 会退化为拷贝以满足强异常安全，性能直接受影响。

RAII 的异常安全价值在于：函数内申请 N 个资源，第 N+1 步抛异常，前面 N 个由栈展开自动释放——不需要写任何 `catch`/`finally`。这使「局部资源 + 异常」可以写得和「局部资源 + 正常返回」一样干净。

**最小例子**：

```cpp
#include <cstdio>
#include <stdexcept>
#include <mutex>

void work(std::mutex& m) {
    std::lock_guard<std::mutex> lk(m);   // 构造加锁
    throw std::runtime_error("boom");    // 抛异常，lk 析构 → 解锁，栈展开保证
}

int main() {
    std::mutex m;
    try { work(m); } catch (const std::exception&) { }
    // 走到这里锁已释放，没有死锁
}
```

`lock_guard` 没有 `unlock()` 接口、没有移动，用完即止——这就是 RAII 的意图：**不给你忘记释放的机会**。需要提前释放或转移锁时用 `unique_lock`。

对比手写版：`m.lock(); doSomething(); m.unlock();` 一旦 `doSomething()` 抛异常就死锁。代码量差别不大，正确性差别却是数量级的。

**面试高频问法**：

1. **「什么是 RAII？为什么 C++ 要它？」→ 考点是确定性析构与异常安全 → 答法**：把资源获取放在构造函数、释放放在析构函数，用对象生命周期管理资源。C++ 保证栈对象离开作用域必析构，所以无论是正常返回还是异常展开，资源都被确定时机释放，不需要 GC，也不需要手写 `finally`。

2. **「RAII 类的析构函数为什么必须不抛异常？」→ 考点是栈展开中的双重异常 → 答法**：如果析构发生在栈展开期间（已有异常在传播），再抛一个异常，标准说 `std::terminate` 被调用。即使不在展开期，析构抛异常也会让资源清理半途而废。因此析构里只做「不会失败」的释放，或内部 catch 掉。

3. **「RAII 句柄应该禁止拷贝还是实现移动？」→ 考点是所有权语义 → 答法**：独占资源用「禁止拷贝 + 移动」，移动后源对象置空以保证析构幂等；共享所有权的资源（如 `shared_ptr`）才允许拷贝，靠引用计数管理。禁止拷贝但允许移动是 `unique_ptr` 的模型，也是自定义 RAII 类的默认建议。

4. **「`lock_guard` 和 `unique_lock` 的区别？」→ 考点是 RAII 的灵活性边界 → 答法**：`lock_guard` 最简单，构造加锁析构解锁，不可移动、不能手动解锁、不支持条件变量；`unique_lock` 可移动、可延迟加锁、可手动 `unlock()`/`lock()`、能与 `condition_variable` 配合。默认选 `lock_guard`，需要额外控制才升到 `unique_lock`。

5. **「移动构造为什么常加 `noexcept`？」→ 考点是容器强异常安全与性能路径 → 答法**：`vector` 扩容时要在强异常安全下搬移元素：若移动构造可能抛异常且中途失败，无法回滚到原容器，于是退化为拷贝构造。标记 `noexcept` 让容器走移动路径，避免不必要的拷贝开销。

**与其他章的衔接**：这章的 RAII 是第 4 章拷贝控制/移动语义的动机来源——拷贝还是移动的决策，本质是所有权在 RAII 句柄间怎么转移；也是第 9 章并发锁管理和第 8 章异常安全话题的地基。

## 第 4 章 拷贝控制与移动语义

**要解决的问题**：当对象被拷贝、赋值、按值传参或从函数返回时，资源（堆内存、文件描述符、锁）究竟是被复制一份还是被转移走。这一章不解决，要么写出双重释放与悬空指针，要么把本该 O(1) 的转移退化成 O(n) 的深拷贝。

**机制**：C++ 给每个类隐式声明五个特殊成员函数：析构、拷贝构造、拷贝赋值、移动构造、移动赋值。编译器自动生成哪些，由用户声明了哪些决定：

1. 用户声明了拷贝构造、拷贝赋值或析构中的任意一个，编译器不再隐式声明移动构造和移动赋值——这是 C++11 最常见的“性能悄悄消失”的原因。
2. 用户声明了移动操作，拷贝构造和拷贝赋值被定义为 `= delete`，于是这个类只能移动不能拷贝。
3. 什么都不写（Rule of Zero），编译器按成员逐成员拷贝和移动。

移动构造的参数是 `T&&`，它只做一件事：把源对象内部指针搬过来、再把源置空。**移动后源对象处于“有效但未指定”状态**，唯一保证是能安全析构和重新赋值。`std::move` 本身不移动任何东西，它只是 `static_cast<std::remove_reference_t<T>&&>(x)`，把一个左值标记成“可以被移动”。

拷贝赋值要同时满足自赋值安全和异常安全，惯用写法是 copy-and-swap：先在临时对象里完成可能抛异常的工作，再用不抛异常的 `swap` 提交。

```cpp
class Buffer {
  char* p_; size_t n_;
public:
  explicit Buffer(size_t n) : p_(new char[n]), n_(n) {}
  ~Buffer() { delete[] p_; }
  Buffer(const Buffer& o) : p_(new char[o.n_]), n_(o.n_) {
    std::copy(o.p_, o.p_ + n_, p_);
  }
  Buffer& operator=(const Buffer& o) {          // copy-and-swap
    if (this != &o) { Buffer t(o); swap(t); }
    return *this;
  }
  Buffer(Buffer&& o) noexcept : p_(o.p_), n_(o.n_) { o.p_ = nullptr; o.n_ = 0; }
  void swap(Buffer& o) noexcept { std::swap(p_, o.p_); std::swap(n_, o.n_); }
};
```

移动构造上的 `noexcept` 不是装饰：`std::vector` 扩容时要保证强异常安全，内部用 `move_if_noexcept` 决策——如果元素移动构造被标注为不抛异常（或元素根本不可拷贝），才用移动；否则宁可拷贝，因为“拷贝失败原对象还在”。漏写 `noexcept` 会让容器扩容悄悄走拷贝路径。

**最小例子**：`std::vector<Buffer> v; v.reserve(4);` 后连续 `push_back` 五个元素。前四次只是在 `v` 的缓冲区上移动构造；第五次触发扩容，因为 `Buffer` 的移动构造是 `noexcept`，旧缓冲区的四个元素被逐个移动构造到新缓冲区，总代价 O(n) 次指针搬运而非 O(n) 次深拷贝。若删掉 `noexcept`，同样代码会走四次深拷贝。

**面试高频问法**：

- **问**：什么时候编译器不给你生成移动构造？→ **考点**：五个特殊函数的隐式生成规则。→ **答**：只要用户自己声明了拷贝构造、拷贝赋值或析构中的任意一个，编译器就不会隐式声明移动构造和移动赋值，此时右值也会走拷贝；如果用户声明了移动操作，拷贝操作则被定义为删除。
- **问**：`std::move` 到底做了什么？→ **考点**：它是类型转换而不是动作。→ **答**：它就是一个到右值引用的 `static_cast`，本身不产生任何代码也不搬运资源；真正的搬运发生在被调用的移动构造或移动赋值里，被 `move` 过的对象之后仍必须可析构、可赋值。
- **问**：为什么移动构造一定要标 `noexcept`？→ **考点**：容器扩容与强异常保证的联动。→ **答**：`vector` 扩容用 `move_if_noexcept` 决定搬移方式，移动构造可能抛异常时它会退回复制以保证原容器不被破坏，标了 `noexcept` 才能让扩容真正走移动。
- **问**：拷贝赋值怎么写才安全？→ **考点**：自赋值 + 异常安全。→ **答**：用 copy-and-swap：先拷贝构造一个临时对象（这一步失败不影响 `*this`），再用 `noexcept` 的 `swap` 换进来，同时天然处理了 `a = a` 的情况。
- **问**：Rule of Zero / Three / Five 怎么理解？→ **考点**：资源管理抽象层次。→ **答**：能靠成员（`string`、`vector`、`unique_ptr`）管住资源就一个都不写（Zero）；一旦要手写析构就要把拷贝和赋值也写全（Three）；C++11 之后再补上移动两件套（Five）。

## 第 5 章 智能指针与所有权模型

**要解决的问题**：把“谁负责释放、什么时候释放、能不能共享”从注释和口头约定变成类型系统里可检查的约束。裸指针表达不了所有权，于是泄漏、重复释放、悬空引用全靠人肉 review；智能指针让所有权在函数签名上就能读出来。

**机制**：三种所有权语义对应三种类型。

`std::unique_ptr<T, D>` 表示独占所有权：不可拷贝、只能移动，析构时用删除器 `D` 释放。默认删除器 `std::default_delete<T>` 是无状态的空类，因此常见实现里 `unique_ptr<T>` 的大小与裸指针相同（按实现而定）。删除器是**类型的一部分**，会参与模板实例化；`unique_ptr<T[]>` 是偏特化版本，析构时用 `delete[]`。C++14 起有 `std::make_unique`。

`std::shared_ptr<T>` 表示共享所有权，由两部分组成：对象指针 + 控制块（强引用计数、弱引用计数、删除器、分配器）。拷贝时对强计数做原子自增，最后一个强引用销毁时析构对象，强计数归零且弱计数也归零时才释放控制块。`std::make_shared` 把对象和控制块放进同一次分配，少一次 `new`，局部性更好，也让“构造对象成功但控制块分配失败”这种半成品状态不可能出现；代价是只要还有 `weak_ptr` 活着，对象那块内存就不能还给分配器。

`std::weak_ptr<T>` 不增加强计数，通过 `lock()` 原子地尝试提升为 `shared_ptr`（失败返回空），它是打破 `shared_ptr` 循环引用环的唯一标准手段。`enable_shared_from_this<T>` 内部持有一个 `weak_ptr<T>`，让对象在成员函数里安全地拿到指向自己的 `shared_ptr`，而不会造出第二个控制块。

接口层面的约定：`unique_ptr<T>` 按值传参表示“所有权移交”；`T*` 或 `T&` 参数表示“借用，不持有，不负责生命周期”；`const shared_ptr<T>&` 表示“共享所有权但我不改这个指针本身”，按值传 `shared_ptr` 才会多一次原子增减。

**最小例子**：树结构，父节点拥有子节点，子节点需要回指父节点。

```cpp
struct Node {
  std::vector<std::unique_ptr<Node>> children;  // 父独占子
  Node* parent = nullptr;                       // 借用，不参与生命周期
  void add(std::unique_ptr<Node> c) {
    c->parent = this;
    children.push_back(std::move(c));
  }
};
```

析构从根开始递归释放整棵树；子节点里的 `parent` 是裸指针，天然不构成环。若把 `parent` 写成 `shared_ptr<Node>`，父子互持强引用，引用计数永远不归零，整棵树泄漏——这才是 `weak_ptr` 该出场的地方。

**面试高频问法**：

- **问**：`unique_ptr` 为什么能做到零开销？→ **考点**：空基类与删除器的类型化。→ **答**：默认删除器是无状态空类，可被空基类优化吃掉，`unique_ptr` 只存一个指针；删除逻辑在编译期确定、可直接内联，所以没有运行期虚调用或额外存储。
- **问**：`make_shared` 和 `shared_ptr<T>(new T)` 有什么区别？→ **考点**：控制块布局与异常安全。→ **答**：前者一次分配同时容纳对象和控制块，异常安全且缓存友好；后者两次分配，且 `new T` 成功、控制块分配抛异常时会泄漏对象。但 `make_shared` 在还有 `weak_ptr` 时无法提前归还原对象内存。
- **问**：`shared_ptr` 是线程安全的吗？→ **考点**：计数原子性 vs 对象本身。→ **答**：引用计数的增减是原子的，多个线程各自操作不同的 `shared_ptr` 实例（即使指向同一对象）是安全的；但同一个 `shared_ptr` 实例被多线程读写、以及所指对象本身的读写，仍需外部同步。
- **问**：循环引用怎么破？→ **考点**：强弱引用分工。→ **答**：把环中一条边改成 `weak_ptr`，它不增计数，用的时候 `lock()` 提升并判空；典型场景是父持 `shared_ptr`、子持 `weak_ptr` 回指父。
- **问**：函数参数该用哪种指针？→ **考点**：所有权语义在签名上的表达。→ **答**：要接收所有权就用 `unique_ptr<T>` 按值；只观察不负责生命周期就用 `T*` 或 `T&`；确实要共享管理权才用 `const shared_ptr<T>&`，因为按值传会多一次原子计数。

## 第 6 章 模板与泛型编程

**要解决的问题**：让同一份算法对任意满足要求的类型都成立，且类型检查发生在编译期、调用点零抽象开销。不解决就只能为每种类型复制粘贴，或者退化成 `void*` 加运行期强转，丢掉类型安全和内联机会。

**机制**：模板是**编译期代码生成器**。编译器看到 `f<int>(x)` 才用 `int` 替换 `T` 并实例化出一份真实函数，因此模板的定义必须在实例化点可见——这就是“模板实现要放头文件”的根本原因（替代方案是在 `.cpp` 里显式实例化 `template void f<int>(int);`，把可用类型集合封闭起来）。

函数模板的推导按值传参时会 decay：去掉引用和顶层 `const`、数组退化为指针、函数退化为函数指针。唯独 `T&&` 是**转发引用**（也叫万能引用），只有在“形参恰好写成 `T&&` 且 `T` 需要推导”时成立：

```cpp
template <class T> void f(T&& x);   // 转发引用
int a = 1;
f(a);    // T 推成 int&，T&& 折叠成 int&
f(1);    // T 推成 int，T&& 就是 int&&
template <class T> void g(std::vector<T>&& v);  // 不是，T 由 vector 决定
```

引用折叠规则只有两条：`& + & = &`，其余含 `&&` 的组合都得 `&&`。配合 `std::forward<T>(x)` 才能把实参原本的值类别原样传下去，这是完美转发的基础。

特化方面：类模板可以全特化和偏特化；函数模板只能全特化（严格说是重载），不能偏特化，需要“部分类型特化”时改用重载或 `if constexpr`。模板里的名字查找是两阶段的：非依赖名在定义时查找，依赖名在实例化时结合 ADL 查找，偶尔需要 `typename` / `template` 消歧义。

约束的演进路径是 `enable_if` + SFINAE（替换失败不是错误，把不匹配的重载从候选集里静默剔除）→ C++17 `if constexpr` → C++20 concepts（写出可读的 `requires` 子句，报错信息从几百行变成一句“不满足约束”）。可变参数模板配合折叠表达式可以把递归展开写成一行。

```cpp
template <class... Ts>
void emit(Ts&&... ts) {                 // 完美转发 + 折叠表达式
  (sink(std::forward<Ts>(ts)), ...);    // 逗号折叠，按序调用
}
template <class T> requires std::integral<T>
T twice(T x) { return x + x; }          // C++20 约束
```

**最小例子**：`emit(1, std::string("a"))`。编译器推导出 `Ts = {int, std::string}`，实例化出接受 `int&&` 和 `std::string&&` 的版本，折叠成 `sink(1), sink(std::string("a"))` 两次调用。若 `sink` 只接受可打印类型，把 `std::string` 换成不可打印类型时，用 SFINAE 的版本是候选集里静默剔除、报“找不到匹配的 sink”，用 concepts 的版本则直接指出第几个实参违反了哪条约束。

**面试高频问法**：

- **问**：`T&&` 一定是右值引用吗？→ **考点**：转发引用的成立条件与引用折叠。→ **答**：不一定。只有当形参严格写成 `T&&` 且 `T` 处于推导状态时它才是转发引用，此时传左值 `T` 推成 `T&`、经引用折叠形参变成左值引用；写成 `std::vector<T>&&` 或 `const T&&` 就退化成普通右值引用。
- **问**：`std::move` 和 `std::forward` 有什么区别？→ **考点**：值类别是否保持。→ **答**：`move` 无条件把实参转成右值，适合“我确定不再用它”；`forward<T>` 按推导出的 `T` 有条件转发，左值仍转发为左值、右值转发为右值，是完美转发的正确工具。
- **问**：为什么模板的声明和定义通常不能拆到 `.h` / `.cpp`？→ **考点**：实例化时机。→ **答**：模板本身不生成代码，编译器在实例化点必须看到完整定义才能生成特化版本；拆到 `.cpp` 后其他翻译单元只看到声明，链接期就找不到符号。补救办法是在 `.cpp` 里显式实例化，或直接定义在头文件里。
- **问**：SFINAE 是什么，C++20 之后还需要吗？→ **考点**：重载决议与约束表达。→ **答**：SFINAE 指模板替换阶段失败只把该候选从重载集中剔除而不报错，`enable_if` 借此按类型能力开关重载；C++20 concepts 用 `requires` 子句把同一件事写成可读的约束，报错更友好，新代码应优先用 concepts。
- **问**：为什么函数模板不能偏特化？→ **考点**：语言规则与替代方案。→ **答**：标准不允许函数模板偏特化，只能全特化；要对一类类型做差异化实现，用重载（形参写成 `std::vector<T>` 这种具体形式即可参与偏序选择）或 `if constexpr` 在函数体内分支。

## 第 7 章 STL 容器与算法复杂度

**要解决的问题**：面试问「什么时候用 vector、什么时候用 map」，实际考的是你知不知道每个容器背后的数据结构、它承诺了什么复杂度、以及这些承诺背后的代价（迭代器失效、缓存不友好、额外内存）。记不住复杂度保证，就只是在背 API。

**机制**：标准规定的是复杂度的上界；具体实现可以更快，但不能更慢。

| 操作 | vector | deque | list | map/set | unordered_map/set |
|---|---|---|---|---|---|
| 随机访问 | $O(1)$ | $O(1)$ | $O(N)$ | 无 | 无 |
| 按 key 查找 | $O(N)$ | $O(N)$ | $O(N)$ | $O(\log N)$ | 平均 $O(1)$，最坏 $O(N)$ |
| 头部插入 | $O(N)$ | $O(1)$ | $O(1)$ | 无 | 平均 $O(1)$ |
| 尾部插入 | 摊还 $O(1)$ | $O(1)$ | $O(1)$ | 无 | 平均 $O(1)$ |
| 遍历 | 连续内存 | 分段连续 | 指针跳转 | 中序有序 | 无序 |

`vector` 的摊还 $O(1)$ 来自容量按几何级数增长：容量满时，它分配更大的块（增长因子按实现而定），把旧元素搬到新块，再把新元素放进去。若每次只增加固定量，$N$ 次 `push_back` 的总搬运量是 $\sum_{i=1}^{N} O(i) = O(N^2)$；几何增长下总搬运量是等比级数 $\sum_{i} c^i = O(N)$，摊到 $N$ 次操作上就是常数。

`list` 是双向链表，每个节点单独分配，`splice` 是 $O(1)$ 且不搬运元素；代价是每元素两个指针、节点分散导致遍历时缓存命中率低。`deque` 是「指针数组 + 固定大小块」的分段连续结构，两端插入 $O(1)$ 且支持 $O(1)$ 下标。

`unordered_map` 是哈希表（链地址法或开放寻址，按实现而定）。退化的条件是哈希函数把所有 key 映进同一个桶（函数差，或被构造出冲突的 key 序列），此时单次操作退化为 $O(N)$。

迭代器失效是这块最高频的考点：

- `vector`：扩容导致全部迭代器、指针、引用失效；不扩容的 `insert`、`erase` 使插入、删除点之后的失效。
- `unordered_map`：`rehash` 使迭代器失效，但不使指向元素的引用和指针失效；`erase` 只使被删元素的迭代器失效。
- `map`、`set`：插入不使任何迭代器失效，`erase` 只使被删的失效。`list`：只使被删的失效。
- `deque`：在两端插入使所有**迭代器**失效，但引用保持有效；在中间插入使两者都失效。

算法侧：`std::sort` 要求 $O(N\log N)$ 次比较，不稳定（内省排序：快排为主，递归过深换堆排，小区间用插入排序，按实现而定）；`stable_sort` 在能申请到足够额外内存时是 $O(N\log N)$，否则退化为 $O(N\log^2 N)$；`nth_element` 平均 $O(N)$。

```cpp
std::vector<int> v;
v.reserve(1024);      // 只改 capacity，一次性分配，消灭后续扩容搬运
v.push_back(1);
v.shrink_to_fit();    // 请求（非强制）释放多余容量；可能导致全部迭代器失效
```

**最小例子**：`std::vector<int> v; for (int i = 0; i < 5; ++i) v.push_back(i);`。按常见实现容量序列为 1→2→4→8，共 3 次扩容，搬运了 $1+2+4=7$ 个元素；改成先 `v.reserve(5)`，搬运次数为 0。另一条：在 `std::list<int>` 上调 `std::lower_bound`，看着像 $O(\log N)$，但 `std::advance` 在链表上是线性的，实际是 $O(N)$ 次比较加 $O(N)$ 次指针跳转；正确做法是用 `std::set`、`std::map` 的成员 `lower_bound`。

**面试高频问法**：

1. 「vector 的 push_back 为什么是摊还 $O(1)$？」→ 考点是几何增长与等比级数求和，不是「因为它会扩容」→ 答法：容量按几何级数增长，第 $i$ 次扩容搬 $c^i$ 个元素，总搬运量是等比级数求和为 $O(N)$，摊到 $N$ 次操作上就是常数；如果是固定增量增长，会退化成 $O(N^2)$。
2. 「vector 和 list 怎么选？」→ 考点是缓存局部性 vs 插入稳定性 → 答法：默认选 vector，连续内存让预取和缓存命中把遍历常数压得很低；只有元素很大、需要在中间稳定插入或频繁 splice、且不关心遍历性能时才用 list。
3. 「unordered_map 什么时候会退化？」→ 考点是哈希冲突与最坏复杂度 → 答法：哈希函数差或被构造冲突时，所有 key 落进同一个桶，单次操作退化为 $O(N)$；可以换哈希并加随机种子，或者改用 map 保住 $O(\log N)$ 的上界。
4. 「vector 扩容后原来的迭代器还能用吗？」→ 考点是失效规则 → 答法：不能，扩容会重新分配内存，全部迭代器、指针、引用都失效；即使不扩容，insert、erase 也会让插入、删除点之后的失效，用完必须重新获取。
5. 「std::sort 为什么不稳定，要稳定怎么办？」→ 考点是算法实现与复杂度代价 → 答法：sort 是内省排序，不稳定但常数小且 $O(N\log N)$ 有保证；要稳定用 stable_sort，代价是额外内存，内存不足时退化为 $O(N\log^2 N)$。

## 第 8 章 异常安全与错误处理

**要解决的问题**：函数执行到一半失败时，对象是否仍在合法状态、资源是否泄漏、调用方能否当没发生过一样重试。面试问「你这个类异常安全吗」，实质是问你知不知道保证级别、会不会用 RAII 和 copy-and-swap 把它做出来。

**机制**：三个保证级别：

- **基本保证**：失败后不泄漏资源、类不变式不被破坏，但对象状态可能已被部分修改。
- **强保证**：失败后对象状态与调用前完全一致（commit-or-rollback，像事务）。
- **nothrow 保证**：承诺不抛异常，通常是 `noexcept` 的 `swap` 或移动构造。

实现强保证靠两条：把可能抛异常的工作全部放到临时对象或副本上完成；最后用 `noexcept` 的 `swap` 提交，这一步不会失败。清理则靠栈展开：异常向外传播时，每一层已构造完成的局部对象按构造逆序析构，析构函数是唯一保证会被执行的清理点。

```cpp
class Buffer {
    std::size_t n_ = 0;
    std::unique_ptr<char[]> p_;
public:
    Buffer(Buffer&&) noexcept = default;
    Buffer& operator=(Buffer o) noexcept {   // 形参的构造（拷贝/移动）发生在进入函数之前
        swap(*this, o);                      // swap 不抛 → 提交阶段不会失败
        return *this;
    }
    friend void swap(Buffer& a, Buffer& b) noexcept {
        using std::swap;
        swap(a.n_, b.n_);
        swap(a.p_, b.p_);
    }
};
```

按值传参是这里的关键：拷贝构造如果抛异常，`*this` 根本还没被碰过，强保证天然成立。

构造函数是特例：对象没构造完成，它自己的析构函数不会被调用，但已构造完成的成员会按逆序析构。所以在构造函数里不要先 `new` 再赋给裸指针成员，用成员 RAII 或函数 try 块。

析构与异常：C++11 起析构函数隐式 `noexcept`，从中抛出会直接 `std::terminate`；栈展开过程中抛出第二个异常同样 `terminate`。确实需要抛，必须显式写 `noexcept(false)`，并保证不在展开期抛。

`move_if_noexcept` 与容器强保证：`vector` 扩容要把旧元素搬到新缓冲，中途失败必须能回滚，所以标准库用 `std::move_if_noexcept`——元素的移动构造是 `noexcept`（或没有可用的拷贝构造）时才移动，否则拷贝。这解释了一个经典现象：写了移动构造却没标 `noexcept`，`vector` 扩容照样走拷贝，性能没提升。

错误码 vs 异常：异常不可被静默忽略、能天然跨多层传播、正常路径几乎零开销（表驱动实现，按实现而定）；错误码不改变控制流、可用于禁用异常的构建（如 `-fno-exceptions`）、适合高频且可预期的失败（解析到一半数据不够、轮询无数据）。C++17 `std::optional` 表达「可能没有值」，`std::error_code` 表达系统错误，C++23 `std::expected` 表达「值或错误」。

**最小例子**：`std::vector<Buffer> v; v.reserve(1); v.push_back(Buffer{}); v.push_back(Buffer{});`，第二次 `push_back` 触发扩容。若 `Buffer` 移动构造是 `noexcept`，旧元素被移动进新缓冲，全程不抛，强保证成立。若移动构造可能抛且 `Buffer` 可拷贝，`move_if_noexcept` 选择拷贝，拷贝中途抛异常时新缓冲被释放、旧 vector 原封不动，仍是强保证。若既不可拷贝、移动又可能抛，标准库无法回滚，只提供基本保证——这就是「移动构造要标 noexcept」的实际收益。

**面试高频问法**：

1. 「异常安全的三个级别是什么？」→ 考点是概念能否落地举例 → 答法：基本保证是不泄漏、不变式不破但状态可能变了；强保证是失败后完全回滚，像事务；nothrow 是承诺不抛。标准库容器多数操作给基本保证，`push_back` 给强保证。
2. 「copy-and-swap 为什么能提供强异常安全？」→ 考点是异常发生时机分析 → 答法：拷贝发生在形参构造阶段，此时 `*this` 还没被修改，拷贝抛异常就直接传播、`*this` 原样；拷贝成功后再用 `noexcept` 的 swap 提交，提交不会失败。
3. 「析构函数能抛异常吗？」→ 考点是栈展开与 terminate → 答法：默认 `noexcept`，抛出会 `std::terminate`；栈展开期间抛出第二个异常也会 `terminate`。所以析构里只能吞掉或记录错误，真要抛就显式 `noexcept(false)`，并保证不在展开期抛。
4. 「移动构造为什么建议标 noexcept？」→ 考点是 `move_if_noexcept` 与容器强保证 → 答法：`vector` 扩容时只有移动构造是 `noexcept` 才敢移动，否则为了保留回滚能力退回拷贝；标了才真正拿到移动的性能。
5. 「什么时候用错误码而不是异常？」→ 考点是错误处理策略的取舍 → 答法：失败是常态且高频（解析、轮询）、需要禁用异常、或要跨 C ABI 边界时用错误码或 `expected`；异常适合真正异常、无法就地处理、需要跨层传播的错误。

## 第 9 章 并发：thread、mutex、atomic

**要解决的问题**：把单线程顺序执行扩展到共享地址空间的多线程，并保证共享数据的访问不落入数据竞争。若这一层没处理好，代码会偶发丢更新、崩溃、死锁，且难以复现。

**机制**：

- `std::thread` 构造即启动一个新执行流。线程对象有 `joinable` 状态：`join()` 阻塞等待结束并回收；`detach()` 分离；析构时仍 `joinable` 会调用 `std::terminate`。线程函数参数默认按值拷贝/转发，要传引用需显式 `std::ref`。
- `std::mutex` 提供互斥进入临界区。`std::lock_guard` 是 RAII 加锁/解锁；`std::unique_lock` 支持延迟加锁、手动解锁，常配合 `std::condition_variable`。多把锁用 `std::scoped_lock`（C++17）或 `std::lock` 一次性锁定，降低死锁概率。
- `std::atomic<T>` 对单个对象提供原子 `load/store/read-modify-write`，默认内存序是 `seq_cst`。它不保护“多个变量共同构成的不变量”，也不自动把一段复合操作变原子。
- `condition_variable::wait(lk, pred)` 内部循环检查谓词，用来防虚假唤醒和丢失唤醒；谓词读共享状态时必须持锁。
- 关键接口：`std::thread t(f, args...)`、`t.join()`、`std::mutex m`、`std::lock_guard<std::mutex> lk(m)`、`std::atomic<int> x{0}`、`x.fetch_add(1, std::memory_order_relaxed)`、`x.load()`。原子操作底层可能编译为原子指令或库锁，按平台和实现而定。

**最小例子**：

两个线程各执行 100000 次自增：

```cpp
#include <atomic>
#include <thread>
#include <iostream>

std::atomic<long> cnt{0};

void worker() {
    for (int i = 0; i < 100000; ++i)
        cnt.fetch_add(1, std::memory_order_relaxed);
}

int main() {
    std::thread a(worker), b(worker);
    a.join(); b.join();
    std::cout << cnt.load(std::memory_order_relaxed); // 200000
}
```

这里只需保证单个计数器的原子性，`relaxed` 足够。若把 `cnt` 换成普通 `long` 并写 `++cnt`，两个线程的读改写会交错，构成数据竞争，结果未定义，可能小于 200000。

**面试高频问法**：

- **问法**：`mutex` 和 `atomic` 怎么选？ → **考点**：临界区范围与不变量。 → **答法**：保护多个共享对象或复合不变量用 `mutex`，单个计数器/标志位用 `atomic`，不要用一堆原子变量手写锁。
- **问法**：死锁怎么避免？ → **考点**：持有并等待、循环等待。 → **答法**：固定锁顺序、用 `std::scoped_lock` 一次锁多把、缩小临界区、避免锁内回调外部代码。
- **问法**：`condition_variable` 为什么 `wait` 要带谓词循环？ → **考点**：虚假唤醒和丢失唤醒。 → **答法**：`wait(lk, pred)` 会循环检查谓词，醒来后条件不成立继续等，且谓词读共享状态必须持锁。
- **问法**：`memory_order_relaxed` 够用吗？ → **考点**：原子性与顺序性分离。 → **答法**：它只保证该原子对象的原子性和修改顺序，不建立跨线程 `happens-before`；要发布数据用 `release/acquire` 或 `seq_cst`。
- **问法**：`std::thread` 析构为什么可能 `terminate`？ → **考点**：`joinable` 状态。 → **答法**：线程对象析构时必须已 `join` 或 `detach`，否则标准调用 `std::terminate`，工程上用 RAII 包装避免漏掉。

## 第 10 章 未定义行为与内存模型

**要解决的问题**：解释为什么有些 C++ 代码“本机跑得好”却不可移植、开优化就失效；同时给出跨线程可见性的标准规则。不解决则无法判断数据竞争、悬垂访问和 `memory_order` 的边界。

**机制**：

- 未定义行为（UB）不是“一定崩溃”，而是标准不再规定程序行为。编译器可以假设 UB 不发生，并据此做优化。常见来源：越界访问、空指针/悬垂指针解引用、有符号整数溢出、读未初始化对象、违反严格别名、对象生命周期外访问、数据竞争。
- 对象模型上，对象有存储期和生命周期；访问生命周期已结束的对象是 UB。用 `reinterpret_cast` 跨类型读写常违反严格别名，`char`、`unsigned char`、`std::byte` 观察对象表示是例外。
- C++11 起标准定义内存模型，核心关系是 `happens-before` 与 `synchronizes-with`。同一内存位置被多个线程并发访问，至少一个写，且没有同步建立 `happens-before`，就是 data race，行为未定义。
- 原子操作加内存序控制重排：`relaxed` 只保证该原子对象原子性和修改顺序；`release` 阻止之前的读写移到该操作之后；`acquire` 阻止之后的读写移到该操作之前；`release store` 与读到该值的 `acquire load` 建立同步；`seq_cst` 额外给所有 `seq_cst` 操作一个全局总序。
- 关键接口：`std::atomic<T>::load/store/exchange/compare_exchange_weak`、`std::memory_order_*`、`std::atomic_thread_fence`、`std::launder`（C++17，用于某些对象复用后的指针场景）。这些工具只保证标准规定的顺序，不替调用者检查逻辑竞态。

**最小例子**：

生产者先写 `data`，再用 `release` 发布 `ready`；消费者用 `acquire` 读到 `true` 后读 `data`：

```cpp
#include <atomic>
#include <cassert>

std::atomic<bool> ready{false};
int data = 0;

void producer() {
    data = 42;
    ready.store(true, std::memory_order_release);
}

void consumer() {
    while (!ready.load(std::memory_order_acquire)) {}
    assert(data == 42); // 成立
}
```

具体执行：`producer` 写 `data=42`，`release store` 将 `ready` 置真；`consumer` 的 `acquire load` 读到该值后，`data=42` 对它是可见的，`assert` 成立。若两个内存序都改成 `relaxed`，`data` 的非原子写和读之间没有 `happens-before`，构成 data race，行为未定义，`assert` 可能失败，也可能发生其他不可预期结果。

**面试高频问法**：

- **问法**：什么是 UB，编译器为什么能“利用”它？ → **考点**：标准约束与优化假设。 → **答法**：UB 是标准不规定结果，编译器可假设该路径不发生并做激进优化，所以“能跑”不等于正确。
- **问法**：data race 和 race condition 有什么区别？ → **考点**：内存模型层与逻辑层。 → **答法**：data race 是未同步的冲突访问，直接 UB；race condition 是结果依赖时序的逻辑问题，用锁后仍可能存在。
- **问法**：`release/acquire` 建立什么关系？ → **考点**：`synchronizes-with` 与可见性。 → **答法**：`release store` 之前的写，对读到该 store 值的 `acquire load` 之后的读可见。
- **问法**：`relaxed` 能做什么、不能做什么？ → **考点**：原子性与顺序性分离。 → **答法**：能保证该原子对象不被撕裂并维持修改顺序，不能保证其他内存操作的跨线程可见顺序。
- **问法**：有符号溢出为什么是 UB，无符号呢？ → **考点**：标准规定。 → **答法**：有符号溢出是 UB；无符号按 $2^N$ 取模回绕，不能把有符号溢出当成可依赖的回绕。
