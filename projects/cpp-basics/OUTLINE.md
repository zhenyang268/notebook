## 一、它在做什么

本项目要搭一个“能亲手验证结论”的 C++ 核心实验工程，用一组自己实现的最小类型、容器和所有权包装，把对象模型、资源管理、泛型与并发这四块知识变成可观察、可对比、可压测的现象。输入是若干 C++ 类型及其使用场景：构造与析构、拷贝与移动、异常路径、容器操作、线程竞争等；输出是三类证据：对象生命周期与拷贝/移动计数日志、容器操作次数随规模变化的曲线、并发压力下的行为记录与 sanitizer/编译器告警报告。验收标准是：对给定代码先预测行为，再用工程复现；能把危险写法改成 RAII、所有权明确、异常安全且并发正确的版本，并说清代价。最终形成一套能讲清“为什么这样设计”的面试口径，而不是题库答案。

## 二、为什么这样做（功能设计）

核心设计是把标准库里最容易被面试追问、又最容易被黑盒化的组件替换成教学版，而不是只读标准。替换发生在用户态接口层：场景程序只依赖值语义、迭代器/视图、所有权接口，底层可在“教学版”和“标准版”之间切换，用同一组场景对比行为。不碰内核态，线程与原子原语仍用标准库，只在外面加可观测壳，避免把项目做成操作系统课。必须自己实现的约定包括：构造函数建立不变量、析构释放资源；moved-from 对象保持有效但值未指定；迭代器失效规则；`unique_ptr` 表达独占，`shared_ptr` 的控制块线程安全与对象线程安全分开。

数据形态与不可靠性要一起设计。日志记录事件序列而不是地址；计数包括构造、析构、拷贝、移动、交换；复杂度用比较/移动/分配次数随 n 的变化验证，而不是只看墙钟时间；并发用固定次数压力循环、原子停止标志和多种调度窗口复现交错。不可靠性来自未指定求值顺序、分配器与地址随机化、线程调度、优化级别和未定义行为。压制手段是确定性事件编号、可注入分配器、ASan/UBSan/TSan、`-O0` 与 `-O2` 对照、重复运行与最小复现；对 UB 只承认可观测的崩溃、告警或行为差异，不把某次运行结果当规则。

关键决策及代价如下：

- **手写 String/Vector/UniquePtr/SharedPtr/ScopeGuard 等最小版本**，接口与 STL 用法对齐，但只实现课程需要的子集。直接用 `std::string`/`std::vector` 会把拷贝、移动、扩容和析构藏起来，面试追问“发生几次拷贝”“迭代器何时失效”时只能背。代价是要自己处理分配失败、自赋值、异常回滚和迭代器失效，出错率更高，但这正是训练点。

- **默认值语义与 RAII，禁止业务代码裸 `new/delete`**；锁、文件、动态库句柄都用 guard。手动 release 在异常和提前返回时会漏释放；代价是对象生命周期被绑定到作用域，需要理解移动和析构顺序。

- **拷贝控制按 Rule of 0/5 决策**：能靠成员自动生成就不手写；需要手写时成对实现拷贝/移动/析构，移动构造标 `noexcept`，拷贝用 copy-and-swap 保异常安全。全部禁拷贝会排除必要的值类型；全部 `shared_ptr` 会掩盖归属、增加计数开销并引入循环引用。代价是要逐个类型判断语义。

- **智能指针分层**：`unique_ptr` 表达独占，`shared_ptr` 只在真共享时用，`weak_ptr` 破环，自定义 deleter 管理非内存资源。裸指针加注释不是编译器可检查的约定；代价是 `shared_ptr` 的控制块线程安全不等于对象线程安全，仍需额外同步。

- **模板以“约束 + 用例”驱动**：先写普通函数，出现重复且类型无关时再模板化；用 `static_assert`/concepts 把错误提前到编译期。宏没有类型检查，`void*` 丢失语义；代价是模板错误信息更长、可能代码膨胀，需要限制实例化范围。

- **STL 选择以复杂度而不是“顺手”为准**：顺序访问用 `vector`，频繁中间插入才考虑 `list`，查找看是否有序、是否需要稳定迭代器；算法用操作计数和曲线验证 O(n)、O(log n)、O(n log n)。全都上 `map` 会忽略常数、缓存局部性和内存开销；代价是要做基准测量，不能只看大 O。

- **异常安全分三级**：不泄漏、不破坏不变量、强保证；只有能证明不抛且必要的操作标 `noexcept`。错误码不能自然解决构造失败和模板库兼容问题；到处 `try/catch` 又会破坏 RAII 的清晰边界。代价是每条资源路径都要设计回滚。

- **并发默认“先正确再快”**：`mutex` + `condition_variable` 保护共享状态，`atomic` 只用于无共享不变量的计数或标志；内存序从 `seq_cst` 起步，确有必要再放宽。上来写无锁队列会把问题变成 ABA、内存序和伪共享的复合故障；代价是锁竞争可能成为瓶颈，需要测量后再优化。

## 三、章节大纲

1. **类型系统**：内置类型、cv 限定、指针/引用、数组/函数/类类型、类型转换与别名；讲清类型决定可用操作和对象布局。验证：对声明判断大小、对齐和隐式转换，用 `static_assert` 固定假设。

2. **值与引用**：值类别、左值/右值、引用绑定、const 正确性、视图类型不拥有资源；验证重载选择与引用折叠，识别悬垂引用。

3. **构造**：默认/拷贝/移动/转换构造、`explicit`、成员初始化列表、初始化顺序、委托构造；验证对象不变量在构造完成时成立，构造失败不泄漏。

4. **析构与对象生命周期**：存储期、构造/析构顺序、虚析构、临时对象、数组与聚合；验证不同作用域、继承和异常展开下的析构次序。

5. **RAII 与资源管理**：guard 包装内存、锁、文件、句柄；Rule of Zero；禁止裸资源；验证提前返回和异常抛出时资源释放。

6. **拷贝控制与移动语义**：拷贝构造/赋值、移动构造/赋值、自赋值、copy-and-swap、moved-from 有效；验证计数变化与 `noexcept` 对容器重分配的影响。

7. **智能指针与所有权模型**：`unique_ptr`/`shared_ptr`/`weak_ptr`、deleter、循环引用、控制块；验证独占转移、共享计数、破环和异常路径释放。

8. **模板与泛型编程**：函数/类模板、特化、可变参数、SFINAE/concepts、编译期约束、代码膨胀；验证同一算法对多类型实例化，错误在编译期暴露。

9. **STL 容器与算法复杂度**：`vector`/`deque`/`list`/`map`/`unordered_map` 的布局、迭代器失效、复杂度、allocator 基础；验证操作计数曲线与容器选择。

10. **异常安全与错误处理**：异常传播、栈展开、`noexcept`、三个保证等级、错误码与异常的边界；验证强保证交换、构造失败回滚。

11. **并发：thread、mutex、atomic**：线程生命周期、锁、条件变量、原子类型、内存序、虚假唤醒、死锁；验证竞态用 TSan 复现，修复后用压力循环验证。

12. **未定义行为与内存模型**：对象生命周期与有效类型、越界、悬垂、未初始化、有符号溢出、数据竞争、优化与 UB；验证 sanitizer 报告与 `-O0`/`-O2` 差异，写最小复现。

## 四、不做什么

不实现完整 STL、通用 allocator、编译期元编程库或 `std::function`/`variant`/`any` 的全量功能；不写无锁数据结构、协程、网络库、内核模块；不覆盖 C++ 全语法、GUI、嵌入式或跨平台 ABI 细节。性能只验证复杂度阶和明显退化，不做微优化，不承诺生产级吞吐。并发正确性以标准库原语和 sanitizer 为准，不把“某次没崩”当正确性证明。

实现自由度包括：容器增长因子、日志粒度和格式、测试框架、使用 C++17 还是 C++20 concepts、错误处理风格的取舍；这些可以自选，但对外语义必须一致，并在文档中说明假设。常见跑偏是：背题不实验；用 `sleep` 和打印代替同步与断言；把 `shared_ptr` 当万能所有权；把 UB 实验观测到的结果当语言保证；过早写无锁结构；只测墙钟时间不看操作计数；异常安全只写在注释里。边界清楚，项目才不会变成“标准库重写”或“面试题收集”。

## 五、面试怎么讲

### 30 秒版本

> “这个项目是我给自己搭的一套 C++ 基础核对清单：把对象模型、资源管理、泛型、并发四块，拆成能被验证的小例子，不是造轮子。最卡的点是，C++ 里‘跑通了’和‘写对了’经常是两回事——悬垂指针、data race、异常路径上的泄漏，正常跑一遍什么都看不出来。所以每条结论我都想配一个失败时会报错的检查：ASan/UBSan 抓内存错误和 UB，TSan 抓竞争，static_assert 钉住 sizeof 和类型假设。验证口径就一句：这条结论有没有工具能证伪它。”

开场只讲“要解决什么、卡在哪、怎么验证”。项目本身多小不重要，面试官听的是你有没有“可证伪”的意识。

### 可能被追问的 6–8 个点

**1. 他问：“虚函数怎么实现的？一个类几个 vptr？” → 考点：分不分得清“标准规定”和“ABI 实现”。**

答：先划边界——标准只规定“通过基类指针调用要派发到动态类型”，vptr 放在对象起始位置、vtable 里 slot 的顺序，是 Itanium ABI 这类实现约定，MSVC 不完全一样。在这个前提下再说：单继承通常一个 vptr 在偏移 0；多继承时从第二个“有虚函数的多态基类”开始，每个基类子对象各带一个 vptr，所以派生类指针转成非首基类指针要加偏移，调虚函数时还要用 thunk 回调整 `this`；虚拟继承一般靠 vbase offset 表项。再补两个能体现读过的细节：构造函数里 vptr 是逐层设置的，所以构造/析构函数中调虚函数只派发到当前层；空基类优化会让 `sizeof` 不等于“各成员 sizeof 之和”。

**2. 他问：“构造过程中抛异常会发生什么？你的 RAII 类怎么保证异常安全？” → 考点：资源归属、异常保证级别。**

答：构造失败时，已构造完成的成员按声明逆序析构，但类自己的析构函数不会执行——所以资源必须交给成员或已构造完的基类持有，裸指针成员就是坑。异常保证按三级说：基本（不泄漏、对象仍可用）、强（copy-and-swap：先在副本上做完，再 swap，而 swap 通常 noexcept）、不抛（`noexcept`）。补一句：析构函数默认 `noexcept`，栈展开时它抛就 `std::terminate`，所以析构里不能抛。顺带说成员初始化顺序按**声明顺序**，不是初始化列表书写顺序，`-Wreorder` 能抓。

**3. 他问：“`std::move` 做了什么？vector 扩容什么时候拷贝、什么时候移动？” → 考点：move 只是 cast；`move_if_noexcept`。**

答：`std::move` 本身不移动任何东西，就是一个到右值引用的 `static_cast`，资源转移发生在被选中的移动构造/移动赋值里。vector 扩容要强异常保证，所以用的是 `move_if_noexcept`：移动构造没标 `noexcept` 且类型可拷贝时，它宁可拷贝——因为移到一半抛了，原容器已被改坏，回不去。还有：一旦用户声明了拷贝构造、拷贝赋值或析构，移动操作就不再隐式生成，后续调用会静默退化成拷贝，得用 `= default` 补回来。移动后的对象是“有效但未指定状态”，只能析构或重新赋值。

**4. 他问：“`shared_ptr` 线程安全吗？`make_shared` 和 `shared_ptr(new T)` 差在哪？” → 考点：线程安全的边界在控制块，不在对象。**

答：`shared_ptr` 只保证控制块安全——引用计数增减是原子的，多线程各自拷贝/销毁各自的实例没问题；但同一个 `shared_ptr` 实例被多线程读写是 data race，所指对象本身也不线程安全。`make_shared` 把对象和控制块放进一次分配，少一次 `new`、局部性更好；代价是只要还有 `weak_ptr` 活着，对象那块内存也释放不掉，对象大而 `weak_ptr` 活得久时反而更费。循环引用用 `weak_ptr` 打断；`enable_shared_from_this` 里就是一个 `weak_ptr` 成员，所以必须在 `shared_ptr` 接管之后才能用，构造函数里调 `shared_from_this` 会抛 `bad_weak_ptr`。

**5. 他问：“模板里 `typename` 什么时候必须写？” → 考点：两阶段名字查找、依赖名。**

答：模板定义时做一次非依赖名字查找，实例化时再做依赖名字查找。凡是依赖模板参数的类型名，编译器默认按值解析，所以要 `typename` 显式说明；依赖名当模板用时要用 `.template` / `->template` 消歧。这也是“定义时不报、实例化才报”的来源。往下可以接 SFINAE——替换失败不算错误，只是把该候选从重载集里去掉，`enable_if`、`void_t` 都是这个机制；再往后是 C++20 concepts，把约束写在签名上，报错位置提前到调用点，不用再堆 `enable_if`。

**6. 他问：“`vector::push_back` 什么复杂度？`unordered_map` 查找最坏多少？” → 考点：摊还 vs 最坏；失效规则。**

答：`push_back` 是摊还 O(1)、单次最坏 O(n)：容量满时按倍数（1.5 或 2）重新分配并搬迁，所以不能对每次调用都承诺 O(1)；`reserve` 过就没有这次搬迁。`unordered_map` 平均 O(1)、最坏 O(n)，全撞进一个桶就退化（有的实现超阈值转红黑树），所以 key 的哈希质量真的影响复杂度。失效规则要分清：`vector` 扩容让所有指针/引用/迭代器失效，`erase` 让删除点及之后失效；`unordered_map` rehash 让迭代器失效，但指向元素的引用和指针仍有效；`map`/`list` 插入不影响其他元素。

**7. 他问：“两个线程同时读写一个 `int`，用 `atomic` relaxed 够不够？`volatile` 行不行？” → 考点：data race 是 UB；happens-before。**

答：非 atomic 的并发读写就是 data race，标准里直接是未定义行为，不是什么温和的“读到旧值”。`volatile` 在 C++ 里是给内存映射 I/O 和信号处理用的，不提供原子性，也不建立跨线程顺序，不能当同步原语。`atomic` 的关键在 order：`relaxed` 只保证这个变量自身的原子性和修改顺序一致，不建立线程间 happens-before；要让 A 线程写的数据对 B 可见，写端 `release`、读端 `acquire`，形成 synchronizes-with；`seq_cst` 在此之上再加全局单一总序，代价最大。双检锁那个经典写法就是 flag 用 release 存、acquire 读，否则可能看到指针非空但对象还没构造完。

**8. 他问：“你怎么确认代码里没有未定义行为？” → 考点：知不知道工具的能力边界。**

答：先诚实——不能完全确认，只能缩小范围。做法是 `-Wall -Wextra` 清告警，再上 ASan+UBSan，并发路径用 TSan（ASan 和 TSan 不能同时开）。但 sanitizer 只覆盖执行到的路径，所以测试要打边界：空容器、自赋值、抛异常的中途、`size() == capacity()` 的瞬间、移动后再用。几个高频坑可以主动提：有符号溢出是 UB（无符号是回绕）、返回局部变量的引用、strict aliasing 下 `reinterpret_cast` 后解引用。这些工具不一定抓得住，得靠类型设计和 review。

### 别说什么

1. **别把实现当标准。** “vptr 一定在对象开头”“标准规定 vtable 有几个 slot”——标准根本不管布局。正确说法是“标准只保证派发行为，布局我看的是 Itanium ABI”。把 ABI 说成标准，一追问 MSVC 就崩。
2. **别把“跑通”当“写对”。** “我跑过没崩”“没有内存问题”——没开 sanitizer、没覆盖异常路径时这话站不住。换成“我能验证的是执行到的路径干净，没覆盖到的是并发和异常中途”。
3. **别报没测过的数字。** “性能提升 3 倍”“内存省了一半”——要么说清口径（什么负载、哪个编译器、什么优化级别、和谁比），要么干脆不说。面试官一句“怎么测的”就能问穿。
4. **别把“我了解”说成“我做了”，也别堆术语不落地。** 一口气报 RAII、SFINAE、happens-before 却举不出一个具体例子（比如“移动构造没标 noexcept，所以 vector 走拷贝”），听起来就是背的。宁可少说一个，把机制讲透；做过的说做过，读过的说读过。
