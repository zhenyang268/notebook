# database · 分章详细

## 第 1 章 关系模型与 SQL 的逻辑执行顺序

**要解决的问题**：把「表是集合」和「SQL 是声明式」这两个前提明确下来，并给出子句的**逻辑**求值顺序。不解决这件事，后面所有讨论都会偏离实际：为什么 `WHERE` 里不能用 `SELECT` 的别名、为什么 `LEFT JOIN` 的过滤条件写错位置会把外连接退化成内连接、为什么 `NOT IN` 遇到 `NULL` 会返回空集、为什么优化器可以任意重排你的子句。

**机制**：

关系模型（Codd, 1970）的三要素是结构（关系/表）、完整性约束（主键、外键、`NOT NULL`、`CHECK`）、操作（选择、投影、连接、并、差，闭包在关系上）。关键点是：**关系是元组的集合，无序、无重复**。而 SQL 表是**多重集（bag）**——允许重复行，除非被 `PRIMARY KEY`/`UNIQUE`/`DISTINCT` 约束掉。这个偏差是 `LIMIT` 不带 `ORDER BY` 时结果不稳定、`COUNT(*)` 与 `COUNT(DISTINCT)` 结果不同等问题的根源。

SQL 是声明式语言：你写的是「要什么」，逻辑执行顺序定义「语义上按什么次序算」，物理执行由优化器决定，可以完全不同的顺序和算法（这就是第 10 章代价模型存在的原因）。逻辑顺序只在两件事上对你可见：**名字可见性**与 **`NULL`/聚合的求值范围**。

```text
R0 = FROM 求值（多表做笛卡尔积，ON 作为连接条件参与）
R1 = WHERE(R0)        -- 行级过滤；此时 SELECT 别名尚不存在，聚合函数非法
R2 = GROUP BY(R1)     -- 塌缩成"每组一行"，此后列只能来自分组键或聚合
R3 = HAVING(R2)       -- 组级过滤，可含聚合
R4 = SELECT(R3)       -- 表达式、窗口函数在此阶段求值
R5 = DISTINCT(R4)
R6 = ORDER BY(R5)     -- 唯一能同时看到 SELECT 别名和聚合结果的阶段
R7 = LIMIT / OFFSET(R6)
```

`NULL` 走三值逻辑：`TRUE`/`FALSE`/`UNKNOWN`，`WHERE` 只保留 `TRUE`；`NULL = NULL` 得 `UNKNOWN`，所以 `COUNT(col)` 跳过 `NULL` 而 `COUNT(*)` 不跳。

**最小例子**：设 `a(id)` 有 `1, 2`，`b(id)` 只有 `1`。

```sql
SELECT a.id, b.id FROM a LEFT JOIN b ON a.id = b.id AND b.id > 1;
-- 结果：(1, NULL), (2, NULL)  —— 条件写在 ON，只影响"能否配上"，左表行照样保留

SELECT a.id, b.id FROM a LEFT JOIN b ON a.id = b.id WHERE b.id > 1;
-- 结果：空集  —— WHERE 在连接之后执行，把 b.id 为 NULL 的行全部判为 UNKNOWN 滤掉
```

另一条：`SELECT COUNT(*) FROM t WHERE v <> 1;` 当 `v` 为 `NULL` 时该行不计数，因为 `NULL <> 1` 是 `UNKNOWN` 而非 `TRUE`。

**面试高频问法**：

1. 「`WHERE` 里为什么不能写 `SELECT` 的别名？」→ 考点是逻辑执行顺序与名字作用域 → 答法：「`WHERE` 在 `SELECT` 之前求值，别名那时还不存在；`ORDER BY` 在 `SELECT` 之后，所以能用别名。MySQL 在 `HAVING` 里放宽了别名引用，那是扩展不是标准。」
2. 「`LEFT JOIN` 的过滤条件写 `ON` 和写 `WHERE` 有什么区别？」→ 考点是外连接语义 → 答法：「`ON` 只决定右表能不能配上，配不上补 `NULL`；`WHERE` 在连接结果上过滤，写右表列的非空条件会把补 `NULL` 的行滤掉，外连接退化成内连接。」
3. 「`SELECT * FROM t LIMIT 10` 每次结果一样吗？」→ 考点是关系无序性 → 答法：「不保证。关系没有顺序，没有 `ORDER BY` 时返回哪 10 行由执行计划和存储顺序决定，分页必须带确定的排序键。」
4. 「为什么 `NOT IN (子查询)` 子查询里有 `NULL` 就查不出数据？」→ 考点是三值逻辑 → 答法：「`x NOT IN (1, NULL)` 展开成 `x<>1 AND x<>NULL`，后半是 `UNKNOWN`，整体不为 `TRUE`，所以一行都不返回；改 `NOT EXISTS` 或加 `IS NOT NULL`。」
5. 「SQL 是声明式的，那执行顺序有意义吗？」→ 考点是逻辑顺序 vs 物理计划 → 答法：「逻辑顺序定义语义，决定别名可见性和 `NULL`/聚合的处理；物理顺序由优化器按代价选，两者可以完全不同。」

## 第 2 章 存储引擎：页、行格式与堆表

**要解决的问题**：为什么数据库不是「读一行就一次磁盘 IO」，而是以**页**为单位搬运；一行数据在磁盘上到底长什么样（隐藏列是第 7 章 MVCC 的物理前提）；以及「堆表」和「索引组织表」这两种表的物理组织方式决定了后面所有索引讨论的走向。

**机制**：

**页是 IO 与缓存的最小单位**。InnoDB 默认 `innodb_page_size = 16KB`（可配 4K/8K/16K/32K/64K），Buffer Pool、redo、磁盘读写都以页为粒度。一次读取 16KB 即使你只要 1 行——这是 B+ 树扇出要尽量大、行要尽量窄的原因。

InnoDB 页的物理布局（16KB 页）：

```text
FIL Header(38B) | Page Header(38B) | Infimum/Supremum 两条伪记录
| User Records（按主键升序单向链表）| Free Space
| Page Directory（稀疏槽位，槽覆盖约 4~8 条记录）| FIL Trailer(8B，含校验和)
```

页内查找先用 Page Directory 二分定位到槽，再在槽内沿链表线性找；页之间是双向链表，上一层是 B+ 树非叶节点（第 3 章展开）。

**行格式**：`REDUNDANT` / `COMPACT` / `DYNAMIC` / `COMPRESSED`，MySQL 8.0 默认 `DYNAMIC`。`COMPACT` 一行的组成是：

```text
变长字段长度列表（逆序）| NULL 标志位图 | 5 字节记录头（含 n_owned、next_record 偏移）
| 列数据 | [DB_ROW_ID 6B] | DB_TRX_ID 6B | DB_ROLL_PTR 7B
```

`DB_ROW_ID` 只在没有主键也没有非空唯一索引时生成；`DB_TRX_ID`（最后修改它的事务 ID）和 `DB_ROLL_PTR`（指向 undo 中的旧版本）是 MVCC 版本链的锚点。`DYNAMIC` 与 `COMPACT` 的关键差别在溢出列：超长变长列不在页内存前缀，而是整行放到溢出页、本页只留 20 字节指针（`COMPACT` 会存 768 字节前缀 + 20 字节指针）。

**两种表的组织方式**：

- **索引组织表（IOT）**：InnoDB。数据即主键的聚簇索引，叶子页存整行；二级索引叶子存「索引列 + 主键值」，所以二级索引查非覆盖列要回表。
- **堆表**：MyISAM 等。`.MYD` 数据文件按插入顺序追加，`.MYI` 索引文件独立，索引叶子存行的物理偏移（RID）。堆表的行位置会因删除空洞和复用而变化，且没有聚簇概念。

空间按「段 → 区（extent，默认 1MB = 64 个 16KB 页）→ 页」管理。

**最小例子**：

```sql
SELECT @@innodb_page_size;                    -- 16384
SELECT NAME, ROW_FORMAT FROM information_schema.INNODB_TABLES WHERE NAME = 'shop/orders';
-- shop/orders | Dynamic
```

容量估算（算术，非实测）：每行约 200 字节时，一页可放 $\lfloor (16384 - \text{页头/目录开销}) / 200 \rfloor \approx 80$ 行；非叶节点每条目约 14 字节（主键 + 页号），一页可放约 1000 个条目。三层树即 $1000 \times 1000 \times 80$ 量级，这就是「B+ 树三四层就够」的来源。再看 `orders(id BIGINT PK, user_id BIGINT, status TINYINT, created DATETIME)`：二级索引 `(user_id)` 的叶子只有 `user_id + id`，查 `status` 必须回表；改成 `(user_id, status)` 就变成覆盖索引，这正是第 3 章和第 10 章的落点。

**面试高频问法**：

1. 「为什么数据库按页读写而不是按行？」→ 考点是 IO 粒度与局部性 → 答法：「磁盘和 Buffer Pool 的最小单位是页（InnoDB 默认 16KB），一次 IO 会覆盖相邻的多行；扇出大、层数少、缓存命中率高，代价是单行更新也要写整页并产生写放大。」
2. 「InnoDB 和 MyISAM 的表在磁盘上有什么本质区别？」→ 考点是聚簇 vs 堆表 → 答法：「InnoDB 是索引组织表，主键索引的叶子就是整行数据，二级索引存主键；MyISAM 是堆表，数据文件按插入顺序放、索引文件独立存行偏移，所以它的索引不覆盖数据、也没有聚簇索引。」
3. 「`DB_TRX_ID` 和 `DB_ROLL_PTR` 是干什么的？」→ 考点是行格式与 MVCC 的衔接 → 答法：「每行隐藏两个列：最后修改它的事务 ID，和指向 undo 里上一个版本的指针；两者串成版本链，快照读就是沿这条链找到可见版本。」
4. 「`COMPACT` 和 `DYNAMIC` 行格式差在哪？」→ 考点是溢出页策略 → 答法：「主要差在超长变长列的存储，`DYNAMIC` 不在页内存前缀、整行放溢出页只留 20 字节指针，`COMPACT` 要存 768 字节前缀；所以 `DYNAMIC` 对含 `TEXT`/`BLOB` 的表页内密度更好。」
5. 「为什么建议用自增主键而不是 UUID？」→ 考点是聚簇索引的插入位置 → 答法：「InnoDB 按主键顺序组织叶子页，自增值总在最右页追加；随机 UUID 会往中间页插，触发频繁页分裂和随机 IO，而且二级索引要存 16 字节主键，比 8 字节 `BIGINT` 更占空间。」

## 第 3 章 索引一：B+ 树的结构、分裂与回表

**要解决的问题**：把「按主键或某个字段找一行」从全表扫描的 $O(N)$ 次磁盘 IO 降到 $O(\log N)$ 次，并且让范围查询和排序也能用上同一棵树。不解决它，SQL 一旦落到百万行以上，任何点查都会是全表扫描。

**机制**

B+ 树的节点就是存储引擎的页（InnoDB 默认 16KB，大小按实现而定）。关键结构分两类：

- 非叶节点只存 `key → 子页号`，不存行数据，所以一页能塞下上千个 key，分支因子大。
- 叶节点存 `key → 行`（聚簇索引）或 `key → 主键`（二级索引），叶之间用双向链表串起来，范围扫描就是链表上顺序走。

树高按假设参数估算：非叶每项 `8B key + 6B 页号 = 14B`，一页约 1170 项；叶行按 1KB 算，一页约 16 行。两层非叶加一层叶可达 $1170 \times 1170 \times 16 \approx 2\times10^7$ 行，也就是三到四次 IO 就能定位。这就是「B+ 树矮胖、磁盘友好」的定量依据。

**分裂**：叶页写满后插入新 key，流程是：

```text
insert(key):
  leaf = descend(root, key)          # 从根按 key 逐层向下
  if leaf.has_space: leaf.insert_sorted(key); return
  new = alloc_page()
  split_point = choose_split(leaf, key)   # 常见是中间位置，顺序插入时
                                          # 可以不均分，按实现而定
  move(leaf[split_point:], new)
  push_up(leaf.max_key, new.page_no)      # 中间 key 上推到父页
  if parent.full: 递归分裂           # 一直裂到根
  if root.full: 新建根，树高 +1
```

父页容量不够就继续向上分裂；根分裂时新建一层根，树高加一。所以 B+ 树是「从叶子长、向根裂」，任何时刻所有叶节点深度相同，天然平衡。

**回表**：二级索引的叶只存主键值。`WHERE user_id = 42` 走二级索引拿到一批 `id`，再用这些 `id` 去聚簇索引逐条查整行——这就是回表，代价是每行一次随机 IO，而且主键无序时等于随机访问。

缓解手段有几种常见做法：覆盖索引（查询列全在索引里，不用回表）、索引条件下推（把能在索引层判断的条件先过滤掉，减少回表行数，MySQL 5.6 起支持 ICP）、以及把主键排序后批量回表（MRR 的思路）。

**最小例子**

```sql
CREATE TABLE orders (
  id BIGINT PRIMARY KEY,
  user_id BIGINT,
  amount INT,
  KEY idx_user (user_id)
) ENGINE=InnoDB;

-- ① 回表
SELECT * FROM orders WHERE user_id = 42;
-- idx_user 叶节点找到 id ∈ {1001, 1007, 2050...}
-- 再按每个 id 查聚簇索引取 amount 等列 → N 次回表

-- ② 覆盖索引，不回表
SELECT id FROM orders WHERE user_id = 42;
-- idx_user 叶里就有 id，EXPLAIN 的 Extra 出现 Using index

-- ③ 联合索引 (user_id, amount) 后
SELECT amount FROM orders WHERE user_id = 42;  -- 也变成覆盖索引
```

用 `EXPLAIN` 看三件事：`key` 走了哪个索引、`rows` 估算扫多少行、`Extra` 里有没有 `Using index`（覆盖）或 `Using index condition`（ICP）。

**面试高频问法**

1. **「为什么 MySQL 用 B+ 树，不用 B 树、红黑树或哈希？」**
   → 考点是磁盘 IO 模型与查询形态。答法：磁盘按页读，树高每加一层就多一次 IO，B+ 树非叶不存数据、分支因子大，树高比 B 树更矮；红黑树是二叉的，几百万行树高二十多层，等于二十多次 IO；哈希只能等值不能范围，也不能排序。所以「矮 + 叶节点有序链表 + 支持范围」三件事同时满足的只有 B+ 树。

2. **「聚簇索引和二级索引的区别？回表是什么？」**
   → 考点是有没有存整行。答法：聚簇索引按主键组织，叶节点就是整行数据，一张表只有一个；二级索引叶节点存的是索引列加主键值。用二级索引查到主键后再去聚簇索引取整行，这一次额外查找就叫回表，成本是每行一次随机 IO，所以要尽量用覆盖索引把回表省掉。

3. **「为什么推荐自增主键，UUID 有什么问题？」**
   → 考点是分裂模式与页填充率。答法：自增主键总是插在最右叶页，满了就右分裂，页填充率高、写入基本是顺序的；随机主键（UUID）插到中间任意位置，会引发频繁的中间分裂，页填充率降到一半左右，而且聚簇索引本身按主键排序，随机主键让插入变成随机写，二级索引里存的主键也更长更占空间。

4. **「联合索引 (a,b,c)，为什么 `WHERE b=1` 用不上索引？」**
   → 考点是排序键的字典序。答法：B+ 树里记录先按 a 排、a 相同再按 b 排、再按 c 排，所以只有给定 a 才能让 b 在树里连续；不给 a，b 的值在整棵树上是分散的，没法二分。同理范围条件会截断后续列，`a>1 AND b=2` 里 b 一般用不上有序性，只能在 ICP 阶段过滤。

5. **「索引失效有哪些典型场景？」**
   → 考点是「列上有没有做运算」。答法：列上套函数或表达式（`WHERE DATE(created_at)=...`）、隐式类型转换（字符串列拿数字比）、前导通配 `LIKE '%x'`、以及优化器估算全表扫描更便宜（区分度太低、要回表的行占比过高）时主动放弃索引——最后这条说明「有索引」不等于「一定走索引」，选择权在代价模型。

## 第 4 章 索引二：LSM 与写放大

**要解决的问题**：B+ 树是原地更新，一次写入要改一个随机页，写密集场景下随机 IO 和页分裂成为瓶颈。LSM 树把随机写变成顺序写，用「追加 + 后台合并」换写吞吐。代价是读放大和写放大，本章就是算清这笔账。

**机制**

LSM 的组件和写入路径：

```text
write(k, v):
  append WAL(k, v)                 # 顺序追加，崩溃恢复用
  memtable.insert(k, v)            # 有序内存结构，通常是跳表
  if memtable.size > threshold:
     freeze memtable → immutable
     background: flush immutable → L0 上的 SSTable（有序、不可变）
  L0 文件数超过阈值 → 后台 compaction:
     选出 L0 若干文件（key 范围重叠）
     与 L1 中重叠的 SSTable 做归并排序
     旧版本 / 墓碑在合并时丢弃，输出新的 L1 文件
     溢出再往 L2 … Ln 推
```

要点：

- **SSTable 不可变**，所以写入永远是新建文件，没有原地更新，也没有页分裂。
- **删除是墓碑**：`delete(k)` 写入一个带删除标记的记录，真正消失要等到 compaction 时与旧版本相遇。
- **读路径自新到旧**：memtable → immutable memtable → L0（新文件优先）→ L1 → … → Ln，每层内部二分。找不到还要确认「确实不存在」，所以每个 SSTable 配一个 Bloom filter，先用它挡掉绝大多数无关文件。
- **三种放大**：写放大 $WA = \dfrac{\text{写入磁盘字节}}{\text{用户写入字节}}$；读放大是查一次要碰的文件数；空间放大是磁盘占用与逻辑数据量之比。

**写放大怎么算**：分层（leveled）策略下每层容量是上一层的 $T$ 倍（常见 $T=10$），一条记录从 L1 一路被合并到 Ln，每层都要被读出来再写一次，所以粗略地 $WA \approx T \times L$（$L$ 为层数），量级在十几到几十。降低 $T$、减少层数能降写放大，但会抬高读放大和空间放大；tiered 策略先攒批再合并，写放大更低、空间放大更高。这是典型的三角权衡，没有免费的参数。

**最小例子**

以一组常见配置为例（具体默认值随版本和实现而变）：memtable 上限 64MB，L0 文件数达 4 触发合并，L1 容量 256MB，层间倍数 10。

```text
写 1000 万条 (key, 100B value) ≈ 1GB 逻辑数据
→ memtable 每写满 64MB flush 一个 L0 文件，共约 16 个
→ L0 到 4 个就合并进 L1：这 256MB 数据被重写一次
→ L1 溢出把约 256MB 推进 L2，再推 L3 …
→ 一条 key 从 L0 走到 L3，被物理写了 4 次左右
→ 加上 WAL 的一份，实测 WA 通常在十几倍量级（按配置而定）
```

调优时看的指标就是这四列：每层文件数、compaction pending 字节数、写入放大、读到的 SST 数。写停顿（write stall）通常来自 L0 文件堆积过快，说明 compaction 跟不上写入速率。

**面试高频问法**

1. **「LSM 为什么写快？代价是什么？」**
   → 考点是随机写转顺序写。答法：所有写入都是追加——先写 WAL，再写内存 memtable，落盘时是一次性顺序写一个新 SSTable，没有原地更新也没有页分裂，所以写吞吐高、写延迟稳定。代价是读要跨多层文件（读放大）、compaction 反复重写数据（写放大），以及旧版本和墓碑占空间（空间放大）。

2. **「写放大是怎么产生的，怎么降低？」**
   → 考点是 compaction 的重写成本。答法：同一份数据在从 L0 逐层推到 Ln 的过程中，每经过一层都要被读出来、归并、再写成新文件，所以写放大近似等于层间倍数乘以层数。降低的手段是调大层间倍数、减少层数、改用 tiered 风格先攒批合并，或者对写多读少的场景直接换更激进的参数——但每一样都会换来更高的读放大或空间放大。

3. **「leveled 和 tiered compaction 怎么选？」**
   → 考点是三者权衡的取舍方向。答法：leveled 每层内 key 范围不重叠，读放大低、空间放大低，但写放大大，适合读多写少；tiered 允许同层多个文件范围重叠，先攒一批再合并，写放大小、空间放大大，适合写密集（比如时序、日志类负载）。很多系统是分阶段混合，热层用 tiered、冷层用 leveled。

4. **「Bloom filter 在 LSM 里解决什么问题？」**
   → 考点是点查的存在性判断。答法：点查不命中时要确认 key 真的不存在，最坏情况得翻遍所有层的所有文件。Bloom filter 挂在每个 SSTable 上，用少量内存给出「一定不存在」或「可能存在」，把绝大部分无效 IO 挡掉，显著降低读放大；代价是有假阳性、不支持范围查询。

5. **「什么场景选 LSM，什么场景选 B+ 树？」**
   → 考点是负载特征而不是优劣。答法：写密集、追加为主、能接受后台 compaction 抖动和较大空间占用，选 LSM（RocksDB、Cassandra、TiKV 这类）；读写均衡、范围查询多、需要稳定低延迟的读、事务语义复杂，选 B+ 树（InnoDB）。本质是「把成本放在写入时重写还是放在读取时随机 IO」的选择。

## 第 5 章 事务与 ACID 的真实含义

**要解决的问题**：把「多条语句要么全做、要么全不做」这件事从应用层下沉到存储引擎。不解决，崩溃和并发交错就要业务代码自己补偿，转账只能在「钱扣了没到账」和「到账了没扣钱」之间二选一。

**机制**：

事务是一个带**提交点**的操作序列。引擎为每个事务分配单调递增的 `trx_id`，所有修改先把旧值写进 undo、改内存页、把新值写进 redo；提交时才在 redo 中写入 commit 记录。**commit 记录落盘的那一刻是原子性的分界**：此前修改即使数据页还没刷盘也算生效，此后算生效。

ACID 四者并不对等，由不同机制承担：

- **A 原子性** → undo log。回滚就是沿 undo 链把旧值写回；崩溃恢复时对「没有 commit 记录」的事务做同样的事。
- **D 持久性** → redo log + WAL。先写日志再写数据页，提交时 fsync 日志；数据页由后台异步刷，checkpoint 只决定恢复从哪开始扫。
- **I 隔离性** → 锁与 MVCC（第 6、7 章）。它是 ACID 里唯一允许业务方主动调低的一项。
- **C 一致性** → 不是数据库「提供」的，而是 A+I+D 加上约束（唯一索引、外键、CHECK、NOT NULL）共同维护的**应用不变量**。引擎只能保证「不破坏你声明过的约束」，声明之外的一致性归应用。

```text
begin:
  trx_id = next_trx_id()
  write_undo(old_value)          # 回滚 + MVCC 读旧版本
commit:
  write_redo(commit_record)
  fsync(redo_log)                # 这一行返回 = 事务已持久
  # 脏数据页由后台刷，崩溃后按 redo 重放
rollback:
  while undo_chain not empty:
      apply(old_value)
```

**最小例子**：

```sql
BEGIN;
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

参数：初始 `id=1` 余额 1000、`id=2` 余额 500。

- 崩溃发生在第二条 UPDATE 执行完、COMMIT 未返回时：恢复时 redo 中查不到该事务的 commit 记录，用 undo 把 `id=1` 加回 100、`id=2` 减回 100。结果 `(1000, 500)`，与事务前一致。
- 崩溃发生在 COMMIT 返回之后：commit 记录已 fsync，redo 重放两条更新。结果 `(900, 600)`。

只有这两个终态，没有 `(900, 500)`。

**面试高频问法**：

1. 「ACID 里哪个是数据库真正保证的？」
   考点：C 的地位。答法：A、I、D 是引擎机制，C 是目的不是手段；引擎只保证声明的约束不被破坏，跨行跨服务的业务不变量得靠应用或分布式事务，「数据库保证一致性」只说对了一半。

2. 「提交瞬间数据页还没落盘，凭什么说不丢？」
   考点：WAL 与提交点。答法：提交只要求 redo 日志 fsync，数据页是脏页异步刷；崩溃后按 redo 重放已提交事务，所以「日志落盘」等价于「事务落盘」。

3. 「undo 和 redo 分别管什么？」
   考点：两种日志的职责边界。答法：undo 存旧值，负责回滚和给 MVCC 提供旧版本；redo 存新值，负责崩溃后重放已提交修改。恢复时两者配合——已提交的重放，未提交的回滚。

4. 「持久性可以降级吗？」
   考点：刷盘策略。答法：可以，取决于提交时是否 fsync 日志（如 `innodb_flush_log_at_trx_commit` 之类的刷盘参数），攒批刷能提吞吐，代价是可能丢最近若干已提交事务；此时 D 的强度就等于刷盘频率。

5. 「隔离性调低会影响原子性和持久性吗？」
   考点：四者解耦。答法：不会。降到读未提交只改变可见性规则，undo/redo 路径不变；反过来异步刷盘牺牲 D 也不影响 A。四者由不同机制实现，可独立取舍。

## 第 6 章 隔离级别：从读未提交到可串行化

**要解决的问题**：定义并发事务之间的**可见性契约**——别人做到一半的修改，我能不能看见。没有这个契约，「并发下读到什么」无法描述，也无法判断一个实现是否安全。

**机制**：

SQL 标准用三种「现象」定义四个级别，**只规定禁止什么，不规定怎么实现**：

| 级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| READ UNCOMMITTED | 可能 | 可能 | 可能 |
| READ COMMITTED | 禁止 | 可能 | 可能 |
| REPEATABLE READ | 禁止 | 禁止 | 标准允许（实现常禁止） |
| SERIALIZABLE | 禁止 | 禁止 | 禁止 |

- **脏读**：读到别人未提交的版本。
- **不可重复读**：同一事务内两次读同一行，值变了（别人 UPDATE 并提交）。
- **幻读**：同一事务内两次按同一条件读，**行数**变了（别人 INSERT/DELETE 并提交）。

实现只有两条路线：**加锁**（读加共享锁、写加排他锁，可串行化靠范围锁/间隙锁禁幻读）和**快照**（MVCC 给每次读一个可见版本集合，读不加锁）。快照粒度是 RC 与 RR 的唯一实质差别：

```text
visible(version, snapshot):
  if version.trx_id == self.trx_id:      return true   # 读自己的修改
  if version.trx_id >= snapshot.max_id:  return false  # 快照之后才开启的事务
  if version.trx_id in snapshot.active:  return false  # 快照时尚未提交
  return true
# RC: 每条语句刷新 snapshot
# RR: 事务内第一条读语句固定 snapshot，全程复用
```

关键实现差异（面试真正的分水岭）：InnoDB 默认 RR，普通 `SELECT` 是**快照读**、不加锁；`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 是**当前读**，读最新已提交版本并加 next-key 锁（记录锁 + 间隙锁）。所以「MySQL RR 没有幻读」只在快照读下成立，当前读防幻读靠的是间隙锁，不是快照。

**最小例子**：表 `t(id INT PRIMARY KEY, v INT)`，初始一行 `(1, 10)`。

```text
S1: BEGIN; SELECT v FROM t WHERE id=1;        -- 10
S2: BEGIN; UPDATE t SET v=20 WHERE id=1; COMMIT;
S1: SELECT v FROM t WHERE id=1;
```

- S1 为 RR：第二次仍读到 `10`。`v=20` 的版本 `trx_id` 落在 S1 快照的 active 列表里，不可见。
- S1 为 RC：第二次读到 `20`。语句级新快照，S2 已提交。

换一条路径看幻读：S1 在 RR 下先执行 `SELECT * FROM t WHERE id > 0 FOR UPDATE`，InnoDB 会对 `(1, +∞)` 加间隙锁；此时 S2 的 `INSERT INTO t VALUES (2, 30)` 被阻塞到 S1 提交，S1 范围内不会凭空多出一行。若 S1 用的是普通 `SELECT`，快照读本来就看不见新行——两条路径分别对应「锁防幻读」和「快照看不见幻读」，机制完全不同。

**面试高频问法**：

1. 「RC 和 RR 一句话区别？」
   考点：快照粒度。答法：RC 是语句级快照，每条语句重新取一次；RR 是事务级快照，事务内第一条读语句定下后全程复用。副作用就是 RC 有不可重复读，RR 没有。

2. 「MySQL 的 RR 到底有没有幻读？」
   考点：快照读 vs 当前读。答法：快照读下没有，因为新插入的行 `trx_id` 在快照之后，根本不可见；当前读下靠 next-key 锁阻塞插入来防。所以既不能说「RR 没有幻读」，也不能说「RR 有幻读」，取决于这条语句是不是当前读。

3. 「SERIALIZABLE 是怎么做出来的？」
   考点：悲观 vs 乐观。答法：两条路线——把读也升级成加锁读（共享锁/范围锁），冲突就阻塞，简单但吞吐低；或者仍走快照、提交时做读写依赖环检测（SSI），冲突的事务回滚一个，不阻塞但会失败重试。具体选哪条按实现而定。

4. 「幻读和不可重复读差在哪，为什么处理成本差这么多？」
   考点：锁的粒度。答法：不可重复读是同一行的值变了，加行锁就够；幻读是结果集行数变了，锁住已存在的行没用，必须锁住「不存在的行」可能出现的区间，也就是间隙锁或谓词锁，代价是并发度下降。

5. 「读未提交还有人用吗？」
   考点：边界场景。答法：基本不用，只适合能容忍脏数据的近似统计。多数引擎把它实现为「完全不加读锁、直接读最新版本」，它省掉的是读锁开销，不是日志或回滚开销。

## 第 7 章 MVCC：版本链、快照与回滚段

**要解决的问题**：让读和写不互相阻塞，同时保证同一事务在快照读中看到一致的数据版本。如果用纯锁实现隔离，读者要加共享锁、写者要加排他锁，读写互斥会把并发度压到很低；MVCC 把「读」变成对一个历史版本的访问，读不加锁，写不阻塞读。

**机制**：以 MySQL InnoDB 为例。每行记录除用户列外，还有 `DB_TRX_ID`（最后修改它的事务 id）和 `DB_ROLL_PTR`（指向 undo 中的上一版本），这两个隐藏列构成版本链的骨架。

- 写操作产生 undo 记录。`INSERT` 产生 insert undo，只用于回滚，事务提交后可立刻丢弃；`UPDATE`/`DELETE` 产生 update undo，它既用于回滚，也用于构造旧版本，必须保留到没有快照再需要它为止。
- undo 记录自身也带一个指向更早 undo 的指针，`DB_ROLL_PTR` → 最新 undo → 更早 undo，形成从新到旧的单向链表，链头是聚簇索引上的当前记录。
- 一致性读时，InnoDB 构造一个 Read View，四个关键字段：`m_ids` 创建时活跃的读写事务 id 列表、`min_trx_id` = `m_ids` 最小值、`max_trx_id` 下一个将分配的事务 id、`creator_trx_id` 本事务 id。

可见性判断（简化伪代码）：

```text
visible(trx_id):
    if trx_id == creator_trx_id: return true       # 自己的修改
    if trx_id < min_trx_id:      return true       # 快照前已提交
    if trx_id >= max_trx_id:     return false      # 快照后开启
    if trx_id in m_ids:          return false      # 快照时还活跃
    return true                                    # 快照前已提交
```

不可见就顺着 `DB_ROLL_PTR` 回退一个版本，再判断，直到找到可见版本或链尾（此时对当前查询不可见，视为删除）。这个过程叫版本回溯。

两个关键差异：

- 隔离级别 RC 下，每条快照读 SELECT 都新建 Read View，所以同一事务两次查询能看到中间提交的变化；
- RR 下，事务内第一次快照读建立 Read View 并复用，之后的快照读都基于同一时间点，这是 RR 能避免不可重复读的原因。

清理由 purge 线程完成：update undo 挂在 history list 上，purge 判断「比最早的 Read View 还旧、且没有事务再需要」时才回收。长事务会导致 `history list length` 持续增长、undo 表空间膨胀、回溯链变长——这是「长事务有害」的具体机制。

还要区分快照读和当前读：`SELECT` 普通查询是快照读；`SELECT ... FOR UPDATE`、`LOCK IN SHARE MODE`、`UPDATE`、`DELETE`、`INSERT` 是当前读，读最新已提交版本并加锁。所以 RR 下「快照读看不到别人改的值，UPDATE 却能看到」并不矛盾。

**最小例子**：

```sql
CREATE TABLE t (id INT PRIMARY KEY, v INT) ENGINE=InnoDB;
INSERT INTO t VALUES (1, 10);

-- 会话 A
SET SESSION transaction_isolation = 'REPEATABLE-READ';
BEGIN;
SELECT v FROM t WHERE id = 1;      -- 10

-- 会话 B
BEGIN;
UPDATE t SET v = 20 WHERE id = 1;
COMMIT;

-- 会话 A
SELECT v FROM t WHERE id = 1;                -- 仍是 10，快照读走版本链
SELECT v FROM t WHERE id = 1 FOR UPDATE;     -- 20，当前读
COMMIT;
```

会话 A 第二次查询时，聚簇索引记录上 `DB_TRX_ID` 是 B 的事务 id，落在 A 的 `m_ids` 或 `>= max_trx_id` 区间，判为不可见，回退到 undo 中得到 10。

**面试高频问法**：

1. 「MVCC 怎么实现？」→ 考点是版本链 + Read View 是否讲全 → 一句话答法：「行上隐藏事务 id 和回滚指针，改一行就在 undo 里留一条旧版本，读的时候用 Read View 判断当前版本可见不可见，不可见就顺指针回溯到可见版本。」

2. 「RR 和 RC 的 MVCC 差别在哪？」→ 考点是 Read View 的创建时机 → 「RC 每条语句新建 Read View，RR 事务内第一次快照读建一次并复用，所以 RC 会读到别人新提交的值，RR 不会。」

3. 「MVCC 解决幻读吗？」→ 考点是快照读与当前读的边界 → 「只解决快照读的幻读；当前读和写操作仍要靠 next-key lock，所以 RR 下 `SELECT ... FOR UPDATE` 还能防幻读，RC 下就防不住。」

4. 「undo log 什么时候能删？」→ 考点是 purge 与长事务 → 「update undo 挂在 history list 上，purge 线程确认没有比它更早的 Read View 需要时才回收；长事务会把这条线卡住，导致 undo 膨胀。」

5. 「版本链很长有什么代价？」→ 考点是回溯成本与存储 → 「每次读要沿链回溯，undo 表空间和 history list 一起涨，最终拖慢查询和 purge，按实现而定具体耗时。」

## 第 8 章 锁：行锁、间隙锁、意向锁与死锁检测

**要解决的问题**：MVCC 只覆盖快照读，当前读和写写冲突必须靠锁解决；锁的粒度决定并发度，锁的范围决定是否防住幻读；多把锁互相等待就会死锁，引擎必须能检测并打破它。

**机制**：InnoDB 的锁分表级和行级两层。

- 表级意向锁：`IS`（打算给某些行加共享锁）和 `IX`（打算加排他锁），由行锁加锁时自动加。目的是让表级锁请求（如 `LOCK TABLES ... WRITE`、`ALTER TABLE`）只需检查意向锁就能判断表内是否已有行锁，不用逐行扫描。`IS` 与 `IX` 互相兼容，都与表级 `S`/`X` 冲突。
- 行级锁加在索引记录上，而不是「行」上。三种形态：
  - Record Lock：锁住某条索引记录；
  - Gap Lock：锁住两条索引记录之间的开区间，不含端点；
  - Next-Key Lock：Record + 前面的 Gap，区间左开右闭 $(prev, cur]$；索引上最后一条记录之后的间隙由 supremum 伪记录兜住。

加锁规则（InnoDB，唯一索引等值查询为例）：命中记录时 next-key 退化为 Record Lock；未命中时退化为 Gap Lock；范围查询则对扫描到的每条记录加 next-key，并在不满足条件的第一个记录处停下、对它前面的间隙加 gap lock。非唯一索引和范围查询会保留 gap 部分。RC 隔离级别下除唯一性检查和外键检查外基本不加 gap lock，所以 RC 挡不住幻读。

插入时加插入意向锁（Insert Intention Lock），它是一种特殊的 gap lock，多个插入意向锁之间兼容，但插入位置落在别人持有的 gap 里就要等待。

死锁检测：InnoDB 维护等待关系，形成 wait-for graph，`innodb_deadlock_detect=ON`（默认）时用深度优先搜索找环，发现环就选「回滚代价小」的事务作为牺牲者（大致按修改行数、持有锁数量衡量），回滚并抛 `ERROR 1213 (40001): Deadlock found when trying to get lock`。若关闭检测，则靠 `innodb_lock_wait_timeout` 超时退避。查看锁：MySQL 8.0 用 `performance_schema.data_locks` 和 `data_lock_waits`；5.7 用 `information_schema.innodb_locks`、`innodb_lock_waits`。

**最小例子**：

```sql
-- t(id PK, v)，已有 id = 1, 5, 10
-- 会话 A
BEGIN;
SELECT * FROM t WHERE id BETWEEN 3 AND 8 FOR UPDATE;  -- 锁 (1,5] 和 (5,10)

-- 会话 B
INSERT INTO t VALUES (6, 0);   -- 阻塞，落在 (5,10) 间隙
INSERT INTO t VALUES (2, 0);   -- 阻塞，落在 (1,5) 间隙
INSERT INTO t VALUES (11, 0);  -- 成功，不在任何被锁间隙
```

死锁版本：

```sql
-- A
BEGIN; UPDATE t SET v = v + 1 WHERE id = 1;   -- 持 id=1
-- B
BEGIN; UPDATE t SET v = v + 1 WHERE id = 2;   -- 持 id=2
-- A
UPDATE t SET v = v + 1 WHERE id = 2;          -- 等待 B
-- B
UPDATE t SET v = v + 1 WHERE id = 1;          -- 成环，一方 1213 回滚
```

**面试高频问法**：

1. 「InnoDB 行锁加在哪？」→ 考点是「锁索引不是锁行」 → 「加在索引记录上；如果查询没走索引，会全表扫描并把扫到的记录和间隙都锁上，效果接近锁表。」

2. 「next-key lock 的区间怎么算？」→ 考点是左开右闭与退化规则 → 「Record 加上它前面的 gap，左开右闭；唯一索引等值命中退化成 Record Lock，等值未命中退化成 Gap Lock。」

3. 「意向锁有什么用，会阻塞谁？」→ 考点是层级锁协议 → 「它标记表内已有或即将有行锁，让表级锁请求 O(1) 判断冲突；IS 和 IX 互相兼容，只跟表级 S/X 冲突。」

4. 「间隙锁之间会冲突吗？」→ 考点是 gap lock 的兼容性 → 「不会，两个 gap lock 可以同时持有同一个间隙；真正让插入等待的是插入意向锁与已有 gap lock 的冲突。」

5. 「线上遇到死锁怎么处理？」→ 考点是从现象到根因 → 「先看 `SHOW ENGINE INNODB STATUS` 的 LATEST DETECTED DEADLOCK 或 `data_lock_waits` 找出两个事务的 SQL 和索引；根因通常是访问顺序不一致或缺少索引导致锁范围过大，改法是固定顺序、缩短事务、补索引。」

## 第 9 章 日志与恢复：WAL、redo、undo、checkpoint

**要解决的问题**：事务已经返回 COMMIT，但数据页还停在内存里，机器断电后这份修改不能丢；事务做到一半崩溃，不能留下“钱扣了但没到账”的中间状态；同时，恢复所需的工作量不能随着数据库运行时间线性增长。WAL（Write-Ahead Logging）把随机写页换成顺序写日志，用日志重放和回滚同时满足持久性与原子性，checkpoint 负责给恢复划定起点。

**机制**：

三条规则确定了整个机制：

1. **先日志后数据页**：任何脏页刷盘前，它对应的日志必须先到稳定存储。用 LSN（日志序列号）表达为 `pageLSN ≤ flushedLSN` 才能刷这个页。
2. **redo 记录“怎么做”**：日志条目形如 `(LSN, txn_id, page_id, offset, before_image, after_image)`，描述对某页某偏移的修改（生理日志：页级定位、页内逻辑）。重放是幂等的——应用前比较 `pageLSN`，已应用过的条目直接跳过。
3. **undo 记录“怎么退”**：前像（before image）用于回滚未提交事务，同时被 MVCC 复用为读旧版本的数据源。

崩溃恢复按 ARIES 三阶段：

```text
analysis : 从最近 checkpoint 扫到日志尾
           重建 活跃事务表(ATT) + 脏页表(DPT)，得到每条记录的 recLSN
redo     : 从 DPT 中最小的 recLSN 开始重放，幂等，重放所有事务(含未提交)
undo     : 从日志尾反向扫描，回滚 ATT 中的未提交事务
           每步写 CLR(compensation log record)，保证回滚中再崩也能继续
```

**checkpoint**：不是“把脏页全刷干净再记一笔”，那会造成停顿尖峰。模糊检查点在日志里写一条记录，内容是 `{活跃事务表, 脏页表(含每条记录的 recLSN)}`，之后脏页照常异步刷。恢复时从 checkpoint 的 `redo 起点 = min(recLSN)` 开始重放，把“从建库重放一遍”压缩成“从最近的脏页起点重放”。

**最小例子**：

```sql
BEGIN;
UPDATE account SET bal = bal - 100 WHERE id = 1;   -- 旧值 500
COMMIT;
```

执行路径：

- 分配 LSN=1000，写 undo 记录（id=1, bal: 500→400 的反向映射）；
- 分配 LSN=1001，写 redo 记录（页 P, 偏移 o, 400），进 log buffer；
- COMMIT 时把 log buffer 刷到磁盘，`flushedLSN ≥ 1001` 才向客户端返回成功。此刻页 P 仍可能是 buffer pool 里的脏页；
- 断电重启：analysis 发现该事务无结束标记 → redo 从 recLSN 重放 → undo 阶段用 undo 记录把 400 改回 500。

**页断裂**：一个页写了一半断电，redo 重放会基于一个损坏的页。InnoDB 的做法是 doublewrite——刷页前先顺序写到 doublewrite 区域，恢复时用副本修复撕裂页。这是“日志之外的另一层保险”，面试常被追问。

**面试高频问法**：

1. **“为什么必须先写日志再写数据页？直接写页不行吗？”** → 考点：随机写 vs 顺序写的吞吐差距、持久性的最小化承诺、torn page。→ 答法：直接刷页意味着一次事务要等多次随机 IO，且断电会产生半页；WAL 把“提交”变成一次顺序日志 fsync，数据页可以延后批量刷，持久性靠日志重放兜底。
2. **“redo 和 undo 各自保证什么？只留 redo 行不行？”** → 考点：持久性 vs 原子性，以及 undo 的 MVCC 副作用。→ 答法：redo 保证已提交事务不丢，undo 保证未提交事务能被抹掉；只有 redo 的话崩溃后无法撤销未提交的修改，而且 MVCC 读旧版本也没有数据源。
3. **“checkpoint 做了什么？为什么恢复不用从日志头重放？”** → 考点：模糊检查点、recLSN、恢复时间上界。→ 答法：checkpoint 记录活跃事务表和脏页表（含每页 recLSN），恢复只需从最小 recLSN 开始，恢复时间被限制在“上次 checkpoint 之后的日志量”，而不是数据库总年龄。
4. **“崩溃恢复的完整流程？”** → 考点：ARIES 三阶段、CLR 的必要性。→ 答法：analysis 重建 ATT/DPT，redo 从最小 recLSN 幂等重放所有事务，undo 反向回滚未提交事务并写 CLR；CLR 让“回滚过程中再崩溃”也能继续回滚而不是重复回滚。
5. **“redo log 和 binlog 为什么需要两阶段提交？”** → 考点：两份日志的一致性、主从与恢复的口径。→ 答法：redo 是存储引擎的物理日志、binlog 是 server 层的逻辑日志，两者独立刷盘；若不协调，崩溃后可能出现“引擎里有、binlog 里没有”（从库丢数据）或反之（从库多数据），所以用 prepare/commit 两阶段加崩溃时的 XA 恢复裁决。

## 第 10 章 查询优化：执行计划与代价模型

**要解决的问题**：SQL 是声明式的，同一条语句有大量等价执行方式——走哪个索引、谁当驱动表、用哪种连接算法、要不要排序——不同选择的实际耗时可能相差几个数量级。优化器要在毫秒级时间内，用不完整的统计信息，选一个“代价估计最低”的物理计划，而不是理论上最优的计划。

**机制**：

分两层。

**逻辑优化（规则驱动）**：谓词下推（把过滤推到离数据源最近）、列裁剪、常量折叠、外连接转内连接（当 WHERE 中有对 null 补空侧的非空谓词时）、子查询去相关/半连接改写。这一层不依赖统计信息，几乎总是收益。

**物理优化（代价驱动）**：

- **基数估算**：`rows = 输入行数 × 选择率`。等值谓词常用 `选择率 ≈ 1/NDV`（不同值个数），范围谓词靠直方图（等深/等频桶），多列谓词默认按**独立性假设**相乘——这是估算失准的头号来源，因为真实数据里列往往相关。
- **代价模型**：`总代价 = IO 代价 + CPU 代价`，其中顺序读页和随机读页的权重不同，CPU 代价覆盖元组处理、比较、聚合；排序和大临时表另有折算。权重是常量，可以按硬件调整，但**不要记具体数字**，各版本各引擎都不同。
- **搜索空间**：访问路径（全表扫 / 二级索引回表 / 覆盖索引 / 索引条件下推）× 连接顺序 × 连接算法（嵌套循环、块嵌套循环、索引嵌套循环、哈希连接、排序合并）× 是否额外排序。表少时用动态规划穷举，表多时切换贪心或启发式剪枝。

```text
best = INF
for p in access_paths(R):            # 全表 / 各二级索引 / 覆盖索引
    rows = R.card * selectivity(p)   # 基数估算
    c = io_cost(p) + rows * cpu_cost + sort_cost(p)
    if c < best: best, plan = c, p
# 多表时对每个连接顺序重复上述比较，取总代价最小
```

执行计划被缓存后按参数复用，于是出现“参数敏感”：同一个计划对某些参数很快，对另一些很慢。

**最小例子**：

```sql
SELECT id, amount FROM orders
WHERE user_id = 42 AND status = 'PAID'
ORDER BY created_at DESC LIMIT 20;
```

无索引时：全表扫描 + 过滤 + 对结果 filesort + 取前 20，`rows` 估算接近表总行数。建 `(user_id, created_at)` 后，优化器可以走该索引：按 `user_id` 定位区间，`created_at` 在索引内已有序，反向扫描直接取 20 条，跳过排序；但 `status` 不在索引里，只能回表后过滤，于是 `rows` 会明显高于最终返回行数，且可能因为“满足条件的行太分散”而放弃索引。

看计划时重点读：

```text
type    : 访问方式（ALL / range / ref / eq_ref / index / const）
key     : 实际选的索引（不是 possible_keys）
rows    : 每步预估扫描行数，乘起来看量级
filtered: 该步过滤后剩余百分比，用来判断回表值不值
Extra   : Using index(覆盖) / Using where / Using filesort / Using temporary
```

`type` 从差到好大致是 `ALL → index → range → ref → eq_ref → const`，但它只说明访问方式，慢不慢要结合 `rows` 和 `filtered` 一起判断：`ref` 扫 200 万行照样慢。

**面试高频问法**：

1. **“线上一条 SQL 变慢，你怎么定位？”** → 考点：慢查询日志、执行计划、估算 vs 实际。→ 答法：先确认是偶发还是持续，拿慢日志里的样本跑 EXPLAIN 看 type/key/rows/filtered，再对比 EXPLAIN ANALYZE 的实际行数与预估行数，差一个数量级就是统计信息或相关性假设出了问题。
2. **“优化器为什么会选错索引？”** → 考点：基数估算、独立性假设、回表代价、索引扫描的随机 IO。→ 答法：它按估算的代价选，不是按真实代价选；统计信息过期、多列相关性、范围谓词估算粗糙、或者它低估了回表的随机 IO，都会让一个看似更便宜的计划实际更慢。
3. **“WHERE 里对索引列用函数为什么索引失效？”** → 考点：B+ 树按列值有序，函数破坏有序性，无法做区间定位。→ 答法：索引的可用性建立在“列值有序”上，`WHERE f(col)=?` 里优化器不知道 `f` 的单调性，无法把条件转成索引区间，只能全扫；要用函数索引（生成列 + 索引）把有序性重建出来。
4. **“驱动表怎么选？嵌套循环和哈希连接分别适合什么场景？”** → 考点：连接算法复杂度与数据分布。→ 答法：驱动表选过滤后结果集小的那个，因为嵌套循环的代价约等于“外层行数 × 内层每次查找代价”；内层有大索引可用时用索引嵌套循环，两边都大且无可用索引时哈希连接更稳（一次建表 + 一次探测），有排序输出需求时排序合并更合适。
5. **“统计信息为什么不准？直方图解决什么？”** → 考点：NDV 估算、数据倾斜、独立性假设。→ 答法：NDV 通常靠采样估算，倾斜数据下均值假设失效；直方图刻画列值的分布形状，能让范围谓词和热点值的估算贴近真实，但跨列相关性它一般不解决，那需要多列统计或多列索引引导。

**边界提醒**：优化器的目标是降低估算代价，不是降低实际耗时；所以“加索引一定变快”“把 JOIN 改写成子查询一定更快”都不成立，讲结论时必须带上“取决于估算与实际分布的偏差”。

## 第 11 章 复制与分布式事务：主从延迟、两阶段提交

**要解决的问题**：单机数据库无法同时满足「读写都扛住」和「挂了不丢数据」。复制解决可用性与读扩展，两阶段提交解决「一个事务跨多个资源要么全成要么全败」。不理解它们，就会把「主从延迟」当成 bug，把「2PC 卡住」当成玄学。

**机制**：

复制有两种主流形态，面试必须先分清：

- **语句复制（statement-based）**：binlog 记录 SQL 文本。副作用是 `NOW()`、`RAND()`、`UUID()`、`LIMIT` 无 `ORDER BY` 等不确定语句会导致主从不一致，所以现在多改成 **行复制（row-based）**，记录「哪一行的哪些列从什么改成什么」。行复制确定性强、体积大。
- **异步 / 半同步 / 组复制**：异步是主库提交即返回，从库慢慢追；半同步是主库等至少一个从库 `ACK` 收到日志（注意是**收到**，不是**应用**）才返回；组复制（如 MySQL Group Replication、Paxos/Raft 类）才真正做多数派确认。

复制链路本质是一条日志流水线：

```
客户端写 → 主库执行 + 写 binlog(2PC 内部提交) → dump 线程推给从库
        → 从库 relay log → SQL/applier 线程重放 → 从库数据可见
```

主从延迟就出在「主库已提交并返回客户端」到「从库重放完成」之间的窗口。常见成因：从库单线程回放扛不住主库并发写（并行复制按 group commit / 按库 / 按行级依赖分片）、大事务（一次删 100 万行要重放很久）、从库上有大查询抢资源、从库磁盘差。

延迟带来的经典坑是 **read-your-writes 被破坏**：写主库立刻读从库，读不到自己的写。工程解法有三类——关键读走主库、会话粘性（同一会话固定路由）、用 GTID / 位点做「读到不低于我写入位点」的等待。

**两阶段提交（2PC）** 解决跨资源原子性，比如「扣库存（库 A） + 生成订单（库 B）」。

```
协调者                         参与者
  |-- prepare(写 undo/redo, 加锁, 不提交) -->|
  |<------------- yes / no -----------------|
  |   （全部 yes 才继续；任一 no 就全体 abort）|
  |-- commit / abort ---------------------->|
  |<------------- ack -----------------------|
```

关键性质与代价：

1. **阻塞协议**。prepare 之后参与者持有锁直到收到 commit/abort；协调者在第二阶段前崩溃，参与者只能一直等（`xa recover` 人工介入）。
2. **协调者是单点**。协调者日志落盘后崩溃，恢复后要重放决议；协调者日志丢了这个事务就悬空。
3. **不是「最终一致」而是「原子提交」**。2PC 保证的是全成或全败，不保证可用性——网络分区时它选择阻塞而非放行（对比 BASE 思路的 TCC / Saga / 本地消息表）。

所以工程上大量系统避开 XA：**本地消息表**（业务写和消息写在同一本地事务，靠投递重试做到最终一致）、**TCC**（Try 预留、Confirm 提交、Cancel 释放，把锁的粒度从数据库行挪到业务资源）、**Saga**（长事务拆成可补偿的短事务链）。它们的共性是放弃「强原子」，换「可补偿 + 幂等」。

**最小例子**：

MySQL 主从，异步复制，两个终端。

主库：
```sql
-- 主库 session A
BEGIN;
UPDATE account SET balance = balance - 100 WHERE id = 1;
COMMIT;                       -- 立即返回，客户端看到成功
```

紧接着在从库（延迟约 200ms 时）：
```sql
SELECT balance FROM account WHERE id = 1;
-- 结果仍是旧值，比如 1000，而主库已是 900
```

判定手段：主库 `SHOW MASTER STATUS` 看 `Executed_Gtid_Set`/位点，从库 `SHOW SLAVE STATUS` 看 `Seconds_Behind_Master`（粗粒度，大事务时严重失真）与 `Retrieved_Gtid_Set` 对比 `Executed_Gtid_Set`——**收到但未执行**的差集才是真实延迟。

2PC 的最小可跑路径（MySQL XA）：
```sql
-- 参与者 1
XA START 'x1'; UPDATE stock SET n = n - 1 WHERE sku = 'A'; XA END 'x1';
XA PREPARE 'x1';              -- 此时行锁未释放
-- 参与者 2 同理 XA PREPARE
-- 协调者决定提交
XA COMMIT 'x1';               -- 两个都 COMMIT 才真正生效
```
在两次 `XA PREPARE` 之后、`XA COMMIT` 之前 `kill -9` 协调者，两个参与者的行锁会一直持有，直到 `XA RECOVER` + 人工 `XA COMMIT/ROLLBACK`。

**面试高频问法**：

1. 「主从延迟怎么产生的，什么时候最严重？」→ 考点是复制链路的异步窗口与回放瓶颈 → 一句话答法：「主库提交返回和从库重放完成之间有个窗口，单线程回放遇到大事务或从库资源争抢时窗口被拉长，所以批量删改和从库跑大查询是两个放大器。」
2. 「半同步复制能保证主从一致吗？」→ 考点是「收到日志」≠「已应用」→ 一句话答法：「不能，半同步只保证日志到了至少一个从库的 relay log，那个从库可能还没重放，主库挂了切过去仍可能丢最近的读可见性。」
3. 「怎么解决写完立刻读不到？」→ 考点是 read-your-writes 与路由策略 → 一句话答法：「三种：强一致读走主库、同会话粘在主库、或者带 GTID 位点去从库等它追上我的写入位点再读。」
4. 「2PC 为什么阻塞，卡在哪一步？」→ 考点是 prepare 后持锁 + 协调者单点 → 一句话答法：「prepare 成功后参与者持锁且不能单方面决定，必须等协调者的决议；协调者此时挂了，参与者只能挂着锁等它恢复或人工裁决。」
5. 「什么时候用 2PC，什么时候用最终一致？」→ 考点是 CAP 权衡与业务容忍度 → 一句话答法：「跨库强一致、参与方少、能接受阻塞和运维成本就用 XA；高并发跨服务场景用本地消息表 / TCC / Saga，用幂等 + 补偿换可用性。」

## 第 12 章 一致性四层串讲：CPU 缓存 / 内存序 / 事务 / 副本

**要解决的问题**：面试里「一致性」被问到四次，含义完全不同却常被混为一谈。这一章把它们放进同一个坐标系：**越往下是硬件帮你排序，越往上是软件自己定义顺序；每一层都在回答同一个问题——多个观察者看到的事件顺序是否一致**。答不上这层映射，就会把「缓存一致性」和「事务隔离级别」当成同一件事讲。

**机制**：

四层各自的「一致性」定义与保证手段：

| 层 | 谁在排序 | 保证什么 | 靠什么实现 |
|---|---|---|---|
| CPU 缓存 | 硬件缓存一致性协议 | 单地址的读写对所有核看到同一顺序（coherence） | MESI 类协议、总线嗅探/目录 |
| 内存序 | 编译器 + CPU | 多地址操作的可见顺序（consistency） | 内存屏障 / 原子指令的 order 语义 |
| 事务 | 数据库 | 并发事务的可串行化或某隔离级别的等价 | 锁 + MVCC + 冲突检测 |
| 副本 | 分布式系统 | 多副本间日志/状态的收敛顺序 | 主从日志、quorum、共识协议 |

**第一层 CPU 缓存：coherence 不是 consistency。** MESI 让每个缓存行处于 Modified/Exclusive/Shared/Invalid 之一，写一个核的缓存行要让其他核的副本失效。它保证的是「**同一个地址**上不会有两个核同时看到不同的最新值」，即 *cache coherence*。但它**不保证**不同地址的写在不同核上的可见顺序——这就是为什么第一层之上还需要第二层。

**第二层内存序：屏障与 order 语义。** 编译器和 CPU 都会重排。经典 store-load 重排（StoreLoad）会导致 Dekker 式互斥失败：两个线程各自写自己的标志再读对方标志，可能双方都读到 0。解决手段是屏障：`mfence` / `dmb ish` / `atomic_thread_fence(memory_order_seq_cst)`；或直接用带语义的原子操作——`memory_order_relaxed` 只保证原子性不保证顺序，`acquire/release` 建立「release 写之前的操作 happens-before acquire 读之后的操作」，`seq_cst` 全局单一总序。

一句话锚点：**coherence 是单地址的，consistency（内存序）是多地址的**。JMM / C++ 内存模型都是在这层做抽象，`volatile` 在 Java 里给的是可见性 + 禁止部分重排，不是原子性。

**第三层事务：把「顺序」变成「等价于某个串行顺序」。** 隔离级别的本质是允许哪些重排（异常）发生：读未提交允许脏读，读已提交禁止脏读但允许不可重复读，可重复读禁止不可重复读但可能允许幻读（视实现而定，MySQL InnoDB 的可重复读用间隙锁 + 一致性快照把大部分幻读也挡了），可串行化要求结果等价于某串行执行。实现手段是锁（两阶段锁 2PL：增长期只加锁、收缩期只放锁）与 MVCC（快照读不加锁，版本链判断可见性）。**注意 2PL 和 2PC 只差一个字母，一个是并发控制协议，一个是原子提交协议，别混。**

**第四层副本：把「顺序」变成「多数派认可的日志顺序」。** 主从异步复制给出的是最终收敛；Raft/Paxos 类协议把「日志顺序」交给 quorum 投票，从而在少数派故障下仍保持线性一致（在 lease/读走 leader 的前提下）。CAP 里的 C 常被误读为「强一致」，准确说是**线性一致（linearizability）**：所有操作看起来像在某个全局时间点上原子生效。

四层的递进关系可以压成一句话：**下层给你「同一份数据多个观察者看到什么」，上层给你「多个操作多个观察者看到什么顺序」；层数越高，代价越大，可放弃的保证越多。**

**最小例子**：

第一层 + 第二层的最小可复现路径（x86 上 StoreLoad 重排导致的意外结果）：

```c
// 两个线程，x = y = 0
// T1: x = 1; r1 = y;
// T2: y = 1; r2 = x;
// x86 上可能出现 r1 == 0 && r2 == 0
// 加屏障后不可能：
// T1: x = 1; __sync_synchronize(); r1 = y;
// T2: y = 1; __sync_synchronize(); r2 = x;
```
反直觉点：x86 是 TSO 模型，StoreStore/LoadLoad 不重排，**唯独允许 StoreLoad 重排**，所以上面这段在 x86 上确实可能双 0，而很多人以为 x86 是顺序一致。

第三层的最小例子（MySQL InnoDB，可重复读）：

```sql
-- 会话 A
BEGIN; SELECT balance FROM account WHERE id = 1;  -- 1000
-- 会话 B
UPDATE account SET balance = 900 WHERE id = 1; COMMIT;
-- 回到会话 A（同一个事务内，快照读）
SELECT balance FROM account WHERE id = 1;         -- 仍是 1000
-- 若 A 用 SELECT ... FOR UPDATE（当前读），则读到 900 并加锁
```
参数与结果：一致性快照在事务第一次读时建立，之后普通 `SELECT` 走版本链，`FOR UPDATE` / `UPDATE` 走当前读。这解释了「同事务内读到旧值」不是 bug。

第四层的最小例子：三副本 Raft，leader 提交需 2 个 `ACK`；网络分区后旧 leader 在少数派侧无法提交，客户端写超时——它选择**拒绝**而非返回可能被回滚的成功，这正是线性一致与最终一致的分界点。

**面试高频问法**：

1. 「MESI 保证了缓存一致性，为什么还需要内存屏障？」→ 考点是 coherence 与 consistency 的区分 → 一句话答法：「MESI 只保证同一个缓存地址在所有核上有单一写序，不同地址的写之间的可见顺序它不管，所以多地址的场景要靠屏障或带 order 语义的原子操作来补。」
2. 「x86 是顺序一致的吗？」→ 考点是 TSO 与 StoreLoad 重排 → 一句话答法：「不是，x86 是 TSO，除 StoreLoad 外的重排都被禁止，唯独允许写后读重排，所以 Dekker 式双标志在 x86 上仍可能双方都读到 0。」
3. 「acquire/release 和 seq_cst 差在哪？」→ 考点是 happens-before 建立范围 → 一句话答法：「acquire/release 只在配对的读写下建立 happens-before，不要求全局总序；seq_cst 额外要求所有 seq_cst 操作有一个所有线程一致认同的单一总序。」
4. 「可重复读和可串行化差在哪，InnoDB 的可重复读算不算串行化？」→ 考点是隔离级别与幻读 → 一句话答法：「差在幻读与写偏斜这类谓词级冲突：InnoDB 的可重复读用一致性快照挡了快照读的幻读、用间隙锁挡了当前读的幻读，但仍有写偏斜等场景，所以它不等价于可串行化。」
5. 「事务的隔离级别和 Raft 的一致性是一回事吗？」→ 考点是四层映射 → 一句话答法：「不是，事务解决并发操作等价于某个串行顺序（并发控制），Raft 解决多副本日志收敛到同一顺序（原子提交 + 多数派），前者是 2PL/MVCC，后者是 quorum，二者都要在『顺序』上做文章但对象和故障模型完全不同。」
