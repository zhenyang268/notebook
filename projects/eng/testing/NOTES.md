# testing · 分章详细

## 第 1 章 测试金字塔与分层职责

**要解决的问题**：在有限的机器时间和人力下，把测试预算分配到「最能暴露缺陷、反馈最快、失败定位最准」的位置；不解决就会要么全押端到端（CI 慢、flaky、定位靠猜），要么只写单元测试（集成错配全漏到线上）。

**机制**：分层不是按工具分，是按「复现一个缺陷需要多少真实依赖」分。判据只有一条：这个行为要真实拉起哪些外部依赖才能验证。依赖越少越下沉。四层的职责边界：

| 层 | 真实依赖 | 单条成本量级 | 失败定位 |
|---|---|---|---|
| 单元 | 无 IO | 毫秒 | 直接指到函数 |
| 集成 | 单进程内的 DB/队列/文件 | 秒 | 指到组件边界 |
| 契约 | 跨进程的接口形状 | 秒 | 指到字段/状态码 |
| 端到端 | 多系统全链路 | 十秒到分钟 | 要翻日志 |

金字塔形状是成本约束推出来的，不是审美。总反馈时间 $T=\sum_i n_i t_i$，其中 $n_i$ 是第 $i$ 层用例数、$t_i$ 是单条平均耗时，受流水线预算 $T \le T_{\text{budget}}$ 约束。因为 $t_{\text{e2e}} \gg t_{\text{unit}}$，要让 $T$ 可控，$n_{\text{e2e}}$ 必须远小于 $n_{\text{unit}}$。同时越上层单条用例覆盖的路径越多、断言越粗，边际查错能力递减——这就是「数量递减」的量化理由。

分层归属的判定可以直接写成决策流程：

```text
def where_to_test(behavior):
    deps = behavior.required_real_deps()   # 复现它必须拉起什么
    if deps == {}:            return "unit"        # 纯计算、纯状态机
    if deps <= {"db","mq"}:   return "integration" # 事务、SQL、序列化
    if deps <= {"svc"}:       return "contract"    # 跨进程字段/错误码
    return "e2e"                                    # 跨系统主干路径
```

配套两条硬规则：一、每个缺陷只应有唯一「主归属层」，其余层放守护用例防回归，不重复穷举；二、e2e 只保留主干路径和高后果场景（钱、权限、数据损坏），其余一律下沉。

**最小例子**：一个电商下单功能，四层各放一条。

- 单元：`discount(100, "VIP")` 断言返回 `90`，无依赖，毫秒级。
- 集成：真实 DB 起一个事务，`placeOrder` 后断言订单行存在**且**库存扣减行同时存在；再注入一次扣减失败，断言订单回滚、库存不变。
- 契约：对支付服务发起真实请求（或回放录制报文），断言响应里 `amount` 是分为单位的整数、失败时 `code` 落在约定枚举内。
- e2e：加购 → 下单 → 支付回调 → 订单变已支付，只此一条。

结果对比：只写单元测试时，「事务边界写错导致订单建了库存没扣」这个缺陷 100% 漏网；只写 e2e 时，同一缺陷能抓到，但要花几十分钟翻全链路日志才能定位到是 `@Transactional` 传播级别的问题。分层的作用就是把「抓得到」和「定位快」同时拿到。

**面试高频问法**：

1. 为什么是金字塔，不是倒金字塔或冰淇淋反模式？ → 考点在成本-反馈权衡，不在形状本身 → 答法：越往上单条用例越慢、越脆、失败越难定位，数量不递减的话 CI 时间被 e2e 吃掉、flaky 率还压不住，所以上层只留主干。
2. 测试奖杯（Test Trophy）跟金字塔冲突吗？ → 考点在是否理解适用条件 → 答法：不冲突，奖杯把集成放中间是因为现代代码大量逻辑在框架和 IO 边界，纯函数变少；选哪个看代码里纯逻辑与集成点的比例，不是信仰问题。
3. 端到端测试到底留多少条？ → 考点在取舍标准 → 答法：只留跨系统主干路径和钱、权限、数据损坏这类高后果场景，一条主链路一条，其余全部下沉到集成或契约。
4. 「单元测试占 70%」是硬指标吗？ → 考点在是否被教条绑架 → 答法：不是，比例是结果不是目标；真正的判据是每层的失败定位时间和流水线总时长预算。
5. 线上漏了一个 bug，你怎么决定补在哪一层？ → 考点在根因分层 → 答法：看最小复现需要哪些真实依赖，需要的越少越往下沉，同时在上层补一条守护用例防止集成错配再犯。

## 第 2 章 单元测试的边界：测行为不测实现

**要解决的问题**：让测试在重构时保持稳定。测试一旦和内部结构绑死，每次等价重构都要改测试，测试就从资产变成负债，团队会开始跳过或删除测试。不解决这一条，前面所有分层都是空谈。

**机制**：先给「行为」一个可操作的判据，而不是口号。设 $R$ 为一次保持外部契约不变的等价重构，测试集 $S$ 合格当且仅当

$$S(M) = S(R(M))$$

即重构前后测试结果一致。换句话说：**测试只允许依赖「从外部能观察到的东西」**。可观察的只有三类：返回值、对外可见的状态变化、对外发出的消息（发给外部协作者的请求内容）。不可观察、因此禁止断言的有：私有方法、内部调用顺序、内部数据结构、同模块内协作者的调用次数。

按这个判据，替身的使用边界也随之确定：mock 只出现在「跨进程、慢、不确定」的边界（支付网关、短信、时钟、第三方 API），绝不用在同模块内部的协作对象上。验证副作用时，断言的是「外部收到了什么」，而不是「内部第几步调了谁」。

```text
# 判定一个断言是否越界
def is_behavior(assertion):
    subject = assertion.observed_subject()
    if subject in {return_value, public_state, outbound_message}:
        return True          # 行为
    return False             # 私有方法 / 内部调用顺序 / 内部协作对象
```

**最小例子**：`OrderService.placeOrder(cart, user)`。

反例（测实现）：mock 掉 `PriceCalculator`、`InventoryRepo`、`OrderRepo`，然后断言 `priceCalculator.calculate` 被调用一次、`inventoryRepo.deduct` 在 `orderRepo.save` 之前被调用。测试是绿的，但它把「先算价再扣库存再落单」这个内部步骤写死了。

正例（测行为）：只 mock 外部支付网关，断言三件事——返回的订单状态是 `CREATED`、订单总价等于 `90`（VIP 折扣后）、支付网关收到的金额是 `9000`（分）。

现在做一次等价重构：把 `PriceCalculator` 内联进 `OrderService`，逻辑不变。反例测试全红，得改测试；正例测试一条不用动，仍然绿。这就是那条等式的实际体现。再补一个副作用场景：发短信通知。正例是断言「短信网关收到 (手机号, 模板 ID)」，而不是断言 `smsService.send` 在 `placeOrder` 第 7 行被调用——前者重构安全，后者一挪代码就断。

**面试高频问法**：

1. 怎么判断一个测试是不是测了实现？ → 考点在重构不变性 → 答法：做一次等价重构，测试红了就是测了实现；不用争论，重构一次就见分晓。
2. Mock 用得越多不是隔离得越好吗？ → 考点在 mock 的边界 → 答法：mock 只该出现在进程外、慢、非确定的边界，mock 同模块内部协作者等于把实现细节抄进测试。
3. 不 mock 内部协作者，怎么验证「发短信」这种副作用？ → 考点在可观察行为的定义 → 答法：副作用也是行为，但验证的是短信网关收到了什么内容，不是 Service 内部第几行调了它。
4. 覆盖率 100% 能保证没测实现吗？ → 考点在覆盖率与耦合是正交的 → 答法：不能，覆盖率只说明行被执行过，不说明断言落在行为上，mock 满天飞一样能刷到 100%。
5. TDD 是不是天然就能避免测实现？ → 考点在 TDD 的真实约束力 → 答法：不一定，先定好内部类结构再写测试一样会耦合；TDD 有用是因为测试先于实现，逼你从调用方视角描述行为。

## 第 3 章 测试替身：mock / stub / fake / spy 的取舍

**要解决的问题**：把被测代码与不可控的外部世界（网络、时钟、数据库、第三方 SDK）隔开，让失败定位在逻辑本身而不是环境。替身选错的代价是双向的：选了过重的 mock，重构就红一片；选了过轻的 stub，测试全绿但线上照样炸。

**机制**：四种替身来自 Meszaros / Fowler 的 test double 分类，区别只有两点——**有没有真实行为**、**断言的是状态还是交互**。

| 类型 | 行为 | 断言方式 | 典型场景 |
|---|---|---|---|
| Stub | 无，返回预设值 | 状态断言 | 「查不到用户时返回 404」 |
| Spy | 无，但记录调用 | 事后交互断言 | 注入点改不动，只能包一层 |
| Mock | 无，预置期望 | 事前/事后交互断言 | 验证「确实发出了 charge 命令」 |
| Fake | 有，但是走捷径的实现 | 状态断言 | 内存 Repository、内存消息队列、可控时钟 |

取舍顺序可以写成一段决策：

```text
double(dep):
  if dep 有状态且被测代码要查询它:      return Fake(dep)      # 内存实现
  if 只关心 dep 返回什么:               return Stub(value)    # 最便宜
  if 断言点就是"有没有发出这条命令":     return Mock(expect)   # 只在进程边界
  if 构造/注入点改不动:                 return Spy(real_obj)  # 包住既有对象
```

关键约束：**mock 只对进程边界用**（支付网关、消息总线、第三方 HTTP 客户端），不要对被测对象内部的协作者用。因为 mock 断言的是「调用序列」，一旦把内部协作关系固化进测试，任何拆分函数、合并调用的重构都会让测试变红——而外部行为没变。这正是「测行为不测实现」在替身层面的落地。反过来，Fake 的代价是它自己也是一份实现，会与真实实现语义漂移，所以 Fake 必须由契约测试对齐真实实现（见第 5 章）。

**最小例子**：

```python
# shop/order.py
class OrderService:
    def __init__(self, repo, gateway):
        self.repo, self.gateway = repo, gateway

    def checkout(self, oid):
        order = self.repo.get(oid)
        if order.total > 0:
            self.gateway.charge(order.total)
            order.paid = True
        self.repo.save(order)

# tests/test_order.py
def test_checkout_charges():
    repo = FakeRepo({"o1": Order(total=100)})       # Fake：有状态
    gw = Mock()                                     # Mock：进程边界命令
    OrderService(repo, gw).checkout("o1")
    gw.charge.assert_called_once_with(100)
    assert repo.get("o1").paid is True

def test_zero_total_no_charge():
    repo = FakeRepo({"o2": Order(total=0)})
    gw = Mock()
    OrderService(repo, gw).checkout("o2")
    gw.charge.assert_not_called()
```

跑 `pytest -q tests/test_order.py` → `2 passed`。注意这里断言的是 `charge` 被调用**几次、什么参数**，以及仓库里的最终状态；没有断言 `repo.save` 在 `charge` 之后被调用——那是实现顺序，不是契约。

**面试高频问法**：

1. **mock 和 stub 到底差在哪？**
   → 考点：交互断言 vs 状态断言，以及是否预置期望。
   → 答法：stub 只负责喂返回值，测试断言的是被测代码的输出状态；mock 预置了「必须被这样调用」的期望，断言的是交互本身。所以 stub 不会因为重构而红，mock 会，这也是 mock 只能放在边界的理由。

2. **什么时候不该用 mock？**
   → 考点：是否理解 mock 与实现耦合。
   → 答法：被测对象内部的协作者不 mock，核心领域逻辑一律用真实对象；只 mock 进程边界——网络、时钟、随机源、第三方 SDK。判断标准是「这个依赖换实现时，测试该不该跟着改」，该改的才 mock。

3. **Fake 有什么隐藏成本？**
   → 考点：测试基础设施也是代码。
   → 答法：Fake 是一份平行实现，会和真实实现语义漂移，而且它自己需要测试。做法是让同一组契约测试同时跑在 Fake 和真实实现上（真实实现那侧放集成测试），漂移才会被抓到。

4. **第三方 SDK 全 mock 了，测试全绿，上线挂了，为什么？**
   → 考点：mock 固化的是你对 API 的假设。
   → 答法：mock 只验证了「我以为的调用方式」，没验证对方真实行为——字段名、错误码、超时语义都可能变。补一层针对真实沙箱的契约测试或录制回放，mock 只留在单元层。

5. **spy 什么时候非用不可？**
   → 考点：注入点不可改时的折中。
   → 答法：遗留代码里对象在自己内部 new 出依赖、没有构造注入点时，用 spy 包住真实对象只观察不改变行为。这是过渡手段，正规做法是把依赖提到构造函数参数，然后换回 Fake 或 Mock。

## 第 4 章 覆盖率的三种口径与骗局

**要解决的问题**：覆盖率度量的是「哪些代码被执行过」，不是「哪些行为被验证过」。口径不说清，数字不可比；口径说清了还拿它当质量指标，就会被优化成指标本身。

**机制**：三种口径，严格程度递增。

- **语句覆盖 / 行覆盖**：可执行语句中被执行到的比例。最便宜，也最容易被满足。
- **分支覆盖（判定覆盖）**：每个判定点（`if`、`while`、三元、短路表达式）的真假两个出口是否都走到。分支覆盖一般蕴含行覆盖，反之不成立。
- **条件覆盖 / MC/DC**：复合判定里每个原子条件是否都能独立影响结果。航空（DO-178C 最高等级）这类场景要求，日常业务项目很少做到。

实现上是插桩：Python 的 `coverage.py` 挂在解释器的 trace 钩子上，逐行/逐 arc（分支跳转）记录命中；C/C++ 侧有 gcov 这类编译期插桩。所以它统计的是**执行痕迹**，与断言无关——这是所有骗局的根源。

一个 3 行的反例：

```python
def is_ok(a, b):
    if a > 0 or b > 0:   # 复合判定 + 短路
        return True
    return False
```

只跑 `is_ok(1, 0)`：三条语句全执行，**行覆盖 100%**；但 `if` 的假分支从未走过，**分支覆盖 50%**；`b > 0` 因短路从未求值，**条件覆盖更低**。同一份测试，三个口径三个数字。

常见骗局清单：

1. **无断言的测试**：调用一遍不断言，覆盖率涨了，bug 一个没抓到。
2. **为覆盖率写测试**：测 getter/setter、测构造函数、测 `__repr__`，行数多、信息量零。
3. **排除标记滥用**：`# pragma: no cover` 用来把难测分支从分母里抹掉。
4. **统计范围污染**：生成代码、迁移脚本、vendored 依赖混进统计目录。
5. **子进程丢失**：`coverage.py` 默认不跟踪 fork/spawn 出来的子进程，多进程服务或 CLI 端到端跑完覆盖率仍是 0；需要开启 `concurrency = multiprocessing` 与 `parallel = true`，再用 `coverage combine` 合并。
6. **总量门禁**：老代码把总量拉低，团队要么放弃门禁，要么写垃圾测试凑数。正确做法是门禁看**增量覆盖率**（本次 diff 涉及的行），存量只做趋势观察。

对抗手段是**变异测试**：故意改坏源码（把 `>` 改成 `>=`、删掉一行、取反条件），看测试是否失败。杀死的变异体比例叫变异分数，它比覆盖率更接近「测试有效性」，代价是运行时间长。工具如 mutmut（Python）、PIT（Java）、Stryker（JS/TS），按项目技术栈选。

**最小例子**：

```bash
pytest --cov=shop --cov-branch --cov-report=term-missing
```

输出形如（数值为示意）：

```text
Name              Stmts   Miss Branch BrPart  Cover   Missing
shop/order.py        42      3     12      5    85%   31-33, 40->44
```

读法：`Branch BrPart = 5` 说明有 5 个判定只走了一个出口——这类点往往就是缺陷藏身处，`40->44` 直接指出「从 40 行跳到 44 行」这条分支没被覆盖。此时 `Cover 85%` 是行/分支的合并口径，**报数字时必须说清用的是哪一种**，否则跨仓库、跨语言对比毫无意义。

**面试高频问法**：

1. **行覆盖和分支覆盖差在哪？**
   → 考点：是否知道行覆盖会被单分支的 `if` 骗过。
   → 答法：行覆盖只问这行执行没执行，分支覆盖问每个判定的真假出口是否都走到。一个只走真分支的 `if`，行覆盖可以满分而分支覆盖只有 50%，所以门禁应该用分支覆盖。

2. **覆盖率 90% 能说明什么、不能说明什么？**
   → 考点：执行 ≠ 验证。
   → 答法：能说明 90% 的代码在测试中被执行过，说明不了这些执行被断言检查过。它排除的是「完全没人碰过的代码」，不能证明逻辑正确——无断言的测试同样能把数字刷到 90%。

3. **团队把门禁设成总覆盖率 80%，会出什么问题？**
   → 考点：古德哈特定律 + 存量代码现实。
   → 答法：老代码拉低总量，新人只能写低价值测试凑数，或者加排除标记。改成增量门禁——本次改动涉及的行和分支必须达到阈值，存量给趋势看板不卡门禁。

4. **多进程服务的覆盖率为什么统计不到？**
   → 考点：插桩是进程内的。
   → 答法：覆盖率数据写在进程退出时，子进程的 trace 不会自动回传。需要配置 coverage 的并发模式与 parallel 输出，跑完用 `coverage combine` 合并各进程的数据文件，再出报告。

5. **有没有比覆盖率更能反映测试质量的东西？**
   → 考点：是否知道变异测试。
   → 答法：变异测试。故意注入小改动看测试会不会红，变异分数衡量的是「测试能不能抓住错误」，而覆盖率只衡量「代码跑没跑过」。缺点是慢，通常放在夜间流水线而不是每次提交。

## 第 5 章 集成测试与契约测试

**要解决的问题**：单元测试用替身把所有接缝都抹平了，于是“我的代码”和“真实依赖”、“我的服务”和“别人的服务”之间的假设没人验证。集成测试验证纵向接缝（代码 ↔ 真实 DB/队列/HTTP），契约测试验证横向接缝（consumer ↔ provider）。不解决，这些假设第一次被检验就是在联调或线上。

**机制**：

集成测试的三个设计决定：

1. **依赖用真的还是假的**：判据是“这个依赖的语义是不是被测逻辑的一部分”。SQL 方言、事务隔离级别、唯一索引冲突、消息的投递语义——是，就必须用真的；发邮件、调第三方支付——用 fake。
2. **边界放在进程内还是进程外**：真 DB 跑容器、外部第三方跑进程内 fake，是多数团队的成本/保真平衡点；全容器起一整套只在少量关键链路上做。
3. **隔离**：每个测试用唯一 schema 或事务回滚；测试数据带唯一前缀（如 `test-{uuid}`），否则并行一开就互相踩。

契约测试的工件流转：

```
consumer 测试 → 生成 pact 文件（JSON） → 发布到 broker（带版本+分支）
                                              ↓
provider 侧拉取该版本 pact → 按 given 准备数据 → 回放请求 → 校验真实响应满足 matcher
                                              ↓
                                    can-i-deploy 判断这组版本能否一起上
```

关键约束：**consumer 只声明它真正消费的字段**。provider 新增字段不算破坏性变更，删字段、改类型、改语义（同名字段含义变了）才算。这条约束决定了契约测试是“消费者驱动的”，而不是“provider 接口文档的复制”。

```python
# 伪代码：pact 风格 DSL
def test_get_user_contract(pact):
    (pact.given("user 42 exists")
         .upon_receiving("a request for user 42")
         .with_request("GET", "/users/42")
         .will_respond_with(200, body={"id": 42, "name": Like("alice")}))  # Like = 类型匹配器
    with pact:
        assert client.get_user(42).name == "alice"   # 只用到 name
# provider 侧：verify(pact_file, state_handlers={"user 42 exists": seed_user_42})
```

**最小例子**：一个服务要测“下单扣库存”这条链路，DB 用真 Postgres：

```bash
docker compose -f docker-compose.test.yml up -d --wait postgres
pytest tests/integration -m integration -q
# 结果：12 passed in 41s
```

`--wait` 会等 compose 里定义的 healthcheck 变成 healthy 才返回，替代了 `sleep 20` 这种既慢又不可靠的等待。测试内每条用例在独立 schema 里建表、跑完 drop，因此可以 `-n 4` 并行。

**面试高频问法**：

1. **“集成测试和契约测试有什么区别？”** → 考点是纵向/横向接缝的区分。答法：集成测试测我的代码和真实依赖拼起来对不对（SQL 能不能跑、事务对不对），是纵向的；契约测试测两个服务对同一份 JSON 的假设一致不一致，是横向的，不碰真实依赖。
2. **“provider 加了一个响应字段，契约测试该不该红？”** → 考点是 consumer-driven 的兼容性判据。答法：不该红。consumer 只声明它用到的字段，加字段对它是透明的；删字段、改类型、改语义才该红，这条规则让 provider 能安全地演进接口。
3. **“契约测试能替代集成测试吗？”** → 考点是契约的覆盖边界。答法：不能。契约只验证请求形状和响应字段，不验证真实 SQL、事务回滚、超时、序列化边界、连接池耗尽这些——那些只有跑真依赖才暴露。
4. **“provider state（given）是干什么的，为什么容易出问题？”** → 考点是契约测试的确定性。答法：契约文件只描述请求和响应，不描述前置数据，所以 provider 侧要为每个 given 写数据准备 handler；handler 和真实数据不一致时契约测试就变 flaky，所以要把它当生产代码维护。
5. **“集成测试慢到没人跑，怎么办？”** → 考点是成本控制而不是砍覆盖。答法：缩小边界（DB 容器化并复用、只对变更模块跑）、并行分片、把纯逻辑从集成里挪回单测，而不是删掉集成层。

## 第 6 章 冒烟、回归、验收：什么时候跑哪一层

**要解决的问题**：测试写全了，但“什么时候跑哪一层”没定义。结果是两种极端：每次提交跑全量 E2E，反馈 40 分钟，红了没人看；或者只跑单测，问题漏到线上。这一章给出按“失败成本 × 反馈时长”调度各层的规则。

**机制**：

分层不是按工具分的，是按**回答什么问题**分的：

| 层 | 回答的问题 | 时机 | 时间预算 | 失败动作 |
|---|---|---|---|---|
| 冒烟 | 这个构建能不能用？ | 部署到环境后立即 | 分钟级 | 回滚，不继续 |
| 回归 | 有没有弄坏以前的功能？ | 合并前 + 夜间全量 | 十分钟级 | 阻断合并 |
| 验收 | 需求做对了没有？ | 发布前 | 小时级 | 阻断发布 + 产品确认 |

门禁排序的经验规则是：单位耗时能拦掉的失败越多越靠前，即近似 $\max \frac{\text{该层可拦截的失败比例}}{\text{该层耗时}}$。所以编译和 lint 在最前，E2E 在最后。

```yaml
# 伪代码：门禁顺序，任一 stage 红则后续不跑
build:       { run: make build lint }                  # 期望 < 2 min
unit:        { needs: build,       run: pytest -m unit }
contract:    { needs: unit,        run: pact-verify }
integration: { needs: contract,    run: pytest -m integration }
deploy_stg:  { needs: integration }
smoke:       { needs: deploy_stg,  run: ./smoke.sh --timeout 300, on_fail: rollback }
regression:  { needs: smoke,       run: pytest -m regression --shard 4 }
acceptance:  { needs: regression,  when: manual }
```

冒烟集的设计原则：只保留 10–30 条，覆盖“进程起得来 + 核心链路成功一次”；只读接口优先，写操作必须能自清理；等待用 healthcheck 而不是 `sleep`；失败信息要能指到具体服务，否则值班的人第一步就得手工排查。

回归的选测：按变更影响面选子集（改了哪个模块跑哪些），夜间跑全量兜底。验收用业务语言写（Given/When/Then），由业务方 review，不追求代码覆盖率。

**最小例子**：

```bash
./smoke.sh --base-url https://stg.example.internal --timeout 300
# 1) 轮询 GET /healthz 直到 200，最多 300s
# 2) GET /v1/catalog?limit=1 → 200 且 body 非空
# 3) POST /v1/orders（固定测试账号）→ 201，随后 DELETE 清理
# 结果：3 passed, 8.4s，退出码 0
```

任一步失败退出码非 0，流水线直接回滚，不再跑回归——因为此时回归结果没有意义。

**面试高频问法**：

1. **“冒烟、回归、验收的区别？”** → 考点是三者回答的问题不同。答法：冒烟问“这个构建能不能用”，部署后几分钟内跑，失败就回滚；回归问“有没有弄坏旧功能”，合并前和夜间跑，失败阻断合并；验收问“需求做对了没有”，发布前跑，失败阻断发布并由产品确认。
2. **“冒烟测试应该写多少条、包含什么？”** → 考点是冒烟是“可用性判定”不是“功能覆盖”。答法：10–30 条、5 分钟内跑完，覆盖进程能起来、依赖能连上、核心链路成功一次；写操作要能清理，只读优先。
3. **“回归太慢，怎么优化？”** → 考点是成本控制手段。答法：按变更影响面选子集，夜间跑全量兜底，用例并行分片，把纯逻辑从 E2E 挪回单测；不要靠删用例来提速。
4. **“冒烟测试自己老 flaky 怎么办？”** → 考点是等待方式和数据治理。答法：`sleep` 换成 healthcheck 加超时重试，固定测试账号和夹具数据，失败信息带上服务名和响应码便于归因；连续 flaky 的用例直接移出冒烟集，回到稳定后再放回。
5. **“验收测试谁来写、要不要自动化？”** → 考点是职责和收益边界。答法：场景由业务方或产品定义，QA 固化成 Given/When/Then，关键路径自动化进流水线，探索性验证留人工；验收的价值在“业务语义对不对”，不在覆盖率。

## 第 7 章 property-based testing 与 fuzz

**要解决的问题**：基于样例的单元测试只覆盖作者想得到的输入，而线上崩溃几乎都发生在想不到的那一侧。这一章解决“如何用生成器批量造输入、用性质而不是期望值做断言，并把偶发崩溃收缩成一个可复现的最小反例”。

**机制**：三个部件——生成器（generator/strategy）、性质（property）、收缩（shrinking）。性质常见四类：不变量（排序后长度不变、结果有序）、往返（`decode(encode(x)) == x`）、幂等（`normalize(normalize(x)) == normalize(x)`）、对照实现（新实现与朴素实现在同一输入上输出相同）。生成器负责把类型映射成输入分布，失败后收缩器反复裁剪输入直到不可再小，最后把反例写入语料库，下次先跑语料库。

fuzz 与 PBT 的区别在于驱动方式：PBT 的输入是结构化值、由生成器按分布采样；fuzz 的输入是字节流，靠插桩得到的覆盖率反馈引导变异，判据通常是崩溃、panic、未定义行为或 sanitizer 报告。Go 的原生 fuzz 把两者衔接起来：引擎给 bytes，开发者负责解码成结构。

```python
@given(st.lists(st.integers()))
def test_sort(xs):
    once = my_sort(xs)
    assert len(once) == len(xs)                              # 不丢元素
    assert all(a <= b for a, b in zip(once, once[1:]))       # 有序
    assert my_sort(once) == once                             # 幂等
```

```go
func FuzzParse(f *testing.F) {
    f.Add([]byte("a=1&b=2"))              // 种子语料
    f.Fuzz(func(t *testing.T, data []byte) {
        v, err := Parse(data)
        if err != nil {
            return                        // 非法输入不算失败
        }
        if !bytes.Equal(Format(v), data) { // 往返性质
            t.Fatalf("round-trip mismatch: %q", data)
        }
    })
}
```

关键工程点：性质的强度决定测试价值。如果性质里把实现逻辑又抄了一遍，那它只是换了输入来源的样例测试，会和实现一起错。另一个坑是分布——默认生成器偏向小值、空集合、ASCII，边界要显式加权或用 `@example` 手动传入。

**最小例子**：Python + Hypothesis 测一个 `parse_duration("1h30m") -> 秒`，性质写 `format(parse(s)) == s`，生成器用 `st.from_regex(r"\d+[hms]", fullmatch=True)`。运行 `pytest -q`，Hypothesis 在若干次采样后报 `Falsifying example: test_roundtrip(s='0s')`，收缩过程把 `"10h3m2s"` 一路裁到最短反例；反例落进 `.hypothesis/examples/`，再次运行会立刻用这条数据失败，不需要重新碰运气。Go 侧：`go test -run=^$ -fuzz=FuzzParse -fuzztime=30s`，引擎跑满 30 秒后把触发 panic 的最小输入写进 `testdata/fuzz/FuzzParse/`，之后普通 `go test` 就会复现。

**面试高频问法**：

1. “PBT 和普通单测的本质区别？” → 考点是输入来源与断言形式 → 答法：单测断言“给定 X 得到 Y”，PBT 断言“对所有生成的输入，性质 P 成立”，失败后自动收缩成最小反例并入库回归。
2. “怎么判断一条 property 写得好不好？” → 考点是会不会把实现抄进断言 → 答法：优先用不变量、往返、幂等、对照实现这四类；如果性质本身复刻了被测逻辑，它就只能验证“代码没变”，验证不了“代码对”。
3. “fuzz 和 PBT 是什么关系？” → 考点是覆盖率反馈 → 答法：PBT 是生成器 + 性质 + 收缩，输入是结构化值；fuzz 是字节变异 + 覆盖率反馈 + 崩溃检测，输入是 bytes；Go 原生 fuzz 用前者把 bytes 解码成结构，两者常配合用。
4. “没有 oracle 的接口怎么 fuzz？” → 考点是判据设计 → 答法：退化判据是崩溃、panic、sanitizer 报错；有第二个实现时做差分测试，同一输入喂两个实现比对输出；再不行就只断言不变量（不 panic、长度守恒）。
5. “生成器的分布为什么重要？” → 考点是假通过 → 答法：默认分布偏向小值和空集合，边界（0、负数、最大长度、Unicode）覆盖不到；要显式加权，并把已知边界用固定样例传入，否则 PBT 会给出“跑了很多次但没测到关键路径”的错觉。

## 第 8 章 flaky test 治理与确定性

**要解决的问题**：一条测试只要偶发变红，团队就会开始“重跑一下”，门禁从此失效——红灯不再等价于“代码坏了”。这一章解决“让同一 commit 的测试结果只取决于代码，而不取决于时间、顺序、机器和网络”。

**机制**：先把根因分类，再谈治理手段。

| 根因 | 典型表现 | 治理手段 |
|---|---|---|
| 真实时间 | `sleep`、读 `now()`、时区/DST、超时太紧 | 注入 Clock，测试用假时钟推进 |
| 随机与哈希序 | Go map 遍历顺序、未固定 seed | 排序后比较；seed 打印并可重放 |
| 并发 | 共享全局态、端口/临时目录冲突、goroutine 泄漏 | 每测试独立资源、端口 bind 0、`-race` |
| 外部依赖 | 真实网络、共享库、第三方限流 | 换 fake/契约桩，测试内自建 schema |
| 顺序依赖 | A 建的数据被 B 依赖 | 测试间零共享；主动随机化执行顺序 |
| 环境差异 | CPU 数、locale、文件系统大小写 | 环境信息进日志，CI 与本地对齐 |

治理顺序是“先量化，再修，最后才止血”。量化指按测试名统计失败率、同 commit 重跑是否复现、是否与并行度相关。设单次失败概率为 $p$，重跑 $n$ 次全绿的概率是 $1-p^n$——重试只是把红灯变成灰灯，成本是 CI 时间和被掩盖的真 bug。

重试只能作为临时手段，且必须绑定三件事：标记（skip/quarantine 带原因和链接）、owner、到期时间。没有期限的重试等于关掉门禁。门禁策略上，新引入的 flaky 立即阻断，已知 flaky 移出阻断集合但仍单独跑并告警。

```python
class Clock(Protocol):
    def now(self) -> datetime: ...

def test_token_expires(fake_clock):
    tok = issue(ttl=timedelta(minutes=5), clock=fake_clock)
    fake_clock.advance(timedelta(minutes=4, seconds=59))
    assert verify(tok, clock=fake_clock)
    fake_clock.advance(timedelta(seconds=2))
    assert not verify(tok, clock=fake_clock)   # 边界确定，无 sleep
```

**最小例子**：某接口测试断言 `created_at` 落在 `datetime.utcnow()` 前后 1 秒内，本地全绿、CI 偶发失败。定位步骤：同一 commit 上用 `pytest -q tests/test_order.py --junitxml=out.xml` 循环跑 50 次，记录失败次数与机器负载；确认失败只出现在慢机上，属于真实时间依赖。改法是把 `Clock` 注入被测代码，测试传 `FakeClock(fixed=2024-01-01T00:00:00Z)`，断言改成精确相等。改完再循环跑 50 次，全部通过，且不再需要 sleep 等待。另一类常见修法是 Go 里对 map 遍历结果先 `sort.Strings` 再和 golden 文件比对，消除顺序随机。

**面试高频问法**：

1. “怎么判断一个测试是真 flaky 还是真 bug？” → 考点是复现性归因 → 答法：同一 commit 重复跑、换机器换并行度跑，同输入不同结果才是 flaky；稳定失败就是 bug 或环境问题，绝不能用重试盖住。
2. “重试机制到底能不能用？” → 考点是是否知道它的代价 → 答法：只能当临时手段，必须配 quarantine 标记、owner、到期时间和失败率指标；无期限重试等于把门禁关掉，红灯失去意义。
3. “时间相关的测试怎么写才不 flaky？” → 考点是依赖注入 → 答法：不要在测试里 sleep 或读真实时钟，把 Clock 作为依赖注入、用 advance 推进；等异步用带 deadline 的轮询或 channel 同步，不用固定 sleep。
4. “并发测试为什么容易不稳定？” → 考点是隔离与竞态 → 答法：共享可变全局态、固定端口、共享临时目录、goroutine 泄漏；解法是每测试独立资源、端口 bind 0、开 `-race`，并随机化执行顺序主动暴露顺序依赖。
5. “本地过、CI 不过，按什么顺序排查？” → 考点是环境差异清单 → 答法：依次过时区/locale、CPU 数与并行度、文件系统大小写与遍历顺序、网络与 DNS、缓存与残留状态；先把这些环境变量和随机 seed 打进失败日志，再谈改代码。

## 第 9 章 CI 流水线：门禁顺序与失败快停

**要解决的问题**：把前八章各自的检查（UT、覆盖率、契约、集成、冒烟、fuzz、flaky 治理）编排成一条流水线，让「该拦的拦住、能快停的别拖」。没有顺序设计，流水线要么慢到没人等，要么门禁松到形同虚设，或者反过来把主干堵死。

**机制**

门禁顺序的设计目标是**单位时间发现缺陷最多**，因此排序原则是三层：**快先于慢、确定性高先于确定性低、失败影响面小先于影响面大**。

典型分层（名字随团队而定，顺序是本质）：

| 层 | 耗时量级 | 内容 | 失败意味着 |
|---|---|---|---|
| L0 静态 | 秒级 | lint、类型检查、编译、依赖漏洞扫描 | 根本不用往下跑 |
| L1 单元 | 十秒~分钟 | 单测 + 覆盖率门限 | 行为写错了 |
| L2 集成/契约 | 分钟级 | 与真实依赖、契约校验 | 接口或数据层不兼容 |
| L3 构建产物 | 分钟级 | 打镜像、制品签名 | 交付物本身有问题 |
| L4 冒烟 | 分钟级 | 部署到临时环境跑关键路径 | 起不来 / 主流程断 |
| L5 全量回归 + fuzz | 十分钟~小时级 | 全量 E2E、长跑 fuzz | 边角退化 |
| L6 手工验收/灰度 | 小时~天 | —— | —— |

「失败快停」（fail-fast）在流水线里落实为两件事：**串行的前置层失败即整条取消**，以及**同一层内部并行分片也取消未完成分片**。多数 CI 系统提供并发取消语义（GitHub Actions 的 `concurrency` 组、GitLab 的 `interruptible: true`、Jenkins 的 `milestone` + `parallel` 中断），概念一致：新提交到达即取消旧运行，层失败即取消下游。

```yaml
# 伪代码，示意结构而非某个具体产品的完整语法
stages: [static, unit, integration, smoke, regression]
cancel-on-new-push: true          # 同分支新提交取消旧流水线

static:
  run: lint && typecheck && build
  interruptible: true
unit:
  needs: [static]                 # 前置失败则不启动
  parallel-shards: 4
  fail-fast: true                 # 任一分片挂 => 取消其余分片
  run: test --coverage --threshold=line:80
integration:
  needs: [unit]
  retry: 0                        # 集成层不轻易重试，先看是不是真 bug
smoke:
  needs: [integration, build-image]
regression:
  needs: [smoke]
  allow-failure: false
  schedule: nightly-only          # 长跑与 fuzz 不进 PR 门禁
```

三个必须明确的口径，否则门禁会被绕过或被乱用：

1. **哪些层堵在 PR 上，哪些放在合并后**。PR 门禁只放 L0–L4（秒到分钟级）；L5 全量回归与 fuzz 移到主干/夜间，结果回写。理由：PR 等待时间与开发者绕过门禁的动机成正比。
2. **重试策略**。重试是 flaky 的止痛药，也是 bug 的遮羞布。合理做法：单元层零重试；集成冒烟层允许 1 次重试但**记录重试率**，重试率超阈值（比如某用例一周内重试成功 ≥3 次）自动开 flaky 治理 ticket，而不是默默重试到绿。
3. **门禁的「绝对 vs 相对」**。覆盖率、性能这类指标，绝对门限（「行覆盖 ≥ 80%」）可预测但容易催生填充式测试；相对门限（「不得低于基线 -0.5%」或「新增代码覆盖 ≥ 90%」）更贴近意图。实践中常见组合：全量用相对基线、增量用 diff 覆盖率。

失败快停的反面是**失败慢停的代价**：一个十分钟的 E2E 层排在只跑三秒的 lint 后面，开发者提交后等十分钟才知道少个分号。所以顺序不是审美问题，是反馈延迟问题。

另一条常被忽略的机制是**门禁的阻断等级**。同一批检查应有不同严格度：lint 警告不阻断、新增代码覆盖率不足阻断、nightly fuzz 崩溃阻断主干但通过 issue 而非直接红叉——因为直接红叉会让主干长期红着，形成「红是常态」的破窗。

**最小例子**

假设一个服务仓库，PR 从提交到可合并：

1. 开发者 push 到 PR 分支，触发流水线。
2. `static` 层：`lint` 报一处未使用变量。层失败，`unit` 及以下**不启动**，流水线 40 秒变红，PR 显示「1 项检查失败」。
3. 修掉后重推。此时 CI 的并发组检测到同分支已有运行，**取消上一次**（即使它已跑到 `integration`），避免旧结果覆盖新结果。
4. `static` 通过（35s）→ `unit` 四片并行，总计 90s，行覆盖率 83%，基线 84%，`--threshold` 设为「不得低于基线 1 个百分点」，**通过**（若设 84% 绝对值则此处会挂，这是口径差异的具体后果）。
5. `integration` 层一个契约校验失败：provider 返回字段从 `string` 变成 `null`。层失败，`smoke` 不启动——**这正是快停的价值**：省下部署临时环境 + 跑冒烟约 6 分钟。
6. 修复后全绿，合并。夜间调度跑 `regression` + 30 分钟 fuzz，失败不阻断合并但自动开 issue 并 @ 模块 owner。

对照跑一次反例：如果把 `regression` 放在 PR 门禁第一层，同样那个分号错误要等 20 分钟才暴露，PR 平均等待时间从 ~4 分钟涨到 ~24 分钟，而多抓到的缺陷数在统计上通常接近于零（因为 L0 已经拦住了大部分低级错误）。

**面试高频问法**

1. **「你们 CI 的检查顺序是怎么定的？为什么 lint 在单测前面？」**
   → 考点是反馈延迟与失败概率的乘积。→ 一句话：按「发现缺陷的单位时间成本」排序，静态检查几秒就能拦掉大量低级错误，把它放前面能让大多数失败在 1 分钟内反馈；慢的、确定性低的层往后放，并且只在前面全绿时才启动。

2. **「fail-fast 具体怎么实现？前置失败后下游任务还会跑吗？」**
   → 考点是流水线依赖语义与并发取消。→ 一句话：两层机制，一是任务依赖里声明 `needs`，前置失败则下游根本不进入调度；二是同分支新提交通过并发组取消旧运行，避免旧结果回写覆盖新结果。

3. **「重试能不能解决 flaky test？」**
   → 考点是重试与 flaky 治理的关系。→ 一句话：重试只是把不确定性藏起来，必须同时统计重试率并对高频重试的用例开治理单，否则门禁会从「拦 bug」退化成「拦不住但也不报错」；单元层应当零重试。

4. **「覆盖率门禁用绝对值还是相对基线？会有什么副作用？」**
   → 考点是 Goodhart 定律在覆盖率上的体现。→ 一句话：绝对值可预测但催生填充式断言，相对基线（尤其 diff 覆盖率只算新增代码）更贴近意图；常见组合是全量用「不低于基线 N 个百分点」、增量用「新增代码 ≥ 90%」。

5. **「夜间任务挂了要不要阻断主干？」**
   → 考点是门禁阻断等级与主干健康度。→ 一句话：要区分「阻断合并」和「阻断发布」，夜间全量与 fuzz 一般不阻断合并，但必须自动开 issue、指派 owner、并计入主干健康度看板，否则会形成长期红叉的破窗效应。
