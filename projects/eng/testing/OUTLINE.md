## 一、它解决什么问题

这项能力拦的是三类东西：**假绿灯、红灯疲劳、以及“测试写了但没人敢改”**。

场景 A（假绿灯）：假设一个 200+ 接口的服务，共享的序列化/鉴权工具类被改了一行。单测全部通过——因为没人覆盖那条判定分支；E2E 也通过——因为 E2E 只跑十来条主流程。问题在灰度后由下游调用方发现，回滚耗时数十分钟。这类事故的共性不是“没测试”，而是**测试不覆盖被改动的那条分支**。

场景 B（红灯疲劳）：一个数千用例的仓库，E2E 套件单次耗时按实现而定在几十分钟量级，其中偶发失败（flaky）占到两位数百分比。团队处理方式退化成“失败了就点重跑”，真 bug 和噪声混在一起，平均修复时间被拉长到天级。共性是**没有区分信号与噪声的口径**。

面试侧对应的是高频题：覆盖率高就代表质量好吗？mock 该 mock 到什么程度？CI 失败了先看什么？消费方单测都过了为什么联调还挂？这些问题只背概念答不出来，考的是口径与取舍。

**入口（本文的读法）**：在“同一 commit SHA、lockfile、test runner 版本下，junit.xml 的用例 ID、coverage.xml 的行/分支/条件计数、contract diff 的 schema 字段、CI exit code 与 fail-fast 开关必须可复现”的约束下，这套东西把假绿灯、红灯疲劳、不敢改判成“哪一层用例被选中、断言哪个返回值/错误码/协议字段/open/read/write syscall 序列、替身注入在哪、覆盖率按什么计数、门禁按什么顺序快停”；换的是 smoke/regression/acceptance 标签、public API 断言对象、mock/stub/fake/spy 注入边界、property seed 与 fuzz corpus、flaky retry 标记与确定性开关、CI stage 的 allow_failure/fail-fast。

**不换的是什么**：全程不变的是 commit SHA、lockfile、test case ID、expected value、random seed、clock/syscall 注入、contract schema 字段、junit.xml 的 pass/fail、coverage.xml 的行/分支/条件计数、CI exit code；看到差异先问“是这些输入/断言对象/契约字段变了导致 junit.xml、coverage.xml、contract diff 或 CI exit code 变，还是只是 CI stage 顺序、retry 策略、mock 注入点、coverage 阈值或 allow_failure 配置变了”。

## 二、为什么这样做（方法论设计）

核心取舍一：**有口径才算数**。“我们测试比较充分”“CI 比较快”“覆盖率还行”都不可证伪。可证伪的表述必须带三要素：指标名、分母、阈值来源。例如“本次变更的新增行分支覆盖率不低于阈值（阈值按仓库风险等级设）”“同一 commit 重跑出现结果翻转的用例计入 flaky 清单”。反过来，“我们用了测试金字塔”如果没有用例数、耗时、维护成本的分布数据，就只是口号。

核心取舍二：**指标必须能归因**。全量覆盖率涨几个点，可能是补了几百个 getter 断言；增量覆盖率只统计变更行，归因更紧。flaky 不用“感觉”，用翻转率：

$$\text{flaky 翻转率} = \frac{\text{同一 commit 重跑出现结果翻转的次数}}{\text{重跑总次数}}$$

覆盖率口径要在文档里写死，行覆盖与分支覆盖不可混用：

$$\text{分支覆盖率} = \frac{\text{被执行的分支边数}}{\text{总分支边数}}$$

核心取舍三：**分层按反馈成本切，不按名词切**。同一段逻辑，单测层在毫秒级给出失败与定位，E2E 层要分钟级且带不确定性。分层依据是四项：反馈时间、失败定位精度、稳定性、单次执行成本。四项都随层级上升而恶化，所以默认下沉，只在“跨进程 / 跨存储 / 跨协议”的真实风险点上升层。

边界与失效条件（不写清就会被当万能药）：
- 遗留代码没有测试网时，先补特征测试（characterization test）锁住现状再重构，不能一上来追求结构漂亮的单测。
- 依赖不可控的第三方（外部支付、硬件）时，契约测试只能覆盖协议层，替代不了联调。
- 并发/时序密集系统，flaky 可能长期收敛不到零；正确做法是设隔离配额（quarantine 上限）并跟踪到期，而不是宣称“零 flaky”。
- 覆盖率阈值对新建仓库与十年老仓不能用同一个数，阈值来源必须写明。

常见错误做法的**代价**：
- 拿覆盖率当 KPI：团队写无断言的执行型测试，用例数与维护成本一起涨，缺陷逃逸率不动——用持续成本买了一个不产生信号的数字。
- 全链路 mock：断言变成“调了哪个方法、调了几次”，实现一重构测试全红，重构成本翻倍，最后团队选择删测试。
- 用 E2E 兜所有风险：反馈从分钟级退化到小时级，flaky 比例上升，红灯被系统性忽略，门禁失去约束力。
- 门禁不分层、串行全跑：单用例按秒级算，数千用例就是小时级，PR 队列被堵，人会绕过门禁。

## 三、章节大纲

1. **测试金字塔与分层职责**：讲分层的四项依据（反馈时间、定位精度、稳定性、成本），金字塔 / 测试奖杯 / 冰淇淋的差异只在比例，比例必须带分母。学完能答：“你们单测、集成、E2E 的比例怎么定？为什么不是 E2E 越多越好？”
2. **单元测试的边界：测行为不测实现**：讲 SUT 边界怎么划、行为契约是什么、断言与实现耦合的识别信号（改私有方法名就红）。学完能答：“重构后测试红了，是测试错了还是代码错了？”
3. **测试替身：mock / stub / fake / spy 的取舍**：讲四类替身的语义差异、fake 优先原则、只在跨边界处用 mock。学完能答：“为什么不该断言 mock 的调用次数和顺序？”
4. **覆盖率的三种口径与骗局**：讲行覆盖 / 分支覆盖 / 变异测试（mutation score）的差别，增量与全量之分，骗局清单（无断言、只覆盖异常抛出、生成代码）。学完能答：“覆盖率 85% 能说明什么、不能说明什么？”
5. **集成测试与契约测试**：讲集成边界（DB / 消息 / HTTP）、测试数据隔离（事务回滚、临时 schema）、消费者驱动契约的流程，契约校验与 schema 校验的差别。学完能答：“双方单测都过了，联调为什么还挂？”
6. **冒烟、回归、验收：什么时候跑哪一层**：讲三者目标不同（可用性 / 不退化 / 需求满足）、触发时机（PR、合并、发布前、发布后）、用例选取按变更影响面与风险加权。学完能答：“发版前你跑哪些用例，为什么不跑全量？”
7. **property-based testing 与 fuzz**：讲性质与例子的区别、生成器与收缩（shrinking）、常见不变量（序列化往返、幂等、排序后有序）、fuzz 的判定标准（崩溃 / 超时 / 断言失败）。学完能答：“什么样的逻辑值得写 property test，什么不值得？”
8. **flaky test 治理与确定性**：讲不确定性来源分类（时间、随机种子、端口与共享状态、异步等待、用例顺序依赖）、隔离与到期机制、无脑重跑会掩盖真 bug。学完能答：“CI 偶发失败你怎么定位和处置？”
9. **CI 流水线：门禁顺序与失败快停**：讲按耗时升序、按失败概率降序的排序原则，fail fast 与 fail complete 的适用场景，必过门禁与提示性检查的分工，缓存与并行分片不能破坏测试隔离。学完能答：“设计一个 PR 门禁流水线，顺序怎么排，为什么？”

## 四、不做什么 · 必要性 · 失效点

### 必要性：删掉会怎样

| 机制 | 删掉会怎样 | 判定 |
|---|---|---|
| 新增行分支覆盖率阈值 | 删掉后，共享序列化/鉴权工具类的未覆盖变更分支不再被 PR 门禁拦截，假绿灯承诺破。 | 必需 |
| flaky 翻转率 | 删掉后，同一 commit 重跑结果翻转不再进入 flaky 清单，红灯疲劳承诺破。 | 必需 |
| 同一 commit 重跑出现结果翻转的用例计入 flaky 清单 | 删掉后，CI 只保留 pass/fail，噪声失败与稳定失败混在同一 commit 的重跑记录中。 | 必需 |
| 特征测试（characterization test） | 删掉后，遗留代码重构前没有现状锁，行为差异错误在灰度或联调阶段暴露。 | 必需 |
| 契约测试 | 删掉后，外部支付/硬件依赖的协议字段变更只能在联调暴露；若服务无跨进程第三方调用，则不启用。 | 选择 |
| 隔离配额（quarantine 上限） | 删掉后，并发/时序用例的长期翻转无限占用重跑窗口，团队只能忽略红灯或绕过门禁。 | 选择 |

### 失效点：哪条前提一破，结论就变

- CI runner 可用核数从 8 降到 2，且门禁不分层、串行全跑 → 单次执行成本超过 PR 队列窗口，E2E 兜所有风险会把红灯疲劳转成绕过门禁。
- 外部支付网关 TLS 协议版本从 1.2 升级到 1.3，契约测试只断言 HTTP status 与 JSON schema 字段 → 协议层握手/密码套件失败绕过契约测试，联调阶段才暴露。
- 测试容器挂载介质从本地 SSD 换成网络文件系统且 fsync 延迟升高，E2E 依赖 SQLite/临时目录写入 → 稳定性前提破，同一 commit 重跑出现结果翻转的用例计入 flaky 清单，flaky 翻转率阈值需上调，否则红灯疲劳复发。
- CI 时钟源从 NTP 稳定同步漂移到 >5s，鉴权工具类依赖 JWT exp/nbf 或证书有效期 → 新增行分支覆盖率达标仍出现时间窗断言翻转，flaky 翻转率被误判为代码噪声。
- 测试进程对鉴权 sidecar 的 unix socket 权限位从 0777 收紧到 0750，E2E 仍用非特权用户连接 → 契约测试与单测通过但真实权限路径失败，假绿灯在联调暴露。

### 不做什么（范围）

- 不讲 408 类考点：白盒/黑盒定义、软件工程名词背诵不在此列。
- 不逐条讲某语言测试框架的 API 与断言语法（JUnit / pytest / Jest 的用法属于语言层）。
- 不给具体工具的配置参数与性能数字；涉及耗时处一律写“按实现而定”。
- 不覆盖性能测试、安全测试、混沌工程的完整方法，只在分层与门禁交界处提及。
- 不给通用覆盖率阈值当标准答案，阈值按仓库与风险等级自定。
- 不做测试团队的组织设计与绩效方案。

## 五、面试怎么讲

**30 秒版本**

我做测试工程是先定口径再谈工具：分层按反馈成本和失败定位精度切，单测管行为契约、集成管跨进程边界、契约测试管消费方与提供方的协议漂移；覆盖率只把增量分支口径当门禁，并用变异测试抽查断言是否“有牙”；flaky 用重跑翻转率量化，进隔离清单而不是靠重跑掩盖；CI 门禁按便宜到贵的顺序排、失败快停。我能拿出的证据是：分层后的用例与耗时分布、增量覆盖率报告、flaky 清单与处置记录、门禁各阶段耗时。

**可能被追问的 8 个点**

1. “你们覆盖率多少？”→ 考点：口径意识 → 先反问口径（行 / 分支 / 增量），再答“门禁用增量分支覆盖，全量数字受历史代码稀释，只作参考；另用变异测试抽查”。具体数值按仓库而定。
2. “覆盖率 85% 说明什么？”→ 考点：执行率 ≠ 正确率 → 只说明 85% 语句被执行过，不说明有断言、不说明分支组合与异常路径；判据是“改一个条件，测试是否会红”。
3. “单测为什么不要 mock 具体实现？”→ 考点：行为 vs 实现 → 断言落在返回值、状态变化、对外发出的事件契约上；交互断言只保留必须发生的副作用，用 spy 而非严格校验次数与顺序。
4. “mock / stub / fake / spy 怎么选？”→ 考点：替身语义 → stub 给预设返回，fake 用内存实现（内存仓储、内存队列），spy 记录调用但走真实逻辑，mock 预置期望并校验交互。优先级：fake > stub > mock，mock 只用在无法 fake 的跨边界（第三方 SDK）。
5. “双方单测都过，联调为什么挂？”→ 考点：契约漂移 → 双方各自 mock 的是自己的假设；用消费者驱动契约把消费方期望固化成契约文件，由提供方在 CI 回放验证。契约管结构不管语义，语义仍需集成测试。
6. “CI 挂了先看什么？”→ 考点：分流能力 → 先看失败阶段（编译 / 单测 / 契约 / 集成 / E2E），再看同 commit 重跑是否复现，最后看分支保护是否已阻断；flaky 与真 bug 走两条处置路径。
7. “flaky 怎么治？”→ 考点：确定性 → 先量化翻转率，再按来源定位（时间依赖、随机种子、端口与共享状态、异步等待、顺序依赖）；修不了就隔离并设配额与到期时间，重跑不是解决方案。
8. “流水线顺序怎么排？”→ 考点：成本与反馈 → lint/静态检查 → 编译 → 单测 → 契约 → 集成 → 冒烟/E2E，耗时升序、失败概率降序；PR 门禁用 fail fast，夜间全量用 fail complete；分片并行不得破坏用例隔离。

**别说什么**

- “我们覆盖率 90%，所以质量有保障。”——把执行率当正确率，一问断言就露怯。
- “我们零 flaky。”——没有翻转率口径的断言，追问重跑策略就站不住。
- “依赖全 mock 掉了，测试很干净。”——直接暴露测试与实现耦合。
- “E2E 全跑最稳。”——说不清反馈时间与 flaky 成本，等于承认没有分层。
