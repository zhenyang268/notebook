# eng/ · 路径手册

## 0 怎么用

- 选路径：§2。
- 五份文档的判据形态差异：§1。

## 1 五份文档的判据形态

| 文档 | 判据落点 | 典型证据 | 失效条件 |
|---|---|---|---|
| `debug-toolchain` | 能否定位到「函数+偏移+可疑变量」 | gdb 回溯、core dump、最小复现脚本 | 无符号/优化后内联，回溯失真 |
| `testing` | 测试是否真的会红 | 注入故障后测试失败、CI 门禁拦截记录 | 测的是实现细节而非行为 |
| `perf-engineering` | 指标名 + 量级 + 方差 | `perf stat` 事件、火焰图、benchmark 十次重复 | 输入不代表真实负载；噪声大于效应 |
| `system-design` | 量级估算与第一瓶颈 | 白板算式、QPS→存储→带宽的推导 | 忽略了某一层的排队效应 |
| `latent-issues` | 触发条件 + 观测手段 | `perf c2c`、`ss -ti`、`dmesg`、上下文切换计数 | 内核/库版本演进使现象消失或变形 |

**一条铁律**：这五份里**任何"提升 X 倍""覆盖率 Y%"都要带括号说明口径**，否则就当没写。

## 2 推荐顺序

### 第一段：定位能力（必做）

`debug-toolchain`：core dump → gdb → strace → sanitizer。

```bash
ulimit -c unlimited
gdb -batch -ex 'bt full' -ex 'info registers' ./app core
strace -f -T -e trace=network,file ./app 2>&1 | tail -30
```

**判据**：给一个段错误现场，十分钟内给出「函数+偏移+可疑变量」与一个最小复现；能说明是哪一类崩溃（空指针 / 栈破坏 / 释放后使用 / ABI 不一致）。

### 第二段：验证能力（必做）

`testing`：金字塔、替身取舍、覆盖率骗局、flaky 治理。

**判据**：拿出一个自己写的测试，**故意把被测逻辑改错**，确认测试变红；再说清哪些地方你没测、为什么。做不到这一步，后面的"测试写得好"都不算。

### 第三段：性能能力（必做）

`perf-engineering`：口径、火焰图、Amdahl。

```bash
perf stat -e cycles,instructions,cache-misses,branch-misses ./app
perf record -F 999 -g -- ./app && perf report --stdio | head -40
```

**判据**：先说瓶颈类（CPU 密集 / I/O 等待 / 锁竞争 / GC / 内存带宽），再给证据；任何"优化了多少"必须附十次重复的方差。

### 第四段：设计能力（建议）

`system-design`：量级估算 → 缓存 → 限流 → MQ → 分库分表 → 秒杀。

**判据**：白板上能在五分钟内从"日活 × 请求比例"估到 QPS 与存储容量，并指出方案的第一瓶颈（通常是某个单点或某层的连接数）。

### 第五段：陷阱索引（加分）

`latent-issues`：不顺序读，**按现象检索**。建议按四类归并记忆：

- 通知语义：惊群、队头阻塞
- 并发可见性：伪共享、ABA、内存序
- 资源生命周期：TIME_WAIT、fd 耗尽、连接池
- 交互细节：Nagle 与延迟 ACK、EINTR

**判据**：每个陷阱能说出「触发条件 + 观测手段 + 常见误判」三件事。

## 3 五个最小可交付

每个项目留一个**可展示的证据**，比读完全文有用：

| 项目 | 最小可交付 |
|---|---|
| `debug-toolchain` | 一份 core dump 分析记录：信号 → PC → 变量 → 根因 → 最小复现 |
| `testing` | 一个"注入故障即变红"的测试集 + 一句"哪些没测、为什么" |
| `perf-engineering` | 一张火焰图 + 一句归因结论 + 一次方差说明 |
| `system-design` | 一页容量估算（QPS / 存储 / 带宽）+ 第一瓶颈 |
| `latent-issues` | 一份自己的"踩坑索引"，每条含触发条件与观测手段 |

## 4 跨项目追问

1. **「你这个优化在别人机器上还成立吗？」** → 口径题：缓存大小、核数、NUMA、编译器版本；结论只在同口径下有效。
2. **「测试全绿但线上出问题，怎么解释？」** → 测试只覆盖了被断言的行为；引出"契约测试"与"生产环境可观测性"。
3. **「为什么加机器没用？」** → 可能撞上单点（数据库主库、单 key 热点）或串行段（Amdahl）；也可能是连接数/文件句柄耗尽。
4. **「这个 bug 复现不了怎么办？」** → 从"复现"退到"观测"：加日志/指标/探针，把概率问题变成计数问题。
5. **「性能问题为什么最后都变成架构问题？」** → 因为瓶颈会迁移：优化了 CPU 就露出 I/O，优化了 I/O 就露出锁，最后只能改结构。

## 5 常见误配

| 误配 | 后果 | 正确做法 |
|---|---|---|
| 先读 `system-design` 再读 `testing`/`debug` | 只会画架构图，一遇到现场就空 | 定位与验证是地基，先做 |
| 用覆盖率当质量证明 | 被"注入故障"一问就打穿 | 用注入故障证明测试有效 |
| 只有火焰图没有结论 | 图表不是归因 | 每个图后面跟一句"所以瓶颈在 X" |
| 把 `latent-issues` 当名词表背 | 追问触发条件就崩 | 每条记三件事：触发/观测/误判 |
| 把方法论讲成流程 | 听起来像管理者 | 每条都要落到一次测量或一次复现 |

## 6 一句话收口

**这五份的共性只有一句：把"我觉得"换成"我测到/我复现了"。** 判据能否写出来，是这一组唯一的分水岭。
