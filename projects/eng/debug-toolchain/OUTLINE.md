## 一、它解决什么问题

这项能力拦的是两类东西：真实工程里“改不动”的事故，和面试里“背了名词但没定位过”的题。

**场景一：线上进程周期性消失。** 一个多线程服务，峰值 QPS 数千，每隔一两天由 systemd 报 `signal=11` 重启一次，日志最后一行是 `recv failed`。此时线上二进制经过 strip、无 debuginfo，`ulimit -c` 为 0 没留 core，retry 掩盖了现象。团队能做的是重启加猜测，这类问题通常以“天”为单位消耗。它需要的不是更聪明的头脑，而是：崩溃前先决定 core 存哪、符号怎么留、`build-id` 怎么对齐；崩溃后能从 `SIGSEGV` 与 `SIGBUS` 的差别、从寄存器与栈帧读出访问地址与映射区间的关系。

**场景二：面试现场。** “这段代码在 `-O2` 下崩、`-O0` 正常，怎么解释？”“ASan 没报错是不是就没内存问题？”“TSan 报了 race，可我明明有 mutex。”这些题不考名词解释，考的是你有没有用这套工具把某个 bug 从现象固定到源码行的完整链条。答不出链条，就只会背“ASan 快、Valgrind 慢”。

**场景三：不可复现的脏读。** 压测 6 小时复现一次，attach 上去所有线程都正常。这类问题的解法是插桩（TSan）、结构化日志、最小复现三条线并行，而不是盯代码。

## 二、为什么这样做（方法论设计）

**有口径才算数。** 本方法论要求每条结论都带可核验的判据：崩溃要能还原到 `(线程, 帧, 源码行, 访问地址)`；内存错误要有一份 sanitizer 报告指明“谁申请、谁释放、第一次越界发生在哪一行”；数据竞争要有 happens-before 边 $a \rightarrow b$ 的断裂点，即两个冲突访问各自的位置与中间缺失的同步。做不到这些的，一律降级为“假设”，标在问题单上而不是结论里。

**看起来专业但无法证伪的。** “我加了两行打印就好了”；“重启后再没出现过”；“应该是编译器优化的问题”；“这段逻辑上不可能出错”；“我用 gdb 跟了一下，没发现问题”。它们的共同点是：结论不指向任何可复现的输入或可解释的机制，事后无法被推翻，因此也无法被信任。工程上要的不是“听起来专业的判断”，而是“错了会被打脸的判断”。

**指标怎么定。** 不设“提升 N 倍”这类指标。可定的是：可复现率 $R = n_{\text{hit}}/N$（同一输入重复 $N$ 次，命中同一栈或同一报告的次数占比），$R \to 1$ 才算固定；报告可解释率（每条 sanitizer 输出都能指到源码行，而不是“大概这里”）；MTTR 分段（发现 / 定位 / 修复 / 验证四段分别计时，定位段是这套工具链真正负责的部分）。

**这套方法在什么情况下失效。** 第一，海森堡效应：插桩与调试改变了时序，竞态消失，问题变得更贵；第二，符号缺失：strip 过且无独立 debuginfo 的 core 基本不可读；第三，权限：容器里 `ptrace_scope`、`perf_event_paranoid`、内核栈可见性都会让工具直接不可用，这不是技术问题而是部署问题；第四，越界范围：ASan 只能抓它插桩到的访问，Valgrind 只能审查它翻译到的指令，未重编译的库、JIT 代码、内联汇编都是盲区；第五，sanitizer 是采样视角不是证明，报告为空不等于没有问题，报告非空也不等于真实缺陷（缺注解的同步原语）。

**常见错误做法的代价。** 用 printf 代替调试器：一次编译-运行 3–5 分钟，且 I/O 本身改变时序，可能把一天的竞态拖成一周。生产上直接 `gdb attach` 再 `continue`：进程被暂停，如果它正持锁，整条调用链会等锁，上游超时雪崩，一次排查换来一次故障。全量开 ASan 上生产：ASan 有固定比例的 shadow memory 与 redzone 开销（具体倍数按实现与配置而定），把稳定性问题换成了容量问题。看到 TSan 报告就加一把大锁：竞争变成性能问题，且真实设计缺陷仍在，只是换了个地方报。靠重试“解决”崩溃：越界可能已经破坏了堆结构，下一次在无关位置崩，定位成本翻倍。

## 三、章节大纲

**1. 从崩溃现场开始：signal、core dump、backtrace**
讲信号的语义差别（`SIGSEGV` 是访问非法，`SIGBUS` 是映射有效但不可用，`SIGABRT` 是主动中止，`SIGILL` 常与 UB 被优化相关）、`core_pattern` 与 `ulimit -c` 如何决定 core 落盘位置与过滤范围、`backtrace()` 与 DWARF unwind 的差别、`-O2` 下缺帧与内联导致的栈失真、符号化三件套（二进制 / debuginfo / build-id）如何对齐。
能回答：“收到 `SIGSEGV`，你手上有什么，第一步做什么？”“core 打不开、栈全是 `??` 怎么办？”

**2. gdb / lldb：断点、条件断点与观察点**
讲软件断点（改写指令）与硬件断点/观察点（调试寄存器，数量有限，按架构而定）的代价差异；条件断点为什么慢（每次命中都要回调试器求值），改用命中计数或 `commands` + `continue`；观察点抓“谁改了这个变量”；`attach` 的停顿风险与线程调度锁；多线程下 `thread apply all bt` 的读法；容器内的 `gdbserver`。
能回答：“一个变量在没人赋值的地方变了，怎么找？”“条件断点为什么拖慢一个数量级？”

**3. 内存错误：ASan 与 Valgrind 的检测原理**
讲 ASan 的 shadow memory 映射 $\text{shadow} = (\text{addr} \gg 3) + \text{offset}$（offset 按实现而定）与红区、隔离队列；Valgrind 的动态二进制翻译（DBI）路径，为什么它能覆盖未重编译的库而更慢；两者共同依赖 redzone 与已释放内存隔离，因此对“未触红区的越界”“生命周期结束但内存尚未复用”不敏感；LeakSanitizer 只报不可达，不报逻辑泄漏。
能回答：“ASan 和 Valgrind 怎么选？”“ASan 没报错是不是就没内存问题？”

**4. 未定义行为：UBSan 能抓什么、抓不到什么**
讲能抓的分类：有符号溢出、移位越界、对齐、空指针解引用的一部分、vptr、有类型信息时的数组越界、函数缺少 return。抓不到：无符号回绕（定义良好）、未初始化读（属 MSan）、悬垂但未复用的指针、以及“编译器据 UB 做优化后，源码与行为已无因果关系”这一类。
能回答：“`-O2` 崩 `-O0` 正常，怎么解释？”“UBSan 报的 runtime error 是否必须修？”

**5. 数据竞争：TSan 的报告怎么读**
讲 happens-before 与向量时钟的实现，以及 TSan 报告的三段结构：冲突的两个访问（读/写、位置是 heap/global/stack）、各自线程栈、以及它试图建立的同步关系。重点讲误报来源：手写自旋锁、futex、内联汇编、部分系统调用、缺注解的无锁结构，以及 `__tsan_acquire`/`__tsan_release` 注解的作用。强调 TSan 只对实际发生的交错负责，未执行路径不报。
能回答：“加了 mutex 为什么还报？”“TSan 干净是否等于线程安全？”

**6. 系统调用层：strace、ltrace 与 dtruss**
讲 `ptrace` 机制带来的数量级拖慢（每次 syscall 进出都要停），因此只适合低频或短时窗口；常用口径：`-f` 跟线程、`-T` 看单次耗时、`-e trace=` 过滤、`-y` 解析 fd 路径（具体选项按版本确认）。它回答“卡在哪个系统调用、返回什么 errno、fd 泄漏”，不回答“用户态在干什么、锁等了多久”。`ltrace` 覆盖不全；`dtruss` 是 macOS 对应物且需权限。
能回答：“进程 hang 住，怎么区分死锁、系统调用阻塞、死循环？”

**7. 资源与运行时：/proc、lsof、perf 的调试用法**
讲 `/proc/<pid>/status` 的 `VmRSS` 与 `Threads`、`smaps` 的映射归属、`task/*/stack` 的内核栈（需权限）、`fd/` 与 `lsof` 查 fd 泄漏与被删除但仍占空间的文件；`perf stat` 看 CPI 与上下文切换、`perf top` 看热点、`perf record/report` 看调用图（完整性取决于 frame pointer 或 DWARF）、`perf trace` 覆盖部分 strace 场景。三种瓶颈分类：on-CPU、off-CPU（等锁/等 I/O）、syscall 密集。
能回答：“CPU 不高但 QPS 上不去，怎么定位？”“内存持续上涨，怎么区分泄漏、碎片、缓存？”

**8. 日志与可观测性：结构化日志、trace id、最小复现**
讲键值/JSON 化让“崩溃前最后 N 条”可机读；trace id 与 span 的父子关系才能还原跨进程因果，只有 id 没有 span 等于没接上；日志分级与采样在高频路径上的成本；最小复现作为调试的终点产物——判据是“一条命令 + 一个输入”稳定命中同一栈或同一报告，方法上对应输入二分（delta debugging）。
能回答：“线上 bug 怎么在 24 小时内给出结论？”“什么算一份好的 bug 报告？”

## 四、不做什么

不做操作系统原理课：页表、调度算法、文件系统实现属于 408 层，这里只讲“调试时怎么读它”。不做语言语法与标准条款考证：UB 只讲能否被抓到，不做标准文本的逐条释义。不做工具版本特性对比表与 IDE/编辑器配置。不深入内核态调试（kgdb、kprobe、eBPF 追踪），只到用户态能看到的 `/proc` 与内核栈为止。不承诺任何性能倍数：所有插桩开销统一写“按实现与配置而定”。不复现厂商基准数据。

## 五、面试怎么讲

**30 秒版本（约 160 字）**
“我按‘现象→工具→判据’的方式组织这条链路：崩溃先看信号语义与 core 是否完整，能不能还原到帧和行；内存问题用 ASan 的 shadow memory 或 Valgrind 的 DBI 去拿一份带申请/释放点的报告，并说清它的盲区；竞态看 TSan 报告里 happens-before 断在哪，缺注解就补注解而不是加大锁；系统调用层用 strace 判断是不是阻塞在 syscall，用 perf 区分 on-CPU 与 off-CPU。我判断一个问题是否算解决，看的是可复现率是否到 1、报告是否能指到源码行，而不是‘重启后没再出现’。”

**可能被追问的 7 个点**

1. **“core 拿到但栈是 `??`，怎么办？”** 考点：符号化链路。答：先确认二进制与 core 的 build-id 是否一致，再确认是否有独立 debuginfo（`debuginfo-install` / 分离符号），最后确认是不是帧指针缺失导致 unwind 断了——改用 DWARF CFI 或从寄存器与栈上手工回溯。判据是能对上源码行。
2. **“ASan 和 Valgrind 选哪个？”** 考点：原理与代价。答：能重编译就用 ASan（编译期插桩、shadow memory，覆盖自编译代码，快但只覆盖插桩范围）；不能重编译或要查第三方库、要 helgrind/DRD 那类分析就用 Valgrind（DBI，覆盖广但慢）。判据是“覆盖范围 vs 时间预算”，不是谁更先进。
3. **“ASan 干净就没事了？”** 考点：盲区。答：不。红区没触到、生命周期结束后内存未复用、JIT/内联汇编、未重编译的库都不在它的视野里。这时补 Valgrind 交叉验证，或退回日志与复现。
4. **“`-O2` 崩、`-O0` 正常。”** 考点：UB 与优化的因果断裂。答：这是 UB 被优化放大后的典型表现，不是“编译器有 bug”。做法是开 UBSan 分组排查（signed-integer-overflow、shift、alignment、vptr），并注意优化后现象可能与源码位置无关，必须靠插桩而不是读代码。
5. **“TSan 报了 race，但我有锁。”** 考点：happens-before 的建立方式。答：先读报告三段——两个访问在哪、各自线程栈、它找到的同步边。常见原因是锁保护的不是同一个对象、锁的作用域没覆盖读侧、或用了 TSan 不认识的同步原语（自旋、futex、内联汇编），后者用 `__tsan_acquire`/`__tsan_release` 注解解决。
6. **“进程 hang 住，怎么分三类？”** 考点：分层定位。答：先 `perf top`/`top` 看是否 on-CPU（死循环），再 `strace -f -T` 看是否卡在某个 syscall（阻塞），再 `/proc/<pid>/task/*/stack` 或等待通道看是否等锁/等 I/O。三者判据不同，不要一上来 attach 打栈。
7. **“CPU 不高但 QPS 上不去。”** 考点：off-CPU。答：这是 off-CPU 分析场景，`perf stat` 看上下文切换与 CPI，`/proc` 看线程状态分布，配合 trace id 定位到具体阶段；不要只做 on-CPU 采样然后得出“没有热点”的结论。

**别说什么**

- “我用 gdb 打了个断点就找到了”——没交代怎么知道该断在哪，等于没答。
- “ASan 没报错，所以不是内存问题”——盲区没交代，判据不成立。
- “TSan 报的大多是误报”——不区分“工具局限”和“你缺注解”，会被追问到底。
- “这是编译器优化的问题”——把 UB 的因果顺序讲反了，容易被追问到崩。
