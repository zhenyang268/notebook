## 一、它解决什么问题

这项能力拦截的是两类真实事故和一类面试题。

**场景一：短链服务上线。** 假设日新增 100 万条短链，读写比 100:1，即日读请求 $10^8$。平均 QPS $= 10^8/86400 \approx 1.16\times10^3$，按业务曲线取峰值系数 3–5，峰值约 $5\times10^3$ QPS。存储侧：一年 3.65 亿条，单条含长短链、创建时间、过期时间约 500B，原始数据约 180GB，加二级索引按 2–3 倍放大。这三个数一旦算出来，「要不要缓存」「单表放不放得下」「要不要分片」就有依据；算不出来，就只能凭直觉决定，上线后才发现单点写入或索引膨胀限制容量。

**场景二：秒杀。** 1000 件库存、10 万人抢、集中在 1 秒内，峰值 $10^5$ QPS。若请求直连 DB，连接池瞬间被打满，其他业务的查询会一起超时——这不只影响秒杀，还会拖垮整个站点的可用性；库存扣减没有原子性，1000 件卖出 1200 件，就要赔钱加处理舆情。事故后果远超技术层面。

对应的面试题是：「这个系统要多少台机器」「缓存击穿怎么处理」「怎么防超卖」「消息重复消费怎么办」。这类题的共同点是——**没有唯一答案，但有明确的对错口径**。考察的是能否从需求推出量级、再从量级推出结构，并且说得清每个选择在什么条件下失效。

**入口（本文的读法）**：任何 system-design 章节都按“约束→机制→失效条件”读：用 QPS、P99、数据量、一致性级别、故障域和成本预算推出 epoll/accept 队列、网关令牌桶/HTTP 429、Redis key/TTL/SETNX、分片键、InnoDB 行锁/唯一索引、Kafka partition/offset、幂等表、对账任务等具体选择。换的是请求路径上的数据结构、指令和协议字段，不是“架构名词”。

**不换的是什么**：全程不变的是同一请求的 trace_id、业务主键、幂等键、状态字段、事务日志（redo log/WAL）、重试计数与补偿队列；看到差异先问重复请求由哪个唯一索引或 SETNX 拦截、状态推进由哪条 UPDATE ... WHERE version=?/stock>=1 或 Redis Lua 指令完成、失败收敛由哪张对账表或 Kafka 重试次数触发。

## 二、为什么这样做（方法论设计）

**哪些是「有口径才算数」。** 量级估算必须可追溯：输入是 DAU、人均请求数、读写比、峰值系数，输出是 QPS、存储、延迟预算三个数，并且能继续推出「几台应用机、几个分片、缓存要扛多少 QPS」。这条链上任何一环断了，结论就不算数。同理，缓存要报命中率 $h=\frac{\text{hits}}{\text{hits}+\text{misses}}$ 和回源 QPS；限流要报阈值和它相对容量水位的位置；幂等要报唯一键是什么。**看起来专业但无法证伪的**是：「用 Redis 提升性能」「引入 Kafka 解耦」「做多级缓存」——这些没有基线、没有阈值、没有失效条件，追问一句「提升多少、代价是什么」就会暴露问题。

**指标怎么定。** 延迟看 P99 而不是平均值，因为平均值会被大量快请求稀释；可用性看 SLI（错误率、超时率）而不是「没挂过」；缓存看命中率和回源放大倍数；队列看积压深度和消费延迟。指标必须配一个**判据**——命中率掉到多少要扩容、积压超过多少要限流，都要有数。

**边界怎么划。** 三条界线必须说清楚：其一，日请求在千万级以下时，本方法的多数手段属于过度设计，代价是运维复杂度；其二，强一致场景（账务、扣减资金）不能套用这里的最终一致方案，只能做到「不超卖、可对账、能补偿」；其三，分库分表解决的是单表数据量与索引深度问题，**不解决慢查询**——跨分片聚合往往比单表更慢。

**常见错误做法的代价。** ① 先选组件再倒推需求：代价是排障链路上多出一层黑盒，真实瓶颈被掩盖，扩容方向错。② 缓存不设空值兜底、TTL 齐平：代价是穿透与雪崩同时发生，回源 QPS 等于全量查询 QPS，DB 直接被打穿。③ 只做网关层全局限流、不分级：代价是核心接口和边缘接口共享配额，所谓「降级」会变成全站一起不可用。④ 重试无退避、无上限：代价是重试风暴，把一次 1% 的失败放大成雪崩，这是最典型的「自伤式高可用」。⑤ 分片键选错：代价是高频查询跨全部分片，二次拆分需要停机迁移。

**什么时候这套方法会失效。** 流量模型偏离历史分布时（大促、热点事件），估算失效，只能靠限流兜底；单 key 热点超过单分片承载能力时，缓存与分片都会失效，要另做热点探测与本地缓存；需要跨分片事务时，本文的补偿思路不成立，要回到分布式事务层面。这些失效条件本身就是答案的一部分。

## 三、章节大纲

**1. 从需求到约束：QPS、存储、延迟的量级估算**
讲三件事：从 DAU 到平均/峰值 QPS 的推导链、存储量的四要素（条数 × 单条字节 × 副本系数 × 增长期）、延迟预算在调用链上的逐跳分配。学完能回答：「这个系统大概需要多少机器和存储？」「为什么你按峰值 5 倍而不是 10 倍算？」答法要给出假设，并声明单机容量「按实现而定」。

**2. 缓存：旁路、击穿、雪崩与一致性**
讲 Cache-Aside 的读路径与写路径、三类失败模式（穿透/击穿/雪崩）各自的成因与对策、缓存与库的一致性窗口如何声明与补偿。学完能回答：「缓存和数据库不一致怎么办，能忍多久？」「缓存击穿了怎么快速恢复？」

**3. 限流与降级：令牌桶、漏桶、滑动窗口**
讲三种算法的形状差异（桶容量决定突发容忍、速率决定稳态）、固定窗口的边界突刺、滑动窗口的精度与内存代价、限流维度分级、降级的具体动作（兜底值、关非核心、读走缓存）。学完能回答：「你怎么设计一个限流器，为什么选令牌桶？」「限流阈值怎么定出来的？」

**4. 消息队列：至少一次、幂等与顺序**
讲三种投递语义的真实边界——工程上多是「至少一次 + 消费端幂等」，而不是 exactly-once；幂等的实现（业务唯一键、去重表、状态机版本号）；顺序性靠同 key 路由到同分区加单线程消费；积压与重平衡的处理。学完能回答：「消息重复消费怎么处理？」「怎么保证同一订单的消息有序？」

**5. 分库分表与路由**
讲先判是否必要（数据量、单表行数、写入 QPS 三条线）、分片键与查询模式的匹配、路由方式（取模、范围、一致性哈希、基因法）、跨分片查询的三种补法、扩容迁移路径。学完能回答：「订单表的分片键为什么不用订单号？」「怎么不停机扩容？」答案是基因法把用户维度嵌入订单号。

**6. 短链系统的完整设计**
讲发号（自增、号段、雪花）加 62 进制转换与哈希加冲突重试两条路线的取舍、跳转链路（301/302 的选择、缓存、布隆过滤器挡无效 key、热点 key 处理）、异步统计与过期回收。学完能回答：「短链怎么生成、怎么保证不冲突？」「跳转延迟怎么压到 10ms 级？」

**7. 秒杀：超卖、库存扣减与削峰**
讲分层拦截链路：前端按钮 → 网关限流 → 库存预热 → Redis 原子扣减 → MQ 异步下单 → DB 落库；超卖的两道防线（Redis 原子操作 + DB 条件更新 `stock >= 1`）；少卖与对账；用户维度幂等；防刷。学完能回答：「怎么防超卖？」「Redis 扣了库存但下单失败怎么办？」——答对账加回补，不答「加分布式事务」。

**8. 高可用：超时、重试、熔断与隔离舱**
讲超时预算的自顶向下分配（下游超时必须小于上游）、重试的三个约束（退避、上限、只重幂等）、熔断三态与半开探针、隔离舱按依赖拆分资源池、一次雪崩的链路复盘。学完能回答：「下游超时你怎么配？」「什么是雪崩，怎么防？」

## 四、不做什么 · 必要性 · 失效点

### 必要性：删掉会怎样

| 机制 | 删掉会怎样 | 判定 |
|---|---|---|
| 缓存 | 平均 $1.16\times10^3$ QPS、峰值 $5\times10^3$ QPS 的短链读请求全部变成 DB 回源 QPS，连接池排队使 P99 超延迟预算 | 必需 |
| 幂等唯一键 | 消息重复消费与秒杀重试可重复扣减库存，1000 件库存可被扣成负数，“不超卖、可对账”承诺破 | 必需 |
| 限流阈值 | $10^5$ QPS 秒杀峰值透传到 DB，连接池上限被打满，错误率与超时率 SLI 失守 | 必需 |
| 空值兜底 | 不存在短链的 miss 每次回源 DB，命中率 $h=\frac{\text{hits}}{\text{hits}+\text{misses}}$ 被穿透流量拉低，DB 读 QPS 等于全量查询 QPS | 必需 |
| 多级缓存 | 不报命中率、回源 QPS、TTL 抖动与本地缓存淘汰策略时，只增加组件层级，不改变 $5\times10^3$ 峰值回源结论 | 选择 |
| Kafka 解耦 | 删掉后秒杀仍可依靠限流阈值、幂等唯一键、库存扣减原子性同步兜底；只有需要队列积压深度与消费延迟判据时才引入 | 选择 |

### 失效点：哪条前提一破，结论就变

- 应用机核数 ≤ 2 且 DB 连接池上限 ≤ 16 → “几台应用机”估算失效，峰值 $5\times10^3$ QPS 不能由单机并发抵消 DB 往返，限流阈值必须按连接池上限反推。
- 存储介质为 HDD 且 fsync 延迟 P99 > 50ms → 短链创建 INSERT 的同步落库延迟预算失效，DB 连接池被 fsync 阻塞，应用机数估算需改为异步落盘或换 SSD。
- HTTP/1.1 keep-alive 超时 < 网关 idle timeout → TCP 连接池被半开连接占满，按 QPS 设置的限流阈值失效，需改为按并发连接数限流。
- NTP 时钟源偏差 > 100ms 且 TTL 由本地时钟计算 → 缓存过期窗口漂移 100ms，TTL 齐平雪崩的回源 QPS 峰值超过 DB 连接池上限。
- 文件系统权限位缺少 /var/run 写权限 → 热点探测进程无法写本地缓存 key 集合文件，单 key 热点仍打到单分片，分片键与缓存失效。

### 不做什么（范围）

- **不碰 408 考点**：TCP 握手、进程调度、页表、LRU 的算法证明属于计算机基础层，本文只用结论不推导。
- **不写具体语言与框架语法**：Java 线程池参数怎么写、Go channel 怎么用、Spring 注解怎么配，属于编码层。
- **不做中间件运维**：Kafka 集群参数调优、Redis 持久化模式选择、MySQL 内核参数，只到「选型依据与失效模式」，不下去到配置文件。
- **不展开分布式共识的理论完备性**：Raft/Paxos 的正确性证明属于分布式理论层，这里只引用「主从切换有不可用窗口」这类工程结论。
- **不做厂商对比与成本报价**，也不编造压测数字——没有真实环境，任何「实测 QPS 多少」都不写，一律「按实现而定」。
- **不做业务建模**：领域划分、限界上下文属于架构层，本文假设需求已给定。

## 五、面试怎么讲

**30 秒版本**

「系统设计这块我能拿出来的不是某个系统上线过，而是一套能被追问的口径：拿到需求先算出 QPS、存储、延迟预算三个数，再用这三个数决定要不要缓存、要不要分片。比如一条日增百万短链的链路，我能从读写比推出峰值 QPS 和一年存储量，并说明命中率掉到多少就必须加机器。往下每个环节我都知道失效点在哪：缓存击穿、消息重复、分片键选错、重试风暴。这八章我按顺序过了一遍，边界也清楚——强一致的账务场景不在里面。」

**可能被追问的 6–8 个点**

1. **「你怎么估 QPS？」** → 考点：推导链是否完整。答：DAU × 人均请求 ÷ 86400 得平均 QPS，乘峰值系数（按业务曲线取 3–5，不用 10），再乘安全系数；给机器数时先给区间，单机容量声明「按实现而定」，不报具体数字。
2. **「缓存和库不一致怎么办？」** → 考点：一致性口径。答：先声明容忍窗口（秒级），写路径走「先更新库再删缓存」，配延迟双删与 binlog 订阅补偿；不选「先删缓存再写库」，因为并发读会回填旧值。
3. **「限流阈值怎么定？」** → 考点：阈值与容量的关系。答：由容量水位反推，取单机安全水位的 70%–80%；令牌桶容量等于允许的突发量；分全局、接口、用户三级，网关做粗粒度，应用做细粒度。
4. **「消息重复消费怎么办？」** → 考点：幂等设计。答：不追求 exactly-once，走至少一次加消费端幂等；用业务唯一键加去重表，插入冲突即丢弃；状态机类业务用版本号做乐观校验。
5. **「分片键为什么不用订单号？」** → 考点：路由与查询模式匹配。答：分片键要匹配最高频查询条件；用订单号会导致「查我的订单」跨全部分片；用基因法把用户 ID 片段嵌入订单号，兼顾两种查询。
6. **「秒杀怎么防超卖？」** → 考点：原子性与兜底层次。答：Redis 用 Lua 单命令判库存并扣减，DB 层 `UPDATE ... SET stock = stock - 1 WHERE id = ? AND stock >= 1` 兜底；两层都要，因为 Redis 可能丢数据或被绕过；少卖靠对账回补。
7. **「下游超时和雪崩怎么防？」** → 考点：超时预算与熔断。答：整条链设总预算逐跳分配，下游超时小于上游；重试必须带退避、上限、只重幂等请求；熔断用滑动窗口统计失败率，半开态放少量探针；隔离舱按依赖拆线程池。
8. **「短链怎么保证不冲突？」** → 考点：ID 生成。答：发号器（号段或雪花）保证全局唯一再转 62 进制，天然不冲突；若走哈希路线必须加冲突检测与重试；发号器本身要说明单点与时钟回拨的处理。

**别说什么**

- 「我们用了 Redis，性能提升 N 倍」——没有基线、没有口径，追问「N 是多少、怎么测的」立刻露怯。
- 「消息队列保证 exactly-once」——语义就说错了，实际是至少一次加幂等，面试官会顺着往下挖。
- 「分库分表解决性能问题」——它解决单表数据量和索引深度，跨分片聚合反而更慢，这话出口就说明没算过。
- 「加机器就行 / 上云就弹性」——说明没做过量级估算，也说不出瓶颈在哪一层。
