## 1. What It Is Doing

This project aims to build the most commonly used components in deep learning by hand, then assemble these components into a working speech recognition system.

The input is data from a fixed source with uniform specifications: speech waveforms are first featurized by fbank into fixed-length tensors of `(batch, 帧数, 40)`; labels are phoneme sequences much shorter than the number of frames. There are two outputs: one is a self-built layer library plus a self-built backpropagation mechanism (not relying on `torch.nn`); the other is a model trained with it, which outputs a phoneme string for each utterance.

Acceptance is in three layers. **The first layer is correctness**: every hand-written layer must pass numerical gradient checking, with relative error on the order of 1e-6 compared with central differences. **The second layer is component metrics**: the classification task reaches the accuracy threshold, and the sequence task reaches the WER threshold. **The third layer is reproducibility**: one command runs from raw features to evaluation report, two runs with the same configuration produce consistent results, and an error analysis that can identify the main confusion pairs is attached. If any layer fails, the later ones do not count.

## 2. Why Do It This Way (Functional Design)

**Replace `torch.nn` with your own layers, with the interface exposed on the user-space tensor API.** Do not touch the kernel, and do not write CUDA; the replacement happens at the Python layer, and `nn.Linear` is replaced by an ordinary object that holds weights and exposes forward and backward. There are four conventions to implement yourself: a layer object must register its own parameters and be able to enumerate them; backward either hand-writes the chain rule or plugs into a self-built automatic differentiation engine; parameter initialization must be written explicitly (Xavier/He), otherwise a deep network dies in the first round; tensor shapes must be written as comments and kept consistent with the code.

Why not just use the framework? Because calling `nn.Linear` directly is done in two lines, while in `dW = X.T @ dout`, where exactly that transpose goes is precisely the entire value of this project. The cost must be acknowledged: pure Python layers are one to two orders of magnitude slower than highly optimized libraries, so the hand-written version only runs on gradient checks and small data, and training switches back to PyTorch. This switching point must be thought through in advance, otherwise you will spend a lot of time on places where performance should not be optimized.

**Moving from hand-written backward to automatic differentiation is forced by complexity.** Deriving formulas manually for each operator will get out of control once there are many layers: changing one operator requires re-deriving three chains. The second step is therefore to abstract the formula derivation into a mechanism—tensors record their own gradients and "who produced me", operators provide forward and backward, forward builds the graph, and backward propagates in reverse topological order. Three pitfalls must be solved once at the mechanism level, otherwise every later model will have to step on them again: gradients of broadcast tensors have mismatched shapes, so in backward you must sum-reduce over broadcast dimensions; the same node is used by multiple downstream nodes, so gradients must accumulate rather than overwrite, a direct consequence of the computation graph being a DAG rather than a tree; reverse mode can only start from a scalar.

**Data unreliability comes from two places: uneven lengths and misaligned labels.** On the feature side, each utterance has a different number of frames; the approach is to pad to the longest in the batch and simultaneously record a vector of true lengths. All subsequent computation—softmax, normalization, CTC—must read this length vector, otherwise pad frames will silently contaminate the loss and gradients: the loss keeps decreasing but metrics do not improve, and this kind of error is extremely hard to locate. The label side is trickier: an utterance of two hundred frames is given only eight phonemes, and which frame corresponds to which phoneme in between is completely unknown. CTC's approach is to marginalize over all possible alignments (including repeats and blank), summing on the forward-backward lattice with dynamic programming. The existence of blank is precisely to allow "the same phoneme occurring consecutively" and "silence transitions" to be expressed; otherwise two adjacent a's cannot be distinguished as one a or two. Numerically, log-sum-exp must be used; directly multiplying probabilities over two hundred frames will underflow to zero. Why not use a simpler approach? Cutting speech into frame-level labels for ordinary classification treats alignment as a known input, while it is exactly the cost we want to eliminate; using a fixed-length-output seq2seq assumes the output length is known, while it is exactly the unknown.

**The statistical dimension of normalization must align with the invariant.** Sequence statistics are unstable along the time axis, and padding makes batch statistics drift with the longest sentence in the batch, so BatchNorm is difficult to use in RNNs; LayerNorm normalizes over the feature dimension and is decoupled from time length, so it becomes the choice for sequence models and Transformers. This is not for stylistic uniformity; choosing the wrong dimension is equivalent to injecting noise into gradients.

**Evaluation and error analysis are not wrap-up work.** Decoded output is a string; edit distance is used to compute PER/WER, then statistics are collected on which phonemes are always confused. Without this layer, tuning is blind tuning: when WER rises by two points, you cannot tell whether it is features, model, or decoding width.

## 3. Chapter Outline

1. **Shape contract and data pipeline**—configuration snapshot, fbank specifications (window length, frame shift, normalization), variable-length batching and length vectors. Knowledge points: framing and spectral features, padding and mask, reproducibility. Validation: for any batch, feature shapes and length vector are self-consistent; the first batch of data from two runs with the same configuration is bit-for-bit identical.
2. **MLP: hand-written forward and backward**—forward and analytical gradients for linear layer, ReLU, softmax cross-entropy. Knowledge points: chain rule, gradient of cross-entropy with respect to logits, numerically stable formulation of softmax, initialization. Validation: passes gradient check; can overfit to near 100% on small data—being able to overfit shows backward is not wrong.
3. **Mini automatic differentiation engine**—tensor and operator abstraction, computation graph, reverse topological sort, broadcast reduction, gradient accumulation. Knowledge points: reverse-mode differentiation, DAG, risks of in-place operations. Validation: gradients of the same set of operators from hand-written version, engine version, and reference implementation agree.
4. **Convolution, pooling, and regularization**—two implementations of convolution (explicit loops and im2col), backward routing of pooling, training and inference differences of BatchNorm and Dropout. Knowledge points: receptive field, gradient summation caused by parameter sharing, running statistics. Validation: convolution backward passes gradient check; reaches target accuracy on an image classification subset.
5. **Sequence models and BPTT**—RNN/LSTM/GRU forward, backward through time, gradient clipping, packing variable-length sequences. Knowledge points: product terms in BPTT, vanishing gradients viewed from products of Jacobians, how gating provides short paths. Validation: gradient check passes; toy tasks (copy, accumulate) can be learned; can plot the decay of gradient norm over time.
6. **CTC**—forward-backward lattice, log-sum-exp, blank insertion rules, greedy and beam decoding. Knowledge points: marginalization over latent alignments, dynamic programming, numerical underflow, beam pruning. Validation: WER meets threshold on a small vocabulary; self-computed loss differs from reference implementation within 1e-5; decoding behavior on degenerate input (all blank) is explainable.
7. **Attention and Transformer**—scaled dot-product attention, multi-head, positional encoding, residual and LayerNorm, two types of mask (padding and causal). Knowledge points: why attention needs positional encoding, variance argument for the scaling factor, trade-off between LayerNorm and BatchNorm. Validation: attention weight rows sum to 1, weights at masked positions are 0; metrics meet threshold on small-scale tasks.
8. **End-to-end assembly and evaluation**—wire together encoder, decoder, training loop, checkpoint, evaluation script, and do confusion-pair analysis. Knowledge points: learning rate scheduling, early stopping, methodology of error analysis. Validation: one command runs from raw features to WER report and is reproducible; error analysis can identify the top three confusion categories.

## 4. What We Do Not Do

**Not required by the course**: distributed training, mixed precision, CUDA operators, inference deployment and quantization. These are systems engineering and orthogonal to the goal of "seeing gradients clearly"; doing them will not make any chapter more solid.

**No large-scale pretraining or paper reproduction**. Compute and time do not allow it, and that is a matter for another track; all it shares with this project is terminology.

**Do not chase leaderboard rankings**. Scores on private evaluations are heavily affected by data splits and ensembling tricks; this project only uses public metrics as the criterion for "did we do it right", and stops once the line is reached.

**Do not write your own STFT and filter banks**. The feature specifications must be consistent with the course; implementing them yourself will only introduce deviations in window functions and normalization, obscuring the part that is actually to be learned.

**Do not require reproducing a complete Transformer purely by hand**. Chapter 7 allows switching back to the framework's automatic differentiation; the hand-written scope stops at "being able to clearly write why the shapes in attention backward are what they are".

**Implementation freedom** (there is no unique answer; choose one and state the reason clearly): whether convolution uses im2col or explicit loops; whether the optimizer uses momentum SGD or Adam; beam width; naming and parameter registration of the layer API; whether to add a switch to the engine to disable gradients.

**Common pitfalls**: skipping gradient check and training directly; when loss does not decrease, it is impossible to distinguish "the formula is wrong" from "the hyperparameters are wrong"—gradient check is the only means to separate the two at small scale; adding mask only to the loss and forgetting to add it to softmax and normalization, so pad frames silently contaminate gradients; applying softmax before CTC and then taking log, throwing away the stability of log-sum-exp for nothing; treating blank as an ordinary class for frame-level classification, bypassing the alignment problem and thus bypassing the entire content of this chapter; copying BatchNorm in RNNs and then spending two days tuning batch size; copying a reference implementation, getting it to run, and stopping, without turning shapes and gradients into something you can restate yourself—the next chapter will immediately get stuck.
