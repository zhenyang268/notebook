## 1. What It Is Doing

This project asks you to start from a single NAND gate and build all the way up to a computer that can play Tetris. There is no black box anywhere in the chain: the CPU wiring is connected by you, the assembler is a string-processing program you write, the compiler is a recursive-descent parser you write, and even the routine that draws a single pixel on the screen is implemented by you.

There are three kinds of input. The first is the interface skeleton files provided by the course: each chip supplies only pin declarations, with no implementation, and you need to fill in content in the `PARTS:` section. The second is test scripts and expected output: at the hardware layer these are `.tst` plus `.cmp`, comparing signal by signal; at the compiler layer they are line-by-line XML. The third is two language specifications: the Hack machine language (two instruction types, a fixed 16-bit encoding) and the Jack high-level language (grammar, types, and runtime memory-layout conventions).

The output is a series of artifacts that can connect to one another: a set of HDL chip files, from `Not.hdl` all the way to `Computer.hdl`; an assembler that translates `.asm` into 16-bit machine code; a virtual machine translator that translates `.vm` into `.asm`; a compiler that translates `.jack` into `.vm`; and a set of operating system routines written in Jack.

Acceptance does not check whether it "looks like" [the reference], but whether it "is the same." At the hardware layer, each chip runs the official script, and the output matches the `.cmp` line by line; for the largest assembly source file provided by the course, the assembler's output is byte-for-byte identical to the reference implementation; the compiler's XML output matches line by line; finally, Pong can be compiled and responds to the keyboard on the CPU you built yourself.

The key is in the last sentence: this chain is self-verifying. If the CPU is missing one wire, if the assembler special-cases some instruction, if the stack-frame offset is off by one byte, the final Pong will not report an error; it will only show a black screen or freeze. You must go back and narrow down the scope layer by layer—this is exactly the ability the project aims to train.

## 2. Why Do It This Way (Functional Design)

**First substitution: do not use Verilog; use the course's custom HDL.** It is very clear at which layer the interface plugs in—each chip's pin declarations are fixed by the skeleton file, and you may modify only the implementation section, not the ports. This brings a very practical limitation: clock semantics are defined as "evaluate once per tick," so you do not need to write an event scheduler, and you do not need to handle races and metastability between `always` blocks. The cost is that you cannot express tri-state gates, gate delays, or process-related things, and you cannot do timing analysis. The benefit is that the official `.tst` can directly serve as the acceptance criterion; switching to Verilog would require building your own testbench and reference model, and the verification cost would exceed the project itself.

**Second substitution: build the entire software toolchain yourself.** The assembler, VM translator, compiler, and OS are all forbidden from calling existing implementations. Their interfaces are all at the text layer—read text, write text—so they can be diffed byte by byte. This is much more demanding than "write a compiler that runs": what you submit must be semantically equivalent to the reference implementation, with zero error.

**The sources of unreliability fall into three layers, and the means of suppressing them differ.** Hardware-layer unreliability comes from timing: feedback in combinational logic means oscillation; the output of a `DFF` must update only after the clock edge; bit width must be strictly fixed at 16 bits; and the ALU result must not have an extra bit. Suppressing it relies on `.tst` comparing the value of every pin against `.cmp` at every time step, so an error is immediately localized to a specific signal. Software-layer unreliability comes from symbols: at the assembly layer it is labels and predefined symbols (`R0`–`R15`, `SCREEN`, `KBD`); at the VM layer it is the eight memory segments and function scope; at the compiler layer it is class scope and the distinction between fields and local variables. Suppressing it relies on "two passes + symbol table + diff." Runtime-layer unreliability comes from memory mapping—the screen is a block of memory starting at 16384, the keyboard is the word at 24576, and if an address is written incorrectly the program will not report an error; it just will not respond.

**Why insert a stack-based virtual machine in the middle.** Many people's first reaction is to have the compiler emit Hack assembly directly. The cost is that the code generator is tightly bound to two instruction types and two registers, and any change to the target platform requires a rewrite.
