## 1. What It Does

Write an offline renderer from scratch. The input is a text file describing a 3D scene—the camera's position and orientation, several primitives (spheres, planes, triangle meshes), material parameters for each primitive, several point lights and directional lights; then give a backend choice and resolution. The output is a PNG image.

The same scene can be rendered into an image through two completely independent paths. The first is the rasterization pipeline: vertices go through the three-stage model, view, and projection transforms into clip space, undergo perspective division to obtain NDC, are mapped to screen pixels, assembled into triangles and filled, a depth buffer is used to decide which primitive ultimately occupies each pixel, and then lighting is computed and textures are sampled per fragment. The second is ray tracing: shoot rays from the camera pixel by pixel, find the nearest intersection with the scene, cast shadow rays toward light sources to determine occlusion, and recurse along the reflection direction.

Acceptance does not look at code structure; it looks at three things. **The image can be produced**: any scene can be rendered to PNG. **The geometry is correct**: for a cube rotating about its own center, the silhouette and occlusion relationships are consistent under the two paths, the projection is not distorted or stretched, and a full rotation produces no broken faces. **The physical quantities are correct**: the sphere's specular highlight position moves as the light source moves, the ground shadow direction matches the light source direction, and two mirror spheres can see each other's images. Plus one performance acceptance criterion: for a scene with one hundred thousand triangles, the rendering time differs by an order of magnitude before and after the acceleration structure is enabled.

## 2. Why Do It This Way (Functional Design)

**Moving the GPU fixed-function pipeline to CPU user mode is the most core replacement in this section.** Using OpenGL or Vulkan is equivalent to getting rasterization, depth testing, and perspective-correct interpolation for free, and these three are exactly what this project needs to test. Therefore, the interface boundary is fixed at "vertices in, framebuffer out": the entry of the rasterization module is the clip-space vertex array already multiplied by the MVP, and the exit is `Framebuffer{color[], depth[]}`. Once the boundary is drawn, all conventions implicitly handled by the GPU must be written down explicitly and documented: whether the NDC z range is $[-1,1]$ or $[0,1]$; whether the screen-space y-axis points up or down; whether the depth buffer stores $z$ or $1/z$; when filling triangles, the top-left rule is used to determine boundary pixel ownership, otherwise shared edges of adjacent triangles will be drawn twice or not at all. The cost is losing hardware acceleration; a pure-CPU frame at 512×512 takes from tens of milliseconds to several seconds, which is acceptable—this is not a real-time project.

**Write the matrix library yourself; do not use Eigen.** The reason is not that reinventing wheels is fun, but that the exam point lies in matrix semantics: column-major order, transform composition order, the meaning of the fourth component of homogeneous coordinates, and the fact that normals must be multiplied by the inverse transpose. With Eigen, these semantics are swallowed by the type system, and when something goes wrong you can only infer backward from "the image looks weird"; only by writing it yourself can you assert element by element in tests whether $P\cdot V\cdot M$ is correct.

**Use a custom scene format; do not use glTF.** The parser can be written in a few dozen lines, whereas glTF's node hierarchy, accessor/bufferView indirection layer, and PBR material parameters all exceed this project's scope.

**Data unreliability comes from three places, each with a corresponding mechanism.** The first is perspective division: depth in screen space is no longer linear, and uniformly interpolating $z$ will produce z-fighting in the distance where surfaces penetrate each other. The solution is to interpolate $1/z$—in the projection matrix $w=-z_{eye}$, and $1/w$ is linear in screen space; the same applies to UVs and normals: perspective-correct interpolation must be performed (attributes are first divided by $w$, interpolated, and then multiplied back). This is not an optimization; it is correctness. The second is floating-point error: ray-triangle intersection uses barycentric coordinates rather than solving simultaneous plane equations, because barycentric coordinates give both "whether it is inside the triangle" and the intersection parameter at once; you only need to perform an eps test on the three components, and there will be no self-contradiction where the parameter $t$ is valid but the intersection point falls outside the edge; the origin of the shadow ray must be offset along the normal by an eps, otherwise self-occlusion produces black spots. The third is the resolution trade-off of shadow mapping: depth comparison inherently has bias problems; if the offset is too large, shadows detach from objects (peter-panning); if too small, striping appears (shadow acne); this constant must be tuned by yourself and its physical meaning written clearly. In addition, lighting must be computed in linear space and sRGB-encoded before output; otherwise midtones look gray and highlights are overexposed—if this is not written down, you will keep feeling that "something is off but you can't say what."
