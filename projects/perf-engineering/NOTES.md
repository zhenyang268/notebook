# perf-engineering · 分章详细

## 第 1 章 指标与口径：吞吐、延迟分布、P99 与饱和点

**要解决的问题**：在性能工作里，所有结论都建立在「你量的到底是什么」之上。如果口径没定，后面 benchmark、profiling、压测全是自我欺骗：平均值好看但用户仍在骂慢，QPS 涨了但成功率掉了，机器加了一倍但延迟没降。这一章要建立一套能写进报告的指标定义，不解决它，后续任何优化都无判定标准。

**机制**：

指标分三层，必须同时看：

| 层 | 指标 | 口径要点 |
|---|---|---|
| 吞吐 | QPS / RPS、bytes/s、ops/s | 必须绑定「成功且满足 SLO 的请求」；失败请求不计入或单列，不能混进分母 |
| 延迟 | p50 / p90 / p99 / p999 / max，以及延迟分布本身 | 用直方图（如 HdrHistogram 类结构）而非「求和取均值」；均值毫无意义，$\bar{x}$ 被长尾和短请求同时稀释 |
| 资源 | CPU util、load、runqueue、内存、IO util、队列深度 | util 到 100% 不等于饱和；饱和点是「再压一点，延迟开始非线性上翘」的拐点 |

延迟分布的定义比读数重要。两个常见口径混用是事故源头：

- **服务端延迟**：从 worker 拿到请求到写回响应，不含网络与排队。好看，但用户无感。
- **端到端延迟**：从客户端发出到收到完整响应。包含连接建立、排队、网络 RTT、重传。用户真正体验的是这个。

报告里必须写清是哪一个，最好两个都报。

P99 的正确读法：$P99 = t$ 意味着 1% 的请求慢于 $t$。它不是「最慢的请求」，也不是「典型用户」。看 P99 要和 p50 一起看**比值**：$P99/p50$ 长期大于 10 说明排队或长尾在恶化，即使两个绝对值都还在 SLO 内。此外 P99 不能跨机器平均：把 N 台机器的 P99 取平均算出的不是集群 P99（集群 P99 必须从合并后的直方图算，或取最差的那台）。

饱和点的找法是一个单调递增压测：逐步加压，记录 (QPS, p99)，画出曲线。曲线分三段：

```
QPS ↑  延迟几乎不变      → 未饱和区（线性区）
QPS 趋平  延迟开始上翘   → 拐点 = 饱和点（knee）
QPS 下降  延迟暴涨       → 崩溃区（congestion collapse）
```

容量决策点是拐点之前留余量，不是「CPU 跑到 80%」。利用率是代理指标，拐点才是事实。

**最小例子**：

用 `wrk` 压一个本地 HTTP 服务，分四次加压，每次 30s：

```bash
wrk -t4 -c16  -d30s --latency http://127.0.0.1:8080/ping
wrk -t4 -c64  -d30s --latency http://127.0.0.1:8080/ping
wrk -t4 -c256 -d30s --latency http://127.0.0.1:8080/ping
wrk -t4 -c1024 -d30s --latency http://127.0.0.1:8080/ping
```

`--latency` 会输出完整分位表。假设得到（示意值，实测按机器而定）：

```
c=16    ~48k req/s   p50=0.29ms  p99=1.1ms
c=64    ~50k req/s   p50=0.31ms  p99=1.6ms
c=256   ~49k req/s   p50=0.9ms   p99=8ms
c=1024  ~41k req/s   p50=3.2ms   p99=42ms
```

读法：QPS 在 c=64 附近见顶，之后不涨反跌，p99 从 1.6ms 跳到 8ms —— 拐点在 c=64 到 256 之间。此时看 `top` / `mpstat -P ALL 1`，若某个核 100% 而其他核空闲，说明瓶颈在单点（如单个接受连接的线程），加连接数无用，要改架构而不是加压力。

注意这里 p99/p50 从 3.8 变成 13，是比「p99=42ms」本身更强的信号：长尾在系统性变差。

**面试高频问法**：

1. **「你们服务 P99 是多少？」→ 考点：会不会追问口径。→ 答法：先反问「端到端还是服务端、哪个接口、多大压力下、成功率多少」；然后说「我们报的是端到端 P99，在 c=xxx、成功率 99.9% 以上的条件下是 xx ms，同时 p50 是 xx，比值大约 x 倍」。**
2. **「平均值能不能代表延迟？」→ 考点：知不知道分布形状。→ 答法：不能，均值是被长短请求混合稀释出来的数，同一均值可以对应「全部 10ms」和「90% 1ms + 10% 91ms」两种完全不同的体验，必须看直方图和分位数。**
3. **「P99 怎么算？多台机器怎么合并？」→ 考点：会不会把分位数当可平均量。→ 答法：P99 不可跨机器或跨时间取平均，也不能由各机器的 P99 推出集群 P99；正确做法是每台保留直方图，合并桶计数后再求分位，或者退一步报最差实例的 P99。**
4. **「怎么判断系统到饱和点了？」→ 考点：util 与拐点的区别。→ 答法：做单调加压，画 QPS-延迟曲线找拐点，拐点前延迟近似平、拐点后非线性上翘；CPU 80% 只是代理指标，很多系统在 util 60% 就因为锁或队列饱和了。**
5. **「吞吐涨了 20%，算优化成功吗？」→ 考点：会不会看约束条件。→ 答法：要看延迟分布和成功率是否同时守住；如果 QPS 涨是靠放宽超时、丢掉慢请求换来的，p99 和错误率会一起恶化，那不是优化是转移。**

## 第 2 章 benchmark 怎么设计才不骗自己（warmup、隔离、重复、置信区间）

**要解决的问题**：绝大多数「优化了 30%」的结论是噪声。同一份代码跑两次差 15%，换了编译参数差 8%，机器上有别人的任务在抢 CPU。这一章要给出一套让数字可信的最小纪律：预热、隔离、重复、区间。不解决它，你无法区分「我改好了」和「今天机器心情好」。

**机制**：

四件事，缺一不可：

1. **warmup**：丢弃前若干秒或前若干轮。原因有三类，都要考虑：JIT 编译（Java/JS/PyPy 等，热点方法在预热后才编译到最优）、页缓存与连接池冷启动（第一次读文件、第一次建 TCP 连接、第一次分配内存）、CPU 频率与调度器稳态（turbo、频率调节器爬升）。做法是固定丢弃时长而非固定丢弃轮数，并在报告里写明丢弃了多少。

2. **隔离**：控制变量，减少干扰源。同一台机器只跑被测程序 + 压测端（或压测端在另一台机器，注意此时网络成为变量）；绑核避免迁移；关掉会周期性抢 CPU 的东西；固定 CPU 频率调节器；保证内存不被 swap。关键是**记录**你做了什么隔离，因为别人复现不了就是无效结论。

3. **重复**：单次运行不可信。至少 N 次（常见 5–10），每次是独立的完整运行（重新起进程），而不是一次运行里切 N 段——后者共享了同一个预热状态，低估方差。报告 N、均值、标准差或中位数与四分位。

4. **置信区间**：不要只报一个数。样本小、分布不明时别假设正态，用非参数方法（bootstrap 重采样求均值或中位数的区间）更稳。判断「A 比 B 快」的正确姿势是看两组区间是否分离，而不是看两个点估计谁大：

```python
import numpy as np
def boot_ci(x, n=10000, lo=2.5, hi=97.5, stat=np.median, rng=np.random.default_rng(0)):
    x = np.asarray(x)
    bs = np.array([stat(rng.choice(x, size=x.size, replace=True)) for _ in range(n)])
    return np.percentile(bs, [lo, hi])

A = [...]  # 基线 10 次
B = [...]  # 改后 10 次
print(boot_ci(A), boot_ci(B))  # 区间重叠 → 现有数据不足以宣称差异
```

还有几条容易被忽略但会直接毁掉结论的：
- **测什么就报什么**：微基准要防优化器把被测代码整个消除（结果没被使用、循环不变式被提出），要制造副作用或使用 benchmark 框架的 `DoNotOptimize` 类设施；不确定编译器行为时用「结果校验 + 校验和输出」保底。
- **压测端不能是瓶颈**：客户端 CPU 打满、连接数上限、端口耗尽（TIME_WAIT 堆积）都会让「服务端到顶」变成「客户端到顶」。要先单独压测压测端或用 known-good 工具做对照。
- **不要跨变量比较**：一次只改一个东西；同时改代码和机器配置，结论无效。
- **区分微基准与端到端**：微基准回答「这个函数快不快」，端到端回答「用户快不快」，前者通过不等于后者通过。

**最小例子**：

测一个纯函数，跑 10 次独立进程，取中位数与 bootstrap 区间：

```bash
for i in $(seq 1 10); do
  ./bench --iters 1000000 --warmup-iters 100000 --json >> runs.jsonl
done
```

每条记录形如 `{"ns_per_op": 42.1, "iters": 1000000}`。汇总：

```python
import json, statistics, numpy as np
xs = [json.loads(l)["ns_per_op"] for l in open("runs.jsonl")]
med = statistics.median(xs)
ci = boot_ci(xs)          # 上一段定义的函数
print(f"median={med:.2f} ns/op, 95% CI=[{ci[0]:.2f}, {ci[1]:.2f}]")
```

示意输出：`median=42.1 ns/op, 95% CI=[41.6, 43.4]`。若改动后得到 `median=40.0, CI=[39.4, 40.9]`，两区间不重叠 → 可以说「约 5% 提升，区间不重叠」。若改动后是 `median=41.5, CI=[40.2, 43.9]`，区间重叠 → 只能说「在本次实验的分辨率下没有观察到显著差异」，不能说「提升了 1.4%」。

这个例子同时暴露了「独立进程重复」的价值：如果只跑一次拿到 40.0 就宣布优化成功，你无法知道那是真实差异还是这台机器当天的抖动。

**面试高频问法**：

1. **「你怎么证明这个优化真的有效？」→ 考点：有没有统计纪律。→ 答法：固定环境做隔离，丢弃 warmup，独立重复 N 次，报中位数加区间；只有当基线和优化后的区间不重叠时才宣称有效，重叠就说明当前分辨率不够，要加大样本或降低噪声。**
2. **「为什么要 warmup？丢弃多少合适？」→ 考点：了不了解冷启动的三个来源。→ 答法：JIT 编译、页缓存/连接池/内存分配器冷启动、CPU 频率与调度稳态；丢弃量按「直到指标曲线走平」的经验时长定，并在报告里写清丢了多少、依据是什么。**
3. **「压测结果不稳定，你怎么排查？」→ 考点：会不会区分噪声源和真实信号。→ 答法：先看做隔离没有（绑核、频率、邻居任务、压测端是否成为瓶颈），再看是不是缺少重复（单次运行方差本来就大），再看是否有周期性干扰（GC、定时任务、日志刷盘），最后才怀疑被测系统。**
4. **「微基准测出来快了 10%，线上会快多少？」→ 考点：知不知道微基准的边界。→ 答法：不一定快，微基准里这个函数可能只占端到端时间的几个百分点，还要看是否被编译器优化掉、缓存是否被理想化；要先做端到端的 profile 确认它是热点，再谈收益。**
5. **「一次只跑一遍的 benchmark 有什么问题？」→ 考点：对噪声与方差的直觉。→ 答法：单次样本既包含真实差异也包含机器抖动，无法分离；同一份代码重复跑常能差出百分之十几，所以必须多次独立运行并给出区间，否则「提升」很可能就是抖动。**

## 第 3 章 CPU profiling：采样 vs 插桩，perf 与 Instruments 怎么用

**要解决的问题**：第 1、2 章告诉你「P99 变差了、benchmark 可信」，但没告诉你 CPU 时间花在谁身上。这一章把「我猜是序列化慢」变成「证据显示 62% 的样本落在 `memcpy` 的平顶上」。不解决这一步，后续所有优化都是加机器或随机改代码。注意 profiling 只回答「时间花在哪」，不回答「为什么慢」——后者要靠第 5、6 章的内存和锁数据。

**机制**：

两种获取时间归属的手段，成本模型完全不同。

- **采样（sampling）**：以频率 $f_s$ 周期性触发中断或让 PMU 计数器溢出，在内核里抓当前指令指针和调用栈，离线聚合。开销近似 $\propto f_s \times c_{stack}$，其中 $c_{stack}$ 是抓一次栈的成本（frame pointer 链很便宜，DWARF 展开很贵）。它不改变程序执行路径，样本是统计无偏的，但**分辨率受限于采样间隔**：执行时间短于 $1/f_s$ 的函数可能一次都没被采到。
- **插桩（instrumentation）**：在函数入口/出口插入计数或计时——编译期 `-pg`（gprof 的 `mcount`）、`-finstrument-functions`；运行期 uprobe/kprobe/eBPF；语言层 JFR、async-profiler 的 wall-clock 模式。计数精确，但开销与**调用次数**成正比，且会抑制内联、扰动 i-cache，属于观察者效应明显的手段。

采样的固有偏差是 **skid**：计数器溢出到 CPU 真正进入内核记录 IP 之间还会执行若干条指令，记录到的 IP 偏向热点之后。Intel PEBS / AMD IBS 用硬件缓冲缓解，但没有免费午餐——不要拿单个样本给一个函数定罪。

perf 的三个用法层次：

```bash
# 1) 先看宏观指标，判断是不是 CPU 受限
perf stat -e cycles,instructions,cache-misses,branches ./bench --iters 100000

# 2) 抓热点：99Hz 是常见选择，避免与目标进程的周期锁步
perf record -F 99 -g --call-graph fp -p $PID -- sleep 30
# 没有 frame pointer 时改用 DWARF，代价是每次采样都要展开栈
perf record -F 999 -g --call-graph dwarf,16384 -p $PID -- sleep 10

# 3) 读：默认按 children 聚合，看「谁自己耗时」要关掉
perf report --stdio --no-children -g graph,0.5,caller
perf top -p $PID -g
```

`--call-graph` 的选择是实战分水岭：`fp` 要求二进制用 `-fno-omit-frame-pointer` 编译（Go 默认保留 frame pointer，C/C++ 在 `-O2` 下常被省略）；`dwarf` 更准但采样频率要降下来；支持的 CPU 上 `lbr` 用硬件记录栈。栈抓不到，后面一切都白做。

Instruments（macOS/iOS）的 Time Profiler 本质是同一个采样器：固定间隔抓所有线程的栈，Inverted Call Tree 从叶子往根看，Self/Weight 两列区分「自身耗时」和「含子树」。命令行入口是 `xctrace record --template 'Time Profiler' --launch -- ./app`。它的坑在符号化：release 构建必须带 dSYM，否则看到的是地址不是函数名。System Trace 是另一条线，看的是线程调度与阻塞，属于第 4 章的 off-CPU 口径。

选型一句话：**找分布用采样，找次数和特定调用用插桩**；两者结论冲突时，采样看占比、插桩看绝对次数，不要互相否定。

**最小例子**：

```bash
perf record -F 99 -g --call-graph dwarf,8192 -o perf.data -- ./bench --iters 100000
perf report -i perf.data --stdio --no-children -g graph,0.5,caller | head -40
```

结果形态（示意）：`bench` 之下 `compress_block` 的 self 占比最高，`malloc` 次之，二者之上还有一条 `main→run→worker` 的路径。此时正确的下一步不是「优化整个 bench」，而是把 `compress_block` 单独提成微基准（固定输入、固定迭代），或者换分配器后再采一次，看 `malloc` 那一段是否变窄。若 `perf report` 里大量 `[unknown]`，先修符号——未 strip、`--symfs`、dSYM 三件事，否则整次分析无效。

**面试高频问法**：

1. **「采样和插桩怎么选？」→ 考点：开销模型与偏差来源 → 答法**：找热点用采样，开销与采样频率成正比、不改执行路径但不保证抓到短函数；要精确调用次数或抓某个特定函数用插桩，开销与调用次数成正比，而且会抑制内联、扰动缓存，结论要打折看。
2. **「perf 采到的函数地址为什么会偏？」→ 考点：skid → 答法**：PMU 计数器溢出到内核记录 IP 之间还会执行若干指令，所以样本偏向热点的后几条指令；PEBS/IBS 能缓解但不是消除，所以只看聚合趋势，不用单条样本定位到指令。
3. **「`perf record -g` 抓不到调用栈怎么办？」→ 考点：栈展开机制 → 答法**：先确认二进制有没有 frame pointer（`-fno-omit-frame-pointer`），有就用 `--call-graph fp`；没有就退到 `--call-graph dwarf`，代价是展开成本高、频率要降；JIT 场景还要额外注册符号表，否则栈会断在 JIT 边界。
4. **「`perf report` 里 children 和 self 有什么区别？」→ 考点：聚合口径 → 答法**：self 是样本恰好落在该函数本身，children 是把以它为根的所有样本都算进去；判断「该优化谁」看 self，判断「从哪条路进来的」看 children，用 `--no-children` 切到 self 视角。
5. **「Instruments 里 Time Profiler 显示的热点和源码行对不上？」→ 考点：优化与符号化 → 答法**：优化构建会内联、会重排，热点常常归到内联后的外层函数或地址区间；要靠 dSYM 符号化，并对照 Inverted Call Tree 和 Self 列，不能直接当源码行归因。

## 第 4 章 火焰图读法：on-CPU 与 off-CPU，宽度、合并与调用栈

**要解决的问题**：profiler 吐出来的是几十万条栈样本，人眼没法读。火焰图把它们压成一张宽度即比例的图，用来看「哪条路径吃掉了多少时间」。但如果不知道宽度是**样本占比**而不是耗时、不知道 on-CPU 与 off-CPU 是两套口径，就会得出「这个函数最宽所以最该优化」这种错误结论。

**机制**：

数据流是两段式的：采样器产出原始栈，`stackcollapse-*` 把每条栈压成一行 `frame;frame;frame count`，`flamegraph.pl` 渲染成 SVG。核心聚合规则就三条：

- **宽度**：某帧的宽度 $w = n_{\text{frame}} / N$，$n_{\text{frame}}$ 是包含该帧的样本数，$N$ 是总样本数。固定采样频率下，它近似等于**时间占比**。所以宽度既不是调用次数，也不是单次耗时——一个调用 100 万次的 1μs 函数，宽度可能远小于一个调用 10 次但每次 100ms 的函数。
- **合并**：只把**完全相同的栈**（从根到叶逐帧相同）累加。同一个叶子函数经由两条不同路径进来，会渲染成两座独立的塔，各自计宽。这就是「同一个函数在图上出现好几次」的原因。
- **方向**：常规火焰图根在底部、火焰向上，底部是入口，顶部是叶子；icicle 图上下翻转，等价。

**on-CPU vs off-CPU 是两种时间，不能相加**：

| | 采样依据 | 宽度含义 |
|---|---|---|
| on-CPU | 线程正在 CPU 上执行时被打断 | 占用 CPU 的时长占比 |
| off-CPU | 线程被调度走/阻塞（`sched_switch`） | 等待的墙钟时长 |

off-CPU 需要内核调度事件或 eBPF，且部分事件依赖 `CONFIG_SCHEDSTATS` / `sched_schedstats` 开关，具体可用性按内核配置而定——不能假设默认打开。把两者画在一起是 hot/cold 火焰图（一半 on-CPU 正向、一半 off-CPU 倒挂），而不是简单相加。

```bash
# on-CPU
perf record -F 99 -g -p $PID -- sleep 20
perf script > out.perf
stackcollapse-perf.pl out.perf > out.folded
flamegraph.pl --title="on-CPU 20s" out.folded > oncpu.svg

# off-CPU：bcc 的 offcputime，-f 输出折叠格式
offcputime-bpfcc -p $PID -f 20 > offcpu.folded
flamegraph.pl --color=io --title="off-CPU" offcpu.folded > offcpu.svg
```

**读图要点**：

1. **先找平顶（plateau）**：大片同宽、上方没有更深帧的区域，是真正在做工的函数（`memcpy`、`malloc`、自旋）。平顶的宽度就是它的自耗时上限。
2. **看宽窄突变**：上层突然比下层宽，说明该层有大量 self 时间，或者栈在这里断了。
3. **断裂栈的识别**：出现 `[unknown]`、或某帧下面帧数明显偏少，先怀疑 frame pointer 链被优化掉、跨语言边界、JIT 未注册符号，而不是「这里没有调用者」。
4. **别跨图比宽度**：只有同一二进制、同一采样频率、同一负载下宽度才可比。要比两次结果，用 `difffolded.pl` 求差，或者回到绝对样本数归一。

**最小例子**：

```bash
perf record -F 99 -g -p $(pgrep -n myserver) -- sleep 20
perf script > out.perf
stackcollapse-perf.pl out.perf > out.folded
flamegraph.pl out.folded > oncpu.svg
grep -c '' out.folded     # 折叠后不同调用栈的行数，即塔的数量量级
```

结果形态（示意）：最宽的一塔是 `main→handle→serialize→memcpy`，`memcpy` 处是平顶，说明自耗集中在这里；旁边一塔 `main→handle→mutex_lock` 也有可观宽度——但**光看 on-CPU 分不清是自旋还是被阻塞**，要再跑一次 off-CPU 图：若 off-CPU 图上同一路径宽而长，就是等锁；若 on-CPU 上是平顶，就是自旋在烧 CPU。这两种情况的修法完全不同（换临界区粒度 vs 减少争用）。

**面试高频问法**：

1. **「火焰图的宽度代表什么？」→ 考点：指标口径 → 答法**：宽度是该帧出现的样本数占总样本数的比例，固定采样频率下近似时间占比；它不是调用次数，也不是单次耗时，所以不能拿宽度直接换算成「这个函数花了多少毫秒」。
2. **「on-CPU 和 off-CPU 火焰图有什么区别，能画在一张图上吗？」→ 考点：时间口径 → 答法**：on-CPU 统计线程在 CPU 上执行的样本，off-CPU 统计线程被调度走或阻塞的时长；两者是不同口径不能相加，需要同时看时用 hot/cold 火焰图左右拼接，而不是把样本混进一个计数里。
3. **「为什么同一个函数在图上出现在好几个地方？」→ 考点：合并规则 → 答法**：折叠只对完全相同的调用栈累加，不同父路径进来的同一叶子是两座独立的塔；所以要沿塔向下看父路径才知道是哪个调用方贡献的宽度，优化时也得按路径分别处理。
4. **「图上一大片平顶说明什么？」→ 考点：热点与栈完整性 → 答法**：平顶表示样本集中在同一函数且没有更深帧，通常是真正的自耗热点（或内联后的外层函数）；但如果同时伴随大量 `[unknown]`，先修栈展开和符号，再谈优化。
5. **「两次采样的火焰图能直接比宽度得出优化收益吗？」→ 考点：可比性 → 答法**：只有同二进制、同采样频率、同负载下宽度才可比；更稳的是用折叠文件求差或者比绝对样本数，否则采样噪声和负载漂移会被当成优化效果。

## 第 5 章 内存与缓存：miss、NUMA、伪共享的量化

**要解决的问题**：现代 CPU 的绝大多数“算得慢”其实是“等数据”，而 CPU profiling 只会把时间算进那条访存指令上，看起来像指令本身慢。这一章解决的是：把“访存慢”这件事从直觉变成可量化的指标——哪一级 miss、miss 到哪去、有没有跨核抢同一行、内存落在哪个 NUMA 节点。不解决，优化就会变成盲目减小数据结构和加线程。

**机制**：首先要分清指标的口径。`perf stat` 里的 `cache-references` / `cache-misses` 是 PMU 硬件事件，在多数 x86 上 `cache-misses` 对应最后一级缓存 miss，具体映射按 CPU 实现而定，不要跨机器比。要算比率就用成对事件：`L1-dcache-loads` / `L1-dcache-load-misses` 看 L1，`LLC-loads` / `LLC-load-misses` 看最后一级，miss rate = misses / loads。事件前缀与可用性因架构和内核版本而异，跑之前先 `perf list` 对一遍。

定位“miss 到哪去了”用 `perf mem record`（采样 load/store，报告命中层级与数据地址），定位“多核抢同一行”用 `perf c2c`：它统计 HITM（该行被另一核以 Modified 状态命中），这是伪共享的直接证据。伪共享的成因是 cache line（x86 上 64B）作为一致性协议的最小单位，两个线程写同一行里不同的变量，行仍然在核间来回弹。修复是对齐填充：C/C++ 用 `alignas(64)` / `__attribute__((aligned(64)))`，Java 用 `@Contended`（需开启对应 JVM 参数）。

NUMA 侧的口径是“分配落在哪个节点、访问落在哪个节点”：`numactl --hardware` 看拓扑，`numastat` 看 `numa_hit` / `numa_miss` / `numa_foreign`，后者非零说明有跨节点访问。注意 Linux 默认 first-touch：页落在首次写它的线程所在节点，所以“绑核不等于绑内存”，要 `numactl --cpunodebind=0 --membind=0` 显式约束。

**最小例子**：

```bash
perf stat -e cycles,instructions,L1-dcache-loads,L1-dcache-load-misses,\
LLC-loads,LLC-load-misses ./bench
```

读法：先算 IPC = instructions / cycles。若 IPC 明显偏低而 `LLC-load-misses / LLC-loads` 偏高，说明时间花在去内存取数上，接着跑 `perf mem record ./bench && perf mem report` 看是哪些符号、哪些层级；若怀疑多线程互相干扰，跑 `perf c2c record -a -- sleep 5 && perf c2c report`，在报告里看 HITM 高的 cache line 及其归属变量。

伪共享的最小验证：两个线程各自 `counter++` 一千万次，变量放在同一结构体相邻位置 vs 各自 `alignas(64)` 隔开。前者会看到 `perf c2c` 的 HITM 集中在那一行，耗时显著更高；后者 HITM 基本消失、耗时下降。具体倍数按平台与核数而定，但“HITM 消失 + 耗时下降”两件事同时成立才算证据闭环。

NUMA 的最小验证：`numastat` 前后对比，加 `--membind` 绑定后 `numa_foreign` 应显著下降，若端到端延迟不降，说明该 workload 不是跨节点带宽敏感，优化点不在这里。

**面试高频问法**：

1. 「cache miss 率高就说明有性能问题吗？」→ 考点是口径与瓶颈判定，不是背指标。→ 一句话答法：miss 率必须和 IPC、访存占比一起看，纯顺序流式访问 miss 率天然高但被预取掩盖，只有当 miss 抬高了 stalled cycles、进而拉高端到端延迟时才算瓶颈。
2. 「你怎么证明是伪共享，而不是普通的内存慢？」→ 考点是证据链。→ 一句话答法：`perf c2c` 里看到某条 cache line 的 HITM 计数高、且该行对应的是多个线程各写各的相邻变量，再加填充后 HITM 与耗时同时下降，三条都成立才是伪共享。
3. 「NUMA 什么时候影响大，什么时候可以忽略？」→ 考点是判断边界。→ 一句话答法：working set 超出单节点缓存、且带宽密集的 workload 影响大；单线程绑核绑内存一致、或数据量小到能待在 LLC 里的场景，跨节点访问占比低，基本可以忽略。
4. 「`perf mem` 和 `perf c2c` 有什么区别？」→ 考点是工具定位。→ 一句话答法：`perf mem` 回答“这次访存落在哪一级、延迟多少”，是单线程视角的归因；`perf c2c` 回答“这条 cache line 被几个核抢过”，是跨核争用视角，伪共享只能靠后者定性。
5. 「做完缓存优化，你怎么量化收益？」→ 考点是实验纪律。→ 一句话答法：同机、同参数、同 workload 跑改动前后两轮，同时看 PMU 指标（IPC、miss rate、HITM）和端到端延迟分布；指标动了但延迟没动，说明瓶颈已经不在缓存上。

## 第 6 章 IO 与锁竞争：iostat、perf lock、临界区怎么量

**要解决的问题**：IO 等待和锁等待都是“不烧 CPU 的时间”，on-CPU 火焰图上直接是空白，`top` 里只表现为 CPU 不高但吞吐上不去。这一章解决的是：把这两类阻塞量化出来——IO 到底堵在哪一层，锁到底等了多久、等了多频繁。不解决，就会对着一条平坦的 CPU 曲线反复怀疑代码“算得不够快”。

**机制**：IO 侧先统一口径。`iostat -x` 的关键列：`r/s`、`w/s` 是**完成**的请求数（不是提交数），`await` 是平均完成时间（排队 + 设备服务），拆开看 `r_await` / `w_await`，`aqu-sz`（旧版叫 `avgqu-sz`）是平均在途请求数，`%util` 是设备“忙”的时间占比。判饱和的正确姿势是三者交叉：`await` 上升 + `aqu-sz` 上升 + 吞吐不再增长 = 队列或设备到头；`await` 上升但 `aqu-sz` 很小 = 单次请求本身就慢（大 IO、设备慢、或上层有同步等待）。`%util` 在支持多队列并行设备的盘上（如 NVMe）可接近 100% 仍有余量，不能单看它下结论。`iowait` 是 CPU 空闲且有未完成 IO 的时间，是结果不是原因，多核机器上还会被严重低估。

锁侧要明确三个量：**竞争次数**（有多少次没直接拿到锁）、**等待时间分布**（尤其是 P99，平均值没有意义）、**临界区持有时间**（拿锁到放锁）。平均持有时间再短，调用频率高时排队照样能把尾延迟拉爆——这是排队论直觉，不是估算公式。

工具路径：`perf lock record` / `perf lock report` 基于内核的锁事件，输出每个锁的 acquired、contended、con-bounces、wait-total、wait-max（字段集合与可用性按内核版本和配置而定，不支持时该命令会直接报错）。更通用的做法是动态插桩，比如用 bpftrace 把 libc 的 mutex 入口和返回配对，直接出等待时间直方图。最后用 off-CPU 火焰图定性：栈顶是 `futex`、`mutex_lock` 还是 `read` / `fsync`，一眼能分出是锁还是 IO。

**最小例子**：

```bash
iostat -x 1
```

某一列出现 `w/s` 不再上涨、`w_await` 从低位翻倍、`aqu-sz` 同步上升，说明写路径已经排队到设备侧；若 `w_await` 涨而 `aqu-sz` 仍是零点几，问题在上层——每次请求本身大或存在同步刷盘，回去查调用栈。

锁等待的最小量化（x86_64 + glibc 路径，按发行版实际路径调整）：

```bash
bpftrace -e '
uprobe:/lib/x86_64-linux-gnu/libc.so.6:pthread_mutex_lock
{ @t[tid] = nsecs; }
uretprobe:/lib/x86_64-linux-gnu/libc.so.6:pthread_mutex_lock
/@t[tid]/
{ @wait_ns = hist(nsecs - @t[tid]); delete(@t[tid]); }'
```

返回值处的差值就是“从发起到真正拿到锁”的时间，无竞争时它只是函数自身开销，量级极小；竞争时直方图右侧会长出长尾。限制要说清楚：这只量到等待，量不到持有；要量持有得在 unlock 侧配对，而 unlock 调用点无法直接告诉你它释放的是哪把锁，通常靠锁地址或业务侧显式埋点解决。

**面试高频问法**：

1. 「`%util` 到 100% 就是磁盘瓶颈吗？」→ 考点是设备并行度这层认知。→ 一句话答法：不一定，`%util` 只表示设备有请求在处理的时间占比，多队列设备可以同时处理多个请求；判饱和要看 `await`、`aqu-sz` 与吞吐是否同时顶住。
2. 「`iowait` 高说明 IO 是瓶颈吗？」→ 考点是区分现象与原因。→ 一句话答法：不能，`iowait` 是 CPU 空闲等 IO 的结果，多核下只是部分核空闲；要看 IO 侧的 `await`、`aqu-sz` 和进程是否真的阻塞在 IO 上。
3. 「锁竞争怎么量化？」→ 考点是有没有具体的量。→ 一句话答法：三个量——单位时间竞争次数、等待时间分布（看 P99 不看均值）、临界区持有时间；`perf lock` 给前两个的现成视图，拿不到锁事件时用 bpftrace 在 mutex 入口/返回配对量。
4. 「临界区平均持有时间很短，是不是就不用管了？」→ 考点是排队放大效应。→ 一句话答法：要看总等待占比，锁被调用的频率会放大排队；单次持有再短，QPS 上来后等待队列照样把尾延迟顶起来。
5. 「CPU 不高但吞吐上不去，你怎么分清是 IO 还是锁？」→ 考点是 off-CPU 视角。→ 一句话答法：抓 off-CPU 火焰图，阻塞栈上是 `futex` / `mutex_lock` 就归锁，是 `read` / `write` / `fsync` 就归 IO；两边都有就先按各自的等待总时长占比排序。

## 第 7 章 压测与容量估算：连接模型、排队直觉、限流位点

**要解决的问题**：把「这台机器能扛多少」从主观感觉变成一个可复现、可解释的数字，并说清这个数字在什么连接模型、什么延迟口径下才成立；否则容量结论无法使用，也无从判断该在哪里加限流。

**机制**：

连接模型先决定分母。thread-per-connection 的成本是每连接一个线程栈（虚拟内存大、常驻按需），上下文切换随活跃连接增长；event loop（epoll/kqueue）把「连接存在」和「线程占用」解耦，代价是任意回调都不许阻塞。连接数并不等于并发请求数：keep-alive 下 N 个连接可以承载远小于 N 的在途请求，反过来一个高扇出请求会占用多条下游连接。容量估算要按**在途请求（in-flight）**和每请求的资源占用记录，而不是按连接数。

排队直觉只需三个式子：Little 定律 $L=\lambda W$（在途数 = 到达率 × 停留时间）；利用率 $\rho = \lambda/\mu$（$\mu$ 为服务率，多服务台则乘台数）；M/M/1 的总停留时间

$$W = \frac{1}{\mu-\lambda} = \frac{1/\mu}{1-\rho}.$$

$\rho \to 1$ 时分母趋零，延迟不是线性变差而是发散。这就是「CPU 跑到七八成之后 P99 突然抬升」的全部数学内容。M/M/1 的泊松到达、指数服务时间假设现实中很少成立，但「利用率越接近 1，排队项越主导」对 G/G/1 同样成立，只是常数不同。

压测的第一号陷阱是开环与闭环。闭环工具（固定并发、收到响应才发下一个）在服务变慢时自动降速，把过载区间隐藏起来；再叠加协调遗漏（coordinated omission），慢请求期间本该发出的请求根本没被计时，P99 被系统性低估。找饱和点必须用**固定到达率**的开环压测。

限流位点决定保护谁：

| 位点 | 保护对象 | 典型手段 |
|---|---|---|
| 入口 / LB | 整个集群 | 按 IP、租户的令牌桶 |
| 应用入口 | 进程内资源 | 并发信号量、准入队列 |
| 下游客户端 | 依赖服务、连接池 | 池大小、超时、熔断 |
| 存储层 | DB | 连接数上限、按成本配额 |

放错层的典型症状：入口限了 1000 QPS，但每请求扇出 10 次下游调用，下游实际承受 10000 QPS，先崩。原则是每个被共享的稀缺资源前都要有一道闸，且每道闸按它保护的那个资源自己的容量标定，而不是按入口 QPS 标定。

开环压测骨架：

```python
rate, inflight = 200, Semaphore(512)
for t in poisson_arrivals(rate, duration=60):
    sleep_until(t)
    if inflight.acquire(blocking=False):
        spawn(send_one, release=inflight)
    else:
        drop += 1          # 丢弃数也是结果的一部分
```

`drop` 不为零说明目标 RPS 已超出服务能力，而不是压测工具不行。

**最小例子**：`wrk -t4 -c64 -d60s --latency` 是闭环的，得到的是「64 并发下的延迟」，不是容量。改用固定速率工具（wrk2 的 `-R`，或 k6 的 `constant-arrival-rate` executor），从 100 RPS 起、每轮 +100 RPS、每档跑 60s，记录吞吐、P50/P99 与丢弃数。拐点判据：吞吐不再随目标 RPS 等比例上升，同时 P99 抬升一个数量级以上。拐点对应的实际吞吐即当前部署在当前请求 mix 下的容量，乘 0.6–0.7 作为规划值。请求 mix、数据量、缓存命中率任一变化，结论都要重测。

**面试高频问法**：

1. 「连接数和 QPS 是一回事吗？」→ 考点是连接模型与在途请求的区别。→ 不是。连接是持久通道，QPS 是在途请求的到达率；keep-alive 下一个连接可以串很多请求，高扇出服务一个请求又占多条下游连接。算容量按在途请求和每请求的资源占用算。
2. 「CPU 才七成，为什么延迟已经很难看？」→ 考点是排队论的非线性。→ 因为延迟里排队那部分按 $\rho/(1-\rho)$ 增长，利用率 70% 时排队项已明显超过服务时间本身，再叠加多队列、锁、GC 的抖动，尾部就发散。留余量是数学，不是保守。
3. 「你的压测为什么没测出真实上限？」→ 考点是闭环与协调遗漏。→ 闭环工具在服务变慢时自动降速，压力永远压不上去；固定并发下慢请求期间本该发出的请求没被计时，P99 被低估。要固定到达率并统计丢弃数才找得到拐点。
4. 「限流该加在哪一层？」→ 考点是共享资源与扇出。→ 加在每一个会被共享的稀缺资源前面，每道闸按其保护的那个资源的容量单独标定；只在入口限流，扇出后下游照样被打穿。
5. 「怎么估一个新服务的实例数？」→ 考点是从单机容量到集群规划。→ 单机开环压出拐点吞吐，按目标利用率打折得单机可用容量，再用峰值 QPS 除以它并加冗余；上线后按真实 mix 复测校准。

## 第 8 章 加速比与扩展性：Amdahl、强扩展与弱扩展

**要解决的问题**：给出「加资源能换来多少」的上界和测法，避免把「加 4 台机器吞吐只涨 1.8 倍」既当成事故也当成正常；否则无法判断该优化串行段还是该继续扩容。

**机制**：

Amdahl 定律，固定问题规模、可并行比例 $p$、$n$ 个执行单元：

$$S(n) = \frac{1}{(1-p) + p/n}, \qquad \lim_{n\to\infty} S(n) = \frac{1}{1-p}.$$

串行部分钉死了天花板，与 $n$ 无关。$1-p$ 哪怕只有 5%，上限也只有 20 倍。

Gustafson 定律，固定时间、规模随 $n$ 增长：$S_{\text{scaled}}(n) = (1-p) + p\,n$。两条不矛盾，回答的是不同问题：Amdahl 答「固定任务能快多少」，Gustafson 答「同样时间能做多大的任务」。

强扩展：固定问题规模只加资源，看时间下降，效率 $E(n)=S(n)/n$。弱扩展：固定每执行单元的负载，加资源的同时加问题，理想情况时间持平，效率 $E_{\text{weak}}(n)=T_1/T_n$。

现实的扩展性比 Amdahl 更差，因为除串行段外还有**一致性开销**：跨核、跨节点的同步、缓存行乒乓、锁争用。Gunther 的通用扩展性定律（USL）把两项都写进去：

$$S(n) = \frac{n}{1 + \sigma(n-1) + \kappa\,n(n-1)}.$$

$\sigma$ 是争用项（曲线趋于饱和），$\kappa$ 是一致性开销项（二次项，$n$ 够大后吞吐**下降**）。$\kappa>0$ 时曲线有峰值，这就是「加机器反而更慢」的定量解释。$\sigma,\kappa$ 可以用实测点拟合出来，用来判断该拆锁（降 $\sigma$）还是该减少跨节点同步（降 $\kappa$）。

测量上三个口径必须固定：一次只改一个维度，改 $n$ 时问题规模、请求 mix、warmup、超时全锁死；报吞吐还是报延迟要写明，服务型系统通常看「固定延迟预算下能扛多少 QPS」而不是裸时间；基线 $T_1$ 用单执行单元测，并确认没被超线程与频率调节污染。

**最小例子**：某服务 4 核，profile 显示 5% 时间在全局日志锁与序列化上，即 $1-p=0.05$。则

$$S(4)=\frac{1}{0.05+0.95/4}=\frac{1}{0.2875}\approx 3.48,\quad E(4)\approx 87\%.$$

若实测只有 2.8 倍，缺的那部分就是 USL 的 $\kappa$ 项——跨核同步开销，Amdahl 解释不了。优化方向由此分叉：把并行度从 95% 提到 99%（拆日志锁）能把上限从 20 提到 100；而在 95% 并行度下把 4 核扩到 8 核，只从 3.48 到 $1/(0.05+0.95/8)\approx 5.9$。先看清瓶颈在哪一段，再决定买机器还是改代码。

**面试高频问法**：

1. 「Amdahl 和 Gustafson 矛盾吗？」→ 考点是两者假设不同。→ 不矛盾。Amdahl 固定问题规模，得出串行段决定的上限 $1/(1-p)$；Gustafson 固定时间、规模随资源增长，得出线性项 $(1-p)+pn$。一个答「快多少」，一个答「能做多大」。
2. 「强扩展和弱扩展分别怎么测、报什么指标？」→ 考点是实验设计。→ 强扩展固定问题规模只加资源，报时间与效率 $S(n)/n$；弱扩展固定每单元负载、同步加问题，看时间是否持平。两者都要锁死 mix 与 warmup，否则数字不可比。
3. 「为什么加到一定规模吞吐反而下降？」→ 考点是 USL 的一致性开销项。→ 除串行段外还有跨节点同步与缓存行乒乓，成本随 $n^2$ 涨；$\kappa>0$ 时曲线有峰值，过峰值再加机器是负收益。拟合 $\sigma$ 与 $\kappa$ 就能看出哪项主导。
4. 「扩展效率 60% 算合格吗？」→ 考点是效率没有通用阈值。→ 没有通用值，取决于成本结构与延迟预算：批处理看单位成本，在线服务看多加一台能否换来接近线性的 QPS 且 P99 不恶化。低于阈值就该停下来优化串行段与同步，而不是继续堆机器。
5. 「给你一条随并发上升的吞吐曲线，怎么判断该优化什么？」→ 考点是从曲线形状反推瓶颈类型。→ 早饱和趋平是 $\sigma$ 主导（锁、连接池、单分区），先拆争用；先升后降是 $\kappa$ 主导（跨节点同步、共享写），先减少一致性开销；单机就上不去，先回 perf 找串行热点。
