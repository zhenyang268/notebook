## 1. What It Is Doing

In one sentence: **replace the kernel's TCP with your own implementation.** There are two inputs—the byte stream written in by the application through the `socket`, `read`, `write` set of system calls, and a sequence of datagrams of bounded length received from some UDP port, which may be lost, out of order, or duplicated; the output is one path—the byte stream read by the peer application via `read`, in correct order, with no duplicates and no omissions, plus the connection being able to be established and torn down normally.

Acceptance does not look at "whether it runs"; it looks at whether three things hold simultaneously:

1. **The replacement is real**: the same application code (for example, send an HTTP GET and print the web page to stdout) has unchanged behavior after the underlying fd is replaced with your own implementation, while the data captured on the NIC for this traffic is UDP packets, not TCP packets.
2. **Reliability is real**: with 30% packet loss and reordering artificially injected, 1 MB of data is still fully transferred, the retransmission count does not exceed 1.5 times the theoretical value, and the timeout backs off at 1, 2, 4, and 8 seconds.
3. **The timing is correct**: packet capture shows the three-way handshake, four-way teardown, `TIME_WAIT` staying for 2MSL, and sequence numbers do not fail at the 32-bit wraparound point.

## 2. Why Do It This Way (Functional Design)

**The replacement point is chosen at the socket layer, not inside the kernel.** Kernel TCP is a monolithic component that cannot be split apart: you cannot turn off only its retransmission, and you cannot intercept a segment midway and handle it yourself. The feasible approach is not to touch kernel TCP, but to treat the kernel as the IP layer—open a UDP socket, stuff the TCP segment you construct as a whole into the UDP payload and send it out, and have the peer unpack and restore it. What UDP provides here is exactly IP's delivery semantics: unreliable, bounded length, no ordering guarantee, and no guarantee against duplication. Thus all the problems TCP must solve remain untouched in your own hands, while the kernel only handles routing, ARP, fragmentation, and the driver—this part is unrelated to transport-layer logic, so delegating it to the kernel is no loss.

The interface lands at the `FileDescriptor` layer: define a set of virtual functions (`read`, `write`, `close`, `connect`, `peer_closed`), with `TCPSocket` and `UDPSocket` each providing an implementation, plus a `LocalStreamSocket` that uses a local memory loopback for fast testing. Application code sees only the fd and not the type, so "replace it with your own stack" manifests in the source as changing one construction call, with everything else unchanged. This is where the word "replacement" lands in the entire project.

**Unreliability comes from three places, and must be suppressed separately.** First, the real network: across machines UDP loses and reorders packets, while local loopback basically does not lose packets, so you cannot rely on "get it running first and talk later"; you must test with an injected loss rate from the start. Second, artificial injection: configure loss rate, duplication rate, and delay jitter so tests are deterministic and parameters can be swept. Third, errors in your own implementation: RTO set too short causes retransmission storms, window miscalculation causes deadlock, and `ackno` off by one causes permanent retransmission. The mitigation is the standard four-piece set—sequence numbers and cumulative acknowledgment, timeout retransmission, receiver reassembly, and receive-window flow control—and this project requires each item to land on variables, not concepts.

**Time must be managed by yourself.** No kernel timer is available. All timeouts hang off a single `tick` of `EventLoop`: each loop iteration computes the nearest expiration time and uses it as the timeout cap for select. The retransmission timer runs only when there are bytes in flight; after a timeout it doubles the backoff, and it resets upon receiving a new acknowledgment; when the window is zero the timer must still run, but the probe sends only one byte and does not back off—if this detail is not written correctly, the zero-window scenario will deadlock.

**Blocking semantics must be preserved.** `read` must not return 0 when the byte stream is empty (that would be treated by the upper layer as EOF); it must block; and the user thread cannot poll the kernel fd itself, because what it waits for may be a TCP segment that has not yet arrived. The approach is to connect a self-wakeup pipe between `EventLoop` and the blocking point: when the loop receives a segment, writes it into the byte stream, and finds that someone is waiting, it writes one byte into the pipe to wake up `read`.

**Why not use a simpler approach.** Using kernel TCP directly—there is no unreliability, so there is no retransmission, no reassembly, and no window, and the entire project is hollowed out. Raw socket—requires root, the kernel sends RST for connections you did not create, and you still have to assemble the IP header yourself, with debugging cost far exceeding the benefit. TUN device—you have to write the IP layer and routing yourself, it is platform-bound, and taking over all the network-layer work actually dilutes the transport-layer mainline. The costs of UDP encapsulation must be accepted: the MTU is eaten into by the UDP and IP headers, packet capture tools see UDP rather than TCP, and it cannot interoperate with a real TCP peer (both ends must be your own stack). These three are actively accepted costs, not oversights.

## 3. Chapter Outline

**Chapter 1 · Skeleton and Byte Stream.** The build system, `sponge`'s `Buffer`/`Reader`/`Writer`, and how to run tests; `ByteStream`'s capacity, blocking when full on write, blocking when empty on read, EOF, and the two cumulative counters `bytes_read`/`bytes_written`. Knowledge points: one-way queue, separation of capacity and watermark. Acceptance: with capacity 1000, after writing 1500 bytes the writable amount is 0, and after reading 600 the writable amount recovers by 600.

**Chapter 2 · Reassembler.** The two cursors `first_unassembled` and `bytes_pending`; trim out-of-order, overlapping, and duplicate fragments into three parts (left already-received part, middle writable part, right part to be buffered); parts exceeding capacity are dropped directly and await retransmission; the EOF position must be able to pass through holes. Knowledge points: interval trimming, capacity upper bound of the out-of-order cache. Acceptance: out-of-order input `[3-5][0-2][6]` must output contiguous 0..6, and duplicate fragments must have zero write count.

**Chapter 3 · Receiver.** Conversion between 32-bit sequence numbers and 64-bit absolute sequence numbers (`unwrap`/`wrap`, anchored by `checkpoint`); SYN and FIN each occupy one sequence number; generate `ackno` (the next expected byte, including SYN); window = capacity − bytes pending reassembly; must still respond under zero window. Knowledge points: sequence number space, wraparound, advertisement mechanism of flow control. Acceptance: cross-check against `tcp_parser`, including the three boundary types SYN/FIN/zero window.

**Chapter 4 · Sender.** The three variables `next_seqno`, `bytes_in_flight`, and the left/right window boundaries; how `fill_window` slices by "the smaller of the peer window and MSS"; how `ack_received` slides and triggers retransmission; RTO initial value, exponential backoff, retransmission count; zero-window probing. Knowledge points: sliding window, timeout retransmission, semantic boundary of cumulative acknowledgment. Acceptance: at 30% packet loss, retransmission count ≤ theoretical value × 1.5, and the backoff sequence is 1, 2, 4, 8.

**Chapter 5 · Connection and State Machine.** Three-way handshake (SYN / SYN+ACK / ACK), four-way teardown, passive close, `TIME_WAIT` and 2MSL, handling of received RST, when `_linger_after_streams_finish` is set. Knowledge points: state transitions, half-close, why the third handshake cannot be omitted. Acceptance: connection establishment, transfer of 1 MB, normal disconnection, and peer closing first can all complete.

**Chapter 6 · Putting TCP into UDP.** One-to-one mapping between segments and datagrams, how ports align, MTU and maximum segment length, checksum; a simulation layer that injects loss/reordering/duplication; why this layer provides exactly IP's semantics. Knowledge points: encapsulation, message boundaries, fault injection. Acceptance: transfer can still complete across two virtual machines (through a real NIC).

**Chapter 7 · socket API Adaptation.** The `FileDescriptor` abstraction, the two implementations `TCPSocket` and `UDPSocket`, and how `EventLoop` + `tick` + the self-wakeup pipe connect "network events" to "user-thread blocking"; degradation and trade-offs of `connect`/`listen` semantics. Knowledge points: fd abstraction, blocking and non-blocking, event loop. Acceptance: `webget` behavior is unchanged after replacing the fd, and `read` neither busy-waits nor returns early.

**Chapter 8 · Integration, Stress Testing, and Debugging.** Connect the send and receive sides into `TCPConnection`; loss-rate sweep (0/1/10/30%); performance numbers (time for 1 MB, retransmission amplification ratio); use packet capture and state printing to locate "which variable it is stuck on". Knowledge points: systematic debugging, metric definitions. Acceptance: the full link runs end to end, and you can state from the logs the trigger reason for every retransmission.

## 4. What Not to Do

**Do not implement full congestion control.** Implement only receive-window flow control; the full forms of `cwnd`, slow start, and fast retransmit/fast recovery are out of scope, but the sender must leave a replaceable slot for "where the window comes from", so that when congestion control is added later, only the window source changes and the reassembly layer is untouched.
