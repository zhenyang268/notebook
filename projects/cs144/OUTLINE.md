## 一、它在做什么

用一句话说：**把内核里的 TCP 换成自己写的。** 输入有两路——应用层通过 `socket`、`read`、`write` 这一套系统调用写进来的字节流，以及从某个 UDP 端口收到的一串长度有限、可能丢失、可能乱序、可能重复的数据报；输出是一路——对端应用按 `read` 读到的、顺序正确、不重不漏的字节流，外加连接能正常建立与拆除。

验收不看“跑通了没有”，看三件事能不能同时成立：

1. **替换是真的**：同一份应用代码（比如发一个 HTTP GET 把网页打印到 stdout），底下的 fd 换成自己的实现后行为不变，而这段数据在网卡上抓到的是 UDP 报文，不是 TCP 报文。
2. **可靠性是真的**：人为注入 30% 丢包和乱序，1 MB 数据仍然完整传完，重传次数不超过理论值的 1.5 倍，超时时间按 1、2、4、8 秒退避。
3. **时序是对的**：抓包能看到三次握手、四次挥手、`TIME_WAIT` 停留 2MSL，序号在 32 位回绕处不出错。

## 二、为什么这样做（功能设计）

**替换点选在 socket 层，不选在内核里。** 内核 TCP 是一整块无法拆的组件：没法只关掉它的重传，也没法在中途截住一个段自己处理。可行的做法是不碰内核 TCP，只把内核当成 IP 层——开一个 UDP socket，把自己构造的 TCP 段整块塞进 UDP 的 payload 发出去，对端拆开还原。UDP 在这里提供的恰好是 IP 的交付语义：不可靠、有长度上限、不保证顺序、不保证不重复。于是 TCP 要解决的全部问题原封不动留在自己手里，内核只负责路由、ARP、分片和驱动——这部分与传输层逻辑无关，交给它不亏。

接口落在 `FileDescriptor` 这一层：定义一组虚函数（`read`、`write`、`close`、`connect`、`peer_closed`），`TCPSocket` 与 `UDPSocket` 各实现一份，另有一个 `LocalStreamSocket` 走本机内存环路供快速测试。应用代码只见 fd 不见类型，所以“换成自己的栈”这件事在源码上体现为换一个构造调用，其余一字不改。这就是整个项目里“替换”二字的落点。

**不可靠性从三个地方来，要分别压。** 一是真实网络：跨机器时 UDP 会丢会乱，本地回环基本不丢，所以不能靠“先跑通再说”，一开始就要用注入的丢包率做测试。二是人为注入：配置里给丢包率、重复率、延迟抖动，测试才有确定性，也才能扫参数。三是自己实现里的错：RTO 设太短导致疯狂重传、窗口算错导致卡死、`ackno` 差一导致永久重传。压缩手段是标准的四件套——序号与累计确认、超时重传、接收端重组、接收窗口流控——本项目要求逐条落到变量上，而不是概念上。

**时间得自己管。** 没有内核定时器可用。所有超时挂在 `EventLoop` 的一次 `tick` 上：每轮循环算出最近一个到期时刻，把它当作 select 的超时上限。重传定时器只在有在途字节时运行，超时后翻倍退避，收到新确认就清零；窗口为零时定时器仍要跑，但探测只发一个字节且不退避——这条细节不写对，零窗口场景会死锁。

**阻塞语义必须保住。** `read` 在字节流为空时不能返回 0（那会被上层当成 EOF），必须阻塞；而用户线程不能自己去 poll 内核 fd，因为它等的可能是一个还没到达的 TCP 段。做法是在 `EventLoop` 与阻塞点之间接一条自唤醒管道：loop 收到段、写进字节流、发现有人在等，就往管道里写一个字节把 `read` 唤醒。

**为什么不用更简单的做法。** 直接用内核 TCP——没有不可靠性，就没有重传、没有重组、没有窗口，整个项目被掏空。raw socket——需要 root，内核会对你没建过的连接回 RST，还得自己拼 IP 头，调试成本远超收益。TUN 设备——要自己写 IP 层与路由，平台绑定，把网络层的活全揽过来反而稀释了传输层这条主线。UDP 封装的代价必须认下来：MTU 被 UDP 和 IP 头吃掉一截、抓包工具看到的是 UDP 而非 TCP、无法与真实 TCP 对端互通（两端都得是自己的栈）。这三条是主动接受的代价，不是疏漏。

## 三、章节大纲

**第一章 · 骨架与字节流。** 构建系统、`sponge` 的 `Buffer`/`Reader`/`Writer`、测试怎么跑；`ByteStream` 的容量、写满阻塞、读空阻塞、EOF、`bytes_read`/`bytes_written` 两个累计计数。知识点：单向队列、容量与水位的分离。验收：容量 1000 时写 1500 字节后可写为 0，读走 600 后可写恢复 600。

**第二章 · 重组器。** `first_unassembled` 与 `bytes_pending` 两个游标；把乱序、重叠、重复的片段裁成三段（左侧已收部分、中间可写部分、右侧待缓存部分）；超出容量的部分直接丢弃等重传；EOF 位置要能穿过空洞。知识点：区间裁剪、乱序缓存的容量上界。验收：乱序输入 `[3-5][0-2][6]` 输出必须是连续 0..6，重复片段写入次数为零。

**第三章 · 接收端。** 32 位序号与 64 位绝对序号的换算（`unwrap`/`wrap`，靠 `checkpoint` 定锚）；SYN 与 FIN 各占一个序号；生成 `ackno`（下一个期望的字节，含 SYN）；窗口 = 容量 − 待重组字节数；零窗口下仍要应答。知识点：序号空间、回绕、流量控制的通告机制。验收：对拍 `tcp_parser`，含 SYN/FIN/零窗口三类边界。

**第四章 · 发送端。** `next_seqno`、`bytes_in_flight`、窗口左右边界三个变量；`fill_window` 如何按“对端窗口与 MSS 取小”切片；`ack_received` 如何滑动并触发重传；RTO 初值、指数退避、重传计数；零窗口探测。知识点：滑动窗口、超时重传、累计确认的语义边界。验收：丢包 30% 下重传次数 ≤ 理论值 × 1.5，退避序列为 1、2、4、8。

**第五章 · 连接与状态机。** 三次握手（SYN / SYN+ACK / ACK）、四次挥手、被动关闭、`TIME_WAIT` 与 2MSL、收到 RST 的处理、`_linger_after_streams_finish` 何时置位。知识点：状态迁移、半关闭、为什么第三次握手不能省。验收：连接建立、传 1 MB、正常断开、对端先关都能走完。

**第六章 · 把 TCP 装进 UDP。** 段与数据报的一一映射、端口如何对位、MTU 与最大段长、校验和；注入丢包/乱序/重复的模拟层；为什么这一层提供的正是 IP 的语义。知识点：封装、报文边界、故障注入。验收：跨两台虚拟机（经真实网卡）仍能完成传输。

**第七章 · socket API 适配。** `FileDescriptor` 抽象、`TCPSocket` 与 `UDPSocket` 两份实现、`EventLoop` + `tick` + 自唤醒管道如何把“网络事件”接到“用户线程阻塞”上；`connect`/`listen` 语义的降级与取舍。知识点：fd 抽象、阻塞与非阻塞、事件循环。验收：`webget` 换 fd 后行为不变，`read` 不会忙等也不会提前返回。

**第八章 · 合体、压测与调试。** 收发两侧接进 `TCPConnection`；丢包率扫描（0/1/10/30%）；性能数（1 MB 用时、重传放大比）；用抓包与状态打印定位“卡在哪个变量”。知识点：系统性调试、指标定义。验收：全链路端到端跑通，且能对着日志说出每一次重传的触发原因。

## 四、不做什么

**不做完整拥塞控制。** 只实现接收窗口流控；`cwnd`、慢启动、快重传/快速恢复的完整形态不在范围内，但发送端要留出“窗口来自哪里”这个可替换的空位，将来接拥塞控制时只改窗口来源、不动重组层。

**不做 TCP 选项。** SACK、时间戳、窗口缩放、选择性重传一概不做；`MSS` 只作为常量，不协商。

**不做网络层与链路层。** ARP、以太网帧、IP 路由与分片交给内核——这正是选 UDP 封装换来的。408 里这两块的知识点用单独题目覆盖，不在这里重复实现一遍。

**不做高并发与多进程。** 不做 epoll 驱动的大量连接、不做 `fork` 后共享 fd、不做跨进程传递连接。

**以下是自由度，怎么做都行：** `ByteStream` 底层用 `std::string` 还是环形缓冲；重组器用有序 map 还是区间列表；状态机用一个大枚举还是收发分离的两个状态；日志格式；测试用例的组织方式。只要外部可观测行为一致，实现路径不作要求。

**常见的跑偏，遇到要立刻回头：**

- 在 UDP 之上先套一层“保证送达”，再让 TCP 层假装不丢包——可靠性练不到，等于白做。
- 为了让用例过而把窗口写死成常数，或把 `ackno` 直接赋成 `next_seqno`——两个变量混成一个，后面所有边界都会错。
- 跳过重组器直接顺序写——顺序测试全过，一注入乱序就崩。
- 只测本地回环。回环几乎不丢包，一切超时逻辑都是死代码，必须靠注入才能激活。
- 把“能传完 1 MB”当终点，不看重传次数和退避曲线——那是唯一能证明可靠性机制真的在工作的数字。

## 五、面试怎么讲

**30 秒版本**

这个项目要解决的是：把应用看到的 socket 字节流，换成我在用户态、基于 UDP 数据报实现的可靠有序字节流。我认为卡点不在收发，而在丢包、乱序、重复和 32 位序号回绕下，把重组、累计确认、超时重传、窗口流控和连接状态机同时做对。验收口径我会说三件事：同一份应用代码换 fd 后行为不变且抓包看到 UDP；注入丢包乱序后数据不重不漏、重传退避为 1/2/4/8 秒；抓包能看到握手、挥手和 TIME_WAIT 2MSL。

**可能被追问的 6–8 个点**

1. **他问：为什么用 UDP 封装，不用内核 TCP、raw socket 或 TUN？**  
   **真实考点：** 你是否理解“替换点”的边界和代价。  
   **怎么答：** 内核 TCP 是一整块，没法只关重传或截某个段；raw socket 要 root，没建过的连接内核会回 RST，还要自己拼 IP 头；TUN 要把 IP 层和路由一起揽过来。UDP 封装拿到的是 IP 的交付语义：不可靠、有长度上限、不保序不保重，所以 TCP 要解决的问题都留在自己层。代价要认：MTU 被 IP/UDP 头吃掉，段长要按 `MTU - IP头 - UDP头` 截；抓包看到的是 UDP；两端都必须是自己的栈，不能和真实 TCP 对端互通。

2. **他问：32 位序号回绕怎么处理？SYN/FIN 为什么要单独算？**  
   **真实考点：** 序号空间、回绕比较、`ackno` 语义。  
   **怎么答：** 接收端用 `checkpoint` 做锚，`unwrap` 把 32 位 seq 按 `checkpoint + int32_t(seq - checkpoint)` 映射到 64 位绝对序号，`wrap` 反向折回；所有比较在绝对序号上做，回绕点不靠裸 `<`。SYN 和 FIN 各占一个序号，`ackno` 是下一个期望字节，收到 SYN 后要 +1；`first_unassembled` 的起点和 FIN 后的 EOF 位置都要把这一位算进去。

3. **他问：重组器怎么处理乱序、重叠、重复和容量？**  
   **真实考点：** 区间裁剪、乱序缓存上
