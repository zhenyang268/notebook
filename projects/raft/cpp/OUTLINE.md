## 一、它在做什么

在真实操作系统约束下实现一个可被故障挑战的共识内核：多进程组网、socket 通信、文件系统持久化、真崩溃（进程被终止）、真分区（网络隔离）。它承诺的不是「符合预期」，而是**一组可检查的不变量在任何注入场景下都不被打破**，且打破时能定位到哪一条先破、对应哪个字段、哪条日志。

**入口（本文的读法）**：把「共识协议的语义」与「它跑在什么之上」明确切开——协议层只借六条不变量，运行时层负责把「内存中的字节」变成「稳定介质上的字节、网卡上的字节」，验证层负责把这两层的承诺变成可断言的检查。**换掉实现（用什么 RPC、什么日志格式、几条线程）都不影响承诺；换掉失败模型（假设网络可靠、假设 fsync 免费）就会让承诺失效——所以失败模型必须先写死。**

**排除集合（换什么、不换什么）**：换掉的是一切「替身」——不再有模拟网络、不再有内存模拟磁盘、不再有进程内的「发送即到达」。不换的是：协议语义与六条安全不变量（与 go-lab 完全一致）、多数派阈值规则、任期作为逻辑时钟。**这条排除集合是本线与 demo 线的唯一但决定性的差别。**

**积木（四件，都能独立验证；其中两件是契约型）**：

1. **原子指令的读改写保证（CAS / fetch-add）**——可以独立验证。它让「谁先到多数派谁赢、且只赢一次」成为一件可观测的事；还能验证「同一任期只投一票」在多个执行线程下是否真的成立。
2. **`fsync` 与目录项语义**——可以独立验证。`fsync(fd)` 保证文件内容到稳定介质；`rename` 在同一文件系统内原子；**目录的 `fsync` 才能保证改名本身落地**。三句话分别对应三个可以单独制造崩溃来验证的事。
3. **socket 的字节流语义**（契约型）——只能端到端验证：TCP 保证字节有序，**不保证请求不被重复处理、不保证超时不重试、不保证对端进程还活着**。验证方式是「注入一个错」：让对端在一次处理中途被杀，观察本端是否把它误当成功。
4. **事件循环的就绪通知**（契约型）——只能端到端验证：注入一个慢调用，看是否阻塞了同一循环上的其他连接；症状必须与预期一致（该饿死的连接饿死、该超时的超时）。

「加个锁保护」不是积木，那是结论；「用个线程池」也不是积木，那是选点。

**最小情形**：两个进程、一次写、一次 `fsync`、一次强制终止。此时协议完全不起作用，只剩两件事：字节有没有出去、字节有没有落地。**这个下界是本线唯一能验证「持久化承诺」的地方**——在它之前谈什么「回复前落盘」都是空的。

**生成（三类叠加，点名）**：

- **累加**：节点数 3 → 5；连接数随节点数增长（每对节点之间至少一条）；日志条数增长 → 段文件滚动 → 快照压缩；客户端并发增长 → 提交路径的批量与流水线。
- **覆盖**：故障类型逐类覆盖——丢包、延迟、重复、乱序、单向隔离、双向分区、进程被强制终止、磁盘写入中途崩溃、磁盘满、慢盘、快照传输中断。每一类对应一组不变量检查与一个可重放语料条目。
- **最坏情形**：任意时刻都可能发生——慢调用落在事件循环上的任意位置、崩溃落在任意一次写之间、分区把任意子集切开。**判据是「任意时刻都正确」，不是「平均正确」。**

**两边是什么**：同一份共识状态的两个持有者——协议侧持有内存字段（当前任期、投票对象、提交点、日志与快照边界），设施侧持有稳定介质上的字节（状态文件、段文件、快照文件）与网卡上的字节流。**设施侧的写入顺序决定了协议侧重启时的初始值**，这条耦合就是本线要显式管理的对象：它不是「实现细节」，它是承诺的一部分。

## 二、为什么这样做（工程设计与取舍）

**它替换掉的是什么**：现实里没人手写共识，更没人手写 RPC。这里两样都自己做，不是为了炫技，而是为了**可观测性**——丢包、延迟、分区必须能精确作用在某一条 RPC 上并且可回放；写入必须能在任意字节边界被打断并且能看到崩溃后果。用现成框架时，这两件事都做不到，于是「不变量成立」只能靠信念。

**七个选择题，每个都标「选点」而不是「原理」**：

1. **线程模型**：可选「每连接一线程」「固定线程池 + 事件循环」「单事件循环 + 工作线程」「全异步协程」。本线选**事件循环负责收发与定时器、协议状态由单线程串行处理、慢操作（fsync、大快照传输）交给工作线程**。理由：协议状态字段耦合极深，串行处理把锁从「必须正确」降级为「几乎不需要」；代价是慢操作绝不能落在循环上，否则整个节点卡住——这个代价本身就是一条判据。
2. **事件循环**：可选 epoll / io_uring / 阻塞多线程。选 epoll 这类就绪通知的理由是它足够透明（能一眼看出某次唤醒是谁触发的），而不是因为它最快。**irq 与边缘触发的差异、以及「就绪通知不等于数据完整」这件事，是这一块的主考点。**
3. **自有 RPC**：消息帧 = 长度前缀 + 类型 + 载荷；请求号用于匹配回执；超时即放弃等待但不放弃语义（可能已在对端执行）。可选的传输是 TCP（字节流、可靠但不保语义）；也允许在测试环境用管道/UDS，但**必须保持同样的语义假设：可能重复、可能超时、对端可能死**。
4. **序列化**：可选「长度前缀 + 手写字段」「protobuf」「自定义二进制」。选点判据不是快，而是**能否精确控制字段边界**——因为故障注入需要「让某条消息在某个字段之后被截断」。可变长编码与未知字段的处理要有明确规则，否则版本换一次就解不开。
5. **日志段文件与 fsync**：选**追加写段文件 + 定期轮转 + 状态文件原子替换**。理由：单个不断增长的文件在崩溃恢复与截断上都是灾难；段文件让「截断到某位置」变成「删掉某几个文件」。fsync 策略可选「每条都同步」「批量同步（group commit）」「上层驱动」，**必须显式写清选的是哪一个，因为它是性能与持久性的唯一交换点**。
6. **快照与截断**：可选「整块快照」「分块流式」。整块更简单但要求一次能放下；分块要处理中断与偏移。选区在实现前定，定完不许在中途改（改就会让已落盘的快照格式失效）。
7. **成员变更**：可选「一次性全量切换」「单步变更」「联合配置」。本线选**单步变更（每次只动一个成员）并保留联合配置作为可选退路**。理由：任意时刻的多数派集合必须两两相交，一次性切换会制造两个互不相交的多数派。

**为什么不用更省事的做法**：

- **为什么不用现成 Raft 库**：库会把「不变量在哪一行被保证」隐藏掉，而这条线的验收正是「能指出它」。
- **为什么不用「TCP 可靠所以不用管重复」**：TCP 保证字节有序，重试与去重是**应用层语义**。把两者混淆是本线头号失效点。
- **为什么不用「覆盖写状态文件」**：崩在写中途会留下截断文件，重启解析失败等于丢掉全部投票记录——必须临时文件 → fsync → rename → fsync 目录。
- **为什么不把 fsync 全去掉先跑通**：那样跑通的只是协议层，持久化承诺一条都没验，回到 demo 线的水平。
- **为什么不追求「零拷贝、无锁队列」**：先有可观测的正确性，再谈这些；顺序反了会用一个不可解释的系统换一点没测过的吞吐。

**数据形态**：日志是段文件序列（每段内追加写、段间按序号排），快照是带边界元组的独立文件，状态文件是任期 + 投票对象的原子替换文件。**所有位置运算都要问一句「这是逻辑位置、段内偏移，还是文件字节偏移」**——三者混算是本线第二大的错误来源（第一大是把 TCP 当成不变式）。

## 三、章节大纲（七个工程块，顺序即依赖）

> 依赖图见总纲 §三。前一块的「做完能……」没拿到就进下一块，会让后面的故障注入变成不可能。

**1. 承诺与不变量（契约层，先写，后写代码）**
两列写清：承诺什么（可观察行为：写成功的，重启后还在；分区期间少数派不服务；任一任期至多一个主）、不承诺什么（不承诺吞吐、不承诺可用性、不承诺线性一致读若不实现读路径）。把六条安全不变量写成**可断言的检查条目**，每条配一个「注入什么错时它必须亮」的反例。做完能：任指一条不变量，说出它由哪一块保证、哪一行顺序错误会让它失效。

**2. 运行时：线程模型与事件循环**
循环负责接受连接、读就绪、定时器到期；协议状态单线程串行；慢操作移交工作线程并回投结果。要处理：就绪通知不等于数据完整（半包）、一次读可能拿到多条消息（粘包）、连接生命周期（对端半关闭、写端阻塞）、定时器的精度与「一次循环做了太久」的自检。做完能：注入一个慢调用，观察到它只饿死预期的那条连接而不是全部；并能在指标里看到循环的单次耗时上界。

**3. 自有 RPC 与序列化**
帧格式、请求号、超时语义、重试语义（**必须承认可能重复执行**）、错误分类（可重试 / 不可重试 / 未知）。序列化要能精确截断到字段边界以配合故障注入。做完能：让一条请求在对端执行中途被杀，本端能区分「没执行」「可能执行」两种状态，并在上层用幂等把「可能执行」压成确定行为。

**4. 持久化：状态文件、日志段与 fsync**
段文件格式（含头部版本、段序号、校验）、追加写、轮转、原子替换状态文件、目录 fsync、崩溃点注入（在写第 N 个字节处终止）。要明确：哪些字段必须落盘（当前任期、投票对象、日志、快照边界）、哪些不必（提交点、已投递点、同步位置、匹配位置——判据是「重启后能否凭剩余信息安全推回」）。做完能：在每个崩溃点上重启，得到「要么没有投票记录（可再投）、要么已记录且不会投第二票」，绝不出现同任期两票。

**5. 快照与截断**
触发策略（按字节/按条目/上层驱动）、边界元组的来源（**必须从被丢弃的最后一条日志里取任期**）、截断与段文件删除的时序（先落新快照再删旧日志，顺序反了会丢数据）、分块传输与偏移（**分块偏移是字节流偏移，与日志位置无关**）、装完后的位置对齐。做完能：让一个节点落后到快照之前，它能被追上；并在传输中断后重试能收敛，不出现半个快照。

**6. 成员变更**
单步变更：每次只改变一个成员，让任意时刻的多数派集合两两相交；配置本身走日志（**配置也是日志条目**），因此变更序列与命令序列共享同一个顺序；变更期间的提交点与会话状态要明确——离开的成员不再计票，但它的日志不能再被当成权威。可选退路是联合配置（两套成员同时需要多数派）。做完能：在变更途中注入崩溃与分区，集群不会出现两个互不相交的多数派同时声称有资格。

**7. 验证：故障注入、不变量检查、性能口径**
注入器要能精确到「对哪条 RPC、哪对节点、哪个方法、哪种故障、持续多久」，且场景可回放（固定种子 + 场景文件）。不变量检查器挂在上面的场景上跑，逐条断言。性能只给口径不给数字（见第四章）。做完能：任一注入场景失败后，输出「哪条不变量先破、现场是哪个字段、哪条日志、哪个崩溃点」。

## 四、不做什么 · 必要性 · 失效点

### 4.1 判据（B 线的验收，写死）

**一句话判据：注入分区/崩溃后不变量仍成立。**

| # | 不变量（可断言） | 注入什么时它最可能破 | 破了说明什么 |
|---|---|---|---|
| 1 | 任期单调不回退 | 崩溃后重启、旧配置残留文件 | 状态文件没原子替换或没落盘 |
| 2 | 同一任期至多一个主 | 分区 + 变更途中 | 投票未持久化，或成员集合不一致 |
| 3 | 同一位置不会出现两个不同任期的条目 | 乱序 + 落后节点追赶 | 前缀匹配检查缺失或偏移算错 |
| 4 | 已提交条目在任何节点不会消失 | 崩溃 + 覆盖写 | 日志在提交前被截断，或提交点越权推进 |
| 5 | 各节点投递序列互为前缀，且不跳序 | 快照装填、并发投递 | 投递点越界或快照边界越过已应用点 |
| 6 | 快照边界不越过已应用点 | 快照传输中断、并发触发 | 触发与编码不在同一临界区 |

**验收形态**：每个注入场景 × 每条不变量，都要有「未破」的结论；且**契约型积木必须做反向验证**——故意改坏一步顺序（例如去掉目录 fsync、把回复提到落盘之前），症状必须与预期一致（该丢投票记录的丢、该双投票的双）。症状对不上，说明这块只是跑通了，没被理解。

**不构成证据的东西**：一次场景通过、demo 线的测试全绿、没有崩溃日志、性能变好。**「没报错」不是正确性证据，是正确的缺席。**

### 4.2 必要性：删掉会怎样

必要性的**定义与后果只在总纲 §4.2 写一次**（含「cpp 专有」两行），本版不复述。

本版只补**判据强度**：同样一条「回复之前落盘」，在 go-lab 里验到「假磁盘可重放」，在这里必须验到「崩溃点注入后仍成立」——在每个写字节位置终止进程，重启只允许出现两种结果（没有投票记录可再投 / 有记录且不投第二票），绝不出现同任期两票。
| 段文件轮转 | 单文件无限增长，崩溃恢复要扫描全量日志，截断无法局部进行 | 选择（工程强建议） |
| 批量 fsync（group commit） | 不影响正确性，只在吞吐上有代价 | 选择（性能） |
| 成员变更的单步/联合 | 一次性全量切换会制造互不相交的多数派 | 必需（一旦做变更） |
| 注入器对「方法 + 目标 + 时长」的精确控制 | 故障场景无法回放，失败不可复现 | 必需（验证层） |

### 4.3 失效点：哪条前提一破，结论就变

- **传输语义是「可能丢、可能重、可能超时、对端可能死」** → 若假设 TCP 可靠就等于「不会重复执行」，去重层会被绕过，业务双写；若假设「超时等于没执行」，会把可能已提交的命令再提交一次。
- **`fsync` 真的到达稳定介质，且目录项也被同步** → 若介质带写回缓存、容器卷不是真持久、或 `fsync` 的错误被忽略，整套持久化验收失效；**症状是「偶发的、只在真断电时才出现」的数据丢失**。
- **协议状态由单线程串行处理** → 一旦有人为了性能把某段逻辑挪到工作线程，就重新引入数据竞争，而竞态检测不一定抓得到（跨线程、低频）。
- **事件循环上的时间预算** → 若某次循环做了慢操作（落盘、压缩、大对象拷贝），定时器精度与心跳周期同时失效，旧主会自我退位，表现为「莫名其妙频繁换主」。
- **成员集合在任意时刻两两相交** → 若变更实现成一次性切换或阈值算错，分区两侧都能凑出多数派。
- **注入场景可回放** → 若场景依赖机器速度、依赖随机时序而无种子记录，失败不可复现，验证层退化成「跑一跑」。

### 4.4 不做什么（范围，写死）

**不做跨数据中心/多组分片**：那属于「屋顶」，与共识层的判据无关；一旦做进来，本线的时间预算会被吞掉。

**不做安全与多租户**：不做鉴权、不做 TLS 之外的加密、不做配额与限流。**但要明确承认这是缺口**：生产系统必需，只是不在这条线的承诺里。

**不做运维面**：不做在线配置、不做热升级、不做备份恢复流程、不做告警。指标只做到「能支撑不变量检查与性能口径」为止，不做可视化。

**不做与大规模存储引擎的集成**：状态机保持极小（键值 + 去重表）。**也不做「接入 RocksDB 之类」当卖点**——那会把「状态机是什么」这个问题变成「库怎么用」。

**不做没有口径的性能工作**：优化必须有口径四要素（测什么、怎么造负载、看哪个分位、基线是哪一版），否则不做。

**明确留给上层**：业务语义、会话与去重表形态、读路径策略（走日志 / 读索引 / 租约）、批处理与流水线。

**实现自由度（怎么做都行，只要不变量成立）**：RPC 帧格式与序列化编码；锁的粒度；定时器实现；日志压缩与段大小；投递队列的形态（单消费者队列 / 环形缓冲 / 条件变量）；指标输出格式。

### 4.5 性能：只给口径，不给数字

本线**不报任何吞吐/延迟数值**。可接受的表述只有「用什么口径测」：

| 口径要素 | 必须写清 |
|---|---|
| 测什么 | 提交通道的吞吐（条/秒）；从提交到投递的延迟分布；故障后恢复时间（换主耗时、落后节点追赶耗时） |
| 怎么造负载 | 客户端并发数、命令大小分布、是否批量/流水线、读请求占比 |
| 看哪个分位 | p50 与 p99（乃至最大值），**不用均值**——延迟分布是长尾，均值没有意义 |
| 基线是哪一版 | 同一提交、同一机器、同一文件系统、同一注入配置；跨机器或跨文件系统的对比视为无效 |

**必须主动指出的两个陷阱**：①`fsync` 是这类系统的主要成本，任何不区分「每条同步」与「批量同步」的对比都是无效对比；②注入开启（丢包/延迟）时的吞吐与关闭时不可直接比较，必须分别标注条件。**任何未注明这四要素的数字，在面试里说出来就是负分。**

### 4.6 常见跑偏

- 把「跑通三节点 demo」当成「实现了共识」——共识要单独论证，demo 只证明管道通了。
- 用 TCP 的存在来回避去重与幂等。
- 覆盖写状态文件、或漏掉目录 fsync——这两种错只在真崩溃时暴露，开发期几乎踩不到。
- 在事件循环上做落盘或大拷贝，然后抱怨「换主太频繁」。
- 注入器只做「随机丢包」，不做「对某条 RPC、某对节点、某段时间」的精确控制，于是失败不可复现。
- 优化跑在注入关闭、负载单一、机器空闲的条件下，然后把结论当成普遍结论。
- 把选点讲成原理：「Raft 就是单线程」「Raft 就是一把大锁」。
- 成员变更做成一次性全量切换，靠「测试里没撞上」蒙过去。

## 五、面试怎么讲

### 30 秒版本

> 「这是一条正经的 C++ 工程线，不是在进程里模拟一个集群。运行时是事件循环负责收发和定时器、协议状态单线程串行、fsync 和大快照这类慢操作交给工作线程；通信是自己写的 RPC，超时和重试的语义写死在文档里——TCP 只保证字节有序，不保证不重复执行；持久化是日志段文件加原子替换的状态文件，回复之前必须落盘，目录也要 fsync。验收不是『跑通了』，而是把六条安全不变量写成断言，挂在故障注入场景上跑：注入分区、注入崩溃点，看哪条先破。破了要能给出是哪条不变量、哪个字段、哪条日志。性能我只谈口径——测什么、怎么造负载、看 p99、基线是哪一版，不给数字。」

### 可能被追问的 8 个点

**1. 「线程模型选了什么点？为什么不是每个连接一个线程？」**
→ 考点：是否标了「选点」而不是把选点当原理（架构档判据 4）。
→ 答法：选点是「事件循环负责 IO、协议单线程串行、慢操作异步化」。不是因为它更快，而是因为协议状态字段耦合极深（一次操作常同时碰任期、角色、日志、位置四组字段），串行处理把锁从「必须正确」降级成「几乎不需要」。代价明确：任何落在循环上的慢操作都会同时破坏定时器精度与心跳，表现为误退位与频繁换主。每连接一线程的问题是 N 个并发线程都要抢同一份协议状态，锁序设计成本远超收益。

**2. 「为什么自己做 RPC？用现成框架不更快么？」**
→ 答法：不是为造轮子，是为**可控的失败注入点**。丢包、延迟、分区、目标方法过滤必须能精确作用在某条 RPC 上并且可回放，否则「不变量在某场景下成立」无法被验证。代价是必须自己处理帧、超时、重试语义、连接生命周期。这个取舍是用「自己维护传输层」换「可观测性」，而不是「自己写的更好」。

**3. 「TCP 可靠，所以你为什么还要去重？」**
→ 考点：本线头号失效点。
→ 答法：TCP 保证的是**字节流的顺序与不丢**，它不保证「请求不被处理两次」。超时重发、连接断开重连、上层重试都会让同一条请求在对端被处理两次；反过来，超时也不等于「没执行」，可能已经执行但回执丢了。所以必须有请求号 + 业务侧幂等去重，把「可能执行一次或多次」压成「确定只执行一次」。**把 TCP 的可靠当成应用层语义，是这类系统最常见的错误。**

**4. 「持久化你怎么保证崩在写中途不坏？」**
→ 答法：三件事。①状态文件不覆盖写，而是写临时文件 → fsync → rename → **fsync 目录**；rename 在同一文件系统内原子，目录 fsync 才能保证改名本身落地，这一步最容易漏。②日志是段文件追加写，崩在段尾最多留下不完整的尾部记录，恢复时靠校验截掉。③顺序上先落新快照再删旧日志，反了就会在中间崩溃时丢掉两边。验法是崩溃点注入：在写第 N 个字节处终止，重启后必须得到「要么旧状态、要么新状态」，不允许「半个状态」。

**5. 「你怎么导致/证明崩溃？」**
→ 答法：不靠「关掉进程试试」。是在写入路径上预留可控的终止点（写到第 N 字节后自杀），配合场景文件固定；每个崩溃点对应一条断言：重启后任期不回退、投票记录不出现同任期两票、日志尾部可被校验截断。**判据是「崩溃后仍能安全推回」，不是「崩溃后还能启动」。**

**6. 「成员变更为什么要单步？」**
→ 答法：因为正确性依赖「任意两个多数派有交集」。一次性从旧成员集切到新成员集，中间可能出现两个互不相交的多数派各自声称有资格；单步变更每次只动一个成员，让任意时刻的集合都两两相交。可选的更强形式是联合配置——中间态要求两套成员各取多数派。这一条要能被追问到底：中间态上一票怎么算、离开的成员还算不算、配置本身走不走日志。

**7. 「性能你怎么谈？」**
→ 答法：只谈口径。测什么（提交吞吐、提交到投递延迟、故障恢复时间）、怎么造负载（并发数、命令大小分布、批量与流水线开关、读占比）、看哪个分位（p50/p99/最大，不用均值）、基线是哪一版（同提交、同机器、同文件系统）。另外主动说两条陷阱：fsync 是主要成本，不比批量策略的对比无效；注入开启与关闭的吞吐不可直接比较。**任何没有这四要素的数字都不说。**

**8. 「注入一个错，你怎么知道症状对得上？」**
→ 考点：契约型积木的验法，也是最难的一问。
→ 答法：给不能独立验证的积木（字节流语义、就绪通知语义）设计反向验证——去掉目录 fsync，症状必须是「崩溃点之后投票记录丢失、同任期出现两票」；把回复提到落盘之前，症状必须是「重启后出现双主」；把一条慢操作塞回事件循环，症状必须是「心跳周期性缺口、任职时间分布出现异常短尾」。**症状与预期一致，才算理解了这块；对不上说明只是跑通了。**

### 别说什么

- **别说「我这个能上生产」。** 它不做安全、不做多租户、不做运维、不做多组扩展；主动交代缺口，比被追问后改口强。
- **别报任何没有口径的性能数字。** 「快了几倍」「延迟只有几毫秒」这类话在这条线上是自毁：一句「你 fsync 策略是什么、p99 多少、基线哪版」就足以拆掉。
- **别把选点讲成原理。**「Raft 就该单线程」「Raft 就该一把大锁」都是反例——那是某些实现选的点，原理层只能说必须/可以/不做。
- **别用 TCP / 现成框架当可靠性论证。** 传输层不提供应用语义。
- **别说「测试全绿所以对」。** 这条线的判据是不变量在注入下成立；说不清注入什么、哪条可能先破，等于没有验收。
- **别把「跑通了」当共识实现完成。** 管道通了和协议对了是两件事，中间隔着整套持久化与验证。
- **别说「已经做过/已经跑过」。** 本文件是路线与判据，不含任何实测结果；凡引用历史材料，必须标注「历史记录，待复核」。
