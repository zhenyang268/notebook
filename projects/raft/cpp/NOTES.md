## 第 1 章 · 承诺与不变量（契约层）

**要解决的问题**：工程线最容易烂尾的地方不是写不出代码，而是**没有人知道自己在承诺什么**。先把承诺与不承诺写成两列，再把承诺翻译成可断言的检查，后面所有块才有靶子。

**机制**：

- **承诺列（可观察行为，每条必须能配反例）**：「写成功的，重启后还在」「分区期间少数派不服务客户端」「任一任期至多一个主」「节点 apply 出的序列互为前缀」。
- **不承诺列**：「不承诺吞吐」「不承诺可用性（少数派就是不可用）」「不承诺线性一致读，除非显式实现读路径」「不承诺跨机房延迟」。
- **六条安全不变量的断言化**：任期单调、单任期单主、同位置同任期唯一条目、已提交条目不消失、投递序列互为前缀且不跳序、快照边界不越过已应用点。每条配「注入什么错时它必须亮」：去掉目录 fsync → 第一条亮；回复提到落盘前 → 第二条亮；偏移算错 → 第三条与第六条亮。
- **选点记录表**：线程模型、事件循环、RPC 帧、序列化、fsync 策略、快照形态、变更形态——每项写「选的是哪个 / 为什么 / 代价是什么」。这张表是防「把选点讲成原理」的唯一手段。

**最小例子（可验证）**：拿一个假想实现，只问到「你的 fsync 策略是哪一种」，然后推导出它**不能**承诺什么。例如选「批量同步」就不能承诺「提交返回即持久」——除非语义改成「提交返回即已被多数派接受、但不保证持久」。可观察结果：能在一张纸上写出「承诺 ↔ 反例 ↔ 失效时哪条断言亮」的三列，且三列数量匹配。写不出反例的承诺就是口号，删掉。

**面试高频问法**：「你在承诺什么、不承诺什么？」——答法：先说承诺是**可观察行为**不是功能名；再说每条承诺的反例；最后主动说缺口（安全、多租户、运维、多组扩展都不做）。追问「那你怎么知道承诺成立」→ 指向第 7 章的不变量断言，不要在这一章就开始讲测试。

## 第 2 章 · 运行时：线程模型与事件循环

**要解决的问题**：协议逻辑再对，如果它被一个慢操作卡住，整套系统会以「频繁换主」「随机超时」的方式腐烂，而这些症状极难归因到「你把 fsync 放循环里了」。

**机制**：

- **三段职责切分**：①一个事件循环线程负责 accept、读就绪、写就绪、定时器到期；②协议状态只在同一线程内被修改（串行处理），因此几乎不需要锁；③慢操作（落盘、快照压缩、大对象编码）移交工作线程，结果以消息回投循环。
- **循环的三条硬约束**：非阻塞 IO；单次循环必须有耗时上界（超了就记一条「循环被打断」的指标）；定时器按最近截止时间排序，一次循环只处理到期的，不 sleep 到下一个。
- **字节流的两个常识**：就绪 ≠ 数据完整（半包要缓冲到凑满长度前缀）；一次读可能带出多条消息（粘包要循环解析）。
- **连接生命周期**：对端半关闭、写端阻塞、连接复用、请求号回落。**任何在循环里等待对端的行为都是禁止的**——包括带超时的同步等待。
- **跨线程交接的唯一形态**：工作线程不回写协议状态，只把「结果消息」塞进出口队列，由循环线程取用；这样「谁能改状态」永远只有一个答案。

**最小例子（可验证）**：两个客户端连同一个节点，其中一个请求触发一次慢操作（人为让工作线程 sleep 一个明显的时间）。步骤：①观察循环上另一条连接是否仍能正常往返；②观察心跳定时器是否仍然准时；③把慢操作**挪回循环内**，重复①与②，观察症状是否变成「另一条连接被饿死 + 心跳出现缺口」。可观察结果：两种写法的症状必须**明确不同**；如果看起来一样，说明实测手段不够灵敏（例如两条连接其实跑在不同循环上），需要先把观测点补上，而不是先改代码。

**面试高频问法**：「你的线程模型是什么？状态由谁改？」「为什么不能把 fsync 放循环里？」「就绪通知和数据到达有什么区别？」——第三问是分层筛子：答「就绪只是说可以尝试读，读到的可能是半个消息，也可能带出两条」才算过。**别答「我用了线程池」**——那不是线程模型，那是选点的一个部件。

## 第 3 章 · 自有 RPC 与序列化

**要解决的问题**：真实网络不提供应用语义。谁来保证「一条请求被处理一次且只一次」、「超时到底意味着什么」、「对端死了怎么知道」——这些必须显式写在协议里，而不能期待传输层。

**机制**：

- **帧格式**：长度前缀 + 消息类型 + 请求号 + 载荷。长度前缀必须先于载荷解析，且要设上限（否则一条恶意或错乱的长度会吃掉全部内存）。
- **请求号与回执匹配**：请求号只用于**匹配回执**，不用于「保证只执行一次」——后者属于业务层幂等。两者必须分清，混起来就会出现「重连后请求号复用、把旧回执当新回执」。
- **超时语义三态**：不是「成功/失败」，而是「确定没执行」「可能执行了」「确定执行了」。超时只落在中间态，上层必须用幂等把它压成确定行为。
- **重试策略**：最多重试一次瞬时错误（连接重置、超时）；参数错误、鉴权类、语义类错误不重试。**这一点与故障注入的语料设计直接相关**：语料里要显式包含「不重试」的错误类别。
- **序列化**：显式字段边界、显式版本号、未知字段处理规则（忽略还是拒绝必须写死）。可变长编码要让「在字段 i 之后截断」成为可构造的操作，这是故障注入的前提。
- **注入点设计**：出口处按「方法 + 目标 + 概率 + 延迟区间 + 持续时长」决定丢/延；并在接收侧支持「处理到一半就终止进程」以验证超时三态。

**最小例子（可验证）**：一次请求，在对端处理中途杀死对端进程。步骤：①客户端发出请求；②服务端读入并开始处理，在「已执行、未回执」的瞬间被强制终止；③客户端超时；④按重试策略重发到另一个节点；⑤检查业务状态里这条命令是否恰好一次。可观察结果：三态必须被区分开——客户端不能把「超时」直接当成「没执行」。如果业务出现两次执行且没有幂等保护，说明三态区分没做，而不是「网络抖动」。

**面试高频问法**：「超时等于失败吗？」「请求号能保证只执行一次吗？」「你的序列化怎么支持版本演进？」——第一问答「不等于，超时是中间态」；第二问答「不能，它只匹配回执，去重靠业务请求号 + 幂等」；第三问要给出「未知字段的明确规则」，不能答「应该没问题」。

## 第 4 章 · 持久化：状态文件、日志段与 fsync

**要解决的问题**：崩溃会发生在**任意一条指令边界**，包括写文件的第 N 个字节。持久化要解决两件事：落盘的最小集合是什么，以及写入的顺序怎样才能让任何崩溃点都留下「可解释的状态」。

**机制**：

- **状态文件（任期 + 投票对象）**：临时文件写全 → `fsync` 文件 → `rename` 覆盖 → **`fsync` 父目录**。四步缺一不可：不 fsync 文件则内容可能没落地；不 rename 则可能留下写了一半的原文件；不 fsync 目录则改名本身可能没落地。
- **日志段文件**：按段序号命名，段内追加写，每条带校验（长度 + 内容）。恢复时从头扫描，遇到第一条校验不过的记录就截断——**这要求日志是追加写、不可原地改**。
- **轮转与删除**：段达到阈值就换新段；被快照覆盖的段可以整体删除，而不是在文件中间打洞。
- **落盘时机**：当前任期变化、投票对象变化、日志追加、快照边界变化——四类事件之后、**回复对方之前**必须完成落盘。纯心跳不落盘（它不改状态）。
- **fsync 策略是唯一的性能/持久性交换点**：每条同步 / 批量同步（group commit）/ 上层驱动。选哪个必须写进第 1 章的选点表，因为它改变了能承诺什么。
- **不落盘的四个字段**：提交点、已应用点、同步位置、匹配位置。判据是「重启后能否凭剩余信息安全推回」——推得回来就不落盘；推不回来（例如投票对象）就必须落盘。
- **错误处理**：`fsync` 返回错误、`rename` 失败、磁盘满、只读挂载——都必须作为**不可继续**处理（拒绝写入、退位），而不是打条日志继续跑。忽略落盘错误等于放弃了全部持久化承诺。

**最小例子（可验证）**：崩溃点注入。步骤：①在状态文件写入路径上预留终止点，分别设在「写了部分字节」「写完未 fsync」「fsync 完未 rename」「rename 完未 fsync 目录」四处；②每处崩溃后重启；③检查读到的任期与投票对象。可观察结果：四个崩溃点都只能得到「旧状态」或「新状态」两种之一，**绝不允许第三种（半个文件、空文件、改名丢失）**。这一条是本线唯一的核心持久化判据，务必手工做一遍，别用「跑测试没挂」代替。

**面试高频问法**：「为什么不能直接覆盖写？」「为什么要 fsync 目录？」「批量 fsync 会影响正确性吗？」「哪些字段不必落盘？」——第三问要答清：不影响**安全**，但影响**能承诺什么**（提交返回即持久的语义会被削弱）；第四问答完要立刻给判据（能否安全推回），并把「提交点不落盘」的理由说透（可从日志 + 选举重建）。

## 第 5 章 · 快照与截断

**要解决的问题**：日志不能无限增长。快照把「状态本身」变成一等公民，同时把日志从「只增」改成「可丢头部」——从此所有位置运算都要区分逻辑位置、段内偏移、文件字节偏移三种东西。

**机制**：

- **边界元组的来源**：快照文件的边界必须包含「最后包含的位置 + 该位置的任期」，而任期只能**从被丢弃的最后一条日志里取**——快照数据本身通常不含任期。这一步是最容易漏、且漏了之后症状最奇怪的一处。
- **触发与编码的临界区**：判定「该不该做快照」与「编码状态」必须在同一个临界区内完成，否则快照的内容与它声称的位置会对不上（差一条）。差一条不会错乱，但会让「边界不越过已应用点」这条断言在小概率下亮。
- **落盘顺序**：先写新快照并 fsync → 再原子更新「当前快照标识」→ 最后才删除被覆盖的段文件。反了会在中间崩溃时出现「旧快照没了、新快照还没好」。
- **传输**：可选整块或分块。分块要带「快照标识 + 块偏移 + 总长 + 校验」，块偏移是**字节流偏移**，与日志位置无关；中断后重试必须能重传而不是留下半块。接收方要拒收：比本地旧、同位置但任期不同、不比当前提交点新。
- **装完后的对齐**：已应用点直接跳到边界（否则会把已压缩的条目再投一遍）；同步位置按边界元组回填；投递序列的前缀断言在这里最容易亮，因为它是唯一「跳变」的地方。
- **截断与段文件的关系**：截断不是「删日志前缀」，而是「删掉被完整覆盖的段 + 记录边界」。段粒度决定了截断的精度——**这是段大小选择的真实理由，不是「方便管理」**。

**最小例子（可验证）**：两节点、落后超过快照。步骤：①持续写入，触发一次快照并确认旧段被删；②让从节点完全断开，过程中再触发一次快照，使从节点需要的段已经不存在；③恢复从节点，确认主改发快照；④在传输到一半时人为中断，再重试；⑤装完后写入新命令，确认复制恢复且投递序列前缀断言仍成立。可观察结果：中断后重试能收敛，不出现半个快照；且装完后第一次追加不被拒（被拒通常说明偏移或边界任期算错）。

**面试高频问法**：「快照的任期从哪来？」「为什么先落快照再删日志？」「块偏移和日志位置是一回事吗？」「装完快照后已应用点怎么处理？」——第三问必须干脆答「不是」；第四问要说出「直接跳到边界」以及不跳的后果（重复投递）。**别用「压缩」两个字概括**——改了「可丢头部」才是原因。

## 第 6 章 · 成员变更

**要解决的问题**：成员集合会变。而「多数派」依赖集合本身，所以一旦两拨人对集合的认知不同，就可能出现两个互不相交的多数派各自声称有资格——这时不是「选不出主」，而是「选出两个主」。

**机制**：

- **配置本身是日志条目**：变更指令和普通命令走同一条日志、同一个顺序。这样所有节点对「哪个配置在哪个位置生效」有唯一答案。
- **单步变更**：每次只增加或减少一个成员。关键性质：任意时刻的旧集合与新集合的多数派必然相交（相差一个成员），因此不可能出现两个不相交的多数派。
- **阈值随配置生效点切换**：日志里某条配置被提交后，才按新集合算多数派；未提交前仍按旧集合。**这个切换点必须精确到「哪一条日志被提交」，不能按「已经收到配置」来切**。
- **离开的成员**：不再计票、不再接受它的投票被算入多数派；但它仍可能持有日志，不能在未经新多数派确认时把它的日志当权威。
- **可选的更强形式：联合配置**。中间态同时要求「旧集合多数派」与「新集合多数派」，正确性最强，代价是任意变更需要两轮多数派、且中间态必须能被重启恢复（要落盘）。
- **变更期间的隔离**：变更过程中若发生分区，正确行为是「凑不齐多数派就不服务」，而不是「按自己记得的集合凑」。**这一条是本章唯一必须被注入验证的点。**

**最小例子（可验证）**：三节点变四节点（只加一个成员）。步骤：①在主上提交「加入节点 4」的配置并让它生效；②在节点 4 拿到配置但还没追上日志时，切断节点 4 与主之间的通信；③检查主是否仍以新集合（4 节点，阈值 3）计算提交点，而不是以 3 节点（阈值 2）继续提交；④恢复后确认节点 4 追上并且计数正确。可观察结果：切换点前后阈值的使用**各有一次可观测证据**；若出现「按旧阈值提交」，说明阈值切换点算错了——这就是整章要防的那件事。

**面试高频问法**：「为什么不能一次性把成员全换掉？」「变更期间的一票怎么算？」「配置为什么要走日志？」「变更中途分区会怎样？」——第二问是深水区，要能说清「未提交前按旧集合、提交后按新集合」以及中间态重启后从哪里恢复（必须落盘）。答不上来就不要把成员变更写进简历。

## 第 7 章 · 验证：故障注入、不变量检查、性能口径

**要解决的问题**：这条线的判据是「注入后不变量仍成立」。这句话有两半：注入要精确可回放，不变量要可断言。缺一半，验证就退化成「跑一跑没崩」。

**机制**：

- **注入器四要素**：作用在**哪条 RPC**（方法名）、**哪对节点**（源与目的）、**哪种故障**（丢 / 延 / 重复 / 单向断 / 双向分区 / 目标进程终止）、**持续多久**（从哪个事件起、到哪个事件止）。缺任何一维，失败都不可复现。
- **崩溃注入点**：在写入路径的字节边界上留可控终止点；场景文件记下「在第几次写、第几个字节」。**这是唯一能验证持久化承诺的手段。**
- **不变量检查器**：把六条不变量写成独立断言，挂在每个场景结束时（以及关键事件点上）检查，输出「哪条先破 + 现场字段 + 相关日志位置 + 崩溃点」。**检查器本身要有反向验证**：故意注入一个已知错误，它必须亮出预期的那一条——否则检查器可能根本没生效。
- **语料与回放**：种子 + 场景文件 + 二进制版本三元组构成一条可回放记录；失败记录必须长期保留，任何一次回归都从语料里跑。**不重试掩盖失败**：偶发失败按「已知失败」处理，不按「抖一下」处理。
- **性能口径（只给口径）**：测什么（提交吞吐、提交到投递的延迟分布、换主耗时、落后节点追赶耗时）；怎么造负载（客户端并发、命令大小分布、批量与流水线开关、读占比）；看哪个分位（p50/p99/max，**不用均值**）；基线是哪一版（同提交、同机器、同文件系统、同注入配置）。必须标注「注入开/关」两种条件不可直接比较。
- **不报数字**：本文件不出现任何吞吐/延迟数值。要对比就现场测，并附上四要素。

**最小例子（可验证）**：最小闭环——三节点 + 一个注入场景（对一条特定 RPC 从某一节点出发 20% 丢包 + 一次强制终止）+ 六条断言。步骤：①在断言全部生效的前提下跑一遍，得到「六条均未破」；②**故意改坏一处顺序**（把回复提到落盘之前），确认「第二条（单任期单主）在指定崩溃点先亮」；③记录种子与场景文件，回放一遍确认症状可重现。可观察结果：②的症状必须与预测一致。**如果改坏了却什么都没亮，问题在检查器，不在实现。**

**面试高频问法**：「你怎么知道它是对的？」「你的注入能精确到什么粒度？」「偶发失败你怎么处理？」「性能你怎么谈？」——第一问的答法结构是：先说不变量是哪六条、再说它们挂在哪些场景上、再说反向验证（改坏一处症状要对上）、最后承认边界（没测到不等于没有）。**千万别答「跑了很多轮都没挂」**——那不是证据，是证据缺席。第三问要答「偶发失败按已知失败处理并留档」，不是「再跑一次看看」。
