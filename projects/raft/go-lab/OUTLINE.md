## 一、它在做什么

在普通进程里模拟一个 3 到 5 节点的集群，实现一个**只做共识、不做业务**的内核：上层调用 `Start(cmd)` 提交命令——自己是 leader 则拿到这条命令将来的 `(index, term)`，不是则拿到「我不是 leader」由上层去别处重试；内核通过一个 apply 通道，把「已被多数派确认、不会再被推翻」的命令按完全相同的顺序投给上层。上层自己执行（写 KV、算数、写文件都行），不需要知道任期、日志、投票这些内部结构。

**入口（本文的读法）**：在「多数派最终可达、任意少数节点可宕机/重启/网络分区」这个给定约束下，把 `Start(cmd)` 变成唯一的 `(index, term)`，再由 apply 通道按全序投递已提交命令。**一切实现选择都可以换**（编码格式、锁的粒度、回退策略、快照触发策略），**只要六条不变量还成立**。所以读任何一段代码，只需问一句：它在保哪条不变量？

**排除集合（换什么、不换什么）**：换掉的是「把不可靠通信变成可靠全序」的那层逻辑——自己写；不换的是两样给定的东西：一个可注入丢包/延迟/乱序/断网的 RPC 框架，和一个只能整块读写字节的假磁盘。**这两样给定，是本 demo 能做得短的根本原因**：真实工程里最贵的部分（真网络、真文件系统）被换成了可控替身，于是注意力可以全部放在协议上。

**积木（三件，都能独立验证）**：

1. **单字的原子读改写（CAS）**——保证 `votedFor` 这种单字段的「看-改-写」不可分割。它能独立验证一件事：同一个任期下是否可能有两个协程都成功写下自己的票。
2. **通道的同步交接**——保证投递方与业务方在「`lastApplied+1` 那条日志」上完成一次交接。它能独立验证：apply 通道是否跳序或重复。
3. **`fsync` 系统调用**——保证「状态字节在返回前到了稳定介质」。它能独立验证：持久化字段是否真的在**回复之前**写完。

三件都是语言/内核给的保证，不是结论。「加个锁保护」不是积木，那是结论。

**最小情形**：两节点、单协程、一次 `Start`。此时 `currentTerm`、`votedFor`、`commitIndex`、`log[index].term`、`nextIndex`/`matchIndex` 这组字段只在一条消息里移动；超时定时器、落盘顺序、多数派计数（两节点下多数派是 2）、快照边界全都不起作用。**先在这个下界上把「一条消息怎么改字段」讲清**，再往里加节点与故障——否则一开始就陷在并发里。

**生成（三类叠加，点名）**：

- **累加**：节点数 2 → 3 → 5，多数派阈值随之推进；客户端并发从 1 到 N；日志条数增长引出「无限增长怎么办」（快照）。
- **覆盖**：故障类型逐类覆盖——杀 leader、杀 follower、分区、断电重启、日志被压缩后的落后节点。每一类对应一组必须成立的检查。
- **最坏情形**：任意时刻都可能发生——消息任意迟到、任意重复、节点在任意指令边界崩溃、分区任意切分。**「最坏」不是平均，均值在这条线上没有意义。**

**两边是什么**：同一份共识状态的两种持有者与两种表示——内存里的字段（`currentTerm`/`votedFor`/`commitIndex`/日志数组）与假磁盘上的字节（状态记录 + 日志 + 快照）。协程持有内存那份并决定什么时候投递给业务，假磁盘持有落盘那份并决定重启后的初始值。**两边一致的那个瞬间，就是「回复之前落盘」这句话的全部内容。**

## 二、为什么要走这五步（功能设计与节奏）

**它替换掉的是什么**：现实里没人手写共识，用现成库几行就能起一个复制组。这里把库整层抽掉，只保留给定的两个替身（不可靠 RPC + 假磁盘），于是**剩下的就是你自己的逻辑**——这正是 demo 的价值：目标不是产出可上线组件，而是让每一行都能被追溯到某条不变量。

**为什么按这个顺序（五步的因果链）**：

1. **Leader Election 先行**，因为它是唯一一个「不需要日志内容也能验」的机制：杀掉 leader，集群必须在选举超时量级内自己选出新的。它同时把三个最容易出错的骨架装上：随机化超时、一任期一票、收到更高任期就退位。**先有主，才谈得上复制。**
2. **Log Replication 第二**，因为它引入「日志匹配」这条本 demo 最核心的检查：每条追加消息带上前一条的位置与任期，接收方对不上就拒绝。乱序与迟到在这里被变成「暂时不接受」，而不是「接受错的」。
3. **Persistence 第三**，不能更早也不能更晚。更早会被「什么样的日志才需要落盘」拖住；更晚会掩盖一个致命顺序问题：投票与追加的**回复必须在落盘之后**。这一条在断电场景下才暴露，而它一旦错，「同一任期投两次票」就成了可能。
4. **Snapshot 第四**，因为它改写前面三步的一个隐含假设：「日志从下标零开始、只增不减」。快照让日志可丢头部，于是所有下标运算都要加偏移——**这是后半程最大的错误来源**，也是唯一必须在前三步都稳定后才敢动的东西。
5. **KV 服务第五**，用来验证内核真的被隔离好了：业务层只能拿到「命令 + 提交位置」，不能反读内核日志。它同时把「恰好一次」这个业务语义补上——重试会重复提交，靠客户端请求号去重。

**为什么不做更简单的做法**：

- **不做单机**：单机不需要共识，问题消失。
- **不要求「主同步写全部副本」**：一台慢机器卡死全组，而且分不清「慢」与「死」，一引入超时就有脑裂，绕回任期与多数派。
- **不用固定超时**：多节点同时超时、选票分散，可能长期选不出主；随机区间是把撞车概率压到可接受的最低成本手段。
- **提交点不取「多数派的最大值」而取中位并检查任期**：更简单的写法会让「本任期之前、其实没被多数派确认」的条目被提交，随后被覆盖，已返回给客户端的命令消失。

**数据形态**：日志是追加写数组，每条带 `(term, command)`，下标隐式；快照是对日志前缀的压缩，压缩后日志不再从零开始，所有下标运算都要加偏移。凡是出现 index 的地方都要问一句「这是逻辑下标还是数组下标」。

**节奏纪律（比顺序更重要）**：每一步都必须有**一个可重复的判据**才允许进下一步；一次跑绿不算通过。判据写死在本文件第四章与 NOTES 各章的「最小例子（可验证）」里。

## 三、章节大纲（五步 + 两块底座）

> 顺序即节奏：前一块的判据拿到手再开下一块。每块末尾的「做完能……」就是该块的验收。

**0. 骨架：接口、并发与定时器**（前置依赖，不补则后面全部断路）
接口两条（提交、投递）与「上层不许反读内部状态」的边界；锁内复制参数 → 锁外发消息 → 回锁重验身份的三段式；定时器与唤醒的写法；为什么持锁发消息会拖住整个节点。做完能用两节点互相发消息、在注入丢包与延迟下仍收敛，且在竞态检测器下不报警——**这一块不算「做完选举」，它只是让后面五步不塌的地基**。

**1. Leader Election**
任期单调递增、一任期一票、候选人日志新旧比较、随机化选举超时、心跳即空追加、收到更高任期就退位。做完能验证：杀 leader 后在选举超时量级内重选；重复多轮不出现选不出；分区期间两侧不可能在同一任期同时获胜。

**2. Log Replication**
追加消息的完整参数、前缀匹配检查、`nextIndex` 回退（逐条退还是按任期跳跃）、用多数派推进提交点、当前任期限制、投递通道有序不重。做完能验证：并发写收敛到同一份日志；被隔离的旧 leader 攒下的未提交条目在恢复后被覆盖，且已提交的一条不丢。

**3. Persistence**
三字段落盘（当前任期、投票对象、日志）、**回复之前落盘**的顺序、重启后的重放。做完能验证：任意时刻断电重启后任期不回退、同一任期不投两票、已提交命令还在。

**4. Snapshot**
快照里存什么、边界元组（最后包含的下标与任期）的语义、逻辑与数组下标换算、何时触发快照传输、装完快照后同步位置怎么对齐。做完能验证：日志被压缩后，全新节点仍能追上并继续正常复制。

**5. KV 服务**
提交 + 投递的实际用法；客户端请求号去重表实现「恰好一次」；为什么读也要走日志（或等价机制）而不是直接读本地表；为什么上层不能反读内核日志做「快速读」。做完能验证：最小 KV 在分区与重启下 get/put 行为符合预期，且业务层没有引用内核内部结构。

**可选加练（不属主线，做了也不改判据）**：按日志条数以外的策略触发快照；把回退改为按任期跳跃并记录取舍；把投递通道换成条件变量并对比可读性。**任何加练都不许以「调大超时/加 sleep」收尾。**

## 四、不做什么 · 必要性 · 失效点

### 4.1 判据（A 线的验收，写死）

| 判据 | 形态 | 不通过的表现 |
|---|---|---|
| 测试通过 | 对应步骤的测试套件多轮全绿，含竞态检测 | 单轮通过、多轮偶发失败（典型：超时边界不稳） |
| 能复述为什么 | 任指一行关键逻辑，能说「删掉它会破哪条不变量」 | 只会说「论文这么写的」 |
| 可复现 | 固定随机种子，失败能回去重放 | 挂了无法重现，只能重跑碰运气 |
| 不许藏不确定性 | 没有为过测而加的 sleep 或超时放大 | 判据失效，视同未完成 |

**注意判据的边界**：这四条证明的是「在给定失败模型下行为符合预期」，**不证明生产可用**。任何把它当成工程证据的引用都是错的。

### 4.2 必要性：删掉会怎样

六条机制（前缀匹配、回复前落盘、提交点查任期、随机化超时、发消息前放锁、快照下标换算）的**定义与后果只在总纲 §4.2 写一次**，本版不复述。

本版只补一条**判据强度**：持久化跑在假磁盘上，所以「落盘」验到的是「写入记录能在重启后读到」，**不到真实介质**；真介质上的部分写、目录 fsync、原子替换不在本版判据内（属 cpp 侧）。
| KV 层去重表 | 重试导致同一条命令执行两次（计数器翻倍、追加重复） | 必需（KV 块） |

### 4.3 失效点：哪条前提一破，结论就变

- **节点数 3 或 5，阈值按 `floor(N/2)+1`** → 若成员数变了阈值没跟着变（例如误配成 1），分区两侧都能提交，两主并存。
- **消息允许丢/重/乱序，且每条追加带前缀匹配字段** → 若传输层被当成可靠有序（**不要因为「本地回环」「进程内调用」就默认它可靠**），接收方不再拒绝分叉日志，投递通道可能吐出不同前缀。
- **假磁盘整块写入在返回前生效** → 若介质带写回缓存、或写入失败被忽略，重启后投票对象可能丢失，同一任期双投票。
- **选举超时依赖本地单调时钟，且随机区间大于一次往返** → 若时钟跳变、核数争用或调度延迟使一次追加处理超过超时，主会自我退位、任期连续递增，客户端长时间拿不到主。
- **「本地回环很快所以不会超时」** → 本 demo 的注入器就是来打掉这个假设的；任何依赖「它应该很快」的写法，都是在把不确定性藏起来。

### 4.4 明确不覆盖（这是本线的边界，不是缺陷）

**生产级传输**：TLS、鉴权、限流、连接池、协议版本协商。给定 RPC 框架只负责「能注入故障地收发」，不负责这些。

**性能**：没有任何吞吐/延迟口径，也不追求。批量、流水线、零拷贝、提交路径的无锁化都不做。**唯一与性能相关的纪律是负面的**：不许用 sleep 或放大超时来让测试变稳——那是把不确定性藏起来，换个种子或多跑几轮就原形毕露。

**运维**：指标、日志分级、在线配置、热升级、备份恢复、灰度。一个 demo 不需要被运维。

**成员变更**：增删节点不做。它与「理解多数派」关系弱，却会显著拉长实现面；真正需要它时去 cpp 线。

**多组分片与迁移**：不做。分片是「屋顶」，与共识层的判据无关。

**明确留给上层**：业务语义、会话与去重表的具体形态、读优化路径、批处理策略。内核只保证「同样的命令以同样的顺序到达每个投递通道」。

### 4.5 常见跑偏

- 为了「跑通」而调大超时、加 sleep——把不确定性藏起来。
- 把一次通过当做完。默认状态就是不稳，必须重复跑、开竞态检测、固定种子。
- 持锁发消息。轻则卡顿，重则死锁，且表现为随机超时，最难排查。
- 先回复再落盘。多数场景能过，专测断电的那类会在最难受的地方挂掉。
- 提交点直接取多数派最大值而不检查任期。
- 上层图省事直接读内核日志拿结果，读到未提交数据，整个分层白设计。
- 只做完选举就以为懂了——那只是「能选主」，不是「能存数据」。
- 防御性分支忘了改返回值：追加处理函数里返回值初值可能是「成功」，任何提前返回的分支若忘记显式置为失败，主会收到假的成功回执，进而把未落盘的副本计入多数派。**每写一个 return 都问一遍：此刻回执的每个字段都对吗？**

## 五、面试怎么讲

### 30 秒版本

> 「这是按 lab 节奏走的 Raft 内核 demo，五步：选主、日志复制、持久化、快照、KV。对外只两个接口——`Start(cmd)` 提交并拿到 `(index, term)`，apply 通道按完全相同的顺序吐出已提交的命令。难点不在投票，在不可靠：消息会丢、会重、会乱序，节点还会断电。所以每个处理函数要幂等，追加消息靠『前一条的位置与任期』做匹配检查，当前任期与投票对象必须在回复之前落盘。验收是测试多轮全绿加竞态检测，加上我能逐条说清某个字段删了会破哪条不变量。它明确不做生产传输、性能和运维——那些是另一条线的事。」

说完这段应能自然接住「为什么」，而不是只重复结论。

### 可能被追问的 8 个点

**1. 「提交点为什么不能直接取多数派记录的最大值？」**
→ 考点：迟到的旧任期条目 + 当前任期限制在防什么。
→ 答法：新主上任时，多数派上记录的位置里可能包含**上一任期**遗留、其实没被多数派确认的条目。直接按最大或中位提交，就可能在它随后被真正的主覆盖之后，已经返回给客户端的命令凭空消失。规则是只有「当前任期」的条目能靠多数派计数直接提交；之前任期的条目只能通过「本任期某条被提交」被间接带过去——实践中新主上任先提交一条空操作就是这个用途。

**2. 「前缀匹配检查到底解决了什么？」**
→ 考点：日志匹配性质，以及它怎样把乱序变成安全行为。
→ 答法：接收方检查「前一条位置」上那条日志的任期是否等于消息带来的任期，不等就拒绝。它不是防重复，是防**接错位置**——迟到消息携带过期前缀信息，检查不过就丢弃，而不是把日志截断到错误位置。三个边界要说清：该位置落在快照范围内时不能直接判失败（应视为已匹配或转去装快照）；该位置超出本地日志末尾要拒绝；拒绝时应回一个可跳跃的提示（冲突任期 + 该任期首条位置），主才能跳过一整个任期而不是一条一条退。

**3. 「同步位置回退为什么可以一次跳一个任期？」**
→ 考点：这个优化依赖哪条不变式。
→ 答法：依赖「同一任期、同一位置上的条目一定相同」，这条由选举限制（候选人日志不能落后于投票者）保证。所以主收到冲突提示后可以跳到该任期最后一条之后，若自己没有这个任期则直接跳到它的首条位置。**如果实现允许同任期同位置出现不同条目，这个跳跃就是错的**——所以它不是纯优化，是拿一条安全性质换来的。

**4. 「持久化要存什么、什么时候存？」**
→ 考点：崩溃点的顺序，不是「存了就行」。
→ 答法：三个——当前任期、投票对象、日志（含快照边界与快照数据）。关键在**回复之前**落盘：投票回复、追加回复，都要先写盘再返回。反过来的写法能跑通绝大多数测试，但会在「投完票、还没写盘就断电」这个点上暴露同一任期投两票，可能选出两个主。实现上通常把几者在同一临界区编码成一整块交给存储，注意日志与快照的写必须一致，不能出现「快照更新了、日志还按老偏移算」的中间态。

**5. 「持锁发消息会怎样？」**
→ 考点：最容易定位不到的那类 bug。
→ 答法：一次远程调用可能是几百毫秒级的，持锁期间这个节点收不了心跳也回不了投票，别人在选主，你卡在锁里；更糟的是处理函数里再取同一把锁直接成环死锁。规矩固定三步：持锁复制出参数 → 放锁发消息 → 重新取锁。回来之后**必须重新校验身份**（我还是主吗？任期还是我刚发出去时那个吗？），否则这份回执属于一个已经过期的自己，拿去更新同步位置就是错的。这个「回来后重查身份」是最容易漏的一步。

**6. 「投递通道怎么保证有序、不重、不阻塞内核？」**
→ 考点：提交路径与投递路径的耦合。
→ 答法：维护一个「已投递点」，只投它的下一条，投完才加一——天然去重、天然有序（重投同一条会被跳过）。不能持锁往通道里发：上层可能在处理里回调内核，一持锁就死锁；常见做法是单独一个协程配合条件变量等「提交点 > 已投递点」。还有一个交互点：装完快照后已投递点要直接跳到快照边界，否则会把已经被压缩掉的条目再投一遍。

**7. 「快照之后下标怎么算？」**
→ 考点：逻辑下标与数组下标，后半程最大的错误来源。
→ 答法：压缩后日志不再从零开始，数组下标与逻辑下标差一个偏移（具体差 1 还是差边界值，取决于数组第 0 位是不是哨兵）。凡是出现 index 的地方都要问一句「这是逻辑的还是数组的」，尤其是提交点、同步位置、前缀位置、已投递点四者混算的地方。还有一个常见混淆：快照传输的分块偏移是**字节流偏移**，跟日志下标完全无关，混了就会在大快照上挂。

**8. 「你怎么知道它是对的？」**
→ 考点：测试方法论，最容易露怯的一题。
→ 答法：先说「一次通过不算通过」。做法是给定故障注入（丢包率、延迟分布、分区、随机重启）跑随机化场景，重复很多轮且带竞态检测，种子固定可复现，挂了能回去重放。判据不是「没报错」，而是几条可检查的不变量：各节点投递出的命令序列互为前缀；已提交条目在任何节点任何时刻都不消失；任期单调不回退；同一任期不出现两个主。如果做到这一步，可以这样答：「我没法说它一定对，我能说的是这几条不变量在多轮随机故障下没被打破，且每个挂过的种子都留着。」

### 别说什么

- **别说「我全部实现了、测试全绿」。** 一句「最难的那个 bug 你怎么定位的」就能验真假；答不出具体现场（哪个种子、哪条不变量先破、日志长什么样），前面全白说。
- **别把库当原理讲。**「用了现成 Raft 库所以……」在这里是反向信号——这个 demo 考的正是库被抽掉之后你还剩什么；讲前缀匹配、讲落盘顺序比讲 API 有用。
- **别报没测过的数字。** 「一秒内一定选出主」「性能提升几倍」都是坑。要谈效果就谈口径：「选举超时设在毫秒级区间、心跳远小于它，在这个前提下杀主后重选应在选举超时量级内完成」——说条件，不说结论。
- **别说「加个 sleep / 调大超时就好了」。** 等于承认把不确定性藏起来了；同理「跑了一遍没报错」不是正确性证据，是正确的缺席。
- **别把 demo 讲成生产系统。** 主动交代不覆盖传输、性能、运维、成员变更，比被追问时才发现好得多。
