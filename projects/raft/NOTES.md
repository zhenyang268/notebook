# Raft 分组总纲 · NOTES（路由用，不含正文）

> 本文件是 `projects/raft/OUTLINE.md` 的配套笔记，职责只有一条：**让下一个读的人在两分钟内决定该读 go-lab 还是 cpp**，并知道哪些结论不能跨版搬运。
>
> 纪律：本文只写「分几组、为什么这么分、边界在哪、哪些待核」，**不复制任何子项目的机制正文**。机制正文在 `go-lab/NOTES.md` 与 `cpp/NOTES.md` 里，协议定义在 `projects/6824/OUTLINE.md` 里。
>
> 全部内容为**路线与判据**（模板口吻），不代表任何实现已完成、不代表任何测试跑过、不含任何实测性能数字。

## 一、分组总纲：要解决的问题

**问题**：同一个 Raft，被要求承担两种完全不同的任务——「让我快速理解它」和「让我在真约束下证明它」。压在一份文档里时，两种任务互相破坏：讲协议时讲者被迫提前解释线程与文件，讲工程时读者被迫回头找协议定义。结果是一份又长又两边都不达标的文档。

**机制（分组方案）**：三份文件、两条线、一个路由器。

```
projects/raft/
├── OUTLINE.md      ← 路由层：清单 + 判据差异 + 路由表（无正文）
├── NOTES.md        ← 本文件：分组理由 + 边界 + 待核清单
├── go-lab/         ← 线 A：课堂工程 demo（机制档偏多，按 lab 节奏）
└── cpp/            ← 线 B：正经 C++ 工程实践（架构档，按块划）
```

分层判据来自 `LEARNING.md` §7.1：两档的**单元**不同（一个机制 vs 一块），**最小情形**不同（一次 `Start` vs 一次 fd 写 + fsync + kill），**验收**不同（失败模型下不出错 vs 接口能预测 + 判据可观测）。档不同就不能同章。

**最小例子（可验证）**：给任意一个具体问题，按路由表判组，两分钟内判对，且判据可复核——

1. 「删掉 `votedFor` 的落盘会怎样」→ 属协议层，去 `projects/6824/OUTLINE.md`；若追问「在真文件系统上怎么观测到这个丢失」→ 属 cpp 线。
2. 「我该不该给 C++ 版加成员变更」→ 属 cpp 线的范围问题，答案在 `cpp/OUTLINE.md` 的「不做什么」。
3. 「lab 的五个步骤顺序能不能换」→ 属 go-lab 线，答案在 `go-lab/OUTLINE.md`。
4. 若某问题在两张表里都能找到答案，说明总纲划块失败，应记入本文「待核」。

**面试高频问法**：「你这份文档的组织方式解决了什么问题？」——答法见下章末的三句话，不要复述子项目内容。

## 二、为什么这么分：四条理由与代价

**要解决的问题**：让「理解」与「工程」两种目标各自有诚实的验收，而不是在一个折中的文档里都不达标。

**机制（四条理由）**：

1. **判据强度不同。** A 线的验收是「测试通过 + 能复述为什么」，B 线的验收是「注入故障后不变量仍成立」。判据不能混用，所以文档不能混写。
2. **失败模型的来源不同。** A 线的丢包、延迟、分区、重启由 lab 框架给定，磁盘是内存模拟的；B 线的失败模型是自选范围（socket 超时、真 fsync、kill -9、容器卷），自选就意味着**必须先写清范围**。范围声明在 B 线，A 线不需要。
3. **实现面的量级不同。** A 线实现面能压到六个名词之内（选举、复制、落盘、快照、投递、去重表）；B 线光是运行时就有线程模型、事件循环、RPC、序列化、文件格式、fsync 策略、注入器、指标——**必须按块归并**，否则就是名词堆叠。
4. **面试话术不同。** A 线要能讲清设计动机；B 线要能被追问到「你的前提破了会怎样」。两者的 30 秒版本不能是同一段话。

**代价（必须承认的三条）**：

- **重复风险**：协议语义在两版都会被提到。压制手段是「只允许引用、不允许复述」，owner 固定在 `projects/6824/OUTLINE.md`。这条纪律靠人守，不会被工具强制。
- **迁移风险**：读者容易把 A 线的结论直接搬去 B 线（最典型：「我们落盘了」→ 直接跳过原子替换与目录 fsync）。缓解手段是总纲 §4.3 里点名的头号失效点。
- **维护成本**：两条线各自演进，改一处需要人工确认另一处影响。这是刻意不做自动同步的结果——自动同步会诱导抄两遍。
- **收敛风险**：B 线的范围可以无限扩张（成员变更做完想做多组分片，再做跨机房）。必须靠 OUTLINE 里的「够」写死边界，否则它会吞掉 A 线的时间预算。

**最小例子（可验证）**：取一个机制——「快照之后的逻辑下标与物理下标」——分别在两版里找它的写法：A 线只要求「能说清为什么下标运算要加偏移，并能指出哪四个量混算」；B 线要求「截断发生时正在进行的传输与读取会看到什么、怎么保证不越过已应用点」。**同一个机制，两种验收深度**，这组对比本身就是分组是否成功的检验。

**面试高频问法**：「两版都讲的话，你不怕讲两遍吗？」——答法：怕，所以 owner 唯一；判断标准是「同一个机制是否在两个块里各被完整讲过一次」，是则合并。

## 三、共享机制清单：作为合同，不是正文

**要解决的问题**：保证两条线覆盖的是**同一个** Raft，而不是各自发明一套，同时不产生两份正文。

**机制**：清单只写「条目 + 覆盖到哪」，具体内容下沉。

| 条目 | A 线覆盖 | B 线覆盖 | owner |
|---|---|---|---|
| 选举与任期 | 机制级：随机超时、一任期一票、日志新旧比较 | 机制级 + 事件循环定时器 + 单任期单 leader 的不变量 | 协议定义归 6824，运行时归 cpp |
| 日志复制与提交点 | 机制级：前缀匹配、回退、多数派推进、当前任期限制 | 机制级 + 回退策略选点记录 + 冲突检测不变量 | 同上 |
| 持久化 | 机制级：三字段、回复前落盘、重启重放 | 机制级 + 段文件格式 + fsync 时机 + 原子替换 + 崩溃点注入 | 同上 |
| 快照 | 机制级：触发、边界、下标偏移、追赶路径 | 机制级 + 分块与校验 + 截断生命周期 | 同上 |
| 成员变更 | **不覆盖** | 单步变更 + 联合配置 + 中间态票数归属 | cpp |
| 线性一致读（可选） | 走日志读（KV 层承担恰好一次） | 三条读路径的代价与正确性条件 | cpp 内部 |
| 故障注入与不变量 | 课程测试 + 竞态检测 + 固定种子 | 自有注入器 + 不变量列表 + 可重放语料 | cpp |
| 性能口径 | 不测（但禁止用 sleep/调大超时掩盖） | 必须给口径，禁止裸数字 | cpp |

**最小例子（可验证）**：拿这一张表去核对两份子 OUTLINE——表里每个非「不覆盖」条目，在两份子 OUTLINE 的章节大纲里都应能找到**恰好一处**主场（其余处只能是引用）。找不到 = 覆盖缺口；出现两处以上详细讲 = 违反单 owner。

**纪律**：这张表只允许出现条目名与覆盖深度，**不允许出现任何机制细节**（出现即下沉失败）。

**面试高频问法**：「你这两版的 Raft 是同一个协议吗？」——答法：协议是同一个，六条不变量完全一致；不同的是承诺边界与验证手段。接着主动指出跨版的失效点（真 fsync、原子替换、TCP 不等于不重复），这是加分点。

## 四、边界、失效点与迁移规则

**要解决的问题**：防止两版互相渗漏——A 线被要求承担工程承诺，B 线被要求承担教学任务。

**机制（边界三条）**：

1. **A 线的上限写死在「不覆盖」里**：生产级传输（TLS/鉴权/流量控制）、性能、运维（指标/在线配置/升级）、成员变更，四条都明确不做。任何一条被要求补上，都应回答「这属于 B 线」。
2. **B 线的下限写死在「够」里**：六条不变量全绿 + 成员变更可解释 + 性能口径写清，达到即停。不追求分片、多组、跨机房，除非另行立项。
3. **跨版搬运需要三重确认**：① 机制在目标版的失败模型下是否仍成立；② 目标版的最小情形能否覆盖它；③ 目标版是否有对应的观测点。任一为否，就当**新内容**处理，不能搬运。

**最小例子（可验证）**：「回复前落盘」这条——从 A 搬到 B 时三重确认全部失败：A 的假磁盘隐去了部分写与目录元数据；A 的最小情形没有崩溃点；A 没有「崩在写中途」的观测点。所以它在 B 线必须重写，并且要多出「原子替换 + 目录 fsync」两件事。这个例子应能独立复述。

**失效点（哪条前提一破，整个分组就失去意义）**：

- **两版共享的协议定义发生漂移**（各自的 NOTES 把同一个机制讲成了两种语义）→ 分组从「两种验收」退化成「两套系统」，读者无法判断哪个是 Raft。判据：任取一条不变量，两版描述必须等价。
- **A 线被当成了 B 线的验收证据**（「demo 跑绿了所以工程版没问题」）→ 判据分层失效。
- **B 线的范围无限扩张**（成员变更 → 多组 → 分片 → 跨机房）→ 吞掉 A 线的时间预算，两条线都不收敛。
- **总纲重新长出正文**（有人为了方便在总纲里补细节）→ 违反单 owner，后续两份 NOTES 开始与总纲打架。

**面试高频问法**：「如果只让你保留一条线，你留哪条？」——答法：取决于要回答的问题，不取决于哪条更强。「证明我理解协议」留 A，「证明我能被故障挑战」留 B。若必须二选一，先说清自己在哪种场合被问——这个回答本身比选择更重要。

## 五、待核与未验证清单（引用前必须复核）

以下是**本线明确标注为未验证/待核**的内容。它们不是结论，是待办核查项：

1. **上游材料里的实现状态（历史记录，非本线现状）**：`projects/6824/NOTES.md` 记录了 Go 侧与 C++ 侧在某个时间点的实现与测试状况（含分支、行数、缺陷编号）。这些记录**只作历史材料**，引用前必须重新确认仓库、分支与提交；本线不把它们当作任何一版的当前事实。
2. **两版的章节归属**：共享机制清单里每条应该落在子项目的哪一章，目前只写了覆盖深度，没写章节号——需在两份子 OUTLINE 定稿后回填核对，避免「两处主场」。
3. **B 线线程模型的选点**：事件循环 + 工作线程只是候选之一，是否采用需在实现前用「慢操作不阻塞循环」这一条判据再确认一次。**未验证**。
4. **B 线成员变更的中间态票数归属**：单步变更与联合配置两种形态都能成立，选哪个取决于是否接受「一次性切换」的风险。**待核**：需写清中间态的一票怎么算，否则这条内容不许作为面试话术使用。
5. **性能口径的具体指标**：本文只给了口径四要素（测什么、怎么造负载、看哪个分位、基线是哪版），**没有任何实测数字**。任何具体数值都必须现场测，禁止沿用记忆或他处数据。
6. **跨版失效点的完整性**：「真 fsync / 原子替换 / TCP 不等于不重复」这三条是目前能点名的头号失效点，但不构成清单完整性的证明——**未验证是否有遗漏**。
7. **A 线与课程范围的对应关系**：五步顺序与课程节奏的对应，本线按常见节奏写为路线，**未逐项核对**具体 lab 的验收脚本与当前版本是否仍有差异。引用前需确认版本。

**纪律**：这七条在任何向下游文档搬运时都必须保留「未验证/待核」的标记，不得改写成陈述句。

**面试高频问法**：「你怎么知道这份组织方式是对的？」——答法：不能说它对，只能说它可被检验：任取一个机制，两版应有不同的验收深度且只有一处主场；任取一个具体问题，两分钟内应能判组；任取一个跨版结论，三重确认应能指出它不成立。这三条之后，剩下的都是上面那七条待核。
