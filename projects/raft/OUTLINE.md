# Raft 分两版 · 分组总纲（OUTLINE）

> 定位：这是**路由文件**，不是正文。它只回答三件事：为什么要把 Raft 拆成两版、两版共享哪些机制、同一套机制在两版各自的判据差在哪。任何一处机制细节都写在子项目的 OUTLINE/NOTES 里，本文只列名字与判据，**不复述子项目正文**。
>
> 写入姿态：全部内容都是**路线与判据**（模板口吻）。本文不声称任何实现已完成、不声称任何测试已跑过、不报任何吞吐/延迟数字。
>
> 上游：本文 §三（共享机制与必要性论证，本线唯一 owner）、`../.gen/archive/6824-2026-11-17/`（旧课lab 材料，属历史材料，**不作为事实依据**）、`notebook/LEARNING.md` §3.1 七步、§2.4 五条判据、§7.1 两档。

## 一、它在做什么

把同一套 Raft 机制拆成两条**互不替代**的工程路线，并用一份总纲决定「什么情况下读哪一版」：

- **(A) `go-lab/` —— 课堂工程 demo。** 按 6.824 lab 的节奏分五步走：Leader Election → Log Replication → Persistence → Snapshot → KV 服务。目标是**用最短路径把共识的骨架跑通并讲清**，判据是「给定测试通过 + 能复述为什么这一行不能删」。
- **(B) `cpp/` —— 正经 C++ 工程实践。** 不以「跑通」为止，而是以「能被故障打、能被不变量卡住、能解释性能口径」为止。主线是线程模型与事件循环、自有 RPC 与序列化、日志段文件与 fsync、快照与截断、成员变更、故障注入与不变量检查、性能基线口径。判据是「注入分区/崩溃后不变量仍成立」。

**入口（本文的读法）**：两版解决的是**同一个**复制状态机问题（把 `Start(cmd)` 变成唯一 `(index, term)`，再由 apply 通道按全序投递已提交命令），分歧点不在协议，而在**承诺的边界**：go-lab 承诺「在课程给定的假网络与假磁盘下行为符合预期」，cpp 承诺「在真网络、真文件系统、真崩溃下不变量不被打破」。因此两版共享协议层，分叉在校验层与运行时层。

**不换的是什么**：两版都不许动的是那六条安全不变量——`currentTerm` 不回退、`votedFor` 每任期最多一次、`commitIndex` 只由多数派 match 推进且不回退、已多数派落盘的 `log[index].term` 不可被覆盖、applied 前缀只按 `lastApplied+1` 单调推进且不跳序、快照边界只能截断 `lastApplied` 之前的已应用前缀。**看差异先查这六条**，而不是先看「用了什么库、几根线程」。

**积木（两版共用，只借不造）**：①CPU 的 compare-and-swap 保证单字读改写原子——它让「同一任期只投一票」「谁先到多数派谁赢」成为可独立验证的一件事；②操作系统 `fsync` 保证写入在返回前到稳定介质——它让「回复之前落盘」这条顺序约束可被观测；③内核的 socket 收发与 epoll 就绪通知（cpp 版）/ 进程内 RPC 框架的收发（go-lab 版）——它让「消息可能丢、可能重、可能乱序」成为可注入的事实而不是假设。三件都是「硬件/内核给的保证」，不是结论。

**最小情形（两版各自的下界，不是同一个）**：go-lab 的最小情形是**两节点、单 goroutine、一次 `Start`**——协议字段在一条消息里移动，其余机制不起作用；cpp 的最小情形是**两个进程、一次 fd 写 + 一次 fsync + 一次 kill -9**——只剩下「字节出去」与「字节落地」两件事，用来验证落盘顺序这一条契约。**两者不能互相替代**：前者验协议，后者验持久化承诺。

**两边是什么**：这是同一份共识状态的两种持有者视角——协议侧看内存里的 `currentTerm / votedFor / commitIndex / log[index]`，设施侧看磁盘上的状态文件 + 日志段 + 快照文件，以及网卡上的字节流。**换约束（真网络、真崩溃、真 fsync 延迟）时，变的是持有者与保证强度，不变的是那六条不变量。**

## 二、为什么分两版

历史上这两件事被压在同一份文档里，结果是**两边都不舒服**：讲协议时被线程模型打断，讲工程时又反复回退去补协议定义。按 `LEARNING.md` §7.1，它们的档位本来就不同：

| 维度 | go-lab（机制档偏多） | cpp（架构档） |
|---|---|---|
| 单元 | 一个机制（选举 / 复制 / 落盘 / 快照 / KV） | 一块（复用方式 + 一组失效模式） |
| 承诺 | 课程测试给定 | 先定：可观察的故障下行为 |
| 证据 | 测试通过 + 口述复述 | 端到端故障注入 + 不变量检查器 |
| 材料地位 | 权威（lab 提供假网络/假磁盘） | 一个选点（自己选的线程模型/文件格式） |

**分成两版的四条理由**：

1. **判据类型不同。** go-lab 的验收对象是「机制在给定失败模型下不出错」，cpp 的验收对象是「接口能预测 + 判据可观测 + 换约束知道哪条失效」（§2.4）。同一段文字无法同时满足两种验收。
2. **失败模型的强度不同。** go-lab 的失败模型由 lab 框架给定（丢包率、延迟、分区、重启都是模拟的，磁盘是内存模拟的）；cpp 的失败模型是**自选范围**：真 socket 超时、真 `fsync` 耗时、真 `kill -9`、真 OOM。范围自选意味着**必须先写清范围再谈正确**。
3. **实现面的数量级不同。** §2.4 判据要求实现面 ≤6 个名词。go-lab 的实现面勉强在限额内（选举/复制/落盘/快照/apply/去重表）；cpp 加上线程模型、事件循环、自有 RPC、序列化、日志段、fsync 策略、成员变更、故障注入、指标口径，**必须各归其块**，否则就是名词堆叠（§8 反模式 1）。
4. **两版回答的面试问题不同。** go-lab 回答「你懂不懂 Raft 为什么这么设计」；cpp 回答「你能不能在真约束下把它做到能被别人挑战」。混讲时前者被后者的细节淹没，后者被前者的结论带偏。

**不分叉的部分**：协议语义、六条不变量、多数派阈值 `floor(N/2)+1`、任期作为逻辑时钟。这些在两版里**只说一遍**，由总纲指向，子项目只引用不复述（§2.4 判据 3：同一工具只有一个 owner，owner = 先引入它的块 → 这里是本文 §三）。

## 三、共享机制清单与块依赖

两版都要覆盖同一份清单，**只是在每一条上验收强度不同**。清单本身是「要覆盖什么」的合同，不是正文：

| # | 机制 | go-lab 的覆盖到哪 | cpp 的覆盖到哪 |
|---|---|---|---|
| 1 | 选举与任期 | 随机超时、一任期一票、日志新旧比较、step down | 同左 + 事件循环下的定时器实现 + 单任期单 leader 的不变量检查器 |
| 2 | 日志复制与提交点 | `prevLog` 匹配、nextIndex 回退、多数派 match 推进、当前任期限制 | 同左 + 回退策略（逐条 vs 按任期跳跃）的选择记录 + 冲突检测的不变量 |
| 3 | 持久化 | 三字段落盘、回复前落盘、重启重放 | 同左 + 日志段文件格式、`fsync` 时机与批、原子替换、崩溃点注入 |
| 4 | 快照 | 触发、`lastIncludedIndex/Term`、下标偏移、InstallSnapshot | 同左 + 分块传输与校验、截断与生命周期、快照期间的一致性 |
| 5 | 成员变更 | **不覆盖**（见 go-lab 的「不做什么」） | 单步变更 + 联合共识的取舍、变更期间的隔离与租约问题 |
| 6 | 线性一致读（可选） | 走日志读（KV 层去重表保证恰好一次） | ReadIndex / lease / 走日志 三种读路径的代价与正确性条件 |
| 7 | 故障注入与不变量 | 课程测试 + race 检测 + 固定种子重放 | 自有注入器（丢包/延迟/分区/崩溃）+ 可检查不变量列表 + 回归语料 |
| 8 | 性能口径 | 不测，只要求「不加 sleep 骗过测试」 | 必须给口径：测什么、怎么造负载、看哪个分位数、基线取哪个 commit |

**块依赖（cpp 侧，go-lab 侧无此图）**：

```
[契约层] 承诺与不变量清单  ← 先定，其余块向它借（owner）
   │
   ├─→ [协议块] 选举+复制+提交点   ← 只借契诺层的"不变量"，自己不发明
   │        │
   │        └─→ [持久化块] 日志段+fsync+原子替换   ← 借协议块的"哪些字段必须落盘"
   │                 │
   │                 └─→ [快照块] 截断+传输        ← 借持久化块的"文件生命周期"
   │
   ├─→ [运行时块] 线程模型/事件循环/自有 RPC/序列化 ← 借契约层的"失败模型"
   │
   └─→ [验证块] 故障注入+不变量检查+性能口径       ← 借协议块与持久化块的观测点
```

依赖纪律：每条边只标「借谁」，不标「照抄谁」。凡是两个块各讲一遍同一件事（例如线程模型既在运行时块讲又在协议块讲），就是块没切对。

## 四、两版判据差异 · 不做什么 · 失效点

### 4.1 判据差异（这是全文件最该记住的一张表）

| 维度 | go-lab | cpp |
|---|---|---|
| **一句话判据** | 测试通过 + 能复述为什么这一行不能删 | 注入分区/崩溃后不变量仍成立 |
| 通过的形态 | 指定测试套件多轮全绿（含竞态检测） | 每个注入场景下，检查器对全部不变量报「未破」 |
| 一次通过算不算 | 不算，必须重复跑与换种子 | 不算，必须固定语料可重放 |
| 「对」的证据 | 逐条对照安全性质口述 | 不变量检查器 + 可回放现场 |
| 错的时候能定位到 | 哪个测试、哪个种子 | 哪个不变量先破、对应哪条日志/哪个字段 |
| 失败模型 | lab 给定 | 自己写清范围，超范围即失效点 |
| 性能 | 不验收，禁止用调大超时/加 sleep 掩盖 | 只验收口径（测什么/怎么造负载/看哪个分位/基线是哪版） |
| 明确的「够」 | 五步走完 + KV 层语义正确 | 六条不变量全绿 + 成员变更可解释 + 口径写清 |
| 明确的「不够」 | 「能选主」不等于「能存数据」 | 「能跑 demo」不等于「实现了共识」 |

**两版的判据不能互相借用**：cpp 的不变量检查器不证明 go-lab 的测试通过；go-lab 的测试全绿不构成 cpp 的工程证据。任何跨版引用都必须重新验证。

### 4.2 必要性：删掉会怎样（两版共用，删除后的后果只在 cpp 侧被观测）

| 机制 | 删掉会怎样 | 判定 |
|---|---|---|
| `prevLogIndex/prevLogTerm` 匹配检查 | 乱序或分区恢复的旧消息会在同一 index 写入不同 term，apply 通道投出分叉命令 | 必需 |
| `currentTerm`/`votedFor` 在回复前落盘 | 断电重启后同一任期可投两票，两个 leader 同时广播，已提交条目可被覆盖 | 必需 |
| `commitIndex` 推进入口检查任期 | 旧任期条目可被多数派直接提交，新 leader 覆盖后，已返回客户端的命令消失 | 必需 |
| 随机化选举超时 | 多 follower 同时参选、选票分散，集群可能长期无 leader | 选择（弱，但便宜） |
| 快照后的逻辑/物理下标区分 | 下标运算错位，落后的节点永远追不上或追到错位置 | 必需 |
| 发送阻塞调用前放锁 | 拖住心跳与投票回复，测试里表现为随机超时 | 选择（工程必需） |
| cpp 专有：原子替换（临时文件→fsync→rename→fsync 目录） | 崩在写中途留下截断文件，重启解析失败变成空节点 | 必需（cpp 侧） |
| cpp 专有：单消费者队列的完整性 | 多个消费者并发 dequeue 会出现 use-after-free / 丢元素 | 必需（cpp 侧，一旦引入第二消费者就必需） |

### 4.3 失效点：哪条前提一破，结论就变

- **成员数为 3/5 且阈值按 `floor(N/2)+1`** → 若成员数变化而阈值没跟着变，分区两侧都可能提交，两版结论同时破。
- **协议消息携带前缀匹配字段，且传输层允许丢/重/乱序** → 若传输层被换成可靠有序 FIFO（cpp 侧很容易因为「反正是 TCP」而这么假设），接收方不再拒绝分叉日志，实现看起来更简单但**已经不是在测 Raft**。TCP 只保证字节流有序，**不保证 RPC 不被重复处理、不保证超时不重试**——这条在 cpp 侧是头号失效点。
- **落盘在回复之前完成且真的到达稳定介质** → 若介质带写回缓存、容器卷不是真持久、`fsync` 失败被忽略，cpp 侧整套持久化验收失效。
- **选举超时依赖本地单调时钟，且随机区间大于一次往返** → 若时钟跳变、CPU 争用、事件循环被长任务阻塞（cpp 侧典型），旧 leader 自我退位、任期连续递增，客户端长时间拿到「我不是 leader」。
- **go-lab 的假磁盘行为与真实文件系统一致** → 若把 go-lab 的落盘结论直接搬到 cpp（「反正我们落盘了」），会漏掉原子替换、目录 fsync、部分写这几件事。**这是跨版搬运最容易出的错。**

### 4.4 不做什么（总纲层的范围声明）

- **不做第三版。** 不再新增「Rust 版」「生产级分支」之类的旁支：两版的边界已经覆盖「理解」与「工程」两端，加一条只会稀释判据。
- **不把总纲写成教材。** 总纲只允许出现清单、判据、路由；一旦出现「具体某行代码怎么写」，说明应该下沉到子项目的 NOTES。
- **不做跨版自动同步。** 两版各自演进，协议层的改动需要人工确认两边影响，不设「一次改动两边生效」的机制（那会诱导把协议细节抄两遍）。
- **不承诺时间表。** 任何「几小时做完」的估计都是路线意愿，不是实测。

### 4.5 常见跑偏

- 把「go-lab 跑绿了」当成「cpp 也能这么做」——两版的失败模型不同，省略原子替换的后果只在 cpp 侧爆炸。
- 在总纲里写实现细节，导致子项目变成「总纲的复制品」，违反「同一工具只有一个 owner」。
- 用 cpp 的工程严谨去否定 go-lab 的教学价值（「这个 demo 根本不能上生产」），或用 go-lab 的简洁去回避 cpp 的故障注入（「协议对了就行」）。
- 只按 lab 名/文件名划块，不按失效模式划块（§8 反模式 9）。

## 五、面试怎么讲

### 30 秒版本

> 「我把 Raft 的工程实践拆成两条线讲。第一条是课堂 demo：按 lab 节奏走选举、日志、持久化、快照、KV 五步，验收就是测试通过加上我能逐条复述为什么某个字段不能删。第二条是正经 C++ 工程：线程模型、自有 RPC 与序列化、日志段文件和 fsync、快照截断、成员变更、故障注入与不变量检查、性能口径，验收不是『跑通了』，而是注入分区和崩溃之后安全不变量一条都没破，而且破了能定位到哪一条先破。两版共享同一套协议语义和六条不变量，差别全在失败模型的强度和验收方式——这也是我为什么要把它们分开写，混在一起两边都讲不清。」

### 可能被追问的 8 个点

**1. 「为什么非要分两版？一份写不完吗？」**
→ 考点：是否理解「机制档」与「架构档」判据不同，而不是为了显得工作量多。
→ 答法：两版的验收对象不同。demo 的验收是「机制在给定失败模型下不出错」，工程的验收是「接口能预测 + 判据可观测 + 换约束知道哪条失效」。同一段文字无法同时满足，写在一起的结果是协议讲到一半被线程模型打断，工程讲到一半又回去补协议定义。拆开后还有一个好处：协议语义只写一遍，两边引用同一个 owner。

**2. 「两版共享的是什么？不共享的是什么？」**
→ 考点：有没有真的把「协议」和「运行时」分开。
→ 答法：共享的是六条安全不变量与协议语义——任期不回退、每任期一票、提交点只由多数派推进、已提交条目不被覆盖、apply 前缀单调不跳序、快照只截断已应用前缀。不共享的是失败模型与验证手段：demo 的丢包、延迟、重启是框架模拟的，磁盘是内存模拟的；C++ 版是 socket 超时、真 `fsync`、真 `kill -9`。所以 C++ 版多出来的工作量几乎全在「把假设变成可观测的契约」上，不在协议本身。

**3. 「demo 那版你能保证它到生产能用吗？」**
→ 答法：明确不能，而且要主动说出为什么不能：它不覆盖生产级传输（TLS、鉴权、流量控制）、不覆盖性能（没有任何吞吐/延迟口径）、不覆盖运维（无指标、无在线配置、无升级路径）、也不覆盖成员变更。它的价值是用最短路径把共识骨架跑通并讲清，这一点做到了就算达标——把「不能上生产」当缺陷是问错了问题，把它当卖点才是问题。

**4. 「C++ 版为什么不直接用现成的 RPC 框架？」**
→ 考点：是否存在真实的取舍，而不是「自己写显得厉害」。
→ 答法：不是为了造轮子，是因为需要**可控的失败注入点**。丢包、延迟、分区、目标方法过滤，这些必须能精确作用在某条 RPC 上并且可复现，否则故障场景无法回放。自有的另一面是代价：必须自己处理超时、重试语义、序列化版本、连接生命周期。这个取舍是「用它换可观测性」，不是「它更好」。

**5. 「线程模型你选了什么？为什么？」**
→ 考点：§2.4 判据 4——是否标了「它选了哪个点」，而不是把选点当原理。
→ 答法：先声明这是选点不是原理。可选点是「每连接一线程」「固定线程池 + 事件循环」「单事件循环 + 工作线程」；我选的是事件循环负责收发与定时器、协议状态由单线程串行处理，理由是 Raft 状态字段耦合极深，串行处理能把锁从「必须正确」降级为「几乎不需要」，同时保留事件循环对超时的细粒度控制。代价是慢操作（fsync、大快照传输）必须交给工作线程，否则会阻塞整个循环——这个代价本身就是一条可以拿去被追问的判据。

**6. 「你怎么证明它是对的？」**
→ 考点：这是全套里最容易露怯的一题，也是两版判据的分界线。
→ 答法：分两层说。demo 层的证据是测试通过 + 重复跑 + 竞态检测 + 固定种子可重放；工程层的证据是不变量检查器：把「任期单调」「单任期单 leader」「已提交条目在任何节点不消失」「各节点 apply 序列互为前缀」「快照边界不越过已应用点」这几条写成可断言的检查，挂在故障注入场景上跑。判据不是「没报错」，而是「注入特定故障后，预期该破的不变量没破，且注入一个错时症状与预期一致」——最后这半句是契约型积木的验法，改坏一步顺序，症状必须对得上。

**7. 「性能你怎么谈？」**
→ 答法：只谈口径，不谈数字。口径包括：测什么（提交通道吞吐、提交到 apply 的延迟、以及故障后的恢复时间）、怎么造负载（客户端并发数、命令大小分布、批量与流水线开关）、看哪个分位数（p50/p99 而不是均值，因为延迟分布长尾）、基线取哪个版本（同一 commit、同一机器、同一文件系统）。没有这四个要素的对比表不允许出现。另外要主动指出：fsync 是这类系统的主要成本，任何不区分「回复前落盘」与「批量落盘」的性能对比都是无效对比。

**8. 「成员变更为什么 demo 版不做、工程版要做？做了难在哪？」**
→ 答法：不做是因为课程范围内它与「理解多数派」无关，做了只会稀释主线；要做是因为「阈值按成员数算」这条假设在生产里一定会被打破。难点不在配置怎么传，而在**变更期间的新旧成员对「谁是多数派」的认知必须一致**，否则会出现两个不相交的多数派同时声称自己有资格。常见解法是从「一次性切换」退到「单步变更 + 联合配置」，每一步只动一个成员，让任意时刻的多数派集合都有交集。这一条是可以被追问到底的：要能说清中间态上一票怎么算。

### 别说什么

- **别说「两版都实现了、测试全绿」。** 这份文件是路线与判据，不是成果清单。一句「你 C++ 版 fsync 崩在写中途会怎样、怎么发现的」就能验真假。
- **别在没有口径的情况下谈性能。** 「吞吐提升 X 倍」「延迟降到 Y 毫秒」在这类系统里如果不说清批量、落盘策略、分位数和机器，等于没说；本文不出现任何未经实测的数字，口头也不该出现。
- **别把「用了 TCP / 用了现成 RPC」当成可靠性论证。** TCP 保证字节流有序，不保证请求不被重复处理、不保证超时不重试，更不保证进程不崩。
- **别用「加个 sleep / 调大超时就好了」收尾。** 这句话等于承认把不确定性藏起来了；同理「跑一遍没报错」不是正确性证据，是正确的缺席。
- **别把选点讲成原理。**「Raft 就是单线程处理」「Raft 就是一把大锁」都是反例——那是某个实现选的点，原理层只说必须/可以/不做。
- **别提任何「已经跑过、实读过」的结论。** 本文件没有做过实测；凡是从上游材料搬来的历史状态，只能标为「历史记录，待复核」，不能当成本线的现状。
