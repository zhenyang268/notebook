## 一、它解决什么问题

这项能力要拦住的是三类真实事故：release 版崩溃定位、链接期失败、跨架构 ABI 误判。

**场景一：线上崩溃。** 一个带调试信息的 ELF 常是几 MB 到几十 MB，core 可到 GB 级。若只看到 `SIGSEGV`，只能猜；有口径时，用 faulting PC 对到“函数+偏移”，再读参数寄存器与栈，才能区分空指针、栈破坏、ABI 不一致。**场景二：链接失败。** 单体仓库里一次 `undefined reference` 往往只有一行，根因却可能在几十个目标文件/库的链接顺序、C++ 名字修饰、符号可见性或版本里；符号冲突会让进程在 `main` 前退出，或运行时绑到错误实现。面试里则对应：参数怎么传、栈为何对齐、PLT/GOT、PIE/ASLR、内联汇编约束。

## 二、为什么这样做（方法论设计）

- **有口径才算数。** 每个结论要能落到可复查输出：`readelf -s` 的 UND/DEF、`objdump -d` 的 `call foo@plt`、GDB 的 `p/x $rsp`、`LD_DEBUG=bindings` 的绑定行。不能落到证据的，如“ARM 更省电”“延迟绑定更快”，不作为结论。
- **指标怎么定。** 不设性能倍数指标，因为受编译器、CPU、OS、链接选项影响，按实现而定。可考指标是：能否定位到具体符号/重定位项；能否定位到具体指令与寄存器；能否给出 x86-64 与 AArch64 的对照判据。
- **边界怎么划。** 以 Linux 用户态、SysV 与 AAPCS64、ELF 为主；不把 Windows PE、macOS Mach-O、内核 ABI 混进来。优化后的源码与汇编不再一一对应，结论必须回到“这个二进制”。
- **什么时候失效。** 高度优化、内联、尾调用、异常展开、手写汇编、不同 loader/链接选项都会让“背下来的栈帧图”失效；此时以 `objdump`、`readelf`、GDB 的实际现场为准。
- **常见错误做法的代价。** 只背寄存器表，遇到 `undefined reference` 仍不会读符号表；把 `-g` 当万能，发布版无符号或栈被破坏时照样定位不了；把“加帧指针”当唯一回溯手段，优化代码和手写汇编会失效；把动态链接当黑盒乱调库顺序，可能暂时压住冲突却引入版本错配。

## 三、章节大纲

1. **从 C 到机器码：预处理、编译、汇编、链接各自产出什么**——讲 `.i/.s/.o/ELF` 的边界与工具停点；能答“`-E/-S/-c` 各停在哪、链接器到底合并了什么”。
2. **x86-64 汇编基础：寄存器、寻址模式与常用指令**——16 个 GPR、RIP 相对寻址、ModR/M/SIB、`mov/lea/call/jmp/cmov`；每个点留 AArch64 对照位。能答“`lea` 为什么不算访存、x86 内存操作数意味着什么”。
3. **ARM64 汇编基础：load/store 架构、条件执行与 x86 的逐条对照**——`ldr/str` 成对与 `[sp, #-16]!` 的 pre-index、`csel/cset/cinc` 替代 `jcc`、NZCV 与 `subs` 的耦合、定长 4 字节编码；每个点都留 x86 对照位。能答“ARM64 为什么几乎没有 `add` 之后跟一条条件跳转这种写法”。

4. **调用约定与 ABI：SysV 与 AArch64、参数传递、调用者与被调用者保存**——整数/浮点参数寄存器分组、第 7 个参数起入栈、结构体分类（≤16 字节拆寄存器 vs 隐式指针）、callee-saved 与 caller-saved 的分界、返回值与间接返回寄存器（x86 `rax/rdx`，ARM64 `x0/x1` 但间接返回在 `x8`）。能答“为什么 ABI 要区分 caller-save 与 callee-save”，而不只是背表。

5. **栈帧与局部变量：帧指针、红区、可变参数、栈对齐**——prologue/epilogue 的形状、`rbp` 链与 unwind 信息的关系、x86-64 的 128 字节红区、16 字节对齐的调用点约束、`va_list` 为什么在寄存器传参下必须落栈。能答“关掉帧指针后回溯为什么还能工作”。

6. **目标文件与 ELF：段与节、符号表、重定位表**——`.text/.data/.rodata/.bss` 与段的关系（`bss` 为什么不在文件里占空间）、符号的 binding/visibility/type、`R_X86_64_*` 与 `R_AARCH64_*` 的常见重定位项、`objdump -dr` 里重定位项与指令的对应。能答“为什么 `undefined reference` 只有在链接期才暴露”。

7. **静态链接与动态链接：符号解析、PLT/GOT、延迟绑定**——按 section 合并与地址分配、强弱符号与常见符号、共享库基址未知导致的位置无关要求、PLT stub 与 `GOT[1]/GOT[2]` 的解析流程、`-z now`/`LD_BIND_NOW`、`LD_DEBUG=bindings` 的读法。能答“PIE 下全局变量的访问为什么要走 GOT”。

8. **装载与运行时：动态加载器、地址空间布局、PIE 与 ASLR**——`execve` 到 `_start` 之间的过程、`PT_INTERP` 与 `ld.so` 的职责、mmap 布局（栈/mmap 区/堆/段）、`ET_DYN` 与基址随机化、`randomize_va_space` 的三个档位、`dlopen`/`dlsym` 与 `LD_PRELOAD` 的顺序。能答“为什么 `&x` 每次不同而 `&a - &b` 恒定”。

9. **内联汇编与 intrinsics：约束、clobber、内存屏障**——`"r"/"m"/"=r"/"0"` 的意义、`"memory"` clobber 是编译器屏障而不是 CPU 屏障、`asm volatile` 阻止的是什么、ARM64 `%w0`/`%x0` 的视图区分、intrinsics 与手写汇编的取舍边界。能答“漏写 clobber 会以什么形式出错”。

10. **两个架构的差异清单：什么时候必须看汇编**——编码密度、内存模型（TSO vs 弱模型）、条件执行、`push/pop` vs `stp/ldp`、SP 对齐要求、参数与返回值寄存器；以及工程判据：什么情况下必须读反汇编（崩溃定位、性能归因、ABI 不匹配、编译器生成代码与源码不一致）。能答“同一份 C 代码在两个架构上，哪类写法会暴露差异”。

## 四、不做什么

**不做 Windows PE 与 macOS Mach-O。** 格式不同但概念同构，混进来会让"节与段""导入表""符号修饰"三件事各讲两遍，反而模糊主线。只以 ELF 为对象，需要时提一句对照。

**不写 x86-64 与 ARM64 的完整指令集。** 只覆盖"读编译器输出"和"读崩溃现场"够用的子集：数据搬运、算术、比较与条件、跳转与调用、栈操作、原子与屏障。SIMD 指令只在内联汇编与 intrinsics 一章点到为止，不做指令选择讲解。

**不做编译器后端的代码生成策略。** 寄存器分配、指令调度、内联与向量化的决策过程属于编译器线（见 `compiler/`）；这里只处理"已经生成了这样一段汇编，它意味着什么"。

**不做内核 ABI 与驱动。** 系统调用号、`syscall` 入口、内核栈与用户栈切换属于 OS 线（见 `os/jos/` 与 `os/linux-api/`）；这里只到用户态 ABI 与装载器为止。

**不做二进制逆向与漏洞利用。** 栈溢出、ROP、格式化字符串这些会改变文档重心；只在"栈溢出能改返回地址"这一处提一句因果，不展开手法。

**不报未经测量的数字。** 熵位数、栈帧大小、内联汇编带来的性能差异，没有同口径测量就只写"用什么命令测、测什么量级"。ASLR 的实际熵与 `randomize_va_space` 的取值不是同一件事，不能混说。

## 五、面试怎么讲

这部分是基础知识，面试官不会问“你做过什么”，只会突然挑一个点往下问，看你是否真懂。所以讲法要体现“我能把整条链路串起来，并且知道我说的每句话怎么验证”，而不要停留在“我学过汇编”。

**30 秒版本（开场可以直接说）**

> 我把从 C 到机器码这条链路当成一条能验证的线来准备：编译器把 C 降成汇编，汇编器产出 ELF 目标文件，链接器做符号解析和重定位，装载器把它映射进地址空间。难点不在写汇编，而在边界：调用约定里谁负责保存寄存器、栈什么时候必须 16 字节对齐、哪些重定位在链接期解决哪些要留到装载期、PIE 下哪些地址是相对寻址。验证方式就是拿最小例子自己看：用 `objdump -d` 看每条指令，用 `readelf -r` 看重定位表，用 `gdb` 单步看栈和寄存器。能对着二进制讲出每一条指令和每一个节的来路，才算真懂。

说完这一段，面试官大概率会顺着“边界”追问，下面就是准备好的落点。

**可能被追问的 7 个点**

**1. “讲讲函数调用时栈是怎么走的。”**
- 真实考点：你是否知道“栈对齐”是调用点（call site）层面的约定，而不是 prologue 里随便减个数。
- 可以这样答：x86-64 System V 规定 `call` 执行完、控制转移过去的瞬间，`rsp + 8` 是 16 的倍数——因为 `call` 压了 8 字节返回地址，所以进入被调函数时 `rsp ≡ 8 (mod 16)`，编译器在 prologue 里 `push rbp` 之后 `sub rsp, N` 的 N 要凑回 16 对齐。叶函数可以用 128 字节红区（red zone）不调 `rsp`。返回地址存在栈上，所以栈溢出能改返回地址。ARM64 不一样：`bl` 把返回地址写进 `x30`（LR）而不是压栈，非叶函数自己 `stp x29, x30, [sp, #-16]!` 保存；返回地址在寄存器里，所以“栈溢出改返回地址”这条利用路径在 ARM64 上要先找到 LR 被 spill 到哪。

**2. “参数怎么传？结构体呢？”**
- 真实考点：ABI 的寄存器分类规则和边界条件（正好 16 字节、正好 4 个浮点）。
- 可以这样答：x86-64 整数参数 `rdi rsi rdx rcx r8 r9`，浮点走 `xmm0-7`，第 7 个整数参数起从右往左压栈，返回值 `rax`/`rdx`。结构体 ≤16 字节且字段都是 INTEGER/SSE 类就拆进寄存器，>16 字节改成 hidden pointer——caller 分配空间、地址放 `rdi`、`rax` 回传这个地址。ARM64 参数是 `x0-x7`，但间接返回地址放在 `x8` 而不是 `x0`，这点和 x86 直觉相反；HFA（同类型浮点 1–4 个）走 `v0-v3`，HFA 超过 4 个或 >16 字节就退回内存。所以 `struct {float a,b,c,d,e;}` 在两边都是 MEMORY 类，但传间接地址用的寄存器不同。

**3. “静态链接和动态链接，链接器到底做了什么？”**
- 真实考点：符号解析 + 重定位，你能不能说出具体的重定位类型。
- 可以这样答：静态链接是按 section 合并 `.text/.data`、解析符号、把每个重定位项写回最终地址。x86-64 上常见 `R_X86_64_PC32`（PC 相对）、`R_X86_64_PLT32`（调用）、`R_X86_64_64`（绝对 64 位）、`R_X86_64_GOTPCREL`；ARM64 对应 `R_AARCH64_ADR_PREL_PG_HI21` + `R_AARCH64_ADD_ABS_LO12_NC`（`adrp`/`add` 一对，因为单条指令装不下 64 位地址），调用是 `R_AARCH64_CALL26`，`bl` 的立即数只有 26 位，范围 ±128MB——超出范围链接器就得插 veneer / long-branch stub，这就是一个具体的边界条件。符号规则：多个强符号报错，强 + 弱取强，多个弱取其一。

**4. “为什么共享库要用 GOT/PLT？延迟绑定是怎么回事？”**
- 真实考点：位置无关代码的必要性，以及“什么时候解析”这个时序。
- 可以这样答：共享库加载基址在链接期未知，所以外部符号不能写死绝对地址，只能在 GOT 里存一份指针间接访问。函数调用走 PLT stub：首次调用跳到 PLT0，PLT0 用 `GOT[1]`（link_map）和 `GOT[2]`（`_dl_runtime_resolve`）触发解析并回填 GOT，之后直接跳。`-z now` 或 `LD_BIND_NOW` 关掉延迟绑定。数据引用在 PIE 下用 RIP 相对（`lea rax, [rip+sym]`），但只对“本模块内且不可被抢占”的符号成立；`-fPIC` 默认要支持 symbol interposition，所以全局变量仍走 GOT。ARM64 的 GOT 访问是 `adrp x0, :got:sym` + `ldr x0, [x0, #:got_lo12:sym]`。

**5. “ASLR 在哪一层生效？为什么每次 `&x` 都变、但 `&a - &b` 不变？”**
- 真实考点：变的是基址不是段内偏移，以及熵从哪来。
- 可以这样答：内核 `load_elf_binary` 里对 ET_DYN（PIE）在 `ELF_ET_DYN_BASE` 基础上加随机偏移 mmap，栈顶、mmap 区基址、brk 起点也各自随机化。`/proc/sys/kernel/randomize_va_space` 三个值：0 关，1 只随机共享库/栈/mmap，2 再加上堆（brk）全随机。粒度是页（4KB），所以同一段内的相对距离恒定、绝对地址变。非 PIE 可执行文件的 `.text` 绝对地址是固定的——这是能讲清楚“为什么 PIE 是缓解不是修复”的地方。

**6. “内联汇编里 `volatile` 和 clobber 各管什么？”**
- 真实考点：你分不分得清编译器屏障和 CPU 屏障。
- 可以这样答：`asm volatile("mfence" ::: "memory")` 里，`volatile` 阻止编译器删除或跨 volatile asm 重排，`"memory"` clobber 告诉编译器内存可能被改写，是编译器屏障——`asm volatile("" ::: "memory")` 一条指令都不生成。但它不是 CPU 屏障，CPU 层面 x86-64 要 `mfence`/带 lock 前缀的指令，ARM64 要 `dmb ish` 或用 `ldar/stlr` 的 acquire-release 语义。约束符上：`"r"` 通用寄存器、`"m"` 内存、`"=r"` 输出、`"0"` 和第 0 个操作数共用寄存器；ARM64 用 `%w0`/`%x0` 区分 32/64 位视图。典型事故是漏写 clobber，编译器把循环里的读提到 asm 外面只读一次。

**7. “x86-64 和 ARM64 最本质的差别在哪？”**
- 真实考点：你能不能跳出“一个是 Intel 一个是 ARM”这种说法。
- 可以这样答：编码上 x86 变长 1–15 字节、靠前缀和解码器换密度，ARM64 定长 4 字节、靠 `csel/cset` 和 NZCV 做条件执行而不是 `jcc`；内存模型上 x86-64 是 TSO，只允许 store-load 乱序（所以需要 store buffer 屏障），ARM64 是弱模型，常规情况下必须显式 `dmb` 或用 acquire/release 指令；栈操作上 x86 有 `push/pop`，ARM64 只有 `stp/ldp` 配 pre/post-index 寻址 `[sp, #-16]!`；对齐上 ARM64 用 SP 做基址的 load/store 必须 16 字节对齐，硬件会报 SP alignment fault，x86 基本容忍未对齐访问（性能损失而已）。这几条差异都能引出一条“所以移植时哪类代码会挂”。

**别说什么**

- **把“跑通了”当“实现对”**。程序输出对不代表 ABI 守住了：栈没对齐、clobber 漏写、callee-saved 寄存器没恢复，都可能在你这个例子里恰好不崩。被追问“你怎么知道寄存器状态是对的”，答不出验证手段就是没做过。
- **把工具当原理**。“GCC 会帮我处理栈对齐”“链接器自动搞定重定位”这类话一出口，下一句必然是“它具体怎么搞的”，答不上来比不说更糟。
- **报没测过的数字**。“ASLR 熵有 32 位”“内联汇编快 3 倍”这种，说之前要能讲出在什么机器、用什么命令、采了多少次——`randomize_va_space` 的值和实际熵位数不是一回事，x86-64 上 mmap 基址的熵大约 28 位。
- **把 x86 的习惯套到 ARM64**。说“返回地址压栈”“`sp` 随便减 8”“看标志寄存器”这几句，一听就知道只熟悉一个架构；反过来只讲 ARM64 也一样。
