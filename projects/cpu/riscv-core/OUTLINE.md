# riscv-core · 从 RV32I 单周期到乱序核

> 本目录只做**造核**：写 RTL、搭 difftest、出时序与面积。
> 「读核 + 用 PMU 归因」在 `cpu-microarchitecture/`；调用约定、栈帧、重定位细节在 `asm-link-arch/`。
> 三份文档共享同一套词汇（ISA / 微架构 / CPI / 关键路径），但只做单向指针，不互相复制正文。

## 一、它在做什么

从一条 `add` 的语义出发，把一台 RV32I 机器真正做出来，并且**用工业界的方式证明它是对的、快的、能收敛频率的**。整条链上有四个可验收的产物，缺任何一个都只是"跑起来了"：

**产物一：周期精确模型（C++ 或 Python）。** 不写一行 RTL，先能算出 IPC、能扫参数。它存在的理由是成本：改一个参数（ROB 从 32 到 128）在模型上是几分钟的事，在 RTL 上是几天。**设计空间探索必须先于实现**——这是"微架构"和"造 CPU 玩"的分界线。

**产物二：RTL。** 单周期 → 五级 → 转发/停顿 → 分支预测 → I/D cache → 乱序（重命名 + ROB + 保留站）→ 乱序访存（LSQ + 消歧）。每一级都可以独立跑通，不要求一次做完。

**产物三：difftest 台 + 测试集。** 每条提交指令与 Spike（RISC-V 官方指令集模拟器）逐条比对，随机程序跑够量。这是本项目的判定核心：**"我觉得对了"在这里没有任何分量**。

**产物四：时序与面积报告。** Yosys 综合出网表，OpenSTA 在 sky130 上做静态时序分析，给出关键路径的 ns 数、面积、以及能跑到的最高频率。**这一项是 Turing Complete 那类沙盒给不了的**——那里延迟是游戏单位，这里是纳秒。

**输入有四类**：RV32I 规范（基础整数指令集一章，很薄）；开源核作对照（Rocket 顺序、BOOM/SonicBOOM 乱序、CVA6）；开源工具链（Verilator / Yosys / OpenSTA / sky130 PDK）；参考模型与测试（Spike、riscv-tests、CoreMark）。

**验收口径不是"能跑程序"，而是四条**：① riscv-tests 的 `rv32ui-p-*` 全过；② 随机 difftest 与 Spike 零分歧；③ 综合通过且 STA 无违例，并报出关键路径起点终点；④ 每个微架构改动都有一张表，四个数——IPC、面积、fmax、以及"这个改动值不值"的结论。

**一句话定位**：把"微架构"从名词表变成**约束下的取舍能力**。你最终要能回答的是"窗口从 32 加到 64，IPC 涨多少、面积涨多少、频率掉多少、值不值"，而不是"我实现了乱序执行"。

## 二、为什么这样做（功能设计）

**取舍一：为什么用 RV32I，而不是自造 ISA 或 x86 子集。** 自造 ISA 会把时间花在写手册、写汇编器、写编译器后端上，而这些跟微架构无关；x86 子集要先解决变长译码和 uop 转换，难度在错误的地方。RV32I 的规范只有一章，指令约 40 条，工具链（GCC、objdump、Spike、riscv-tests）全部现成，还有 Rocket/BOOM 可以逐段对照结构。**代价是失去了"自己定编码"的乐趣**——那部分恰好是 Turing Complete 的强项，两边互补。

**取舍二：为什么先写周期精确模型，而不是直接写 RTL。** RTL 仿真一次要编译、要跑波形，改一个参数就要重来；模型上扫一遍窗口大小的成本接近零。更重要的是**模型强制你把性能想清楚**：每个结构参数对 CPI 的影响在模型里是一个公式，在 RTL 里是一堆 waveform。跳过这一步的人通常会做出"结构齐全但说不出为什么这样配"的核——缺的正是「结构为什么是这个尺寸」这一维。

**取舍三：为什么必须用 Spike 做 difftest，而不是靠自己的测试程序。** 自写测试的覆盖面永远等于自己的想象力，而 CPU 的 bug 几乎全在"想不到的组合"里（`x0` 被写、`jal` 立即数错位、forwarding 漏了 `x0`、flush 时保留站残留）。Spike 是官方参考模型，随机程序打进去做逐提交比对，能把 bug 定位到"第 N 条提交指令不一致、PC=0x...、寄存器 x7 期望 A 实际 B"。**判定口径是「逐条相同」而不是「最后结果对」**。

**取舍四：为什么用开源 PDK 而不是先上 FPGA。** FPGA 给的是真实可运行的 fmax，但它不可比：同一个设计在 Artix-7 上的 50 MHz 与 sky130 上的 ns 没有换算关系，你也看不到关键路径经过哪几级逻辑。OpenSTA + sky130 给的是**可归因的时序**——哪条路径违例、经过哪些单元、差多少 ps。代价是没有"真的跑起来"的体感，以及工具链安装更折腾。**建议顺序是反过来的**：先用开源流程把时序闭环跑通（能出报告就够），把上板留到后期当奖励。

**取舍五：为什么不用 Chisel/SpinalHDL 起步。** 它们能让你更快地生成 RTL，但会把"寄存器传输级到底怎么动"这一层抽象掉——而这层恰好是你想学的。用 SystemVerilog 写，写到你嫌烦了，再换高层语言，你才知道高层语言省掉的到底是什么。

**取舍六：为什么砍掉 MMU、特权级、多核、浮点、向量。** 每一件都会把项目重心从"微架构"移到别处：MMU 是 OS 与体系结构的交叉（那条线在 `os/jos/`），多核是一致性协议，浮点/向量是数据通路与编译器的交叉。RV32I 的整数核已经足够把流水线、预测、乱序、访存这四件事做完整；**加法应该加在深度上，不是加在面积上**。真要加，唯一值得加的是 Zicsr + `mcycle`（为了在 RTL 里读周期计数器），以及 Zbb 里的一两条指令。

## 三、章节大纲

按"能独立验收"的顺序切十一步，每一步都只依赖前面的产物。

**S0 工具链与最小验证台。** 装 Verilator + RISC-V GCC + Spike，写一个最小的 `Top`（一个计数器即可）和 C++ testbench，把"改一行 RTL → 编译 → 跑 → 出波形"这条回路打通。判据：`verilator --lint-only -Wall` 无告警；能 dump VCD 并在波形里看到时钟翻转。**这一步不打通，后面每次调试都要还债。**

**S1 单周期 RV32I。** 取指、译码、立即数生成、ALU、分支、load/store、寄存器堆、`x0` 恒零。先不关心性能，只要求功能正确。判据：riscv-tests 的 `rv32ui-p-*` 全过，`p` 后缀意味着自检通过（写 `tohost` 报 1）。

**S2 五级流水线。** 插入 IF/ID、ID/EX、EX/MEM、MEM/WB 四级级间寄存器，加 stall/flush 通路。判据：同一批测试仍然全过（**流水线改造后测试必须一次不挂，挂了说明级间语义错了**）；并且能在波形上指出"第 5 条指令在 WB 时，第 9 条正在 IF"。

**S3 冒险与转发。** 转发单元（EX/MEM、MEM/WB 两路，优先级前者高）、load-use 停顿、分支冲刷。判据：写一段刻意依赖的汇编（`lw` 后紧跟 `add`），数出停顿拍数与理论一致；误预测冲刷后寄存器状态与顺序模型一致。

**S4 分支预测。** 从 always-not-taken → BHT（2-bit 饱和计数器）→ + BTB（目标地址缓存）→ 可选 TAGE-lite。判据：CoreMark 或自写循环程序上，每千指令误预测数（MPKI）随预测器变强而下降，且 IPC 上升；**两个数都要报，只报 IPC 说不清因果**。

**S5 存储：I/D cache 与存储器接口。** 先做直接映射，再升两路组相联；写策略从 write-through 改 write-back + write-allocate；加 MSHR 雏形（可选）。判据：给定一段顺序/跨步/随机访存 microbench，miss 率与手算的集合冲突一致；IPC 相对无 cache 版本的变化可解释。

**S6 difftest 与随机测试。** 把 Spike 的提交日志接进 testbench，逐条比对 PC、指令、写回寄存器；再写一个随机指令生成器（约束在合法编码与有限循环内）。判据：**连续跑够量随机程序零分歧**；人为注入一个 bug（例如把 `x0` 的写使能打开），确认 difftest 能抓到——抓不到的 difftest 等于没有。

**S7 乱序前端：重命名 + ROB + 保留站。** 架构寄存器映射到物理寄存器池、ROB 按序分配按序提交、保留站等待源就绪后乱序发射。判据：同一程序在顺序版与乱序版上结果一致；参数化 ROB/RS 深度扫一遍，得到 IPC 随窗口的饱和曲线（**这条曲线是本章唯一的交付物**）。

**S8 乱序访存：LSQ + 消歧。** load/store 队列、store 提交前不落地、保守消歧 → 地址预测器投机。判据：`memcpy`、链表遍历、随机访存三个 microbench 的 IPC 分别变化，且"保守 vs 投机"的差值能归因到假依赖次数。

**S9 时序与面积闭环。** Yosys 综合、OpenSTA 在 sky130 上跑 STA、报关键路径与面积。判据：能指着报告说"当前 fmax 卡在哪一级的哪条路径"，并给出一次真实的取舍实验（例如把 ALU 里的比较器拆到下一级，频率上升、CPI 略升，四个数都要报）。

**S10 性能归因（可选，收口章）。** 把自研核的 IPC 分解成前端受限/错误投机/后端受限/访存受限四类，与 `cpu-microarchitecture/` 的 Top-down 口径对齐。判据：能对自己写的核做一次"瓶颈在哪"的判断，且判断能被下一次改动的实测印证。

**S11 上板与功耗（可选，纯加分）。** FPGA 上跑通并报 fmax；功耗只做量级估算（门数 × 单位功耗），不做签核。判据：板上跑通 CoreMark 并给出与仿真周期数一致的结果。

## 四、不做什么

**不做 MMU、特权级、异常陷入、Linux。** 跑 Linux 需要页表、TLB、U/S 模式、中断、原子指令一整组，加进来项目就变成"移植 Linux"而不是"做微架构"。这条线在 `os/jos/`，两边不合并。

**不做多核与缓存一致性。** 一致性协议（MESI、目录）是独立的一大块，且没有多核就没有可观测的收益，硬加只会增加验证负担。

**不做浮点与向量。** RV32I 整数核已足够覆盖流水线、预测、乱序、访存四件事；浮点会引入舍入与异常标志，向量会引入变长与掩码，都是新的验证面。

**不做形式化全覆盖。** 只对关键小模块（译码、转发选择、ROB 提交逻辑）做有界模型检验（BMC），不做全核等价性证明。

**不做功耗签核与物理设计。** 无布局布线、无 IR drop、无时钟树综合；面积只报综合后的单元面积，频率只报 STA 的估计值。这些是数字后端的工作，不是微架构。

**不追 SPEC 分数。** CoreMark/Dhrystone 只作为相对比较的载体，不与任何商用核比绝对值——跨核比 IPC 而不比面积功耗，是方法论错误。

**不用现成核改来交。** Rocket/BOOM 可以读、可以对照、可以抄结构思路，但不能拿来做自己的实现——那样 difftest 依然会过，而你没有得到任何能力。

**几个常见跑偏**：跳过周期模型直接写 RTL（结果只会"能跑"不会"能权衡"）；一开始就做乱序（顺序流水线都没干净，乱序的 bug 无法归因）；先装一整套 PDK 再写代码（工具链成了项目本身）；用自写测试替代 difftest（覆盖面等于想象力）；报 IPC 不报面积与频率（违反约束前提）。

## 五、面试怎么讲

**30 秒版本**（开场直接说，120–180 字）

> 我做的是 RV32I 的核，从单周期做到乱序：先写周期精确模型做设计空间探索，再写 RTL，用 Spike 做逐提交 difftest，最后用 Yosys + OpenSTA 在开源 PDK 上出关键路径和面积。所以每个结构改动我都能给出四个数——IPC、面积、fmax、以及值不值的结论。我认为微架构的核心不是"实现过乱序"，而是"在频率与面积的约束下说清某个结构为什么是这个尺寸"；这也是我不做 MMU 和多核的原因，那些属于 OS 与一致性协议，会稀释这条线。

**可能被追问的 8 个点**

1. **"为什么 RV32I 而不是自己设计 ISA？"** → 真实考点：知不知道 ISA 与微架构的分工。
   → 答法：自造 ISA 的时间花在手册、汇编器、编译器后端上，与微架构无关；RV32I 有官方参考模型（Spike）、现成测试集与开源核可对照，能把时间全花在流水线与乱序上。**自己定编码的价值在另一条线上**（沙盒类项目），两者互补不冲突。边界：RV32I 只有整数，没有 CSR/浮点，想读周期计数器要额外实现 Zicsr。

2. **"周期精确模型和 RTL 是什么关系？既然有 RTL 为什么还要模型？"** → 真实考点：设计空间探索的位置。
   → 答法：模型是**参数扫描的工具**，RTL 是**正确性与时序的载体**。窗口从 32 扫到 256 在模型里是几分钟，在 RTL 里要重新综合、重新跑完测试。模型给出"该取哪个尺寸"，RTL 证明"这个尺寸能做出来"。边界：模型必须用同一份 trace 校准，否则两条曲线不可比。

3. **"你怎么证明这个核是对的？"** → 真实考点：验证方法学，而不是"我跑通了程序"。
   → 答法：三层。① riscv-tests 的 `rv32ui-p-*` 功能自检；② 随机程序 difftest，对 Spike 的提交日志逐条比 PC、指令、写回值，零分歧；③ 注入故障测试——故意打开 `x0` 写使能或改错一条立即数，确认 difftest 能抓到。抓不到的验证等于没有。

4. **"load 后面紧跟用它的指令，为什么一定要停？"** → 真实考点：值的可用时间点，不是"有没有依赖"。
   → 答法：load 的数据在 MEM 末才可用，消费者在 EX 就要，转发无法提前于产生；所以停一拍，再从 MEM/WB 转发。乱序核里这条依赖仍在，只是被别的指令填掉了空拍——**乱序不消除依赖，只消除等待**。

5. **"乱序窗口是不是越大越好？"** → 真实考点：收益递减与代价的三次方。
   → 答法：窗口扩大能覆盖更多长延迟操作，但受程序固有 ILP 限制，IPC 上升会在某个尺寸饱和；同时 ROB/RS 的面积近似线性、唤醒与选择逻辑的面积与延迟超线性，fmax 会掉。**所以答案是一张曲线，不是一个数字**——我的做法是扫参数，取 IPC 边际收益开始低于面积与频率代价的那个点。

6. **"关键路径卡住了怎么办？"** → 真实考点：能不能把时序报告翻译成结构改动。
   → 答法：先看 STA 报的起点终点。常见的三处：ALU 的进位链（拆流水级或用超前进位）、保留站的唤醒+选择（用 age matrix 代替优先级编码、分 bank）、重命名到发射的读端口（减宽或分批读）。每次改动都要重报四个数，频率上升但 CPI 上升时要说明净收益。

7. **"为什么不用 FPGA 标准流程？"** → 真实考点：知道两种流程各自能给什么。
   → 答法：FPGA 给真实 fmax 和"真跑起来"，但不可比、不可归因（看不到具体路径经过哪几级逻辑）；开源 PDK + OpenSTA 给可归因的 ns 与面积，代价是没有上板体感。所以我先用开源流程把时序闭环，把上板当后期奖励。

8. **"和体系结构课上的五级流水线有什么区别？"** → 真实考点：是不是只背过课本。
   → 答法：课本给的是结构与公式，实际做要处理课本不写的东西——flush 时保留站残留、`x0` 的写屏蔽要贯穿所有写口、store 必须等提交才落 cache、误预测恢复要与 ROB 回滚对齐。**这些边界正是课本与实现之间的距离**。

**别说什么**

- **"我实现了乱序 CPU。"** 一问"窗口多大、为什么是这个数、面积多少、fmax 多少"就露馅。要讲的是四个数的取舍过程。
- **"我用了 Verilator/Yosys 所以懂验证/综合。"** 工具是工具，要讲的是 difftest 的比对口径、注入故障测试、以及 STA 报告怎么读。
- **"IPC 提升了 X 倍。"** 没有同口径基线（同一份 trace、同一时钟约束、同一综合目标）就不要报数；可以说"同一份随机测试集上，窗口从 32 到 128 时 IPC 上升 A%，面积上升 B%，fmax 从 C 掉到 D"。
- **"和 i7 比怎么样。"** 教学核与商用核的工艺、面积、功耗预算完全不同，跨核比 IPC 是方法论错误。要比就比同工艺下的面积-性能点。
- **报没测过的频率与面积。** 没跑过 STA 就不要说"能到 1GHz"；没综合过就不要说"面积很小"。
