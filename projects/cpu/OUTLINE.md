# cpu/ · 体系结构与编译器主线

> 这一层是**分组**，不是新项目：它把四条互相咬合的线放在一起，并规定「先读哪一章、再动手哪一步」。
> 四个子项目各自仍是完整的两件套（`OUTLINE.md` + `NOTES.md`），本文只做**路由与路径**，不复制它们的正文。

## 一、这个目录是什么

四个子项目，各回答一个问题：

| 子项目 | 回答什么 | 一句话 |
|---|---|---|
| `asm-link-arch/` | **读得懂吗** | 从 C 到机器码再到装载：调用约定、栈帧、ELF、重定位、PLT/GOT、PIE/ASLR |
| `cpu-microarchitecture/` | **说得清吗** | 从五级流水线到乱序的因果链 + 用 PMU/roofline 把「慢」归因到某一层 |
| `riscv-core/` | **做得出来吗** | 自己写 RV32I 核：单周期 → 流水线 → 乱序，配 difftest 与 STA，交出四个数 |
| `compiler/` | **编得动吗** | LLVM 一线：IR/Pass/后端/ABI，再到 GPU 与域特定语言（Triton/TVM/XLA/MLIR）的分层取舍 |

四条线共享一套词汇：**ISA / 微架构 / CPI / AMAT / 关键路径 / ABI / IR / SSA / dialect**。面试里最容易被问倒的不是单点，而是跨线追问——「你说这个 pass 让循环快了，那生成的指令在流水线上为什么就没卡住」「你说这个核 IPC 高，那 ABI 的栈对齐跟它有什么关系」。单独成组的理由就是这个：**它们必须在同一个叙事里被讲出来**。

**读法约定**：先看本文 §三 选路径，再进子项目读章节。不要从子项目第一章开始顺读。

**入口（本文的读法）**：按「源码 → `objdump`/`readelf` → `perf`/PMU → `difftest`/STA → LLVM」这条链读，四个子项目各是链上的一段：看得懂（汇编与链接）→ 说得清（流水线与乱序）→ 做得出来（RV32I 与 difftest）→ 编得动（LLVM pass）。换的是表示层与机制层，不换的是「同一份源码在每一层都留下可核对痕迹」这条主线。

**不换的是什么**：全程不变的是“同一输入下 `PC`/`x0–x31`/`FPR`/`CSR`/内存/异常状态的转换、`RV32I` 指令语义与 `misa`/`mstatus`/`mepc`/`scause` 行为、ABI 的 `ra/sp/s0–s11`/16B 栈对齐/`callee-saved` 规则、`ecall`/`sbi` 的 `a0–a7`/`sepc`/`scause` 系统调用约定、内存模型对 `load/store/AMO` 的可见顺序、`PMU`/`difftest` 对 `retire`/`stall_frontend`/`stall_backend` 的计数口径”，所以看到差异先问“哪条指令的 `rd/rs1/rs2`、`PC`、`CSR`、`ROB` 条目、`relocation` 类型、`PLT/GOT` 槽位、`IR` operand 或 `Pass` 依赖边变了”。

## 二、为什么这样分组（功能设计）

**取舍一：四个文档而不是一个大文档。** 合并会立刻出现两个问题。一是验证口径不同：`asm-link-arch` 的判据是「能不能对着二进制说清每一句」（`objdump`/`readelf`/`gdb`），`riscv-core` 的判据是「difftest 零分歧 + STA 无违例」，两者的"算数"标准根本不一样，混在一份文档里会互相稀释。二是读者路径不同：只想读核的人不需要 RTL，只想造核的人不需要读 PTX 汇编。**分组是为了让每份文档只守一个判据。**

**取舍二：为什么 `asm-link-arch` 放在这条主线里，而不是当成独立的基础课。** 因为它是另外三条线的**观测手段**：读核时要看反汇编确认编译器生成了什么，造核时要靠 ABI 决定调用约定，改 pass 时要靠 `objdump` 验证指令选择。把它单列成"基础"会被跳过去，放进主线里则是随手可查。

**取舍三：为什么 `compiler` 也在这里。** 编译器是这条链的**上游**：它决定生成什么指令序列，体系结构决定这些指令在流水线上怎么走。只懂编译器会写出「IR 指令数降了 20% 但动态指令数没变」的优化，只懂体系结构会解释不了「为什么这段循环没被向量化」。把两者放在同一个目录里，追问才能闭环。**GPU 与域特定语言编译（Triton/TVM/XLA/MLIR）放在 `compiler/` 第 11 章**，因为它们的核心问题仍是"把高层表示降到硬件"，与 LLVM 一线共用同一套判断口径。

**分组不改变任何约定**：子项目仍各自两件套、各自五段、各自 §五 面试口径。本文只负责三件事——分组说明、路径编排、跨线追问。

## 三、两条路径：60 分与 80 分

60 分与 80 分的区别**不是读了多少**，而是：**有没有实测数字、有没有取舍判断、有没有一次"我猜错了"的记录**。

### 60 分版：面试不失分

目标：被追问三层还能站住，任何结论都能落到可复查的证据上。

| 顺序 | 读 / 做 | 范围 | 判据 | 投入量级 |
|---|---|---|---|---|
| 1 | 读 `asm-link-arch` | 第 4（ABI）、5（栈帧）、6（ELF）、10（差异清单）章；第 2/3 章当字典查 | 能对着 `objdump -d` 说清一个函数的 prologue、参数寄存器、栈对齐；能读 `readelf -s/-r` 的一个符号与重定位 | 小 |
| 2 | 读 `cpu-microarchitecture` | 第 1–4 章（ISA 分离 / 五级 / 冒险与转发 / 分支预测）+ 第 9 章（PMU 与 roofline） | 能不看稿讲 8 分钟因果链；每个结论后面跟一句「按实现而定，判据是什么」 | 中 |
| 3 | 做 `riscv-core` | S0（环境）→ S1（单周期）→ S2（五级）→ S3（转发与停顿） | riscv-tests 的 `rv32ui-p-*` 全过；能数出 `lw` + `add` 的停顿拍数与理论一致 | 中 |
| 4 | 读 `compiler` | 第 3（IR/SSA/phi）、5（源码到 IR）章；`OUTLINE.md` 全文当索引 | 能读懂一段 `-O2` 的 IR：循环在哪、phi 在哪合流、`sret` 说明什么 | 小 |

**做完能讲到什么程度**：结构讲得清、口径说得准、动手有一次真实验。答不出"你测过吗"以外的所有问题基本都能扛住。

### 80 分版：有区分度

目标：从"能答"变成"能证明"。增量全部落在**实测与取舍**上。

| 顺序 | 增量 | 范围 | 判据 | 投入量级 |
|---|---|---|---|---|
| 1 | 读 `cpu-microarchitecture` 剩余 | 第 5（乱序）、6（乱序访存）、7（超标量与 SMT）、8（存储层次/TLB）、10（现代核对照）章 | 能说清 ROB 满与保留站满的区别、LSQ 消歧的三档代价、VIPT 与别名 | 中 |
| 2 | 做 `riscv-core` 的硬骨头 | S4（BHT/BTB）→ S5（I/D cache）→ **S6（difftest）** → S7（重命名+ROB+RS）→ S8（LSQ） | 与 Spike 逐提交零分歧，且注入的故障能被抓住；IPC 随窗口的饱和曲线 | 大 |
| 3 | 做 `riscv-core` 的物理约束 | S9（Yosys + OpenSTA + sky130） | 一条具体的关键路径（起点 → 经过哪些单元 → 终点）+ 一次取舍实验的四数表 | 中 |
| 4 | 读 `asm-link-arch` 剩余 | 第 7（静态/动态链接）、8（装载与 ASLR）、9（内联汇编与屏障）章 | 能用 `LD_DEBUG=bindings` 与 `ldd`/`readelf -d` 解释一次绑定过程 | 小 |
| 5 | 读 `compiler` 深水区 | 第 6（优化管线）、7（后端与寄存器分配）、9（可观测性）、**11（GPU 与域特定语言编译）** 章 | 能判"这段循环为什么没被向量化"；能说清 Triton/TVM/XLA 三者的分层差异与选型判据 | 中 |

**做完能讲到什么程度**：手里有可展示的东西——一张四数表、一条 IPC 曲线、一份 STA 报告、一次"我原本以为 A，实测是 B"的记录。这三样是区分度所在，也是**没法靠背换来**的部分。

## 四、不做什么 · 必要性 · 失效点

### 必要性：删掉会怎样

| 机制 | 删掉会怎样 | 判定 |
|---|---|---|
| `difftest` | `riscv-core` 的“做得出来吗”承诺破：RTL 与 RV32I 指令语义的分歧不可见，单周期→流水线→乱序的四个数失去可验证性。 | 必需 |
| `STA` | 单周期→流水线→乱序的时序承诺破：关键路径超过时钟周期，`riscv-core` 交出的频率/IPC 数字不可复现。 | 必需 |
| `objdump` | `asm-link-arch` 的“对着二进制说清每一句”承诺破：无法把 C、机器码、ELF、重定位、PLT/GOT 对齐到反汇编行。 | 必需 |
| `PMU/roofline` | `cpu-microarchitecture` 的“把慢归因到某一层”承诺破：低 IPC/CPI 无法归因到五级流水线、乱序、AMAT 或关键路径。 | 必需 |
| `Triton/TVM/XLA/MLIR` | `compiler` 第 11 章的 GPU/域特定语言分层承诺破：无法说明高层表示降到 PTX 汇编/硬件的取舍；LLVM IR/Pass/后端/ABI 主线仍可守判据。 | 选择 |

### 失效点：哪条前提一破，结论就变

- 时钟源从固定仿真周期改为 FPGA PLL 抖动超过 STA 裕量 → `riscv-core` 的关键路径结论从“周期可闭合”变为“必须重排流水线寄存器或降频”。
- 核数从单核 RV32I 改为多核共享总线 → `cpu-microarchitecture` 的 AMAT/CPI 归因从本地 cache miss 变为 MESI 状态、snoop/invalidation 和总线仲裁；没有 PMU 事件时慢因无法定位。
- 介质从本地静态 ELF 改为 PIE/ASLR 下的共享库 → `asm-link-arch` 的调用解释必须经过 PLT/GOT 与重定位表；`objdump` 看到的 `call` 目标不再等于运行时跳转地址。
- 权限位从用户态可执行改为 GOT/RELRO 只读或 mmap 缺页 → `asm-link-arch` 的装载承诺从“符号可解析”变为“重定位写入触发权限异常”；`gdb` 断点可能停在 PLT 而非目标函数。
- 协议版本从 RV32I 扩展到 RV32M/RV32A/RV32F/RV32D → `riscv-core` 的 `difftest` 零分歧前提破；新增指令编码、CSR 和异常状态必须进入 `difftest` 比对的指令语义集合，否则流水线/乱序核的指令语义分歧不可见。

### 不做什么（范围）

**不把四个子项目合并成一份文档。** 判据不同，合并即稀释（见 §二）。本文只做路由。

**不做 MMU、特权级、多核一致性、向量与浮点。** 它们会让重心从微架构移到 OS 与协议；边界写在 `riscv-core/OUTLINE.md` §四。

**不做 CUDA kernel 的手写调优。** 线程映射、共享内存 bank、访存合并、Nsight 归因属于 `langs/cuda/`；这里只从编译器的角度讲"高层表示怎么降到 GPU"。

**不做 MLIR 全栈教程。** `compiler/` 第 11 章只讲 dialect 分层的定位与取舍，不教怎么写一个 dialect；也不做 GCC 内部结构。

**不做工艺与物理设计。** 无版图、无时钟树、无功耗签核；面积与频率只到综合后估计。

**不追 SPEC 分数、不与商用核比绝对值。** 跨核比 IPC 而不比面积功耗是方法论错误。

**不写排期与进度。** 路径只给顺序与判据，不给日期。

## 五、面试怎么讲

**30 秒版本**（开场直接说，150–200 字）

> 我把体系结构这条线拆成四段互相咬合的能力：读得懂——能对着反汇编说清 ABI、栈帧、重定位；说得清——能把「这段代码为什么慢」拆成 IPC 与各级 miss 的可测量归因；做得出来——自己写过 RV32I 的核，从单周期到乱序，用 Spike 做逐提交 difftest，用开源 PDK 出关键路径和面积；编得动——能读 LLVM IR、写 pass，也知道 GPU 与域特定语言那条线（Triton/TVM/XLA/MLIR）为什么存在、各自替你做了什么。四段共享一套判据：结论必须能落到可复查的输出上，没有实测就说没测过。

**可能被追问的 8 个点**

1. **「你为什么先做单周期再做乱序？直接上乱序不是更省时间？」** → 真实考点：会不会做工程排序，而不是会不会背结构。
   → 答法：单周期是**语义基线**，后面每一版都要拿它比对；顺序五级是**结构基线**，转发与停顿的 bug 只能在它上面被干净定位。乱序一旦先做，bug 会在「重命名写错」和「流水线本来就错」之间无法区分。边界：这条经验的前提是有 difftest，没有 difftest 时任何顺序都不可靠。

2. **「读别人的核和自己造核，哪个更有价值？」** → 真实考点：两种能力的边界。
   → 答法：读核给的是**归因能力**——用 `perf`、Top-down、roofline 判断瓶颈在哪一层，这是日常工作的主战场；造核给的是**取舍能力**——在频率与面积约束下说清某个结构为什么是这个尺寸。只读不造，讲不出"为什么窗口不是越大越好"；只造不读，讲的都是自己的玩具。两者必须成对。

3. **「你说的『按实现而定』是不是在回避问题？」** → 真实考点：有没有能力给出量级与判据。
   → 答法：不知道具体参数时，正确的说法是给出**结构因果 + 量级关系 + 判据**：例如"误预测代价约等于流水深度 × 前端重填宽度，具体拍数要按该实现的公开资料取"。说"按实现而定"就结束是回避；说"按实现而定，但比例关系是这样，判据是 X"才是专业。

4. **「编译器和体系结构的关系，用一句话说清。」** → 真实考点：两条线是否真的打通。
   → 答法：**编译器决定生成什么指令序列，体系结构决定这些指令怎么在流水线上走，两者的交点是指令数与 CPI 的乘积**。所以"IR 指令数降 20% 但动态指令数不变"和"IPC 高了但指令数暴涨、程序更慢"是同一类错误的两个方向。

5. **「为什么现在都在做 DSL 编译器，直接写 CUDA 不行吗？」** → 真实考点：知道分层的代价，而不是跟风。
   → 答法：手写 CUDA 控制力最强，但把「算法」和「调度」绑死在一起，换硬件就要重写。DSL 的思路是**把调度从算法里拆出来**（Halide 的 algorithm/schedule 分离是最清晰的表述）：Triton 用 block 级编程模型，让编译器决定线程映射、共享内存与流水线；TVM 把 schedule 原语与自动调优暴露给用户；XLA 走整图视角做算子融合与 layout 分配。代价是**控制力下降 + 依赖编译器的启发式**，所以极端 kernel 仍然手写。

6. **「Triton、TVM、XLA 三者到底怎么选？」** → 真实考点：能不能给出选型判据而不是背功能列表。
   → 答法：看**你手里的是什么形状的输入**。单个 kernel、要极致性能又不想写 CUDA → Triton；要跨多种后端（CUDA/OpenCL/CPU/Metal）部署一个算子库、且愿意付自动调优的时间 → TVM；整模型图、以算子融合和 layout 为主、生态固定在 JAX/TF → XLA。判据是三件事：控制力需求、后端数量、可接受的调优与编译时间。

7. **「你怎么保证你说的每个结论不是背来的？」** → 真实考点：有没有可复现的习惯。
   → 答法：每个结论背后有一条命令或一个文件：结构结论对 STA 报告或波形，性能结论对 `perf stat`/difftest 计数，ABI 结论对 `objdump`/`readelf`，编译结论对 `opt -print-changed`/`llc -stop-after=`。**给不出出处的时候我会说没测过**，这是这套口径里唯一不能妥协的地方。

8. **「GPU 编译器难在哪，跟 CPU 编译器最大的区别？」** → 真实考点：是否理解并行模型带来的新问题。
   → 答法：CPU 编译器的主战场是**指令级**（寄存器分配、指令调度、向量化）；GPU 编译器多出三层：**线程映射**（一个 block 的 tile 怎么切给线程/warp）、**显存层次**（global/shared/register 的搬运与 bank 冲突）、**流水线化**（把 load 提前、用多级 staging 隐藏延迟，对应 Triton 的 `num_stages`）。这些在 CPU 上不存在或形态不同，所以 GPU 编译器更多做**空间与流水线变换**，而不是指令选择。

**别说什么**

- **「我全做过。」** 四段能力一起打包说，第一句就被拆穿。按「读得懂/说得清/做得出来/编得动」分开说，各给一个证据。
- **「我实现了乱序 CPU。」** 追问窗口大小、面积、fmax 就崩。要说的是四个数的取舍过程。
- **「用了 Triton 所以懂 GPU 编译。」** 工具不等于原理，被问「block 级模型下共享内存是谁决定的」「`num_stages` 在编译里对应什么变换」就露馅。
- **报没测过的数字。** 频率、面积、加速比、IPC 提升，没有同口径基线就只说口径，不说数。
