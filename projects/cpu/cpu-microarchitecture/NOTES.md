# cpu-microarchitecture · 分章详细

## 第 1 章 从指令集到微架构：ISA 与实现的分离

**要解决的问题**：这是整条因果链的起点。它要拆掉的是「指令就是硬件动作」这个隐含假设：如果一条指令必须对应一份固定的硬件电路，那么性能只能靠改指令集来提升，软件生态会被硬件绑死；更麻烦的是，「这条指令要花几个周期」将没有独立于具体实现的答案，后面流水线、乱序、发射宽度全都失去讨论的基础。这一章确立一个划分：**ISA 规定可见状态怎么变，微架构规定用多少时间、按什么顺序把它做出来**。没有这个划分，就无法解释为什么同一份二进制能在不同代、不同宽度、不同乱序程度的核上运行，只是快慢不同。

**机制**：

ISA 是一份约定，它的内容是**架构状态**：PC、通用寄存器堆、内存、条件码或标志位、异常与中断的进入语义、内存一致性模型、原子指令的语义、对齐要求。一条指令的语义可以写成一个纯函数：

```
// ISA 层：与周期数、内部顺序无关
step(state, instr) -> state'
// state = (PC, R[0..N-1], mem)
// 只约定执行完后可见状态是什么，不约定几条微指令、几个周期
```

微架构是实现，它的内容是**时间与结构**：流水线级数与分级方式、发射宽度、乱序窗口、分支预测器、cache 容量与组织、TLB 层级。这些量可以在一代产品里翻倍，而 ISA 保持不变。

两者的边界必须写清，不能随便挪动。凡是**程序员能观察到**的乱序效果，都必须进入 ISA：内存一致性模型规定了多线程下哪些执行结果是合法的，原子指令规定了读改写不可分割，页表格式规定了地址翻译的粒度。这些内容微架构不能自由发挥，只能在这个范围内优化。反过来，流水线深度、缓冲区条目数、替换策略属于实现细节，ISA 不承诺，程序也不该依赖。

关键取舍在于**复杂度往哪边放**。变长编码、条件码、寄存器数量少的 ISA，把负担压在取指（指令跨 cache 行边界）和译码（需要串行确定长度）上；定长编码、load-store 分离、寄存器多的 ISA，把负担推给编译器，让译码保持规整。这是设计取向的差异，并不代表性能的高低。

**最小例子**：取一条 RISC 风格的三操作数加法 `add x1, x2, x3`，同一份机器码在两种实现上：

- 单周期实现：1 个周期执行完，但 $T_{clk}$ 必须覆盖最慢路径（取指 + 译码 + ALU + 访存）。设教学假设下该路径为 800 ps，则吞吐 = 1 条 / 800 ps。
- 五级流水线实现：单条指令延迟 5 个周期，每级教学假设 200 ps 加 20 ps 级间寄存器开销，$T_{clk}=220\text{ ps}$，延迟 $5\times220=1100\text{ ps}$，但稳态吞吐 = 1 条 / 220 ps。

（以上数字是教学模型的假设值，不对应任何真实产品。）

结果：**同一份二进制，延迟从 1 周期变成 5 周期，吞吐却提高了约 3.6 倍**。这正是 ISA 与实现分离的价值：换核不用重新编译，只换时间。同时它也暴露了下一章的起点：ISA 只说「这条指令语义是什么」，从不说「怎么让多条指令同时在路上」，单周期实现把 CPI 锁死在 1，永远追不上频率与并行度的收益。

**面试高频问法**：

1. **「ISA 和微架构的区别是什么？」** → 考点：约定与实现的边界。答法：ISA 规定一条指令执行完后可见状态怎么变，微架构规定用几个周期、按什么内部顺序做出来；同一份二进制换核能跑，只是快慢不同。
2. **「x86 为什么保留变长指令，这不是历史包袱吗？」** → 考点：兼容性的经济价值与译码成本如何权衡。答法：存量二进制软件的价值远大于译码器成本，代价是取指要处理跨边界、译码要串行确定长度，这个成本交给前端和 uop cache 吸收。
3. **「RISC 一定比 CISC 快吗？」** → 考点：ISA 不等于实现。答法：ISA 只约束编码与译码的复杂度，性能由发射宽度、乱序窗口、cache 决定；现代 x86 把变长指令译成定长内部操作后，后端与 RISC 没有本质差别。
4. **「为什么内存一致性模型必须写进 ISA，而 cache 大小不用？」** → 考点：分离的边界在哪。答法：一致性模型决定了多线程下哪些结果合法，程序员能观察到，不写进约定就会导致同一程序在不同核上结果不同；cache 大小只影响快慢，不影响正确性。
5. **「延迟和吞吐，哪个属于 ISA？」** → 考点：分清语义与时间。答法：都不属于。ISA 只给语义，延迟和吞吐都是微架构属性，所以它们能随实现变化而不破坏兼容性。

## 第 2 章 五级流水线：取指、译码、执行、访存、写回

**要解决的问题**：第 1 章把 ISA 和实现分开之后，紧接着的问题是：**单周期实现把时钟周期定在最慢的那条指令路径上，快的指令被迫陪跑**。一条 `add` 只要过 ALU，一条 `load` 要过 cache，如果它们共用一个周期，时钟就只能按 load 来定，所有 ALU 指令都在浪费硅的时间。这一章要解决的就是这个利用率瓶颈：把一条指令的执行拆成若干级，让不同指令同时占用不同级，用**吞吐**换**延迟**。

**机制**：

经典五级划分按指令经过的自然阶段切：

| 级 | 名称 | 做什么 |
|---|---|---|
| IF | 取指 | 用 PC 访指令 cache，读出指令，PC 更新 |
| ID | 译码 | 译码、读寄存器堆、生成控制信号 |
| EX | 执行 | ALU 运算；load/store 在这里算地址 |
| MEM | 访存 | 只有 load/store 真正访问数据 cache，其余直通 |
| WB | 写回 | 结果写回寄存器堆 |

核心数据结构是**级间寄存器**：IF/ID、ID/EX、EX/MEM、MEM/WB。它们每一拍把「当前级的中间结果 + 后续级需要的控制信号」锁存下来，传给下一级。这不只是数据搬运：冒险检测（第 3 章）读的就是这些寄存器里的目的寄存器编号，转发路径也是从它们身上引出的。

单拍推进可写成：

```text
每拍：
  WB  <- MEM/WB 的结果写入寄存器堆
  MEM <- EX/MEM  访问数据 cache（仅 load/store）
  EX  <- ID/EX   ALU 运算
  ID  <- IF/ID   译码 + 读寄存器
  IF  <- fetch(PC); PC <- PC + 4
```

理想情况下 $\text{CPI}=1$：稳态每拍完成一条。n 条指令跑完需要的周期数是

$$T = k + (n-1),\quad k=5$$

时钟周期由**最慢一级加上级间寄存器开销**决定：

$$T_{clk} = \max_i T_i + t_{reg}$$

这条公式直接给出了设计取舍：把指令执行阶段切得越细，$T_i$ 越小，但级数一多，固定的 $t_{reg}$ 占比就上升，而且一旦出现分支误预测，需要清空的级数也更多。所以「流水线越深越快」并不成立，净收益递减，具体在哪里拐弯**按实现而定**。

**最小例子**：5 条互不依赖的指令 i1…i5 进入五级流水线（下面每一拍推进一个阶段）：

| 指令 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | 9 |
|---|---|---|---|---|---|---|---|---|---|
| i1 | IF | ID | EX | MEM | WB | | | | |
| i2 | | IF | ID | EX | MEM | WB | | | |
| i3 | | | IF | ID | EX | MEM | WB | | |
| i4 | | | | IF | ID | EX | MEM | WB | |
| i5 | | | | | IF | ID | EX | MEM | WB |

代入上式计算：第 5 条指令在第 9 拍写完，总周期数 $5+(5-1)=9$；如果严格一条一条串行执行则要 25 拍。含填充的 CPI $=9/5=1.8$，进入稳态后每拍吞吐一条，$\text{CPI}=1$。

这个例子的前提是「互不依赖」。一旦变成 `i1: load x1` 后面紧跟 `i2: add x2, x1, x3`，i2 在 EX 级就需要 x1，而 i1 要到 WB 才写回，流水线必须停下来。**这就是第 3 章要处理的冒险**：五级流水线把利用率问题解决了，代价是引入新的耦合。

**面试高频问法**：

1. **「五级流水线为什么正好切在这五处？」** → 考点：切分依据。答法：取指、译码读寄存器、ALU、访存、写回是每条指令都要经过的路径，切在这几处能让各级延迟大致均衡，因为时钟由最慢一级决定，不均衡的切法没有收益。
2. **「流水线级数越多越好吗？」** → 考点：级间寄存器开销与冒险惩罚。答法：$T_{clk}=\max T_i + t_{reg}$，级数增加时固定开销占比上升，且误预测要清空的级数变多，净收益递减，具体拐点按实现而定。
3. **「五级流水线里，单条指令的延迟和稳态吞吐分别是多少？」** → 考点：延迟与吞吐的区分。答法：延迟 5 个周期，稳态吞吐 1 条/周期，$\text{CPI}=1$；n 条指令总周期数是 $5+(n-1)$。
4. **「级间寄存器到底存了什么，为什么必须有？」** → 考点：流水线的结构基础。答法：存当前级的中间结果和后续级需要的控制信号，既把各级解耦成可以并行推进的独立阶段，也是冒险检测和转发路径的信息来源。
5. **「单周期实现和流水线实现，同样 ISA，谁更快？」** → 考点：延迟换吞吐。答法：n 大时流水线吞吐高约 k 倍，但单条延迟更长、时钟因级间寄存器略慢；n 小时，填充开销占主导，加速比接近 1。

## 第 3 章 流水线冒险：结构冒险、数据冒险、控制冒险，转发与停顿

**要解决的问题**：第 2 章的五级流水线默认每周期取一条指令、每条指令相互独立，因此 $CPI=1$；但真实程序会争用资源、存在数据依赖，遇到分支还会改变 PC。冒险处理就是补上这些被理想假设忽略的地方，否则流水线要么算错，要么退化成接近串行。

**机制**：结构冒险指同一周期两条指令争用同一硬件。经典五级若只有一个存储器端口，IF 取指和 MEM 访存就会冲突；工程上用分离的 I/D cache、多端口或多 bank、指令队列来缓解。数据冒险在顺序五级中主要处理 RAW：后一条指令在 EX 级要用前一条尚未写回的结果。转发单元比较 EX 级源寄存器与 EX/MEM、MEM/WB 的目的寄存器，命中就把 ALU 结果或写回值旁路到 EX 输入，优先级是 EX/MEM 高于 MEM/WB。这样大多数 ALU 依赖可以零停顿。转发解决不了 load-use：load 的数据在 MEM 末才可用，紧邻的消费者在 EX 就要，必须停一拍。控制冒险是分支方向和目标未定，取指单元不知道下一条 PC；经典五级在 EX 解析分支，已取入的年轻指令要冲刷，按这个模型是 2 个周期。取舍：转发增加旁路 mux 和比较逻辑，可能压 EX 关键路径；停顿简单但直接损失 IPC；编译器调度可拉开依赖距离，但不能替代硬件冒险处理。

```text
ID: 读寄存器 -> rs1v, rs2v
EX: 若 EX/MEM.regwrite 且 EX/MEM.rd == rs1 -> rs1v = EX/MEM.alu
    若 MEM/WB.regwrite 且 MEM/WB.rd == rs1 -> rs1v = MEM/WB.wb
    对 rs2 同理；EX/MEM 优先于 MEM/WB
load-use: ID 发现 load.rd == 下一条.rs -> stall 1 拍，插 bubble
branch: EX 算出 taken/target；与预测不符 -> flush 年轻指令
```

**最小例子**：`add x1,x2,x3` 后接 `sub x4,x1,x5`。无转发时，sub 在 ID 读 x1，add 还在 EX，读到旧值，需停 2 拍；有转发时，sub 在 EX 从 EX/MEM 取 x1，零停顿。换成 `lw x1,0(x2)` 后接 `add x4,x1,x5`，load 的 x1 到 MEM 末才可用，add 在 EX 就需要，停 1 拍后从 MEM/WB 转发。若 `beq` 实际 taken 而前端按 not taken 取指，经典五级要冲刷 2 条年轻指令，代价 2 周期。

**面试高频问法**：
- 问：有了转发，为什么还会有数据冒险停顿？→ 考点是“值何时可用”而非“有没有依赖”→ 答：转发只能提前已经算出的值，load 的值最早在 MEM 末出来，紧邻消费者在 EX 就要，必须停一拍。
- 问：WAR/WAW 在五级顺序流水线里要处理吗？→ 考点是冒险分类与乱序的边界→ 答：顺序五级按程序序写回，WAR/WAW 不会造成错误；到乱序多发射才用寄存器重命名消除。
- 问：结构冒险在现代处理器里怎么缓解？→ 考点是资源复制与流水化→ 答：分离 I/D cache、多端口或多 bank、队列化，把冲突变成排队，代价是面积和功耗。
- 问：控制冒险和分支预测是什么关系？→ 考点是本章到下一章的因果→ 答：控制冒险是“不知道下一条 PC”的停顿，分支预测用猜测把停顿移出关键路径，猜错再冲刷。

## 第 4 章 分支预测：静态与动态、BTB、TAGE、误预测的代价

**要解决的问题**：第 3 章的控制冒险是流水线最贵的停顿：分支在 EX 才解析，前端每遇分支就可能空等；流水越深、发射越宽，空等浪费越大。分支预测把“每分支必停”改成“平时猜着取，猜错才付代价”，让控制冒险从常态变成例外。

**机制**：预测要回答两件事：方向（taken/not taken）和目标（target）。目标常用 BTB：以分支 PC 索引，缓存目标地址和有效位；命中则下一周期直接从目标取指。方向预测分静态和动态。静态如 always not taken、BTFN（backward taken, forward not taken）、编译器 hint；动态常用 2-bit 饱和计数器，连续两次反向才翻转，能抵抗一次噪声。更复杂的有全局历史相关预测器、锦标赛预测器和 TAGE。TAGE 用全局历史寄存器 GHR 的多个不同长度前缀哈希索引多张带 tag 的表，再加一个基预测器；命中时优先选历史最长且 tag 匹配的表，置信度不足则回退到较短历史或基预测器。长历史捕捉长距离相关性，短历史和基预测器保证冷启动与别名容错。

**最小例子**：三种典型的可预测性，决定了预测器的收益上限。

- **计数器循环**：`for (i = 0; i < 1000; ++i) sum += a[i];` 的分支稳态取 999 次、退出一次。2-bit 计数器很快锁在 `11`，稳态预测率接近 100%，只在退出时误一次。按经典五级「分支在 EX 解析、冲刷 2 条年轻指令」的口径，代价约 2 个周期，摊到 1000 次迭代上可以忽略。
- **短内层循环**：`for (i) for (j = 0; j < 2; ++j)` 的内层分支序列是「取、取、不取」的重复模式。每个分支只用一个 2-bit 计数器时，序列 `T T N` 会周期性把一个计数器从 `11` 压回 `10`、再回 `11`，稳态误预测率明显高于长循环——这就是**只看单个分支的历史不够**的直接证据，也是全局历史相关预测器存在的理由。
- **数据相关分支**：`if (a[i] > 0)`，当 `a` 的符号无规律时，任何基于历史的预测器都退化成掷硬币；此时要么改写成无分支形式（`cmov` / 掩码运算），要么接受误预测率，别指望换预测器。

量级关系要能说清：**一次误预测的代价 ≈ 流水深度 × 前端重填宽度**。经典五级在 EX 解析、每拍取 1 条，代价 2 拍；换成 15 级、每拍取 4 条，代价就到十几到二十几拍——所以深流水必须配更强的预测器，否则前端收益被惩罚吃掉。

**面试高频问法**：

1. **「误预测的代价由什么决定？」** → 考点：代价的结构来源，而不是一个固定周期数。答法：约等于「要冲刷的年轻指令数 × 每拍能取回的指令数」。分支解析得越晚（EX 甚至 MEM 才解析）、流水越深、取指越宽，代价越大；把解析提前到 ID 能省一半，加预测器正确时则把代价降到零。具体周期数按实现而定。
2. **「2-bit 计数器比 1-bit 强在哪？」** → 考点：噪声容忍。答法：1 位在一次偶然反向就翻转，遇到循环退出、嵌套分支时会连续误预测；2 位要求连续两次反向才改变预测，能吸收单次抖动。代价是收敛慢一拍，对模式突变反应迟钝。
3. **「BTB 和方向预测器各管什么？」** → 考点：两件事不要混。答法：方向预测器回答「跳不跳」，BTB 回答「跳到哪」。只有方向为 taken 时才需要目标；BTB 未命中而方向为 taken 时，前端仍然要等目标算出。所以 BTB 的命中率和方向准确率是两个独立指标，都要测。
4. **「TAGE 什么时候会输给两级自适应？」** → 考点：长历史带来的别名与冷启动。答法：历史很长时不同分支会共享同一条目产生别名，短历史或基预测器兜底不足时会误判；分支行为频繁相位变化时，长历史反映的是旧相位。判据仍是 MPKI，不做「哪个更好」的定性判断。
5. **「预测器会不会成为时序瓶颈？」** → 考点：预测在取指关键路径上。答法：会。BTB 的读 + tag 比较 + 多表选择常常决定前端频率上限，真实核因此把 BTB 分级、把预测拆到多拍、或先给出方向再补目标。

## 第 5 章 乱序执行：重排序缓冲、保留站、寄存器重命名

**要解决的问题**：分支预测解决了控制冒险，但五级流水线仍然是**顺序发射、顺序完成**的：一条正在等待 cache 的 load、一条多周期除法，会把后面所有指令堵住，哪怕它们和这条指令毫无关系。乱序执行把「程序顺序」和「执行顺序」解耦，让窗口内所有操作数就绪的指令先跑。不解决它，流水线深度和功能单元数量带来的收益会被长延迟指令吃光。

**机制**：前端仍按程序顺序取指、译码，指令进入一个按程序顺序编号的队列，之后分成三条正交的机制：

1. **寄存器重命名**：架构寄存器（如 32 个）映射到一池物理寄存器（Preg）。每条写指令分配一个新的 Preg。这样 WAR（写后读）和 WAW（写后写）这两种假依赖消失——旧读者仍指向旧 Preg，新写者写新 Preg，互不干扰。只有真正的 RAW 依赖保留，通过 Preg 编号在保留站里匹配。
2. **保留站（RS）/ 发射队列**：指令在此等待，记录「源 Preg + 是否就绪」。某个功能单元算完并把结果广播到总线上，等待该项的指令被唤醒，按就绪顺序（不按程序顺序）发射。这就是乱序发射。
3. **重排序缓冲（ROB）**：所有指令按程序顺序分配 ROB 项，执行完标记 done，但**只有到达 ROB 头部才提交**。提交时才写架构寄存器、释放旧 Preg。异常和分支误预测时，ROB 头部之前的已提交、之后的全丢弃——这就是精确异常的基础。

关键取舍在**窗口大小**：ROB 项数决定能同时「在飞」多少指令，窗口越大，能挖出的并行越多；代价是面积、功耗，以及误预测时必须清空的项数。窗口不是越大越好，收益随程序本身的固有并行度递减。

```text
fetch/decode (in order)
  → rename: arch reg → new Preg, alloc ROB entry (in order)
  → dispatch to RS, wait for src Preg ready
  → issue (out of order) when all srcs ready
  → execute, broadcast result Preg + value
  → mark ROB entry done
  → commit at ROB head (in order): update arch state, free old Preg
```

**最小例子**：假设一段指令，`load` 命中 L2 需约 20 个周期，`add`、`mul`、`sub` 各 1 个周期（示例假设值，不代表任何真实核）。顺序执行：`load` 之后的 3 条必须等 21 个周期才完成；乱序执行时，重命名后 `add`、`mul`、`sub` 的源操作数都已就绪（`r4`、`r5`、`r9`、`r10` 早已写好），它们立刻发射，在 `load` 返回前就算完，只是卡在 ROB 里不能提交。总时间从约 24 周期降到约 21 周期。如果这段窗口里还夹着一条 `mul` 依赖 `load` 结果，那它仍然要等——乱序只挖掘**真实无关**指令的并行。

**面试高频问法**：

- 「重命名到底消除了哪类冒险？」→ 考点是 WAR/WAW 是假依赖。答法：WAR/WAW 只是寄存器名字复用造成的假依赖，物理寄存器池够大时，写指令换一个新 Preg，旧读者继续读旧 Preg，冲突自然消失；RAW 是真依赖，重命名不解决，只能靠转发或等待。
- 「ROB 和保留站分别管什么？」→ 考点是顺序提交与乱序发射的分工。答法：保留站管「什么时候能执行」，按操作数就绪乱序发射；ROB 管「什么时候算数」，按程序顺序提交，保证精确异常和误预测可回滚。
- 「窗口是不是越大越好？」→ 考点是收益递减与代价。答法：窗口扩大能覆盖更多长延迟指令，但受程序固有并行度限制，边际收益递减；同时面积、功耗、误预测清空代价都随窗口线性增长，所以是权衡不是单调最优。
- 「乱序执行怎么保证精确异常？」→ 考点是提交点唯一。答法：执行阶段不修改架构状态，只写 ROB 和物理寄存器；异常在指令到达 ROB 头部时判定，此时它之前的指令已全部提交、之后的全部丢弃，现场就是精确的。
- 「为什么乱序核必须配强分支预测？」→ 考点是误预测代价与窗口深度的耦合。答法：误预测要清空整个窗口内未提交的指令，窗口越深浪费越大；预测准确率不够时，乱序挖出的并行会被反复的 flush 抵消。

## 第 6 章 乱序访存：load/store 队列、内存消歧、store-to-load forwarding

**要解决的问题**：第 5 章用重命名消除了寄存器的假依赖，但**内存没有名字可换**。`store [r1], x` 和 `load r2, [r3]` 是否访问同一地址，编译期和发射期都未必知道——`r3` 可能还没算出来。如果 load 随意越过更老的 store 先执行，可能读到过期值；如果一律不许越过，访存就成了新的顺序瓶颈，乱序收益被大幅吃掉。乱序访存要在这两者之间找到可回滚的折中。

**机制**：

- **load/store 队列（LQ/SQ）**：访存指令按程序顺序登记。load 可以提前发射，但提交前要验证没有被更老的 store 覆盖；store 在提交前**不写 cache**，数据先放在 store buffer 里，等 ROB 提交时才真正落地。这是精确异常的要求：误预测清流水时，未提交的 store 必须能一并撤销。
- **内存消歧（memory disambiguation）**：load 发射时查 SQ，判断是否有更老的 store 可能别名。三种策略：
  - 保守：只要存在地址未知的更老 store 就等——安全但慢；
  - 激进：预测不别名，先执行，事后验证，错了就 replay（memory order machine clear）；
  - 折中：**地址/依赖预测器**记住「这条 load 上次和哪条 store 冲突过」，按历史决定等还是冲。
- **store-to-load forwarding**：store 数据还在 store buffer、没进 cache 时，后来的 load 命中同一地址，直接从 store buffer 取，省掉「等 store 提交再读 cache」的往返。难点在**部分重叠**：load 的字节范围可能只覆盖 store 的一部分，或跨两条 store，硬件要按字节偏移和掩码拼接；覆盖不全或跨 cache line 时通常只能停顿。

```text
load issue:
  addr = compute(...)
  for each older store in SQ (newest first):
     if store.addr known and overlaps(load.addr, store.addr):
         if store covers load range: forward bytes, done
         else: stall / partial forward
     if store.addr unknown:
         consult dependence predictor → wait or speculate
  if no conflict: read cache, mark load for later verification
```

**最小例子**：`store [r10+0], r11`（4 字节），随后 `load r12, [r10+0]`（4 字节）。地址完全相同，SQ 地址比较命中，直接 forwarding，load 不必等 store 提交，省掉一次 store→cache→load 的往返。再看部分重叠：store 写 `[0x1000] = 0x11223344`（小端，字节依次为 44 33 22 11），随后 `load` 2 字节于 `[0x1002]`，应得 `0x1122`。forwarding 逻辑要按偏移取 store 数据的高两字节拼出结果；若 load 范围是 `[0x1002, 0x1006)`，就跨出了这条 store 的覆盖范围，需要合并下一条 store 或停顿。

**面试高频问法**：

- 「load 能不能越过更老的 store 执行？」→ 考点是消歧与可回滚性。答法：可以，前提是能判断别名或能事后验证并回滚；地址未知时靠依赖预测器猜，猜错触发 memory order clear 重放，猜对就赚到并行。
- 「store 为什么必须等到提交才写 cache？」→ 考点是精确异常。答法：store 一旦写了 cache 就无法撤销，误预测或异常后内存已被改脏；放在 store buffer 里等 ROB 提交，才能保证清流水时一起丢弃。
- 「store-to-load forwarding 的难点在哪？」→ 考点是部分重叠与对齐。答法：要按字节偏移和掩码判断 load 的字节区间是否被 store 完全覆盖，部分覆盖需要拼接，跨多条 store 或跨 cache line 时往往只能停顿，逻辑面积不小。
- 「内存消歧猜错的代价有多大？」→ 考点是流水线清空。答法：要把违规 load 及其之后的指令清掉重放，量级接近一次分支误预测，所以预测器准确率直接决定激进策略是否划算。
- 「为什么乱序访存比乱序算术难？」→ 考点是地址的运行时性。答法：算术指令的源寄存器编号译码时就知道，依赖可静态匹配；访存地址要等地址计算指令执行完才存在，别名关系动态且不可静态判定，所以必须靠队列 + 运行时比较 + 预测。

## 第 7 章 超标量与 SMT：发射宽度、超标量的极限、超线程共享了什么

**要解决的问题**：第 6 章的乱序访存让一条指令流里的多个 load 能重叠起来，但整条流水线前端每周期仍然只取一条、译码一条、退休一条——窗口再大，IPC 的硬上限也是 1。要让 IPC 超过 1，必须让流水线“横向”同时处理多条指令；而单线程能挖出的 ILP 有限，窗口里常常凑不满可发射的指令，于是还要“纵向”从第二个线程借指令填槽。前者是超标量，后者是 SMT。

**机制**：

宽度是一条链而非单个数字：取指 $W_f$ → 译码 $W_d$ → 重命名/分配 $W_r$ → 发射 $W_i$ → 退休 $W_r'$。有效宽度是整条链的最小值（min），还受队列（取指队列、ROB、调度器项数）和端口约束。公开资料里常见取值是每周期 4~8 条，按实现而定。

超标量并不复制多条流水线，它的结构是共享一个有序前端 + 一个乱序核心 + 多个执行端口：

- 统一调度器把指令分派到不同端口：ALU 端口、load 端口、store 端口。某类端口数量少，就构成该类的吞吐上限。
- 寄存器堆与旁路网络的端口数随宽度超线性增长：$W$ 宽发射每周期要读约 $2W$ 个源操作数，旁路网络近似 $W\times W$ 的交叉开关。这是「不能无限加宽」的物理原因，而不只是「程序没那么多并行」：即便 ILP 足够，端口数与选择逻辑的延迟也会先把时钟周期顶上去。真实核的对策是打散——把大 mux 换成树形、把寄存器堆分 bank、按操作数类型划分端口、把发射宽度定在「端口数与频率可以同时接受」的那个点上。

**SMT（同时多线程）** 是同一套结构的另一种用法：复制架构寄存器与重命名表（部分实现连 ROB/保留站也分区），共享取指前端、执行单元、L1 与 BTB。它不提高单线程延迟表现，只把发射槽里的空泡用另一个线程的指令填上，因此收益完全取决于单线程能否把窗口填满——**访存密集、ILP 低的负载收益最大，纯计算密集负载可能只剩争用**。

**最小例子**（以下数字都是示意，用于说明「宽度是链条不是数字」）：设某核取指 4 条/拍、译码 4 条/拍、重命名 4 条/拍、发射 4 条/拍，但执行端口是 2 个 ALU + 1 个 load + 1 个 store。

| 工作负载 | 每拍需要的端口 | 可达 IPC 上限 |
|---|---|---|
| 纯整数算术（ALU 占 80%） | ALU 密集 | 受 2 个 ALU 端口限制，约 2 |
| 指针追逐（load 占 60%） | load 密集 | 受 1 个 load 端口限制，约 1.6 |
| 混合（ALU/load/store 约 2:1:1） | 四端口刚好打满 | 接近 4 |

结论：**把取指宽度从 4 提到 8 对第一行毫无帮助**。加宽必须加在最窄的那一环，否则只是把空泡变得更深。这也是为什么微架构优化要先归因（第 9 章）再动结构。

**面试高频问法**：

1. **「发射宽度是不是越大越好？」** → 考点：链条最短环 + 端口与旁路代价。答法：有效宽度是「取指/译码/重命名/发射/提交/端口」这条链的最小值，任意一环窄了就是上限；同时寄存器堆读端口与旁路网络随宽度超线性增长，先把频率顶下去。所以宽度是频率约束下的取舍，不是一个可以单调调大的参数。
2. **「超标量是不是复制多条流水线？」** → 考点：结构理解。答法：不是。它是「一个有序前端 + 一个乱序核心 + 多个执行端口」，宽度体现在每拍能派发几条、能提交几条，而不是并排摆几条独立流水线。
3. **「SMT 提升了什么、没提升什么？」** → 考点：共享与私有的边界。答法：共享取指、执行单元、L1、BTB，私有架构寄存器与重命名空间（部分实现连 ROB 也私有）。提升的是吞吐与面积效率，不改善单线程延迟；代价是资源争用与共享微架构状态带来的侧信道面。
4. **「什么时候加宽无效？」** → 考点：瓶颈定位。答法：当某类执行端口已经打满、或取指/I-cache 带宽不足、或程序本身 ILP 太低时，加宽只增加空泡。判据是归因数据：如果「后端端口受限」占比高，加宽无效；如果「前端受限」占比高，才轮到取指与译码。
5. **「超线程和多核有什么区别？」** → 考点：资源复制粒度。答法：多核复制整套执行资源，靠并行换吞吐，成本接近线性；SMT 只复制寄存器状态，共享执行资源，用「填别人的空泡」换吞吐，成本低但收益依赖负载，且两条线程延迟会互相干扰。

## 第 8 章 存储层次与 TLB：多级 cache、预取、页表遍历的隐藏开销

**要解决的问题**：第 7 章把发射宽度拉满、又用 SMT 把发射槽填上之后，核内能同时并行的指令数已经接近架构上限，但乱序窗口是有限的：ROB 条目数、load/store 队列深度、MSHR 数量都按实现而定，量级是几百条。一条 load 如果落到 DRAM，几百周期的延迟足以在等待期间耗尽整个窗口，前端只能停摆。换句话说，宽发射带来的收益被“平均访存延迟”这个乘数抵消了：指令流再宽，数据不在核附近也发不出去。这一章要解决的就是：让绝大多数访存不落到 DRAM；当确实落到 DRAM 时，也不要让整条流水线跟着等；同时处理一个容易被忽略的访存来源，即地址翻译本身。

**机制**：

**层次结构与 AMAT**。L1 分离为 I-cache 与 D-cache，私有的 L2 通常统一，L3 在片上共享，再往下是 DRAM。每层需要记住的只有四个量：容量、关联度、块大小（行大小常见 64B）、命中延迟与缺失代价。整个层次的收益用平均访存时间衡量：

$$AMAT = t_{hit} + mr \times (t_{hit,2} + mr_2 \times (\cdots + mr_n \times t_{DRAM}))$$

因此，可以调整的只有三处：降低命中时间、降低缺失率、降低缺失代价。

**L1 为什么通常是 VIPT**。页内偏移在地址翻译前后不变，因此 cache 的 index 位可以取自虚拟地址，与 TLB 查表并行启动；tag 比较则用物理地址。这样 load 不必先等翻译完成再访问阵列，命中延迟从“TLB 命中 + cache 命中”变成两者的较大值。代价是别名问题：不同虚拟地址映射到同一物理行，若不处理，就可能在 cache 里出现两份。常见的约束是 index 位宽不超过页偏移，这样 VIPT 等价于 PIPT，从而天然避免别名；具体容量与路数如何配合，按实现而定。

**缺失处理**。MSHR 记录正在进行的缺失，同一行的第二次缺失会被合并到同一条记录上，不再发第二次请求。配合非阻塞 cache，多个缺失可以同时在处理中，这才是第 6 章乱序访存能起作用的前提：有 outstanding miss 才有 MLP，没有 MSHR 空闲槽，后续 load 只能等。写策略一般是 write-back + write-allocate。

**预取**。硬件 stride/stream 预取器观察访存地址序列的规律，在需求发生之前把行搬进 L2 甚至 L1；软件预取指令如 x86 的 `PREFETCHT0`、ARM 的 `PRFM` 只是提示，不产生异常也不改架构状态。预取对顺序、等步长模式非常有效；对指针追逐基本无效，因为下一个地址要等上一个数据回来才知道。

**TLB 与页表遍历**。TLB 是页表项的 cache，而页表遍历本身是“由访存触发的访存”：

```c
// 概念上的 x86-64 四级页表遍历（每级取 9 位索引）
phys = cr3;
for (level = 4; level >= 1; --level) {
    idx  = (va >> (12 + 9*(level-1))) & 0x1FF;
    pte  = load(phys + idx*8);   // 这一步自己也是一次访存
    if (!pte.present) -> #PF;
    phys = pte.frame << 12;
    if (pte.ps) break;           // 命中大页，提前终止
}
```

关键点是：这 4 次 load 互相构成串行依赖链，即使每级都命中 L1（4 周期），也是十几个周期；若某级页表项掉到 L2、L3，代价翻倍；最坏情况是 4 次 DRAM，接近上千周期。而且页表项通常是热数据，真正全落 DRAM 的情况并不常见，所以“TLB miss 有多贵”的答案往往不是“4 次内存访问”。缓解手段主要有三种：L2 TLB 提供更大的覆盖范围、大页、以及页表遍历缓存。大页（x86 的 2MB/1GB 页）同时减少遍历级数和放大 TLB 覆盖，是性价比很高的一环。

**最小例子**（以下延迟与容量均为假设的示意参数，只用于演示算术，不代表任何具体核）：

设 4KB 页、L1 dTLB 64 项、L2 TLB 2048 项。覆盖范围分别是 $64\times4\text{KB}=256\text{KB}$ 和 $2048\times4\text{KB}=8\text{MB}$。

顺序遍历一个 256MB 数组：L2 TLB 也装不下，每 4KB 触发一次遍历，共 $256\text{MB}/4\text{KB}=65536$ 次。假设每次遍历 4 级、每级平均 5 周期串行，就额外增加约 $65536\times20\approx1.3\text{M}$ 周期。改用 2MB 大页后，整个数组只占 128 个页，全部驻留 TLB，遍历次数降为零。

再对比两种访问模式访问同一块数据：顺序扫描能被硬件预取器识别，缺失被提前发出，有效延迟摊到接近 L2 命中；而 1M 个节点的随机链表（指针追逐，每节点 64B）无法预测下一个地址，MSHR 也填不满一条依赖链，每次 load 都要真等。若平均每次 100 周期，1M 次就是 100M 周期，这个量级足以说明：存储层次优化的重点常常是把“随机”变“顺序”，剩下的工作交给预取器和 MLP。

跨页是预取器的一个典型失效点：预取请求通常不跨越页边界，页末几行会漏掉，所以遍历大数组时能观察到周期性的小停顿。

**面试高频问法**：

1. **“L1 为什么要用 VIPT？会不会有别名问题？”** → 考点在虚拟索引与物理 tag 的并行、页内偏移不变性，以及如何用 index 位宽约束换掉别名。答法：L1 用虚拟地址低位做 index，与 TLB 并行启动，tag 用物理地址比较；只要 index 位全落在页偏移内，VIPT 就等价于 PIPT，别名自然不存在，代价是容量×关联度受页大小约束。

2. **“TLB miss 的代价是多少？”** → 考点在页表遍历是串行访存链，以及页表项本身会被 cache。答法：一次 miss 要按页表级数逐级读页表项，是 4 次左右的串行 load，不是一次；这些页表项通常命中了 L1/L2，所以代价是几十周期的串行链，最坏情况才会出现多级缺失。

3. **“预取器什么时候帮倒忙？”** → 考点在模式识别与资源污染。答法：遇到指针追逐、随机访存、跨页访问时预取基本无效；误预取会占掉稀缺的 MSHR 和 L2 带宽，还可能把有用行挤出去，所以预取器要有置信度和开关。

4. **“乱序窗口已经很大了，为什么还是躲不过 DRAM 延迟？”** → 考点在窗口容量与 MSHR 上限，是第 5 章乱序的边界。答法：能同时 outstanding 的缺失数受 MSHR 和 LQ 条目限制，窗口填满后前端必须停，所以靠乱序提升的 MLP 是有上限的，剩下的只能靠层次结构降低 miss 率。

5. **“想提高性能，加容量、加关联度、还是加一层？”** → 考点是 AMAT 三项的边际收益。答法：加容量降 miss 率，加关联度降冲突缺失，但两者都会抬高命中时间并增加访问延迟，因为要多路比较，甚至要跨周期；加一层只在 miss penalty 远大于新增命中时间时才划算，实际要靠性能计数器，也就是第 9 章要讲的 MPKI，来定位是命中时间还是缺失率的问题。
## 第 9 章 性能计数器与 roofline：怎么判断是算力受限还是带宽受限

**要解决的问题**：前八章一直在讲「怎么让流水线跑得更快」，但没有回答「我这段代码到底卡在哪、还值不值得优化」。缺少归因手段时，优化就只能靠猜：很可能花一周做向量化，最后发现程序本来就卡在主存带宽上，提速为零。这一章提供两样东西：把「慢」拆成算力项和带宽项的度量方法，以及判断「是否已经接近硬件上限」的标尺。

**机制**：

其一，硬件性能计数器（PMU）。每个核内有一组可编程计数器，能统计周期数、退休指令数、各级 cache 的 access/miss、TLB miss、分支误预测等事件。Linux 上通过 `perf_event_open` 暴露，`perf stat` 是常用前端。核心推导量是 IPC：

$$
\text{IPC} = \frac{\text{instructions retired}}{\text{cycles}}
$$

IPC 只告诉你「每周期退休几条」，必须和 stall 归因事件一起看才有意义。两个陷阱：一是**多路复用**——要统计的事件数多于物理计数器数时，内核分时切换计数器再外推，短程序误差很大；二是 **retired 语义**——只统计退休的指令，被误预测冲掉的指令不计入，所以误预测率高的代码 IPC 会显得「虚高」。

其二，roofline 模型。横轴是运算强度 $I$（每从主存搬运 1 Byte 完成多少 FLOP），纵轴是可达性能。两条上界：算力上界 $P \le \pi$，带宽上界 $P \le \beta I$。合起来：

$$
P \le \min(\pi,\ \beta I), \qquad I^{*} = \frac{\pi}{\beta}
$$

$I^{*}$ 是拐点。$I < I^{*}$ 时程序在斜线段上，属于**带宽受限**，再怎么优化运算都没用；$I > I^{*}$ 时在水平段上，属于**算力受限**，此时唯一的出路是换算法、换指令（SIMD/FMA）或换更宽的核。分块（cache blocking）的作用就是提高 $I$，把工作点从斜线推到水平段——这正好接上第 8 章的存储层次：分块让数据在高层 cache 里被复用。

**最小例子**：

设（以下为便于计算的假设值，不是实测某型号）：双精度峰值 $\pi = 100$ GFLOP/s，可持续带宽 $\beta = 25$ GB/s，则 $I^{*} = 4$ FLOP/Byte。

对 $C = A \times B$ 做边长为 $b$ 的分块，double 占 8 Byte，每块搬入 $2b^2$ 个元素、$16b^2$ Byte，完成 $2b^3$ FLOP：

$$
I = \frac{2b^{3}}{16b^{2}} = \frac{b}{8}
$$

| $b$ | $I$ (FLOP/Byte) | 上限 | 状态 |
|---|---|---|---|
| 8 | 1 | $25 \times 1 = 25$ GFLOP/s | 带宽受限，仅峰值 25% |
| 32 | 4 | 拐点 | 恰好平衡 |
| 64 | 8 | $\pi = 100$ GFLOP/s | 算力受限 |

一次真实测量走这条路径：

```bash
perf stat -e cycles,instructions,cache-misses,LLC-load-misses ./a.out
```

若 IPC 只有 0.3 且 LLC-load-misses 很高，先怀疑带宽与预取，不要急着改计算内核；若 IPC 已接近该核的发射宽度，说明前端和后端都被喂饱了，属于算力受限，此时只有 SIMD 化、提高 FMA 占比或换核才有用。注意「发射宽度」的具体值按实现而定，要从该核的公开微架构资料取，不要凭经验猜。

**面试高频问法**：

1. 「IPC 低就说明程序不好吗？」→ 考点是 IPC 与工作点的关系。→ 答法：IPC 低只说明每周期退休的指令少，可能是带宽受限、可能是分支误预测、也可能是代码本身是长依赖链。要配合 stall 事件和 roofline 上的位置一起判断，单独一个 IPC 没有诊断价值。

2. 「roofline 的拐点怎么来的，为什么它很重要？」→ 考点是 $\pi/\beta$ 的物理含义。→ 答法：拐点是算力和带宽两个上界相等的点，$I^{*} = \pi/\beta$。拐点左边的优化方向和右边完全相反，所以要先测出自己站在哪一侧，再决定是提高运算强度还是减少运算量。

3. 「怎么把一段内存受限的代码变成算力受限？」→ 考点是分块与复用。→ 答法：提高运算强度 $I$，最直接的办法是分块，让载入的数据在寄存器或 cache 里被复用多次；再配合预取把延迟隐藏掉。本质是把第 8 章的存储层次当作提升 $I$ 的工具。

4. 「perf 统计出来的数为什么有时不可信？」→ 考点是多路复用和 retired 语义。→ 答法：事件数超过物理计数器时内核会分时复用再外推，运行时间短就偏差大，应加长采样或减少事件；另外 retired 只统计退休指令，被冲掉的指令不计入，误预测多的场景要交叉验证。

## 第 10 章 现代核的横向对照：大小核、向量单元、多发射与能效

**要解决的问题**：第 9 章给出了「上限在哪、你离上限多远」，但同一张 roofline 图上可以有好几种核可选，它们并不是同一条曲线的等比缩放，而是在 $\pi$、$\beta$、单线程延迟、面积和能效上做了不同取舍。不理解这些取舍，就解释不了「为什么手机 SoC 要大小核」「为什么同一段 AVX2 代码在两种核上表现差一倍」「为什么服务器核不追求最高单核频率」——也就无法判断一项优化在目标硬件上是否成立。

**机制**：

**同 ISA、不同微架构**。ISA 只是一份契约，规定有哪些指令、什么语义，不规定几级流水、多宽发射、多深的缓冲。所以「x86 与 ARM 的差别」往往小于「同一 ISA 内两个核的差别」：译码宽度、发射宽度、重排序缓冲深度、访存并行度（MSHR/LFB 数量、load/store 队列深度）都是按实现定的，公开的微架构分析（各家 Hot Chips 之类）会给出这些结构参数，但**周期数与缓冲区的确切数值必须以对应实现为准**，不能跨核套用。

**宽核与窄核、大小的分工**。宽核靠加宽发射、加深窗口来提高单线程 IPC，代价是面积和功耗按经验上超线性增长（Pollack 规则：复杂度翻倍，性能大致只有 $\sqrt{2}$ 倍）。因此单核不可能无限加宽，这是「大小核」存在的结构原因，而不是厂商偷懒：宽核负责延迟敏感、突发的交互负载，窄核负责能效优先、可并行的长尾后台负载。两者共享 ISA 和 cache 一致性协议，调度器按负载类型迁移任务；迁移的代价是 cache 变冷、频率域切换，所以调度策略本身会影响实际性能。

**SMT（超线程）**。两个逻辑核共享同一个物理核的前端、执行单元和 cache，只复制寄存器状态与少量缓冲。它的收益是把发射槽的空隙填满，提高吞吐和面积效率，代价是不改善单线程延迟、且两个线程争抢共享资源；安全性上因为共享微架构状态而引入侧信道攻击面。「SMT 提升多少」按实现和工作负载而定。

**向量单元**。SIMD 宽度是 ISA 契约的一部分：SSE 128 位、AVX2 256 位、AVX-512 512 位、ARM NEON 128 位，SVE 是可变长度、实际长度按实现。加宽向量直接提高 $\pi$，但同时也提高了每周期取数的需求：如果 $\beta$ 跟不上，roofline 拐点会右移，对内存受限代码来说宽向量毫无收益；另外高宽度向量运算在部分实现上会触发降频，幅度按实现而定，这也是宽向量在通用负载上收益不稳定的原因之一。

**能效**。动态功耗约 $P_{dyn} \approx \alpha C V^{2} f$，而性能大致正比于 $f$，所以单纯提频是接近三次方的功耗代价；这正是现代核转向「每瓦性能」、把并行度做在宽度和多核上的原因。

**最小例子**：

假设一个任务有 $10^{9}$ 条指令（数字为假设，用于说明取舍）。窄核 IPC 1、2 GHz，宽核 IPC 2、2 GHz：

| | 时间 | 动态功耗 | 动态能量 |
|---|---|---|---|
| 窄核 | $10^{9}/10^{9} = 0.5$ s | 5 W | 2.5 J |
| 宽核 | 0.25 s | 15 W | 3.75 J |

宽核在延迟上赢 2 倍，纯动态能量上却更差。若再计入 2 W 静态功耗：窄核 $0.5 \times 7 = 3.5$ J，宽核 $0.25 \times 17 = 4.25$ J。结论不是「宽核不好」，而是**「快」和「省」是两个目标**：交互式负载用户感知的是延迟，宽核值得；持续后台负载看的是能量，窄核更优。而当静态功耗占比很高时，宽核的 race-to-idle 会反超——这就是为什么同一套大小核策略在手机和服务器上的最优解不同。

**面试高频问法**：

1. 「大小核为什么不能只保留大核？」→ 考点是宽核的功耗与面积超线性代价。→ 答法：宽核提高单线程 IPC，但面积和功耗增长快于性能增长，全用宽核会让能效和芯片面积都难以接受；窄核在可并行的长尾负载上每瓦性能更好，两者分工而不是冗余。

2. 「超线程提升了什么，没提升什么？」→ 考点是共享与私有的边界。→ 答法：SMT 复制寄存器状态、共享前端、执行单元和 cache，它填的是发射槽的空隙，所以提升的是吞吐和面积效率；单线程延迟基本不变，而且两个线程会争抢共享资源。

3. 「为什么加宽向量寄存器不一定更快？」→ 考点是 roofline 与降频。→ 答法：加宽 SIMD 提高的是 $\pi$，但如果代码本身 $I < I^{*}$，瓶颈在 $\beta$，加宽没有用；另外宽向量在部分实现上会触发降频，具体幅度按实现而定，要实测。

4. 「同一份二进制在不同核上 IPC 差很多，怎么解释？」→ 考点是 ISA 与实现的分离。→ 答法：ISA 只约定语义，发射宽度、窗口深度、访存并行度和 cache 层次都是实现自由；IPC 是微架构属性而不是指令集属性，所以跨核比较必须回到具体的结构参数，而且要按该实现的公开资料取，不能从别的核类推。
